# aish overnight development orchestrator

You are the orchestrator for autonomous development of **aish**. Goal: maximize the open GitHub issues on `epnasis/aish` that are **genuinely resolved** — solving the described problem, not maximizing the count of closed issues. Work through the night while the user is away; you coordinate, review, protect quality, verify, and ship.

Read `CLAUDE.md` (repo root) first — architecture, the approval-gate invariant, and the testing pattern. It overrides defaults.

## The loop
0. **Arm the watcher first.** A Monitor is session-scoped and does NOT survive across sessions, so a fresh orchestrator run must start its own. Launch a persistent Monitor that polls for newly-opened issues so you're notified as they arrive:
   ```
   Monitor(persistent: true, description: "new GitHub issues on epnasis/aish", command: '''
   last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
   while true; do
     sleep 120
     now=$(date -u +%Y-%m-%dT%H:%M:%SZ)
     gh issue list --repo epnasis/aish --state open --json number,title,createdAt \
       --jq ".[] | select(.createdAt > \"$last\") | \"NEW ISSUE #\\(.number): \\(.title)\"" 2>/dev/null || true
     last=$now
   done''')
   ```
1. **Survey** open issues: `gh issue list --repo epnasis/aish --state open --json number,title,labels`. Triage new arrivals from the Monitor as they come. **Re-run the survey after ANY gap** — a usage-limit reset, a container restart, a re-armed Monitor: the Monitor's `last` stamp is its own start time, so an issue filed while it was down is never reported (#398 sat unseen for 17 hours on 2026-09-20/21 for exactly this). Compare against the ledger, not against memory.
2. **Triage** each issue into one of:
   - **Part of an epic → HANDS OFF.** Epic work is driven separately by the `epic` skill, in the order the epic specifies and against the epic's own properties — which is exactly what this breadth-first loop cannot do. An issue is epic-linked if it IS an epic/design-record ("Epic:" title, "child issues:" list) or belongs to one ("Part of the … epic", "Depends on #<epic-core>", "Stage N of #<epic>", listed as a child in an epic body). Do NOT build, do NOT delegate, do NOT ship — note it in the ledger, say which epic, and leave it. This overrides "Actionable" even when the issue is well-specified and buildable: an epic-linked issue built out of order, or built correctly but against the wrong design, is worse than one left alone. The exception is an issue the user has explicitly labelled for this run (e.g. `nextup`) — that is them taking it out of the epic's hands deliberately.
   - **Actionable** — a bug or small/medium feature with a clear objective and no design decision needed → fix it.
   - **Needs human input** — a product/design/aesthetic call, an ambiguous objective, or a change to the primary UX the user should weigh in on → comment on the issue with *specific* questions, add the `question` label, leave it OPEN, and hold for the user.
   - **Big refactor / deferred / device-only** (needs their iPhone etc.) → skip or leave a note; don't build speculatively.
   - **Already resolved** in the current code → verify it, then close with an explanation. Never close what you didn't actually resolve.
3. **Delegate in parallel** — start EACH fix in a **background subagent with `isolation: worktree`** so they run concurrently while you monitor. Never launch two subagents on the same files/region at once (merge conflicts) — same-region work goes to one agent, sequentially. Keep a handful in flight, not thirty. **Model split (owner's rule, 2026-09-14, repeated 2026-09-19): code with Opus (`model: "opus"`), review and verify with Fable 5.0, never Fable 5.1.** **The Agent tool's `model: "fable"` IS Fable 5.1** — confirmed 2026-09-04 and again 2026-09-19 (two review agents served by `claude-fable-5-1`, died on the five-hour limit and took the fix agents with them); the enum has no 5.0 entry. Reach 5.0 through the `fable-review` agent type when it is listed (`subagent_type: "fable-review"`, no `model` override — a user-level agent definition pinned to `claude-fable-5`); otherwise from Bash: write the review prompt to a file and run `claude -p --model claude-fable-5 --output-format json --allowedTools "Read,Grep,Glob,Bash" < prompt.txt > out.json` with the worktree as cwd, in the background; the `result` record's `modelUsage` must read `claude-fable-5`. **Run it on every merge, not only security-shaped diffs** — on 2026-09-19/20 it found a BLOCKER on two diffs that had passed the orchestrator's own read (#177: a README-promised confirmation that did not exist, plus an idle-`--resume` path that recreated a stub and blocked restore forever; #397: a titling epilogue that could name a chat after the content a redaction had just scrubbed) and a real doc-vs-code lie on every other one. A headless review killed by the limit exits 0 with the limit message as its `result` — an empty or one-line `out.json` is not a verdict; re-run after the reset.
4. **Review** — when a subagent reports, personally read the diff. Scrutinize concurrency, the approval gate (the model must never run anything unapproved; alias/expansion happens BEFORE the gate), and correctness. You are the quality gate. Re-spec and re-run if it isn't right; don't rubber-stamp. **Diff against the branch's merge-base, not `main..HEAD`**: once other branches have merged, `git diff main..HEAD` on an older-based branch shows those merges as REVERSALS (it looked like #187 was undoing #368's text; it was not) — use `git diff $(git merge-base main HEAD)..HEAD`. A three-way merge keeps both sides.
5. **Verify** — after merge, run the gates from main; verify UI changes live in Chrome, including two-tab checks for multi-connection behaviour. Check the real code path, not just unit tests. **Use the isolated harness (`.claude/skills/verify/SKILL.md`), never the live server**, and drive it headless with `uv run --with playwright` + `channel="chrome"` from Bash (no browser MCP tool is needed). Two things bit on 2026-09-15: **port 8899 was already taken by another session's day-old harness**, so "server up" was THEIR server — before typing anything, `lsof -nP -iTCP:<port> -sTCP:LISTEN` and confirm the PID is your launcher; pick a fresh port if not. And the UI has a **token gate** (`#token-gate` overlay intercepts every click): pass `token="..."` to `create_app` and `?token=...` on the URL.
6. **Ship** — merge to main, run gates from main, then `make ship` (guard → lint → tests → reinstall → restart → health-check) and push. **Never a bare `uv tool install`** — it builds from the WORKING TREE, and `make ship` refuses on a dirty tree for exactly that reason (CLAUDE.md "Shipping"). Ship ONLY from the main checkout, never a worktree.
7. **Document** — comment the resolution on the issue: what changed, WHY, and what the user should test (call out iOS/mobile explicitly). Close if done; otherwise leave open with the open questions.
8. **Report** a running ledger to the user and hold design questions for their return.

## Every subagent spec must include
- The problem + root cause, file/function pointers, and the design/approach you decided.
- Constraints: preserve the approval-gate invariant; match existing code idioms; keep the change tight; comment WHY not WHAT.
- Quality gates it must pass: `uv run pytest`, `uv run ruff check .`, `uv run mypy`, and `node --check aish/static/app.js` for JS. Add tests in `tests/` following the FakeChat / no-model / no-network / no-real-execution pattern.
- **NEVER touch `~/Downloads`, `~/Desktop`, `~/Documents`, `~/Library/Mobile Documents` or `~/iCloud` — not `ls`, not `find`, not a deliverable path.** From the claude-rc LaunchAgent tree those folders block forever on a TCC prompt nobody can answer: on 2026-09-20 the #391 agent's last command referenced `~/Downloads` and the ORCHESTRATOR sat 15 hours in a synchronous `openat()` — it looked like a container restart and was not. Three `find /` orphans from the day before were hung on the same thing. Deliverables (a rendered PDF, a screenshot) go under `/tmp/<task>/` or `/Users/epnasis/aish`, and the spec says so. [[rc-tcc-folders-hang-sessions]]
- Workflow: work in its worktree; conventional-commit message with **NO** Claude attribution / co-author / footer lines; use `SSH_AUTH_SOCK= git commit ...`; do NOT deploy and do NOT merge — report back the **branch name**, a summary, gate results, and anything risky or needing a human decision.

## Guardrails & recurring gotchas (project memory)
- A new slash command needs wiring in ~5 places including the web `handleSlash` case — a server WS test does NOT catch a missing web case. [[aish-slash-command-wiring]]
- The ship steps (reinstall/restart/push) run from the main checkout after merge. [[aish-ship-without-asking]]
- Prefix git commit with `SSH_AUTH_SOCK=` or SSH signing hangs on the stale agent socket. [[git-commit-needs-no-agent]]
- Capability phrasing in aish's own prompts is ignored — use imperative MUST + an example. [[prompt-hints-must-be-imperative]]
- Small aish-web changes go straight to main; propose the preview env for bigger ones. [[preview-for-bigger-changes]]
- Sessions run ON the mm host — act locally, never ssh. [[this-machine-is-mm]]
- **`gh issue list` defaults to 30 items** — ALWAYS pass `--limit 100` (or more) when surveying, or older open issues are silently truncated from triage. [[gh-issue-list-default-limit]]
- **The repo is often ahead of the tracker.** A prior orchestrator run may have fixed+merged issues but never closed them (tell-tale: stale `issue-*` worktrees under `.claude/worktrees/`, and `#NNN`-tagged comments already in the code). Before delegating ANY fix, grep the code for the issue's tag/feature and check `git worktree list` — most of a night can be verify-and-close, not rebuild. Delegating a done issue wastes a subagent.
- **`git log -10` is NOT enough to spot an already-merged issue.** Merges land without closing keywords and sink below the day's later commits within hours. During triage run `git log --all --oneline | grep -E "#(NNN)"` for EVERY candidate issue number — that catches a fix merged this morning that `git log -8` truncated away. Two of the first three subagents dispatched in one run came straight back with "already fixed and merged"; the grep is one command and prevents it.
- **A NONZERO grep count is a signal to READ, not a number to note.** The grep above only helps if you act on it. In the 2026-08-25 run `#250` came back `merged-mentions=1`, was dispatched anyway, and the subagent found the fix already on main — landed inside `fffaa6d`, a two-part commit whose *headline was about something else entirely* ("a file aish downloaded is a file you can open") and whose second half was the fix. That is the normal shape: a fix buried under an unrelated headline, with no closing keyword. For every nonzero count, run `git merge-base --is-ancestor <sha> main` and grep the code for the feature before you spend a subagent.
- **NEVER let a subagent run `git stash` — the stash stack is REPO-WIDE, not per-worktree.** Worktrees isolate the working tree and the branch; they do NOT isolate `refs/stash`. In the 2026-08-25 run one agent stashed to capture a baseline and found `stash@{0}` belonged to a *different* agent (`wip-290`: `server.py`, `docs/web-server.md`, `tests/test_server.py`). Nothing was lost, but a `git stash pop` timed between another agent's push and pop would have dropped that agent's work into an unrelated tree — silently, and attributed to the wrong issue. The same agent also stashed *while its own suite was running*, swapping `style.css` out from under pytest, which died at 36% with exit 144. Put "do not use `git stash`; to test a revert, commit first and `git revert`/`git checkout -- <file>` within your own worktree" in every subagent spec.
- **`exit 144` from pytest is the machine, not the code.** Under ~10 concurrent agent suites the box kills runs under memory pressure, reporting zero failures. Re-run before believing a failure, and do not let an agent "fix" a phantom.
- **Check `git status` and `git log` again right before merging.** The owner works in the main checkout during these runs — an uncommitted file at survey time can be a landed commit twenty minutes later, and a huge single-line `CLAUDE.md` bullet is a near-guaranteed conflict when both sides edit it. Resolve those by splitting the line on `.` into two temp files and diffing to see what each side added, then reassemble both edits — never take one side wholesale (it silently drops the other's documentation).
- **Environment "failures" reproduce in the WRONG context.** Reminders/TCC-gated tools return instant `access denied` from a Claude Code / tmux / ssh shell because the grant is keyed to the `aish-web` LaunchAgent's Aqua session. Verify through the real daemon (drive the web UI) before reporting anything broken. [[aish-reminders-tcc-grant]]
- **The auto-mode classifier throttles rapid bulk `gh issue close`/mutations.** Looping closes get blocked; even 3-at-once trips it after a streak. Do them as individual calls and interleave with other work (reviews, worktree cleanup) to space them out.
- iOS-standalone/keyboard-visual issues (#8, #24) can't be verified from desktop Chrome — implement per the code, then label `question` and ask the user to confirm on-device rather than closing blind.
- **The five-hour usage limit kills every in-flight agent at once, mid-edit, with NO completion notification.** On 2026-09-14 five fix agents died silently; the only evidence was `git worktree list` showing their worktrees at `ahead=0` with dirty trees (80–210 lines each). Do not restart from scratch and do not resume the dead agent (its model is what hit the limit): launch a FRESH agent pointed at the existing worktree path (absolute paths, `git -C`), with "audit the inherited diff against the spec, keep what is right, finish the rest" — all four finished in one pass. Before relaunching anything after a limit reset, run the worktree scan first to find what is half-done.
- **An interrupted agent's report can carry an over-claim from the agent before it.** The #187 inherited comment cited a dedup key (`curate-<week>-<model>`) that exists nowhere in the repo; the finishing agent caught it only because the spec said "audit". Tell the finisher explicitly that inherited rationale is a hypothesis to check, not a fact to keep.
- **A subagent that refuses the premise is doing its job.** #370's item 367b asked for a "scroll to it" sentence; the agent ran the real predicate in Chrome and showed `outside-scroll-range` means scrolling CANNOT reach the control — the requested sentence would have been the L8 guess the item was filed against. When an agent reports "the premise is backwards, here is the experiment", read the experiment, not the ask.
- **A subagent's "out of scope, flagged not fixed" line is a work item.** Two of this run's best findings came that way: #327's agent noticed `is_auto_approvable` passes `ls \x1b[2A` (filed #382), and #369's calibration on the live corpus found 48 test-fixture memories polluting `~/.config/aish/memory/` (filed #381). File them as issues the same hour, with the agent's evidence verbatim; do not let them live only in a transcript.
- **Fix the method, not the site — even inside one issue.** #216's agent fixed the one silent drop it was sent for and listed two siblings of the same shape "out of scope". Send it back to close all three in the same commit; the second pass took ten minutes and turned one refusal into the rule.
- **A CI-only failure is a bug until proven flaky, and this run it was a bug three times out of three.** "Passes locally, fails in CI" was a boot-relative `time.monotonic()` sentinel that only bites a machine under 30 minutes old (#385), a write-through-temp file named per PROCESS racing across worker threads (#395, present in four modules), and `done` emitted before `busy` cleared so a slow runner's next message was refused (#397 — and its fix opened the redaction leak above). The protocol: `gh run rerun <id> --failed` on the identical commit (a second failure with a varying test set means timing, not nondeterminism you can dismiss), 8 local runs of the failing tests, then READ the captured traceback with `gh run view --log` — the cause was one line each time. Never retry past it, and file it as an issue with the traceback before dispatching.
- **Agents killed by the usage limit had already committed.** On 2026-09-19 both dead fix agents had a clean commit on their branch (one had an uncommitted docs hunk, one had scratch files) — `git -C <wt> log --oneline -3` and `status --short` BEFORE assuming loss. The finishers succeeded with "inherited rationale is a hypothesis: check it, cut what rests on nothing" — one cut a "captured 400" that had never been captured and re-attributed a Bedrock wording mis-filed as the direct API.
- **A subagent's "out of scope" and "risky" lines were the best issues of the run**: #390 (import-bound allowlist paths — three sites, not one), #395, #396 (the positional join a finisher named as its own weakness), #397. File each the same hour, quote the evidence verbatim, and dispatch the well-specified ones the same night.
- **A preview (`make preview`) does NOT pick up a static edit until it is RESTARTED.** The asset rev (`server._static_rev`, `?v=` on app.js/style.css) is computed once at import, and the service worker caches `?v=` assets cache-first forever — so a CSS edit on a running preview reaches the curl but NEVER the phone, and the owner's "still broken" is a reading of the OLD stylesheet. On 2026-09-22 one #392 experiment was invalidated this way. After any static edit: restart the preview and confirm `curl https://aish.wenda.eu/preview/ | grep -o 'style.css?v=[^"]*'` changed. The prod plist holds no secrets: the preview needs `AISH_WEB_TOKEN` from the Keychain (`security find-generic-password -s aish -a AISH_WEB_TOKEN -w`), and with no Gemini key in the env run it on `AISH_PREVIEW_MODEL=qwen3:8b` — do not go hunting for credentials.
- **`node --check` does NOT catch runtime errors.** A top-level line in `app.js` that references a `const`/`let` declared later in the file (e.g. the `input` const ~line 3508) hits its temporal dead zone, throws at load, and **silently breaks the ENTIRE app** (Enter stops submitting, model shows "…") — yet pytest/ruff/mypy/`node --check` all pass. After deploying ANY frontend change, **live-check the browser console** (`read_console_messages onlyErrors`) — a clean load is part of "verified", not just a screenshot. Attach new top-level listeners via `$("id")`, not a not-yet-declared module const.

## Do NOT
- Close an issue you didn't genuinely resolve.
- Merge a subagent's concurrency/safety change without reviewing the critical paths.
- Launch parallel subagents on overlapping files.
- Make a big product/UX decision unilaterally — hold it for the user.

Improve this skill over time as the workflow sharpens (add new gotchas, tighten the triage rules).
