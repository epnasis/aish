# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`aish` is a terminal AI agent (local Ollama model by default, cloud backends optional) that runs shell commands, edits files, and browses the web — with a mandatory user-approval gate on anything that mutates state. The README covers user-facing behavior thoroughly; this file covers what you need to change the code safely.

## Commands

```sh
uv run pytest                          # full test suite — no model/network needed
uv run pytest tests/test_agent.py      # one file
uv run pytest tests/test_agent.py -k compaction   # one test by keyword
uv run ruff check .                    # lint (also formats config: line-length 100)
uv run mypy                            # type check (CI-gated; config in pyproject.toml)
uv run aish                            # run from source
```

After changing code, the user's installed `aish` does NOT pick it up — uv freezes the wheel and caches it at the same version. Reinstall with:

```sh
uv tool install --force --reinstall --no-cache /path/to/aish
```

## Workflow: when to use a worktree

Before editing code, check `git status`. Work in a git worktree on a feature branch (via EnterWorktree) instead of this checkout when either:

- the change is **non-trivial** — a multi-file feature or refactor, not a small fix; or
- the tree is **not clean with changes you didn't make** — the user or another session is mid-work in this checkout.

Merge back to main after tests pass, then remove the worktree. Trivial fixes on a clean tree go directly in this checkout. The reinstall/ship step (`uv tool install ...`) always runs from this main checkout after merge — never from a worktree path.

## Never type into a chat you did not create

**A verification run MUST NOT send a message to a chat it did not start.** Use the isolated harness in `.claude/skills/verify/SKILL.md` (its own `state_dir`, port 8899); if a check genuinely needs the live server, click ＋ for a NEW chat first and drive only that. The port is not a defence — `scripts/aish-preview.sh` points preview at PROD's `AISH_STATE_DIR` deliberately, so :8788 writes the same sessions as :8787. On 2026-07-28 a verification run drove the live UI through Chrome while the browser was parked on the owner's own shopping chat and typed five probes into it; a chat has no way to delete a message, so they are permanent, they auto-retitled the chat, and days later they were still what the owner saw when the chat flagged itself as having something new (#201).

## Architecture

The core invariant: **the model never executes anything directly.** Backends only return structured tool-call requests; `Agent._dispatch()` in `agent.py` is the single execution point, and `run_command` is unreachable there unless the `approve()` callback returns the (possibly user-edited) command.

Data flow: `cli.py` (REPL/argv, slash commands, rendering) constructs an `Agent` with a chat callable from `backends.py` and an `approve` callback, then calls `agent.run_task()`. The agent loops: model proposes tool calls → `_dispatch()` executes them (gated) → results appended → repeat until a final answer. Approver verdicts: `True`/edited-string approve, `None`/`False` deny, `Blocked(reason)` (denylist — unapprovable), `Denied(comment)` and `Approved(comment, command=None)` — both web-card-only (CLI approvers still return bool/str/None), and both constructed ONLY when the user typed a comment. **A comment makes approve and deny mean opposite things (issue #81):** `Denied(comment)` = STOP — the action is denied, the comment appended to the denial result, and the **stop gate** armed; `Approved(comment, ...)` = CONTINUE but ADJUST — the original action is HELD (never run, even if `command` was edited), and the model is told to rework it to the comment and re-propose (the adjusted action is approved again before it runs). The **stop gate** (`_stop_gate`, arms via `_arm_stop_gate`, only denials arm it): eager models run another tool before addressing a denial, so while `self._pending_comment_response` is set every tool call is refused; the main loop clears it only on a **text-only turn** (not a same-turn text+tool: chatty preamble alongside a command would otherwise slip past), and that text-only turn ends the task — deny means stop. `run_task` resets the flag so it never leaks across tasks. Approvals never arm the gate (continue); the HOLD + re-approval is what keeps an unwanted original command from running. The step budget is **progress-gated (#108)**, not a flat cap: a step counts as progress when a tool call yields a (tool, args, result) tuple seen for the first time (reusing the loop detector's `repeats` dict — no extra model call, no timer). A progressing task may run past `max_steps` up to the unconditional hard ceiling `max(max_steps, HARD_STEP_CEILING=60)`; `MAX_STALL_STEPS` (8) consecutive no-progress steps stop it early. The loop ends three ways: a text-only answer, a cancel, or `_finish_stopped()` — reached at a stall, the hard ceiling, or when loop detection fires (identical call + identical result: warn at 3 repeats, stop at 5) — which runs one final no-tools turn so the model reports completion state instead of cutting off; the ceiling is never silently exceeded.

- **`backends.py`** — routes `--model` strings to a chat callable. Every backend (Ollama, Gemini, Claude API, OpenAI) is adapted to the *exact* `ollama.chat` calling convention (`chat(model, messages, tools, options, think, stream)`), so `agent.py` never knows which provider it's on. New backends must preserve this shape.
- **`claude_max.py`** — the exception: routes through the Claude Agent SDK / local `claude` CLI login. It strips Claude Code to bare inference and injects aish's own tools, so the approval gate still applies. Keeps its own session state. Three invariants added by #178 P0-4: (1) the SDK owns the loop, so the inner Agent's `run_task` — where per-task state normally resets — never runs; `ClaudeMaxAgent.run_task` therefore calls `Agent._reset_task_state()` (the SHARED extraction of run_task's top: stop gate, skill gates, `_run_meta`, `task_sources`, `_cancel` — add new per-task fields THERE, never inline in run_task, or claude-max wedges again). (2) The constructor has NO `**kwargs` sink — every capability the entry points pass is either kept on the wrapper (`on_message`, `on_token`, `status`, `max_steps`) or forwarded to the inner Agent (approvers incl. `approve_tool`/`approve_import`, trace/command/state sinks, steering callbacks, `semantic`, `aliases`); an unknown kwarg is a TypeError, so a new Agent capability can never silently no-op here. Plugin tools register on the SDK MCP server (`_current_tool_defs` = `TOOL_SCHEMAS + inner._plugin_defs`, refreshed per task by `_refresh_server`, mutating ones only when a tool approver is wired). (3) SDK tool handlers may run concurrently while the inner Agent is not thread-safe: `_locked_dispatch` is the single execution path — a `threading.Lock` around `inner._call_result(... inner._dispatch ...)`, which also emits the same tool_start/tool trace steps as the native loop and contains tool exceptions. Tested by `tests/test_claude_max.py` via a FakeSDK injected at the `_load_sdk` seam (no SDK package, no CLI, no network).
- **`approval.py`** — conservative parser classifying commands as read-only for auto-approval. Philosophy: only approve what it *positively* understands; anything ambiguous falls through to a prompt. Auto-approval is scoped to session roots (launch dir + `/add-dir` + directories the user trusted at a prompt); path arguments escaping them (absolute, `~`, `..`, symlinks resolved — including a plain relative token that IS an in-root symlink pointing outside, #178 P1-1; tokens naming nothing on disk are never resolved, so patterns/flags/future files can't false-positive) prompt even when allowlisted — `escaping_dirs()` names the escapes so the prompt/card can offer "trust this directory" (`Agent.trust_root`, session-memory only). Shell path operands also get `files.is_sensitive_path` on their RESOLVED target (mirroring the read_file sensitivity prompt), so `cat link-to-ssh-key` or an in-root `.env` prompts even when containment holds. The prefix allowlist has two lifetimes: `a`/"Always allow" is durable and file-backed, while `s`/"Allow this session" lands in `Agent.session_prefixes` and dies with the session (see the roots paragraph below — one rule for both halves of the scope). When touching this file, err toward prompting.

Model execution is **stateless**: every `run_command` runs in the project directory (`Agent.cwd`), a bare model-issued `cd` is rejected with guidance instead of executing (see `CD_NOT_STICKY` in `agent.py`), and excursions are `cd x && ...` subshells (`cd` is in `SAFE_COMMANDS` because it is subshell-scoped and root-checked). Only user actions move cwd: `/cd` and its alias `!cd` both move cwd AND re-anchor `roots[0]` (`Agent.rebase`). This keeps the model permanently anchored to the project directory — do not reintroduce model-driven cwd mutation.

**Auto-approval scope belongs to the SESSION, not the process (#176).** Both halves of that scope — the `roots` that bound auto-approval to directories, and `Agent.session_prefixes`, the command prefixes granted with `s` / "Allow this session" — live on the Agent and are reset by the SAME call, `restore_workspace`, so a session change drops them by construction rather than by someone remembering to. The approvers never own the prefix set: `cli.make_approver` and `server.make_web_approvers` both take a late-bound `get_session_prefixes()` returning the live set off the agent (same holder pattern as `get_scope`/`trust_dir`, because the agent is built after its approvers), and keep a set of their own only for an unwired approver in a test. `restore_workspace` CLEARS the prefixes and never restores them — unlike trusted dirs they are not recorded on disk, so resuming BACK to the chat that granted one asks again rather than inventing persistence the log cannot back. The persistent `a` allowlist is deliberately untouched by all of this: it is file-backed, shared by CLI and web, and outlives every session.

`restore_workspace(cwd, trusted)` is AUTHORITATIVE, never additive: on resume/cold-open it rebuilds `roots` to be EXACTLY that session's own workspace — its recorded `kind:"cwd"` (or `Agent.launch_cwd` when it never recorded one, matching the base the web gives a cold-opened session) plus its own recorded `kind:"trust_dir"` dirs, which `/add-dir` and an approval-prompt "trust this directory" both write. Both directions are bugs, because `roots` is what scopes auto-approval: a dir trusted in the chat you LEAVE must not stay auto-approvable in the one you land in (the CLI reuses ONE live Agent across `/resume`, so this leaked; the web builds a fresh Agent per cold open and never did), and a dir this chat DID trust must come back. `/new` re-anchors the same way (`restore_workspace(agent.cwd, [])` — you are still in that directory in this terminal, but the previous chat's grants stay with it). It sets state directly, never via `rebase`/`trust_root`, so restoring emits no fresh record (a replay feedback loop). The corollary: roots a PROCESS owns rather than a session — the web's uploads dir — must be appended AFTER the call, which is why `open_session` adds it below the restore block, not at construction.
**Origin-gated egress (#178 P0-2).** `Agent.origin` (constructor kwarg, default `"user"`; the server's `open_session` passes the session's origin, cli.py passes nothing) scopes two read-side capabilities to attended sessions. In a non-`user` session: (1) `web_search`/`read_url` (`EGRESS_TOOLS` — read-only locally, but their INPUTS leave the machine) hold on the existing `approve_tool` channel when they reach a host outside **provenance** — `_owner_hosts` (extracted by `_hosts_in_text` from owner-authored text ONLY: the task/trigger prompt in `run_task`, mid-task steering in `_inject_pending_messages`, `add_user_context`, and user-role turns in `load_history`; never tool results or fetched pages, which are exactly what an injection controls) plus `_approved_hosts` (hosts vouched on an earlier egress card; a plain approve caches the host for the session). `_egress_gate` mirrors `_dispatch_plugin_tool`'s #81 verdicts, passes the novel host as the card's `preview` (zero frontend change), and fails closed: no approver → `EGRESS_NO_APPROVER`, unparseable URL → gated. `_read_needs_prompt` routes gated calls out of the parallel read path so the gate can't be bypassed. (2) `_recall` drops the past-session archive search (knowledge entries stay) and says so in the result so the model doesn't retry. `user`-origin sessions are byte-identical to before — no new prompts. `TestEgressGate` in test_agent.py pins all of it.
**Origin-gated knowledge writes (#196).** The third capability the same axis scopes, and the one the axis was never applied to: `remember`/`forget_memory` (`KNOWLEDGE_WRITE_TOOLS`) auto-approve, deliberately, so capturing a fact costs nothing — but that reasoning is **attended-only**, and unattended the text proposing the write can be injected email while the result persists into EVERY future session and is retrieved by preflight. That makes the frictionless write a **persistence primitive reachable from untrusted input** — strictly worse than the read exposure #178 P0-2 closed, because it outlives the session. `_knowledge_gate` (called from `_dispatch` immediately before both branches; they are not in `READ_ONLY_TOOLS`, so the parallel read path can never reach them) returns on its first line for `origin == "user"`, so attended behaviour is byte-identical. Non-`user`: deletion is refused **structurally** — no card — because there is no unattended case where autonomously deleting the owner's knowledge is right, so asking would only park a worker on a question already decided (the #185 curate pass's intended path was always *proposing* retirement in its summary; v1's prompt-level `MUST NOT call forget_memory` was #190's own thesis sitting in aish's code — a policy that exists only as prompt text is a policy that does not exist). Saving **holds** on the `approve_tool` card (verdicts mirror `_egress_gate`/`_dispatch_plugin_tool` #81 exactly; no approver → fails closed), because a triggered session does legitimately learn things and the owner should see what lands in the corpus. `_triggered_safe` must never shortcut `remember` (pinned in test_server.py). Every refusal names the slug and the real destination — #190 decision 2, the harness carries the feedback so the owner doesn't have to. `TestKnowledgeGate` in test_agent.py pins it.
**claude-max got origin (#196 side-fix).** `ClaudeMaxAgent.__init__` had no `origin` parameter while `open_session`'s `common` dict has always passed one — and with the deliberate no-`**kwargs` sink (#178 P0-4) that meant **every** claude-max web session raised TypeError at construction. It now takes `origin` and forwards it to the inner Agent, which is what makes both origin-scoped gates hold on that backend: they live in `Agent._dispatch`, and `_locked_dispatch` is the single path to it.

- **`tools.py`** — `run_command` (approval-gated shell) and `read_docs` (auto-approved, so it takes only a bare command name validated against PATH — never a shell string). The denylist (unrecoverable commands blocked even with approval) lives here. Also the **tool result envelope** (#192): `ToolOutcome` + `classify_output`. The envelope exists because the runtime used to decide whether a call succeeded by sniffing a string prefix (`result.startswith("ERROR")`), which recorded `youtube_analyze` — `transcript: ""`, populated `error_log`, **exit 0** — as a green ✓ while the model silently substituted six web searches for the source the user had named. `ToolOutcome` is deliberately a **`str` subclass**: every existing caller keeps treating it as the result text, so the verdict rides along with no ripple through ~30 dispatch branches, and — the load-bearing half — the metadata travels WITH the value instead of in instance state, which is what makes it correct on the parallel read-only path where several calls are in flight at once (`_run_meta` could not have been used there). The caveat that follows from the same choice: a string operation returns a plain `str` and silently drops the envelope, so a `ToolOutcome` is always built LAST, after any `_with_feedback` concatenation. `classify_output` is the deterministic verdict — exit code, then emptiness, then declared required fields (#193's contract, empty until it ships), then a populated error channel (`error`/`error_log`/`errors`, a NAMED field the wrapper author chose, never prose). `read_tool_output` is the native read-only tool that pages a truncated result from the cache.
- **`files.py`** — pure `plan_*` functions compute (old, new, diff) without touching disk; `commit()` writes. The gap between plan and commit is where the diff is shown and approval obtained — nothing is written unseen.
- **`web.py`** — `web_search`/`read_url`, auto-approved but their inputs leave the machine, so every call is echoed and fetched content is wrapped in an untrusted-content banner. http/https only. `fetch_binary` is the same guarded fetch for non-text bodies (`show_image`), sharing `_require_public` + `_opener` so the redirect re-check applies. **TLS trust has ONE source (`_trust_store`, #189):** Python's default store on macOS is Apple's legacy `/etc/ssl/cert.pem` — not the Keychain system store — which is years stale and missing newer roots (GlobalSign Root R46 among them), so fetches to whole swathes of the web failed with `unable to get local issuer certificate` while other hosts worked fine; it reads as a broken SITE rather than a broken client, and it silently affected `read_url` too, not just the image fetch that surfaced it. `_opener` now carries an `HTTPSHandler` built from **certifi**'s current Mozilla root set (declared in pyproject because we import it), falling back to the default context if certifi is ever absent — a stale store still verifies most of the web, refusing everything would be worse. The `_PublicOnlyRedirects` handler stays wired alongside it (`TestTrustStore` pins both: verifying a certificate on a fetch aimed at cloud metadata is no win).
- **`media.py`** — the media store behind **`show_image`** (#188): where pictures an answer displays actually live. The problem it fixes is that "show me what X looks like" was a routine request with NO capability — five unrelated primitives (text search, text fetch, shell+curl, markdown image syntax, a roots-gated `/file`) the model had to reassemble blind, every failure landing in the browser AFTER the turn, and the model compensating by writing memories (six of them, one of which told it to litter the project tree). Three properties carry the design. (1) **The fetch is server-side**, through web.py's SSRF guard — that is what lets arbitrary image sources work while the browser still loads only same-origin bytes, so the CSP/`IMG_FETCH_HOSTS` whitelist stays exactly as strict and the zero-click `![](https://attacker/…)` channel (#178 P0-2/P1-12) stays closed. Security preserved by RELOCATING the fetch, not by loosening policy. (2) **Format detection is magic bytes, never the extension** (`sniff`) — the failure it exists to catch is a WAF/hotlink block or the page itself served under a `.jpg` URL, which the extension agrees with and no decoder does. (3) **Files are content-addressed and the store is bounded LRU** (`store`/`prune`, `MEDIA_MAX_*`) — a retry is free, duplicates are impossible, and a re-fetch restores anything evicted. The store is `state_dir/media`, deliberately NOT the scratch workspace: scratch is deleted at session end and a transcript is permanent, so a picture left there is a broken image on every reopen (different lifetimes). `Agent._show_image` orchestrates and returns a **ready-built markdown line** — aish composes it, so a caption with a bracket or newline can't silently break the image parser — and every failure returns a sentence naming what went wrong, so the model learns DURING the turn. `show_image` is in `READ_ONLY_TOOLS` (its only write is an image into aish's own store, never user state — same reasoning as the scratch dir's auto-approval; content-addressed writes make it thread-safe) AND in `EGRESS_TOOLS` (its URL form is an outbound GET at a model-chosen host; its local-path form reaches no host and `_egress_novel_hosts` never gates it).
- **Image roots — ONE boundary, three renderers.** `Agent.image_roots()` = `roots` + the media store + the scratch dir; consumed by `/file` (`WebServer._image_roots`), the PDF exporter, and the CLI's `term_image`. They disagreed before #188: the exporter trusted the scratch dir and `/file` did not, so a file the model wrote where it is TOLD to write throwaway files printed fine in a PDF and 403'd in the chat with nothing saying why. Deliberately DISTINCT from `roots`, which is the auto-approval scope and is rebuilt authoritatively per session (`restore_workspace`, #176) — the process-owned directories must be displayable without becoming directories the model may run commands in, and without being dropped on a session switch.
- **Render-error channel (#188 layer 2).** The browser is the only place that knows something didn't render, and it used to keep that to itself (`img.onerror` wrote a note into the DOM and told nobody), so the model's only feedback was the user typing "images don't show". `app.js`'s `// [RENDERERR-START/END]` block batches failures (debounced, capped, reporting the model's ORIGINAL target — never the rewritten `/file?…&token=` URL, which would put the access token in the session log) and sends `{type:"render_error", items, live}`; `WebServer._render_error` writes a `kind:"render_error"` trace record (durable evidence in the shape the #185 curate ledger reads) and hands the model a note only when the failure was in a LIVE turn — merely opening an old chat whose images were evicted must not grow it a turn. **The report is LIVE-ONLY, and the record is deduped (#201).** It used to be written ALWAYS, on every render, and that was the same mistake in a second place: a failure to render is a fact about the turn that WROTE the image (the only turn anyone can act on it in — the model is handed the note solely when live), so a replayed report was never anything but ledger noise. Reporting it on every read made it noise that COMPOUNDED, because each report is a log write and a log write read as fresh activity: a chat holding a dead image was marked unread by the act of reading it, forever, and one had accumulated 53 identical records, up to four per open. `noteRenderError` now returns early when not `live` — the gate sits in that ONE function rather than at its call sites, so a future call site cannot forget it — and `_render_error` drops a report identical to `Session.last_render_error` as the backstop no client can route around. A property of the transcript is not an event; only its arrival was. It renders NOWHERE: nothing is emitted live and `reconstruct_events` skips the step explicitly, so hot/cold parity holds by the same argument #171 makes for `[aish: …]` notes, and the user's signal is the broken-picture note already in the answer. The note goes through `Agent.add_system_note`, NOT `add_user_context` — the latter calls `note_owner_hosts`, which would let a host in a model-chosen image src launder itself into egress provenance.
- **Governance records are renderless, and that needs TWO mechanisms (#192, `docs/trace-contract.md` §1.2/§1.3).** The trace contract is MERGED AND BINDING: every record #191-#194/#197 emits must match it. The mechanical fact everything here is sized against: `app.js`'s `traceStep` calls `ensureTrace()` **before** it dispatches on `step.kind`, so a record kind with no renderer does NOT degrade to "renders nothing" — it opens an **empty live trace card with a running ticker**. So a kind that must not render needs both halves: `Agent._emit_record` (log-only — writes to `step_log`, never `on_step`) AND membership in `session.RENDERLESS_STEPS`, which `reconstruct_events` skips. **Either alone still produces the card** (live emit, or cold replay). Do not add a third mechanism — a frontend guard in `traceStep` is explicitly NOT the design, and `tests/js/test_renderless_ghost_card.js` fails if one appears, because the Python discipline was sized against `traceStep` behaving exactly as it does. `has_trace` is set by the `kind == "trace"` arm BEFORE the skip, so a log holding only governance records still reconstructs instead of falling back to a flat history blob. Pinned from both sides by `TestRenderlessRecords`, each half independently mutation-checked.
- **Turn/call identity (#192, contract §2).** `Agent._turn` (advanced in `_reset_task_state`, so claude-max — whose SDK loop never enters `run_task` — counts turns too) and a per-turn `call` counter assigned in `_call_result`. `call` is carried as a LOCAL, never read back off the agent: read-only tools run in parallel, so an attribute would hand two concurrent calls the same id. Stamped on `tool_start`/`tool`/`knowledge` plus every renderless kind (design fork 1 = option b); `thinking` is deliberately left alone as the high-volume kind. This replaces the positional correlation `curate._windows` apologises for in its own docstring.
- **A refused action is never a green step (#192).** ONE rule, applied last in `_emit_tool_step`: a `decision` in `REFUSED_DECISIONS` (`denied`/`held`/`blocked`/`rejected`) forces `ok: false`, `status: "failed"`, `verdict_by: "gate"` — whichever path set it. This is wider than the contract's §6.13 table, which names five plugin constants: `run_command` sets `decision` in `_run_meta` but never `ok`, and `DENIED_RESULT` ("USER DENIED…"), `HELD_FOR_ADJUSTMENT` ("NOT RUN…") and `BLOCKED_RESULT` ("BLOCKED…") start with none of the sniffed prefixes, so a denied **shell command** logged green too — ten sites, one defect. Deriving both fields from one source also keeps them coherent (`ok` IS `status == "ok"`; the envelope and `_run_meta` could previously disagree). The near-duplicate memory gate is the same story and the sharpest one: its refusal begins `"NOT saved — …"`, so the gate that demonstrably WORKED in #190's evidence logged its refusals as successes. It now emits an `admission` record carrying `sim`/`floor`/`mode`/`against` via `save_memory(on_admission=…)` — a callback, not a changed return type, because the string return is what cli.py, curate.py and every test read — which is what finally makes `DEDUP_MIN_SIM` ("provisional until measured") measurable.
- **`session.py`** — append-only JSONL per session in `~/.local/state/aish/`: conversation (for `--resume`), audit trail of every command decision — **all file writes serialize on the per-instance `_write_lock`** (#178 P2: the agent worker thread and the event-loop thread both write — rename, console-open audit — and an unserialized write on the buffered handle is a torn/lost JSONL line every reader silently skips; any NEW code path that appends to or rewrites the log must hold it, see `TestWriteLock`), plus `kind:"trace"` records — the structured activity-trace steps (the same dicts the web renders), logged from BOTH entry points via the agent's `step_log` sink so the trace is UI-agnostic and survives eviction/restart. Terminal-block framing (`kind:"cmd_start"`/`"cmd_end"`) is persisted the same way via the `command_log` sink. `reconstruct_events()` replays a logged session as the EXACT event stream a rich client emits live — `user`/`step`/`done` plus, for each run_command, its full `command_start → stream → command_end → tool` sequence — so a cold-loaded web session feeds the frontend identical events and renders an identical terminal block (no fallback path). The command's output rides on the `tool` step (not duplicated in the framing records) and is spliced back in as one `stream` with run_command's trailing `[exit code: N]` marker stripped (`_EXIT_MARKER_RE`), matching the live body where the code arrives via `command_end`; a legacy tool step with no framing gets a synthesized block. One `done` per task carries the final assistant text; it returns `None` for pre-trace logs, and the server falls back to a flat `history` blob then. `step_log`/`command_log` are orthogonal to the agent's `on_step`/`on_command_*` (rich-renderer hooks; `on_step` gates terminal chatter via `_note`) — the CLI wires the log sinks only, so it logs without changing its inline output. Its ranked excerpt search (`search_excerpts`, output hard-capped) backs the sessions section of the `recall` tool; the agent gets `state_dir` + `current_session` at construction and excludes the live session from results. `user_command_history()` (#104) aggregates the user's OWN successful `!` commands across recent sessions (only `decision:"user-direct"` records whose `cmd_end` reports exit 0 — model tool-loop commands never pollute the palette) and feeds the web terminal-mode autocomplete via the hello payload's `cmd_history`. `task_start`/`task_end` records (#164) bracket a web task on disk; `pending_task()` returns the unfinished one (with an `attempts` count = starts since the last end) and `interrupted_sessions()` lists them newest-first inside an age window — the durable half of restart recovery (see `server.py`). **Synthetic user turns (#171):** aish writes text into a conversation as `role:"user"` that the human never typed; the model must read it as the turn's input, so it is logged like any user message and the TEXT is the only thing a cold replay can classify it by. `synthetic_kind()` (markers `RESUME_MARKER` + `_NOTE_MARKERS`, which the producers build from or are pinned to by test — never an import of `server.py`, the higher layer) returns `"resume"` for a synthetic turn that really DID start a task: it replays as a normal `user` event carrying `synthetic`, so the frontend still runs the whole turn-management path and only swaps the blue bubble for a quiet system row. It returns `"note"` for the annotations that start no task — the `[aish: …]` loop/stall/step-limit nudges, the `/cd` + `/add-dir` announcements, console text shared into context — and those are SKIPPED entirely, because live they never reached the transcript at all (a `/cd` shows as a `workspace` marker) and one landing mid-turn also SPLIT that turn in two. A triggered session's opening prompt is arbitrary text with no marker to match, so it is identified positionally instead (`"trigger"` = the first user message of a non-`user`-origin log — the same message `handle_trigger` marks live). Because it classifies by text, logs written before #171 replay correctly too. The same classifier keeps aish's own notes out of `_derive_title`/`_derive_snippet`, so a chat opened with a `/cd` is no longer titled with the announcement that produced. `_parse` returns a **`ParsedLog` NamedTuple** (not a bare tuple) so log metadata can grow without rewriting every unpacking call site. **Activity is a property of the RECORDS, not of the file (#201).** "Last interaction" used to be the file's mtime, which cannot tell a chat that DID something from one that was merely looked at — and looking at a chat CAN append to it. A chat holding an image that fails to render (a remote host off the fetch whitelist, an evicted media file) had a `render_error` written on every replay, landing a second or so AFTER the client stamped "seen" (`markSeen`, `[SESSION-ENTER]`) — so `sessionUnread` saw activity newer than the look that caused it and the chat came back unread the moment you left it, permanently, with opening it to check being what re-armed the signal. `ParsedLog.activity_ts` is computed in `_parse`'s existing single pass by `_is_activity`, whose rule reuses a distinction this module already draws: **a record that renders nowhere is not activity** — `RENDERLESS_STEPS` is the one registry, so a future governance record inherits this instead of re-teaching it, and `model` is excluded for the same reason it is written lazily at all (it says which model a chat runs, never that it ran). `SessionInfo.activity` carries it (falling back to `mtime` for logs with no usable stamps — nothing may lose its place in the list), and every consumer of "when did this chat last do something" reads it: the `session_list` row `ts`, `pager_titles` (the deck ages members on it), and `/offline/session`'s `ts`. `_by_recency` deliberately stays on `stat()` — it is the cheap newest-first pre-filter and a superset — and so does the offline ETag, which genuinely IS about the bytes on disk. Pinned by `TestActivityIsNotAFileTouch`. **Parse caches (perf):** the read-only listing paths — `info`/`list_sessions`, `load_entries`, `_peek`/`pager_titles`, `user_command_history` — serve from stat-keyed module caches (`_PARSE_CACHE`/`_ENTRY_CACHE`, key `(mtime_ns, size)`), because re-parsing hundreds of JSONL logs on every session switch was the bulk of a swipe's server time and the parsing holds the GIL. The caches hand out SHARED objects, so they are for consumers that never mutate what they read: resume paths (`load_messages`, the CLI's `_parse` calls) stay on the raw `_parse` BY DESIGN — restored history flows into an Agent whose `_trim_tool_message` rewrites message dicts in place, which would poison a shared cache. `_by_recency` prunes cache keys for deleted files, scoped to its own state dir (tests run many dirs in one process). `user_command_history`'s command/exit pairing moved into `_parse` (`ParsedLog.user_cmds`) so it rides the same cache. **Auto-titling (#175):** `set_title(title, auto=…)` stamps the `kind:"title"` record with who chose the name, and `ParsedLog.title_auto` reads it back — that flag is what makes a hand-typed rename permanent (a record with no `auto` key predates the feature and was, by definition, a manual rename). `title_drifted(title, recent_text)` is the free lexical gate in front of the retitle model call: the fraction of the title's 4+-character words still present in the recent exchange, below `DRIFT_KEPT_RATIO` = drifted. Deliberately NOT embeddings — spending a model call to decide whether to spend a model call is a bad trade, and being wrong either way is cheap. **A chat has an eraser (#202).** The transcript was append-only and replayed whole, so anything that landed in it was permanent short of deleting the chat or hand-editing JSONL with the server stopped — a probe fired at the wrong chat (#201), a message an autocorrect Return sent half-typed, a secret pasted into the composer. `redact_turn(turn)` is the removal, and the unit is the **TURN**, never one bubble: an answer repeats what it was asked and a command echoes the argument it was given, so half a turn is not a removal. It is a REAL delete plus a POSITIONED tombstone rather than the issue's hide-only tombstone — the records leave the file and a dated `kind:"redact"` record takes their place AT THEIR POSITION, so the removal stays auditable (when, which turn, how many records) while the text is gone from disk, which is the only answer that works for the pasted-secret case. Three details are load-bearing. (1) The cut runs from the turn's `task_start`, not its user message: `task_start` is written FIRST and carries the prompt VERBATIM, so cutting from the message would leave a copy of exactly what was removed — and would strand an unmatched `task_start`, which restart recovery (#164) reads as a task to resume. The same walk-back decides the END, or the removal takes the NEXT turn's `task_start` with it (found in browser verification, pinned by test). (2) Turns are NAMED: `SessionLog.message` mints a `turn` id on every user record and `reconstruct_events` carries it on the `user` event, with `_turn_id` falling back to the record's LINE INDEX for logs written before ids existed — which is every chat holding a message someone wants gone. The id is minted by the SERVER (`_turn_event` → `Session.open_turn` → `LogRef.pending_turn`) so a LIVE turn is removable too; the message you most want back is the one you just sent, and a log-minted id would only exist after a cold replay. (3) `Redaction.occurrence` says WHICH identically-worded turn it was, because the live Agent's messages hold no ids (its dicts go straight to the backends) and two turns saying "ok" would otherwise be indistinguishable — dropping the wrong one from the model's context is the one thing this must not do. A redaction IS activity, unlike the renderless records #201 exempted: every device mirrors the transcript and only refetches a session whose activity stamp MOVED, so an unmoved stamp would leave the removed text in IndexedDB on each of them — hence `_parse` now takes the LATEST activity stamp rather than the last one in file order (a rewrite made file order stop meaning chronological order). An AUTO title is re-derived and its stale records DELETED (a model-written name is a summary of the conversation and can quote the very text being removed); a hand-typed title is the user's own words and is left alone. Pinned by `TestRedaction`.
- **`prompt.py`** — the boxed input UI, built as a small prompt_toolkit `Application` (not `PromptSession`) because the footer-under-input layout requires it.
- **`server.py`** — `aish-web`: the same Agent behind a Starlette WebSocket instead of a TTY. `Bridge` is the core mechanism: `run_task` runs via `asyncio.to_thread`, callbacks emit JSON events through `call_soon_threadsafe`, and the approval callbacks block the worker on a `queue.Queue` slot until the browser answers — the approval gate is unchanged, only the transport differs. The process holds many open `Session`s (each its own Agent + SessionLog + Bridge + busy flag, capped at `MAX_OPEN_SESSIONS` with idle eviction) and serves many connections at once (**multi-connection, #102**): each socket is a `Client` (its own `ws`, `outbox`, `sender`, and independently-chosen `viewing` session), tracked in `WebServer.clients`; per-connection state that used to be singletons on `WebServer` (`self.ws`/`self.sender`/`self._active`) now lives on the Client. `Bridge._put` fans each event out to EVERY viewer's outbox (`Session.viewers`, owned by the bridge), and each Client's own sender coroutine drains its own outbox to its own socket — the transcript-append + all viewer-outbox pushes happen on the loop thread (via `call_soon_threadsafe`/`_show`), so no locking is needed (the invariant that kept replay snapshots race-free). **Session firewall (#182):** the fan-out stamps every LIVE delivery with the bridge's session name (never overwriting an event's own `session`, e.g. `session_state`), and the client's `ws.onmessage` drops a stamped event naming a session other than `currentSession` (`foreignSessionEvent`, `// [SESSION-FIREWALL-START/END]` in app.js) — closing the client-side switch window (prefetched swipe, offline-mirror tap) where the OLD session's live tail kept rendering into the new view until the server processed the resume. Exempt: `hello` (the switch mechanism itself), `session_state` (sent only to non-viewers by design), `session_renamed` (by-name, idempotent). The stamp rides ONLY the delivery — the recorded transcript stays byte-identical to `reconstruct_events` (hot/cold parity), and replayed events bypass the gate anyway (the replay loop feeds `handle()` directly, which is also why the drop lives at `ws.onmessage`, like the `viewDirty` mark). Pinned by `TestSessionStamp` + `tests/js/test_choreo_session_firewall.js`. Connections coexist WITHOUT preempting — `_attach` no longer closes the previous socket (the old single-client `CLOSE_REPLACED` path is gone); a bare connection (no `?session=`) lands on the default startup session (`WebServer._default`), a named one on `?session=`. Background sessions keep running, their events buffering into their transcript; switching a Client's view = hello + full transcript replay (`_show`), which is also what makes phone lock/unlock lossless. Control is **last-actor-drives**: every action handler calls `_claim(client)` first, stamping `Session.controller` and (when it changes) broadcasting a NON-recorded `role` event (`{controller, you}`) to that session's viewers; view messages (switch, files, jobs, dequeue, reconnect) never claim. There is no locked role and no disabled UI — the approval card fans out to all viewers, any may answer, and the asyncio loop serializes messages so exactly one `answer()` reaches the blocked worker (`Bridge.answer`'s pending-slot guard drops the duplicate). On disconnect (`_detach`→`_leave`) the Client leaves its session's viewers and, if it was controller, releases control (`role` → `controller:null`). `_evict_idle` never closes a busy session, one with viewers, or the default. **Session-row directory:** each row in the sessions list is labelled with its working directory (`_send_sessions` → `_row_cwd`) — read LIVE from the agent for sessions open in memory (it may have moved since the last recorded `/cd`) and otherwise from the log's last `kind:"cwd"` record (`SessionInfo.cwd`, picked up in `_parse`'s existing single pass), so the label no longer depends on the accident of which few sessions survived the `MAX_OPEN_SESSIONS` sweep. A session sitting in the server's launch workspace (`WebServer.base_cwd`, set by `create_app`) shows NO label: stamping the same path on every row is noise, so the chip's presence *is* the signal "this chat is somewhere else". The `role` event is never recorded, so cold replay re-derives control from live membership. The `active` property survives only as a representative-session helper for HTTP endpoints (no socket context) and tests; `/file` scopes to the union of all open sessions' roots. A session that fell out of memory (idle-evicted or after a restart) is reopened cold from its log and reconstructed into the same replay event stream (`SessionLog.reconstruct_events`), so its activity trace looks identical hot or cold. **Removing an exchange (#202)** is `_redact_turn`: refused while the chat is busy (the turn may be the one running, its records are still being written, and `agent.messages` belongs to the worker thread), then log → model context → transcript. The transcript is REBUILT from the scrubbed log via `reconstruct_events` rather than edited in place — that function is DEFINED to produce what a live session shows, so leaning on the parity invariant both repaints correctly and guarantees no residue survives in memory for the next viewer to replay — and the fresh `replay` goes out through the BRIDGE so every viewer repaints (a removal on the phone must not leave the laptop showing the text). That replay carries `seen: true`, true by construction because it reaches only clients currently VIEWING the chat: without it the removal, which counts as activity so every mirror refetches, would come back as an unread dot for the person who just made it. The vanilla-JS frontend lives in `aish/static/` (no build step, iOS-styled, inline SVG icons). Standalone PWA mode hides Safari's chrome, so a stalled socket has no browser refresh to fall back on (#18): `reconnect()` in `app.js` force-closes the current `ws` (even one still reporting `readyState OPEN` — a "zombie" socket the browser hasn't noticed died) and reconnects immediately, bypassing the backoff ladder. It's reachable from the session-title `⋯` menu ("Reconnect") and by tapping the existing `#connbar` "reconnecting…" bar itself. `requestNewChat()` wraps New Chat's `send({type:"new"})` to reconnect-then-retry when the socket is in a *detectable* dead state (CLOSING/CLOSED/CONNECTING) instead of silently no-op'ing; a zombie socket isn't detectable client-side, which is why the manual Reconnect control exists as the general fix. Pull-to-refresh was considered and skipped: `messagesEl` already runs a hand-rolled horizontal swipe-paging gesture with delicate vertical-vs-horizontal disambiguation (touchstart/touchmove/touchend near the bottom of `app.js`), and layering a vertical pull gesture on the same element risked fighting that logic for a case the menu/connbar controls already cover. **Session rail (replaces the #169 working-set deck and the swipe pager).** Chats are switched from a LEFT SLIDE-OVER panel (`// [RAIL-START]…[RAIL-END]`, `#session-rail` + `#rail-scrim`), opened by a rightward drag ANYWHERE ON THE TRANSCRIPT that follows the finger (`// [RAILSWIPE-START/END]` — the pure `railSwipeOpens` decision; the wiring sits on `messagesEl` beside the touch-freeze) or the top-bar button, dismissed by the scrim, the button or Escape. It shipped edge-only first and that was wrong: an edge drawer is the platform default, but this app is navigated between chats constantly and a 24px strip is a fiddly one-handed target. What made an edge tempting — transcript children that scroll sideways (unwrapped command output, code blocks, tables) — is handled by `scrollsHorizontally`, standing down when the pan STARTS inside one; that is the same test the old swipe pager used on this exact surface, so it is a solved problem rather than a reason to shrink the target. The listener is PASSIVE and never `preventDefault`s (a blocking touchmove on the scroller is the phone's biggest jank source); `#messages`'s `touch-action: pan-y` is what actually stops the browser scrolling a horizontally-started gesture, and the scrolling children opt back in with `pan-x pan-y`. The keyboard guard reads `body.kb-open`, NOT "an editable has focus" — the composer holds focus indefinitely on a desktop, so the focus test meant the gesture never armed there at all (a phone hides that, because the two coincide). There is deliberately NO drag-to-close on the list — a leftward drag on a row is already swipe-to-delete, and two recognizers on one surface is the exact collision that cost #169 its per-row delete. `begin/dragTo/endRailDrag` are the drag's whole lifecycle and `endRailDrag` ALWAYS hands the panel back to the stylesheet (`clearRailDragStyles`), because a gesture that can end with an inline transform still on the element leaves the rail resting somewhere no CSS class accounts for — the same failure shape as the pager's parked transcript. **One panel, two widths:** past `RAIL_DOCK_MIN` (900px) it simply stays open as a sidebar and the app shell is inset. The inset goes on `body`'s padding — and the rail needs NO counter-offset, which is the counter-intuitive part: `body` carries `transform: translateZ(0)` so it IS the containing block for its fixed descendants, but a fixed child resolves offsets against the containing block's PADDING BOX, whose left edge is body's border edge (0). Padding moves the flex children and leaves `left: 0` where it was. Measured, not reasoned: "compensating" with `left: calc(-1 * var(--rail-w))` put the rail entirely off-screen. A full-screen list was rejected on purpose: it would be a separate SCREEN, i.e. a second navigation model to reconcile with the desktop sidebar later, and it has no sliver of chat to say "this is temporary". Pinned by `tests/js/test_session_rail.js`.

**Why the deck went (#169's premise was wrong).** The deck bet on SPATIAL memory — chat X is always two swipes left — in a surface that never showed a map: you saw one page at a time, the order lived in per-device localStorage, a wrong guess cost a full page transition plus a transcript rebuild, and nothing ever taught you the right one. Worse, it was a SECOND source of truth about which chats matter, permanently reconciled against the server's real session list — seeding, 48h idle eviction, phantom pruning (`deck_check`/`deck_gone`), fork anchoring, and the park/unpark/watchdog/landing choreography were all that reconciliation. Recency ordering is a pure function of the session logs the server already has, so all of it is deleted, and phone and laptop finally agree on the order. What the pager was genuinely good at — bouncing between two chats — recency does BETTER: the other chat is permanently row one. Don't reintroduce a client-side membership set. **Unread is the rail's organising axis (`// [SEEN-START/END]`).** The list is banded by ATTENTION, not provenance: `Needs you` (holding an approval, or activity newer than this device's last look), then `Active now` (running), then `Pinned`, then date buckets. That replaces the Recent/Automated TABS, and the tabs' own design admitted they were on the wrong axis — attention counters had to be computed for the HIDDEN tab so it could still flag things, and search dropped the split entirely because it lies about relevance. A held email-triggered session and your own unattended long-running task want you identically; a three-week-old triggered chat is just an old chat. Provenance is now a GLYPH in the row's avatar slot. `seenAt`/`seenSince` (`aish-seen`, per-device — "I looked at it" is a fact about a screen) is written ONLY by `markSeen`, called from `[SESSION-ENTER]` (entering a chat IS looking at it) and at `done` on a live turn — that second call is load-bearing, because a turn keeps writing to the log after the hello that stamped it, so without it every chat you had just used came back unread the moment you left it and the band became the whole list. `seenSince` is the first-run floor, for the same reason: without it a new device renders its entire archive unread. `sessionUnread` is pure and takes `current` (the chat on screen can never be unread). Pinning is now ONE concept — top band AND never evicted from the offline mirror — instead of two toggles for "I care about this chat". Pinned by `tests/js/test_session_unread.js`.

**The eraser is a chip on the prompt (`// [REDACT-START/END]`, #202).** It lives on the PROMPT because a turn is named by its prompt, and it deletes the whole exchange; it sits at the START of the chip row, so copy and reuse — tapped constantly and without thinking — keep the trailing edge a thumb lands on by habit. What replaces the turn is a quiet, UNDATED `Message deleted` row: a chat that silently loses an exchange leaves the answer above it reading as a reply to nothing, and a deletion you cannot see is indistinguishable from data going missing — but a time ON that row reads as "deleted at", which is not what the only available number means (it is the deleted MESSAGE's own stamp), so the row carries none and its POSITION between two timestamped turns says when. The tombstone keeps its `at` on disk, where it is the audit trail rather than a rendered claim. The word is DELETE everywhere the user sees it — "remove" reads as "taken off this screen", and what happens here is that the text stops existing (the on-disk record kind stays `redact`, which names the MECHANISM: content gone, tombstone kept). Pinned by `tests/js/test_redact_turn.js`.

**ONE confirmation modal for every irreversible action (`// [CONFIRM-START/END]`, #202).** It replaced the two-tap arm-then-confirm guard everywhere that existed, because that guard **communicates by changing the control itself, which on a phone happens under the finger covering it**. The chat menu's version got away with it by rewriting its LABEL ("Delete chat" → "Confirm delete"); the transcript's delete chip is an ICON, so "armed" was a 17px glyph turning red beneath a thumb — tap, nothing seems to happen, tap again, gone. Functionally one tap, and the owner reported it as exactly that. The second defect is geometric: the confirming tap lands on the SAME PIXEL as the arming one, so a double-tap habit or a "did that register?" retap commits. The modal fixes both and adds what neither guard had — it states the CONSEQUENCES ("the log file on the server", "the copy mirrored to your devices", "cannot be undone"), because a verb and a red button say what you are doing and never what it costs. Invariants: nothing runs until Confirm; every dismissal (Cancel, tap-outside, Escape) is a NO and DROPS the pending action, so a dismissed dialog leaves nothing half-committed; the action closes over what it was asked about (the chat name is captured at ask time, never read back at confirm time); Cancel takes focus, never the destructive button; Escape is claimed AHEAD of `escapeExit()` since the modal can be raised over any surface. It is centered with its own dim layer rather than a bottom sheet — a sheet is a picker you browse, this is a question you answer over whatever raised it. Deliberately no undo anywhere near it: an undo buffer is a copy of the thing just asked to be destroyed. Pinned by `tests/js/test_confirm_modal.js` (which also fails if a second bespoke confirmation appears).

**Row anatomy.** The status icon answers ONE question — what state is this chat in — in priority order: running (green spinner) > waiting (orange alert) > automated (a tinted origin glyph: clock / envelope / bolt) > a plain chat mark. It used to answer two badly: a blue TICK for "this is the chat you are in" (which the row's own highlight already says, and which reads as *done*), and provenance only when nothing else was showing — so a screen of ordinary chats was a column of identical grey marks and automation was invisible. "Current" is deliberately not an icon. **Unread is a badge cornered on that icon**, not a column: a leading slot is the mail convention, but mail rows are wide and this panel is phone-width, so an always-reserved gutter spent real title space on a state most rows do not have. Bold titles alone were measured on a real phone and found illegible — the dot is the signal, the weight step is support. The pin sits BELOW the timestamp (the space the row's trash used to take), not beside it, for the same width reason — and it is `--dim`, NEVER the accent: blue on a rail row is the attention vocabulary (it is exactly what the unread dot is), so a pin painted in it read as "this one is new", which is the one thing a pin never means. It shares its colour with the timestamp it sits under, which is the company it belongs in. There is no per-row trash and no swipe-to-delete: leftward on this panel closes it, and having that same drag mean "delete a chat" was the destructive reading of an ambiguous gesture. Deleting is the chat menu's row, which asks in the shared confirmation modal ([CONFIRM], pinned by `test_confirm_modal.js`) — the ONE sender of `delete_session`.

**Reach and consistency.** New chat exists in TWO places on purpose: the rail's bottom bar (thumb range, where you already are after swiping) and the app header (findable without knowing the rail exists). They are the same glyph with the same styling — a filled tint on the rail's copy made one action read as two different buttons. The rail button in the header is 44x44 with real separation from the session-title menu, which is `flex: 1` and therefore huge: a near-miss did not just fail, it opened the wrong thing. **The pin lives in the chat menu**, not the title bar (a rarely-touched per-chat setting was competing for the scarcest space in the app), and its glyph carries the state — upright + solid = pinned, tilted back + hollow = not — because having to read On/Off is not a state indicator. Tilted-and-blue read backwards: a pin at an angle is one that is NOT pushed in.

**When a turn happened (`// [MSG-STAMP-START/END]`, #200).** A transcript said nothing about WHEN, so an old chat surfacing in the rail was undated once you were inside it. The data was always there: `SessionLog._write_line` has stamped every record with an ISO timestamp since the first version of the file, so this is a read, not a migration — chats written long before the feature get their times back. It rides `at`, deliberately NOT `ts`: on a live event `ts` means "this turn is starting now" and drives the trace card's clock, and cold replay must never look like a running turn, so the two stay separate fields with separate meanings (`record_epoch` converts the log's ISO stamp; unparseable → None → nothing rendered, never a wrong time). Sent as EPOCH SECONDS, not the ISO string, because that string carries no timezone and a browser would read it as its own local time — a phone away from the server would silently show the wrong hour. Rendered on the turn's OPENING message only: a turn's two halves are seconds apart, so stamping the answer as well prints the same time twice, and the answer's row already carries how LONG it took (asked at 14:32, took 12s). The format is ABSOLUTE — a rail row is re-rendered every time you open the list so "2m" stays true there, but a transcript line is written once and read months later, where "2m" becomes a lie. Adding the field moves the offline mirror's prefix signature once, so mirrored sessions re-sync a single time; self-healing, and the reason the field was not squeezed into `ts`.

**Jump to the start of an answer (`// [ANSWER-TOP-START/END]`).** A long reply runs off the top of the screen while you read it, and finding where it began means scrolling back through its own body hunting for a boundary that looks like all the other text. The chip lives ON the answer (that is what "this answer" means) at the far right of the tool row — apart from the cluster that acts on the answer, because it navigates. The arithmetic has one trap worth keeping the comment for: `#messages` is a SIBLING below `#topbar`, not underneath it, so an element at the scroller's own top is ALREADY clear of the header; subtracting the header's height as clearance (which reads as obviously right) overshoots by exactly the header and lands above the answer — and on a short transcript lands at 0, which looks like a working scroll-to-top button and is not the feature. The chip HIDES itself when the answer is no taller than the transcript viewport: if it fits, then whenever you can see its tool row you can already see its first line, so tapping would scroll nowhere — which reads as broken rather than as "nothing to do". Height-vs-viewport is the whole test (scroll position never enters it), re-evaluated by a ResizeObserver because images, fonts and the reading-size stepper all change an answer's height after it is built. `tests/js/test_answer_top.js` pins the maths and the show/hide rule.

**Composer affordances (`// [COMPOSER-SLOT-START/END]`).** Split by WHAT THEY ACT ON, which is the rule to keep when the next one is added: the FIELD owns its content, so clearing is a control inside the field (the platform's clear button), shown only when there is something to clear; the ROW owns actions on the message, so pasting is a button beside attach / dictate / send and is ALWAYS present. They were one shared slot first (paste when empty, clear when not) and that failed the actual flow — you type a few words and THEN paste ("review this: <url>"), so the shared slot hid paste at exactly the moment it was wanted. Mutually exclusive on screen is not mutually exclusive in use. The composer now goes full-width (`tall`) at the SECOND line rather than the third, decided by `composerLines()` measuring against the computed line-height — a pixel constant means "two lines" at one reading-size setting and "three" at another — because the in-field clear button has nowhere sensible to sit in a two-line box still sharing its row. `tests/js/test_composer_slot.js` pins the split, plus the refused-clipboard path saying so instead of looking like a dead button. Gesture recognizers yield explicitly: the pager sets `touchConsumedByTranscript` whenever it decides what a touch IS — standing down for a vertical scroll OR claiming a horizontal page-drag — and the window-level swipe-up respects it; geometry alone cannot tell a flick-scroll from an open-the-drawer swipe (the bottom zone overlaps the transcript), and the claim used to be one-sided (scroll only), so one diagonal flick could both commit a page switch AND open the drawer over it. Eligibility for a window-level gesture is decided at **touchstart**, never at touchend (a window listener runs last, after element handlers have already mutated the state it would read). **Session identity has one owner (`// [SESSION-ENTER-START/END]`, #181 phase 2):** "the view is now chat X" used to change in FOUR hand-rolled variants — a hello, an offline mirror read, the boot paint, and the warm-peek paint in `resumeSession` — each writing a different SUBSET of the facts coupled to identity, which is where the subset-drift bugs lived (the boot paint reset no fingerprint and remembered no session; an unguarded mid-hello `localStorage` write aborted the rest of the hello in private mode). `enterSession(name, {source, title, stash})` is now the ONLY writer of `currentSession` and the only caller of `deepLinkSession` + the `aish-session` key, doing every coupled write in one fixed order: stash the outgoing view → reset the fingerprint **iff the name changes** → identity → provenance (`offlineViewing`, derived from `source`) → title → guarded persistence → URL → mirror MRU + pin toggle. Two decisions live in it. The model is a pure judge: no tools, no session, no server — `_make_judge` calls `backends.make_chat` directly. **The action envelope is CODE, not prompt obedience**: `parse_verdict` admits only the four verbs (a repair without a replacement description is a parse failure; one format-nudge retry, then an unparseable skip), and `update_entry_meta` rewrites FRONTMATTER ONLY — description/keywords/pinned/status, body preserved byte-for-byte, other lines (expires) kept, deletion has no code path. Every judged entry (skips included) lands in `curation-actions.jsonl`, which doubles as the **cooldown** (`ACTION_COOLDOWN_DAYS`) — the ledger's stats lag reality by up to `LEDGER_DAYS`, so without it every pass would re-flag what the last one fixed; it also makes retried launchd runs idempotent with no server-side dedup. Layer 3, the **duplicate pass**: cross-entry judgment can't fit a one-entry prompt, so `dup_candidates` proposes pairs DETERMINISTICALLY (identity-line embeddings via `SemanticIndex.scores` at `MERGE_MIN_SIM` — 0.72, deliberately stricter than save_memory's `DEDUP_MIN_SIM` because on the live corpus every TRUE dup scored ≥0.77 while every related-but-distinct trap sat at 0.63-0.66; difflib at `DEDUP_LEXICAL_RATIO` when embeddings are down) and the judge answers one pairwise merge-or-distinct; a merge names the survivor (naming neither = invalid, the envelope never guesses) and disables the loser. **Envelope guards (from the first live v2 run, each a code refusal — never judge wisdom):** `_same_family` bars pairs where one name extends the other with a dash (reply/reply-all, gmail/gmail-send — deliberately similar siblings, and exactly what the 8B judge wrongly merged); a `disable` verdict on a PINNED entry is refused (repair stays allowed — the judge retired two standing rules); a skill never loses a merge to a memory (a playbook outranks its one-line echo); and dry runs use the SAME embedding scorer as live runs, so the candidate list a dry run shows is the list a live run judges. `TestEnvelopeGuards` pins all of it. **Privacy (#186):** evidence excerpts quote owner-typed text, so the judge defaults to the LOCAL model (`DEFAULT_MODEL` qwen3:8b — also this host's memory ceiling, see the 14B crash) and nothing leaves the machine unless `--model`/`AISH_CURATE_MODEL` names a cloud spec explicitly. A completed pass with actions sends one Pushover summary (`notify_fn` seam). Deliberately absent: automatic threshold retuning — the ledger informs, `PREFLIGHT_MIN_SIM` moves by human decision. Seams: `run_curate(judge=…, scores=…, notify_fn=…, state_dir=…, now=…, dry_run=…)`; `--dry-run` lists suspects + pairs with no model calls and no writes. `tests/test_curate.py`. (The `/trigger` `model` override in server.py remains — general-purpose, no longer used by curate.)

- **`export.py`** — local Markdown → PDF for the web UI (#64): `markdown` → HTML → `xhtml2pdf` (pure Python, no system libs), the text never leaves the machine. Two shapes: one answer, or a whole session's FINAL answers — "final" is structural (an assistant message NOT immediately followed by a tool result), which cleanly drops thinking/tool turns. Media embedding (#133): local `![](path)` images inline as base64 only when the symlink-resolved path stays inside the caller's `image_roots` (since #188 that is `WebServer._image_roots`, the single boundary `/file` also serves under — anything outside becomes a captioned link card, never read); remote images, whitelisted Google static-map snapshots (needs `GOOGLE_MAPS_API_KEY`), and YouTube thumbnails ARE fetched at export time, each with a timeout + size cap and link-card fallback — and each through web.py's SSRF guard (#178 P1-4): `fetch_image` runs `web._require_public` and opens via `web._opener` (the redirect-re-checking opener), so a model-written `![](http://169.254.169.254/…)` can't fire a server-side GET at metadata/LAN targets when the owner taps export; a blocked URL degrades to the same link card as any other fetch failure. Its closing-fence regex allows the opening indent **+3 spaces and no more** — accepting any indentation let the inner close of a ` ```markdown ` demo end the outer block early and desync everything after it; a column-0 block is skipped wholesale as the stock extension's job. `FlattenLists` is a treeprocessor that rewrites every `<ul>`/`<ol>` into `<p>`s carrying a hand-drawn marker with a hanging indent (`text-indent: -Npt`) plus a `margin-left` continuation `<div>`: xhtml2pdf silently DROPS an `<li>`'s marker as soon as the item holds a block child (exactly what a loose/multi-paragraph item is) and renders sub-lists flat, so correct HTML still printed unnumbered. Continuation indents are RELATIVE, so a nested list simply stacks its own hang on the parent's. A `<p>` holding only a raw-HTML placeholder is never merged into a marker line — the postprocessor only substitutes a bare `<p>placeholder</p>`, so merging would leak the placeholder into the PDF. **Titling an answer export (#172):** the title (which is also the download name, via `safe_pdf_filename`) used to be the PROMPT the frontend sent along — a request ("test it with some difficult nested markdown"), not a description of the document. Now `handle_export_answer` takes no title at all: `WebServer._answer_title` asks the session's OWN agent (`?session=`, `agent.chat` called directly — no `run_task`, so the turn never enters the conversation or the log) for a 3-6 word title in the document's own language, off-loop via `asyncio.to_thread` under `TITLE_TIMEOUT`. `export.clean_title` unwraps what models pad a one-liner with (a `Title:` label, quotes, a `##`, a sentence of preamble — the LAST non-empty line is the title) and returns None for anything that isn't a title, which is the fail-safe: every failure path (claude-max, which exposes no `chat`; a transport error; a timeout; a rambling reply) falls back to `export.derive_title`, a deterministic local read of the answer's lead heading or first sentence. A title is a nicety and must never fail or block an export. The whole-session export still uses the chat's own title, which is what the sessions list shows. **Chat auto-titling (#175):** the chat title was `SessionLog._derive_title` = the first user message, which left a FORK wearing its parent's name forever (a fork copies the parent's log, so the "first user message" is the parent's) and a long chat named after its opening line. The load-bearing constraint is that the drawer lists sessions COLD (`list_sessions`) and the pager peeks them (`_peek`) — neither can afford a model call — so the name is computed at WRITE time and persisted as the same `kind:"title"` record a rename writes; the read path is untouched. `_maybe_retitle` runs at the end of a successful `_run_task` (never after a cancel — a stopped turn named nothing) and is gated by `_retitle_due`: never when `custom_title` is set and `title_auto` is False (a hand-typed name is the user's call, permanently); always when `retitle_forced` (set on a fork, so it earns its own name at its first turn); otherwise at turns 1, 3, 7, 15 … (`(turns + 1) & turns == 0`, logarithmic so it can never thrash — a name you navigate by must be stable) and, past turn 1, only when `session.title_drifted` says the chat left its current title. `_title_source` returns three things: the current title, the body to name from (**first two messages + last two, non-overlapping** — not the whole transcript, which would cost 50-100x the tokens for no better name), and the LATEST exchange alone for the drift check — measuring drift against the opening too would mean a chat could never drift from a title derived from that opening. `_model_session_title` mirrors `_model_title` exactly (bare prompt, no tools, called via `agent.chat` not `run_task`, so the naming turn never enters the conversation or the log) and every failure path — claude-max exposing no `chat`, transport error, timeout, a reply `clean_title` rejects — simply keeps the existing name. The new name is broadcast as a `session_renamed` event with **record=False** (a rename is UI state, not transcript; cold replay re-reads it from the title record), and the frontend needed NO change — it already handles that event. In tests, `FakeChat` answers titling calls (detected by prompt prefix) WITHOUT consuming the scripted response list and records them in `title_calls` rather than `calls`, so a response list stays a script of task turns; `title=None` (the default) means the backend declines to name anything, keeping every pre-existing test's behaviour identical.

- **`skills.py`** — the knowledge store: skills (playbooks, `~/.config/aish/skills/`; project-scope `./.aish/skills/` discovery is DISABLED by default — #178 P0-1 interim, opt-in via `skills.INCLUDE_PROJECT_DIRS`, which neither entry point sets) and memory (one fact per file, same md+frontmatter format, `~/.config/aish/memory/`; project `.aish/memory/` behind the same switch), plus legacy `lessons.md` lines as synthetic memory entries until `/learn lessons` migrates them. A skill is either a flat `<name>.md` OR an agentskills.io-compatible folder `<name>/SKILL.md` bundling `scripts/`/`references/`/`assets/` (name defaults to the dir, frontmatter still wins; `_dir_entries` scans subdirs for `SKILL.md` only for `kind=="skill"`, so memory stays flat); `read_skill`/`load_skill` append a `_bundled_note` naming the folder's files so the model reads/runs them via read_file/run_command. This is the substrate for the **skills-primary, tools-as-scalpel** capability model (epic #141): tools are added later only for hot, shell-fragile, reliability-critical ops that a documented skill snippet can't do safely. Progressive disclosure is the design rule: `knowledge_index()` renders a capped, byte-stable name+description index that `agent.compose_system_content()` rebuilds into `messages[0]` at EVERY `run_task` (that live rescan is what makes new skills appear without restart — don't reintroduce boot-time caching); full bodies load via `read_skill`; the long tail is searched by the `recall` tool (`rank_entries` + `recall_text`: deterministic difflib tiers, two-phase, hard caps, mtime-cached parsing). A per-task `TASK_REMINDER` system message is re-inserted before each user message (directly, never via `_append`, so it stays out of logs/transcripts) — recency is what makes small local models actually consult skills. `remember` writes via `save_memory` (slug-validated, create-or-update, deduped) and stays auto-approved; skill files are written with normal diff-approved `write_file`/`edit_file`. **Pre-flight injection (#40/#43, precision overhaul #183):** `skills.preflight` picks the top entries for a task and `run_task` injects their bodies into the per-task reminder up-front (capped by the `PREFLIGHT_*` constants; oversized bodies get a teaser + a read gate armed until `read_skill` loads them). Selection must be able to ABSTAIN — a judged audit of 481 live injections (issue #183) measured 46% pure noise, because the old single 0.24 floor sat below the live corpus's noise floor (the median task cleared it with 7-8 entries, so the 4 slots always filled). The rules now: injection needs `PREFLIGHT_MIN_SIM` (0.35, calibrated on that audit — relevant median 0.458 vs irrelevant 0.290), while `SEMANTIC_MIN_SIM` (0.24) remains the floor for deliberate `recall` search AND for keyword-rail confirmation — a keyword hit is a strong PRIOR that lowers the bar, never a bypass (keywords are model-authored; one generic word used to guarantee injection on a third of tasks), a NAME hit stays unconditional (naming an entry is unambiguous, and short names can embed poorly). `pinned` standing rules NEVER compete for preflight slots — they are already in every task's index, and re-injecting them stole slots from actual skills. Short tasks (< `PREFLIGHT_CONTEXT_TASK_CHARS`) embed WITH recent prior user turns (`context` arg, threaded from `run_task`, synthetic `[…]` notes filtered) because a bare follow-up ("show on map") is a hopeless query alone; the rails still scan ONLY the current message. `Preload.mode` ("semantic"|"lexical") plus per-item `sim`/`rail` (or lexical `score`) diagnostics ride the `knowledge` trace step into the session log, so retrieval precision is auditable from logs alone — the #183 audit had to reconstruct this; keep it cheap. `save_memory` dedupes and caps keywords (`KEYWORDS_MAX`) at write time. In lexical fallback (no embeddings) the keyword rail remains a full guarantee — there is no similarity to confirm against. Index caps are per-type (`INDEX_SKILLS_MAX`, `INDEX_MEMORY_MAX`), so one entry type growing large can never evict the others from the prompt. **Knowledge-layer hardening (#178 Gate 2):** (1) *Standing rules (P1-7)* — `pinned: yes` frontmatter (`kind: policy` accepted as alias) puts a memory in a "Standing rules" index section under its OWN budget (`INDEX_PINNED_MAX`), exempt from the mtime-recency cap and sorted by NAME, because a behaviour rule must not stop applying when newer facts rotate past it and WHICH rules render must never depend on whose mtime moved last; `remember` sets it (`pinned` arg; `save_memory(pinned=None)` preserves the flag on update). (2) *Lifecycle (P1-8)* — `status: disabled` and `expires: YYYY-MM-DD` retire an entry without deleting the file: `entry_active()` is evaluated at READ time (a long-running process crosses an expiry with no mtime change) and enforced INSIDE `load_entries`, so index/preflight/recall/dedup inherit it by construction; `load_skill` names the retire reason instead of claiming the skill is missing; read-side date parsing is tolerant (malformed = no expiry + warning), write-side (`remember`/`save_memory`) strict. `save_memory`/`remember` take `disabled` (#185: None preserves on update, True writes `status: disabled`, False revives) — the reversible retirement verb, so curation never needs `forget_memory`. (3) *Near-duplicate gate (P1-8)* — a NEW slug whose identity line is too similar to an existing memory is refused WITH that entry's name (update/forget it, or `force=true`), via the wired `SemanticIndex.scores` (`DEDUP_MIN_SIM`, provisional until measured on the live corpus) or a conservative difflib ratio fallback (`DEDUP_LEXICAL_RATIO`); updates to the same slug are never gated. (4) *Semantic recall (P1-9)* — `rank_entries`/`recall_text` take `semantic` and `Agent._recall` passes it, so embeddings reach the deliberate-search path, not only preflight; fusion keeps strong lexical hits (exact name / whole-query-in-identity) as the deterministic rail on top, similarity orders the rest, and a `None` from `scores()` degrades byte-identically to pure lexical. Retrieval quality is regression-gated by `tests/test_retrieval_quality.py` — a recall@3 harness over a fixture corpus with a deterministic concept-axis embedder injected at the `embed=` seam (semantic must score 1.0 on both preflight and recall incl. the Polish→English cases; lexical-only floors 0.6/0.3 asserted).
- **`embeddings.py`** — the semantic layer over knowledge retrieval (#43): one local Ollama embedding model (`embeddinggemma` by default — multilingual because tasks arrive in Polish while entries are English; `AISH_EMBED_MODEL` overrides) scores task-vs-entry similarity regardless of which chat backend runs the task, so retrieval behaves identically on every `--model` and the corpus never leaves the machine. Entries embed as a single identity line (`name: description (keywords: …)`), never bodies — selection reads identity, so vectors stay stable while playbooks grow; vectors cache in the state dir keyed by sha256(model + text). Retrieval-tuned models need task-type prefixes Ollama does NOT add (`_PREFIXES`; skipping them measurably collapses similarity separation ~2x). Any failure (ollama down, model not pulled) makes `scores()` return `None` and callers fall back to the lexical tiers — lexical word-matching is the guaranteed floor, embeddings are an upgrade, never a dependency. Both entry points wire it the same way: `Agent(semantic=SemanticIndex(state_dir))`; the agent threads `scores` into preflight, `recall` (#178 P1-9), and `save_memory`'s near-duplicate gate.
- **`tool_plugins.py`** — plugin tools (epic #141, the tools-as-scalpel half): droppable `TOOL.md` manifests the model calls as structured tool calls, **indistinguishable from native tools** because `to_tool_def()` emits the exact `{"type":"function","function":{…}}` shape `tools.TOOL_SCHEMAS` uses and `agent._dispatch` routes both through the same gate. A tool is a folder `<name>/TOOL.md` under `~/.config/aish/tools/` (global), bundling an optional wrapper; project scope (`./.aish/tools/`) is DISABLED by default (#178 P0-1 interim — a repo's read-only manifest would run its wrapper ungated), opt-in via `tool_plugins.INCLUDE_PROJECT_DIRS`, which neither entry point sets. Doctrine: **schema on the way IN** (validated JSON args handed to the executable on **stdin — no shell**, so free-text args can't be mangled by quoting; this is the one irreducible win over a skill's shell-invoked script), **prose on the way OUT** (raw stdout+stderr + `[exit code: N]`, no output schema). Frontmatter is dependency-free line parsing (`schema` is a JSON object string); `mutating` is **required** (fail-closed — a manifest that doesn't declare it is invalid, never silently read-only) and a **floor never authority**. The linter (`_parse_tool`) is deterministic and skips invalid manifests with a warning rather than crashing discovery; `resolve_executable` only runs a bundled `./wrapper` inside the tool dir or a bare PATH binary (no absolute/escaping paths). The agent rescans only when the dirs' `signature()` (mtime set) moves — a mid-task manifest edit is picked up on the next step. **Approval:** read-only tools auto-run; **mutating tools are gated by `approve_tool`**, a fourth approval callback wired from both entry points (`cli.make_tool_approver` → y/N; `server.make_web_approvers`' `approve_tool` → an `approval_request` of `kind:"tool"` rendered by `app.js`'s `buildToolCard`, **reusing the command card verbatim**). `_dispatch_plugin_tool` mirrors `run_command`'s #81 verdict semantics exactly: `True` runs, `None`/`False` denies, `Denied(comment)` STOPs (arms the stop gate + appends feedback), `Approved(comment)` HOLDs (args not run — the model reworks and re-proposes, re-approved before running). Mutating tools are exposed to the model ONLY when a tool approver is wired; without one they stay hidden and fail closed in dispatch — a mutation never runs ungated. There is deliberately **no denylist/auto-approval on tools** (a mutating tool always prompts): the tool's safety is manifest review (`create_tool` + human diff-approval) plus this per-call gate. **Preview seam (#157):** a manifest may declare `preview: yes` — then before gating, `_dispatch_plugin_tool` calls `tool_plugins.preview()`, which re-runs the SAME wrapper with `AISH_TOOL_PREVIEW=1` set; the wrapper is contracted to RESOLVE + describe its args (e.g. an id-addressed `reminders_delete` does `rem show <id>`) and print ONE human sentence WITHOUT mutating, and that ground-truth string is threaded as the optional 3rd arg of `approve_tool` onto the card (web: `request["preview"]`, rendered above the now-secondary raw args by `buildToolCard`; CLI: printed dim under the prompt). This is the tool layer's plan/commit gap, mirroring `files.py`'s diff — it fixes id-opacity (the human sees *what* they're approving, not `id=F5D0…`). It is **fail-OPEN** (no `preview`, error, empty, timeout, unset secret → None → raw-args card) and **ground-truth by the system**, deliberately NOT a model-supplied summary (a wrong id with a right-sounding summary is exactly what the gate must catch). Read-only plugin tools parallelize like native `READ_ONLY_TOOLS` (the uniformity invariant): `_execute_tool_calls`' concurrent filter includes `_is_readonly_plugin`, and `_read_only_call` has a plugin branch (`_run_readonly_plugin` = validate + execute, thread-safe subprocess). A project TOOL.md **shadows** a same-named global one (project dirs first in `discover`), but `mutating` is a **monotone floor across scopes** (#178 P1-3): a shadow may RAISE a global tool to mutating, never lower it — a downgrading shadow (project `mutating: no` over a global `mutating: yes`, which would route the mutation through the ungated parallel read path) is REFUSED outright in `discover`, the global mutating tool survives (still gated by `approve_tool`), and a loud warning names both paths; same-flag and upgrade shadows keep project-wins with the existing warning (louder when the flags differ). Dormant at default since project dirs aren't scanned, load-bearing for the future trust gate. **Soft tool budget (#178 item 14):** when the TOTAL exposed count (native `TOOL_SCHEMAS` + plugin defs) exceeds `TOOL_BUDGET` (25), `budget_warning()` emits a one-line consolidation nudge naming the largest `<prefix>_*` family (e.g. "9 reminders_*" — the per-subcommand explosion the doctrine forbids) through the same once-per-rescan warning channel as shadow warnings; no tool is ever hidden — every schema is resent every turn, so the budget guards the context window, not capability. **Drift nudge (#140):** a manifest may declare `prefer_over:` — a comma-separated list of raw command prefixes this tool should be used INSTEAD OF (alternatives, not only commands it wraps; e.g. `gh issue create, gh issue new`); `create_tool` can populate it. The agent builds `_tool_prefer` from EXPOSED tools and, when the model runs a raw `run_command` matching any prefix, appends an advisory note steering it to the tool next time (`_tool_for_command`) — the command still runs; it's a learning nudge, not a block. Native-tool nudges (cat/sed→read_file) are a separate mechanism, parked in backlog #150. **Authoring (`create_tool`, #138):** a native, model-autonomous tool (in `tools.TOOL_SCHEMAS`) that writes a new `TOOL.md` + wrapper. Three guardrails the model cannot bypass: the WHEN test lives IMPERATIVELY in the tool description (create only when frequent + shell-fragile args + reliability; otherwise write a skill — never for read-only/simple/one-off); `Agent._create_tool` LINTS the drafted manifest in a temp dir and refuses to write on any error (structured feedback → correct-and-retry, so a broken tool can't land); and both files go through the normal `approve_write` diff gate (wrapper first — the executable, the critical thing to review — then manifest; a denial aborts without an orphan). The wrapper is chmod +x'd after commit and the plugin signature reset so the new tool is offered next step. `wrapper_lang` sets the file/shebang (sh|python); `scope` picks global (`~/.config/aish/tools`, backed up by the knowledge-git agent); `scope: project` is refused with a structured error while project discovery is off (a tool never discovered would be a silent no-op). It can also declare `preview:` (#157) — the parameter's description states IMPERATIVELY when to set it (args that are opaque identifiers, with the `reminders_delete` → `rem show <id>` example) and the `wrapper` parameter's description carries the contract the wrapper must honour (check `AISH_TOOL_PREVIEW` first, resolve + print ONE sentence, exit 0 WITHOUT mutating), because capability phrasing in aish's own prompts gets ignored by small models unless it is a MUST plus a concrete example. A non-bool value is written to the manifest verbatim rather than coerced, so the existing lint-in-a-temp-dir refusal catches it and the model gets structured feedback instead of a tool that silently promises a preview it never emits. Each tool is its OWN directory `<scope>/tools/<name>/` holding `TOOL.md` + the wrapper — the **manifest is written/approved FIRST** (the interface: review intent, then verify the code), then the wrapper. The tool description states this layout imperatively so the model stops inventing a flat `.json` layout (a real Gemini mis-narration this fixed). Out-of-project write cards show the full home-abbreviated path (`app.js` `relTarget`) so a global-config destination can't be mistaken for a file in the current project. **Knowledge reconciliation (#150):** after a tool is created, `_reconcile_candidates` deterministically finds skills/memories that mention a `prefer_over` command or share the tool's subject words, and `create_tool`'s RESULT appends an imperative instruction to UPDATE (repoint to the tool) or forget the ones describing the now-superseded manual way, while KEEPING orthogonal context — detection is code, the judgment + gated mutations are the model's, so stale guidance can't silently contradict a new tool. **Secrets (#142):** a manifest may declare `secrets: NAME1 NAME2` (env-var names); `execute()` resolves each via the Keychain (`secrets.get`) and injects them into ONLY that wrapper's subprocess env (`env=`), never into args — so a value can't leak into logs or the model's context; a declared-but-unset secret is a hard error, not a silent empty env. `create_tool` can populate `secrets:`. **Result envelope + continuation (#192):** `execute()` returns a `tools.ToolOutcome` (see tools.py) rather than a bare string, and `envelope()` builds it — status, `verdict_by`, `exit_code`, `bytes`, and a `truncation` object. The plugin cap WAS a hardcoded `6000+2000` that consulted nothing: not the model, not the context window. `output_caps(window)` now derives it from the real backend (`backends.context_window`), floored at the old constants so a small local window never regresses and ceilinged at `_OUT_CEILING` so a 1M window does not hand the model a novel — an Ollama-8k session and a Gemini-1M session get visibly different caps, which is #192's own acceptance criterion. Truncation is no longer a **dead end whose only escape was improvisation**: the full output is cached content-addressed in `state_dir/tool-output` (`store_continuation`/`read_continuation`, LRU-pruned like the media store) and the truncated result carries an imperative note naming the exact `read_tool_output(continuation=…, page=2)` call. Pages are served from that cache, so **the wrapper never re-runs** — for a nondeterministic or mutating tool a re-run is a different result or a second side effect, not merely slower. When status ≠ ok the result also carries `_incomplete_note`, the imperative in-band instruction that #190's failure-policy MEMORY structurally could not be: it is delivered on the result itself, on the channel where the triggering state lives, at the moment it lives there, rather than depending on retrieval keyed on user text to surface a rule about a tool OUTCOME.
- **`secrets.py`** — local secret store backed by the **macOS login Keychain** (#142), for the non-CLI integrations aish must hold a credential for (Fastmail/HA/ntfy/webhook — "auth stays with the CLI" covers none of them). Each secret is a generic-password item under service `"aish"` via `/usr/bin/security` (`put`/`get`/`delete`/`names`); a plaintext NAME index (values never) in the state dir backs `aish secret list`. Chosen (owner + Fable) over sops+age for being Apple-native, zero-dependency, and **structurally un-committable** — a Keychain item is not a file, so it can't be swept into the git-backed `~/.config/aish`. Managed with `aish secret <set|get|list|rm>` (`_secret_cli`, intercepted before the main arg parser; `set` reads via getpass). The honest security ceiling is FileVault + login-unlock: this defends against disk theft and accidental leakage (git, logs, model context), NOT a live attacker already running as the user.
- **`skill_import.py` + `import_skill`** — import a skill from a git repo or local path (#139). The untrusted surface is **imported skills** (their instructions + scripts are what the model would follow); tools need no import check because they're BUILT here via `create_tool` + diff-approval. `skill_import.stage()` only fetches (a shallow, read-only `git clone` that never executes the skill's code) + validates (real `SKILL.md`, name-checked) + collects the **text** files (binary assets skipped — not part of the trust surface). `Agent._import_skill` then presents ONE **consolidated review** via the `approve_import` callback (a 6th approver, wired from both entry points): the whole skill in a single decision — description, deterministic **risk flags** (`skill_import.safety_scan` — network/pipe-to-shell/sudo/sensitive-path patterns), and EVERY file's full contents rendered **syntax-highlighted** by `app.js`'s `buildImportCard` (reusing the vendored hljs via `highlightFences`; `kind:"import"` card) — NOT per-file diffs (that was approval-fatigue + all-green-diff-unreadable). On approve, all files install at once (`files.commit`, no further prompts); a denial installs nothing. The CLI reviewer (`cli.make_import_approver`) prints the flags + every file, one y/N. **CLI escape hatch (`aish skill <import|approve|list|discard>`, `cli._skill_cli`):** `import` STAGES to a quarantine dir (`skill_import.stage_to_disk` → `~/.local/state/aish/skill-imports/<name>/`, nothing installed) and prints the risk flags + path, so you review the files in your OWN editor, then `approve` (`install()`) moves them into the skills dir — the review-with-your-tools path for big skills. Safety is enforced in code, not by asking the model. Trustworthy public sources: `anthropics/skills`, `VoltAgent/awesome-agent-skills`.

Startup safety: launching either entry point from `$HOME` re-anchors the session to `~/aish` (`cli.default_workspace`, also used by `create_app`) so the home tree never becomes the auto-approval root; explicit `cwd` overrides are respected.

Web-only UI conventions the model is told about (in `web_usage_context`): quick-reply chips — `[Label](aish-reply://answer text)` links rendered as one-tap buttons by `app.js` — and the approval-card feedback field that produces `Denied(comment)`.

## Testing pattern

Tests script the model side instead of running one: `FakeChat` (see `tests/test_agent.py`) returns pre-canned responses shaped like the ollama library's, injected via `Agent(client_chat=...)`. Tool implementations are monkeypatched at the module level (`agent_module.tools.read_docs`, `agent_module.web.web_search`). Follow this pattern — tests must run with no model, no network, no real command execution. Frontend logic gets dependency-free Node checks in `tests/js/`: the REAL function is extracted from app.js by source markers and run in a `vm` context against a minimal fake DOM — the shipped code is tested, never a hand-copied duplicate. `tests/test_frontend_js.py` runs each script inside the pytest suite (skipped when node is absent).

**Choreography harness + ownership lint (#181).** Those checks verify DECISIONS; every one of the four #181 incidents had a correct decision function and a broken feature, because the defects live in the *choreography* — when a decision is consulted, what happens if a step is skipped, what happens when two sources race. `tests/js/harness.js` (a plain CommonJS module, NOT a test — the runner globs `test_*.js`) is the shared, **hostile-by-default** world for new choreography tests: page hidden unless asked otherwise, `requestAnimationFrame` callbacks collected and never fired, timers as `{fn, ms}` data the test fires by predicate, the lying element (computed transform tracked apart from the inline style, because "the DOM lies" was itself a bug), and `FakeWebSocket` — records sends, `deliver()`s messages on demand, fires `onclose` out of order, and goes `zombie()` (readyState OPEN, silent, `close()` observably nothing — the failure no event announces). Existing tests deliberately keep their own copies; harness.js is for NEW tests only. Pins today: `test_choreo_socket_replace.js` (#179 — replacing a socket through the real `connect()` leaves exactly one live feed), `test_choreo_wake.js` (the wake handler's two subsystems), `test_choreo_console_status.js` (the #180 follow-up, as a property over every interleaving — plus, since phase 3, `openConsole`'s own guard sequence: only a REAL open may disarm the placeholder guard, since it used to be re-armed ABOVE the early returns and an open-while-open call disarmed it for good), `test_choreo_session_switch.js` (phase 2's identity races, on `sessionWorld()`), `test_choreo_midstream_replay.js` + `test_choreo_trace_switch.js` (phase 3 — a replay landing at every position in a token stream must leave exactly ONE answer bubble holding the COMPLETE text, and a live trace must never outlive the transcript it was drawn into, while a `noop` landing disturbs neither). Convention going forward: a race fix ships with its interleaving as a test, not just its decision function. `tests/js/test_ownership.js` is the enforcement half — a manifest of `owned variable → fenced region(s) allowed to assign it`, checked against app.js, whose failure NAMES THE OWNER to call instead (`ws`→`[CONNECT-WIRE]`+`[RETIRE]`, `currentSession`→`[SESSION-ENTER]`, `seenAt`→`[SEEN]`, `viewFp`/`viewDirty`→`[SESSION-ENTER]`+`[CONNECT-WIRE]`+`[REPLAY-LANDING]`, `answerEl`→`[TURN-RESET]`+`[ANSWER-OPEN]`+`[ANSWER-CLOSE]`, `currentTrace`→`[TRACE-OPEN]`+`[TRACE-CLOSE]`). Adding an owned variable is one manifest line; deliberately not every variable, only the invariants the user can see (over-fencing turns the lint into noise) — `answerAbandoned` is deliberately OUT, its writers being the owner plus the two turn boundaries that already reset `sawAnswer`, which no honest fence covers.

**Tests must never reach the outside world, and "no network" includes the developer's phone.** `notify.configured()` reads the LIVE macOS Keychain, so any test that runs a triggered session to completion with no viewer reaches `_notify_done` and sends a REAL Pushover push — the restart-recovery tests did exactly that, firing two notifications on every `uv run pytest` (bodies `read it` / `sent the reply`, and no deep-link, since the test env sets no `AISH_PUBLIC_URL` — that missing URL is what identified them). The autouse `no_real_notifications` fixture in `tests/conftest.py` sets `AISH_NOTIFY=0` suite-wide, which short-circuits `pushover()` before it touches credentials or the network; tests asserting notification behaviour monkeypatch `notify.pushover`/`configured` themselves and are unaffected, and `test_notify.py` (which exercises the sender) opts out via its own autouse fixture with `urlopen` stubbed. The general rule: a module that reaches a real credential store needs a suite-wide guard, not per-test discipline — `test_suite_never_reaches_the_real_notifier` pins it.
