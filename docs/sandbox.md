# Sandbox — the kernel boundary for commands nobody approved (epic #462)

`sandbox.py`, the routing in `agent.py` (`_would_run_cardless`, `_confine`, `_card_reason_for`, `_sandbox_note`, the `run_command` branch of `_dispatch`), the typed verdict `approval.AutoApproved`, the seam `tools.run_command(…, confinement=…)` / `tools.Unsandboxed`, and `processes.py`.

**How to use this file.** What slice S1 built and why, then the profile line by line with the measurement behind each rule, then the routing and the record, then what was measured against the owner's own command history, then the residuals — stated, not claimed as contained. Slices S2–S5 (owner-allowed tools, card-approved commands, unattended grants, plugins) are the epic's; nothing here claims them.

---

## Why

A cardless shell command was decided by the classifier in `approval.py` alone: `SAFE_COMMANDS`, `UNSAFE_FLAGS`, prefix rules, root checks. It enumerates commands × flags × spellings, and it kept losing. Reproduced on shipped code, 2026-10-17, each with no card: `sort -o/Users/epnasis/.zshrc notes.txt` (the glued flag value slipped past `UNSAFE_FLAGS` and the root check, overwriting any file), `man -P "touch X" ls` (ran `touch` — arbitrary execution), `file -C -m m` (wrote `m.mgc`), `cat .en*` (read `.env` while `cat .env` carded — the shell expands the glob after the gate looked). The owner: *"catching each command and its combination is not sustainable. We need a systemic fix."*

So every command the classifier lets through with no card now runs under a macOS Seatbelt profile (`sandbox-exec`), enforced by the kernel whatever the command line turns out to mean. **The classifier still decides card or no card; it is no longer what holds the line.** In S1 that is Tier R — the commands that need no prefix rule — plus the scratch-workspace shortcut.

## The profile (`render_profile`)

`(version 1)(allow default)`, then a deny and the narrower allows that reopen part of it, per section. **Seatbelt applies the last rule that matches**, so the order of the sections is load-bearing; `TestTheProfile` pins it. Every deny carries `(with message "<per-run nonce>")`.

| rule | what | why / measured (macOS 26.6.2, 2026-10-26) |
|---|---|---|
| exec | `(deny process-exec*)` + literal paths: `/bin/sh`, the shell `/private/var/select/sh` points at, and each of `SAFE_COMMANDS` ∪ mkdir/touch/rm/true/echo as the command's own PATH resolves it, symlinks resolved | The kernel matches the REAL path, so a symlink to python or a copy of python named `grep` is refused. A name resolving to a script (`man`, `shasum` — their interpreter would have to be listed), a setuid/setgid file (`ps`), or anything in `INTERPRETERS` (perl, python, ruby, node, awk, env, xargs, osascript, launchctl, pagers, other shells…) is left off and refused at exec, which IS recorded. |
| `/bin/bash` | on the list | macOS's `/bin/sh` is a launcher that execs the shell `/private/var/select/sh` names — bash here. A shell's two escape primitives are closed independently: `/dev/tcp` by `(deny network*)` (review: refused `network-outbound`), `enable -f`/dlopen by the map-executable rule (measured: refused, the constructor never ran). |
| map-executable | denied except `/System`, `/usr/lib`, `/usr/libexec`, `/Library/Apple`, `/private/var/db/dyld`, `/Library/Preferences/Logging` | A shared object written to scratch or shipped in a project cannot be loaded. |
| `UNTRUTHFUL_INSIDE` | `which` off the list | `/usr/bin/which` asks access(X_OK), and the kernel answers "not executable" for every program off the exec list **without logging a denial**: `which node` exited 1 with node installed and nothing in the log. Refused at exec instead, so the model is told — and `type` (the shell's own lookup, which reads the mode bits) was measured to answer correctly. `test -x` lies the same silent way and cannot be taken off any list (it is a builtin); that is a residual. |
| write | deny; allow the chat's scratch, `/dev/null`, `/dev/zero`, `/dev/tty`, `/dev/dtracehelper`, `/dev/stdout`, `/dev/stderr`, `/dev/fd/N` | `/dev/tty` and `/dev/dtracehelper` are opened by ordinary programs at start (bash, sort). The numbered `/dev/ttysN` are NOT listed: they are every terminal the owner has open, and the design review proved one could be opened for write from inside. **The project is read-only** — a writable project is how a sandboxed command poisons the owner's later unsandboxed git (`.git/hooks`, `core.fsmonitor`; epic evidence). |
| read | deny `/Users`, `/Volumes`, `/private/tmp`, `/private/var/folders`; allow the chat's workspace roots (`Agent.workspace_roots()`, the same list the classifier scopes by) and scratch; deny aish's own state and config trees again and reopen only the roots/scratch inside them (uploads, media, the scratch itself); deny the `files.is_sensitive_path` names; finally `(allow file-read-metadata)` | A trusted `~` must not hand out every chat's log. The secret-name rules are generated from `files._SENSITIVE_*`, so the gate and the kernel cannot disagree, and they are enforced AFTER the shell expanded the glob — exactly where the classifier could not see. stat() stays open everywhere: getcwd/realpath walk the project's parents, and `ls -l` in a project with a `.env` would otherwise fail. |
| network | `(deny network*)` | Loopback and DNS both refused (review). |
| IPC | `(deny appleevent-send)`, `(deny mach-lookup)` + `MACH_SERVICES` (notification centre, opendirectoryd libinfo/membership, logd, system logger, diagnosticd) | `id`/`whoami` need the directory services; `uptime` asked for DNSConfiguration, was refused, and still exited 0 — the refusal is recorded and harmless. |
| signals | `(deny signal)` + `(allow signal (target self) (target pgrp))` | The command runs in its own session (`start_new_session`), so its group is exactly the command. Measured: `kill -TERM <a same-uid sleep outside>` refused (`signal others`), the victim alive. **The new session is load-bearing**: the delivery review launched the same profile WITHOUT one and the outside process shared the group and died. `tools._spawn` always starts one, pinned by `TestTheSeamHasNoDefault`. |

**Environment** (`clean_env`): an allow-list — PATH, LANG, LC_ALL, LC_CTYPE, TERM, USER, LOGNAME, SHELL, COLUMNS, LINES, TZ — plus the real HOME (paths the classifier resolved with `~` must mean the same thing) and TMPDIR / XDG_CACHE_HOME inside scratch (git and the developer tools fail on a TMPDIR they cannot write). Tokens, keys, `SSH_AUTH_SOCK`, `DYLD_*`, `LD_*` are dropped by construction: nobody has to name a new secret variable for it to be dropped. `DYLD_INSERT_LIBRARIES` is ignored by Apple's binaries, which is all Tier R runs; it is scrubbed anyway because it runs code inside third-party binaries (epic evidence), which S2 will run.

The command runs as `sandbox-exec -p <profile> /bin/sh -c <command>` — the shell the classifier models and `shell=True` used. `TestTheExecList`, `TestTheEnvironment`; on a Mac, `TestTheRealProfile` runs the real profile (exec off the list, signals, the environment, scratch writes, a library in scratch).

**The four exploits are permanent tests** (`TestTheFourExploitsAreRefusedByTheKernel`, marker-gated to macOS, skipped on Linux CI): each through the real CLI approver and the real profile, asserting the damage did not happen and the kernel's refusal was recorded. `man -P "touch <project>/pwned" ls`, `file -C -m m` and `cat .en*` still auto-approve on the classifier's word — the test asserts that, so it is the kernel that stops them. `sort -o<path>` now cards (the glued-flag fix), so its test drives it through an approver that waves it through anyway, standing in for the next spelling nobody has found yet. Run against main (5de6673) with the same driver, all four did their damage with no card: the victim file overwritten, `pwned` created, `magic.mgc` written, `SECRET_VALUE=hunter2` in the result.

## Fail closed — and never from an exit code

`SeatbeltSandbox.prepare` returns a `Confinement` or an `Unavailable(observed)`. Unavailable when: not macOS (`sys.platform`), `sandbox-exec` or `/usr/bin/log` missing, a path that cannot be spelled in a profile (a control character), or **the canary**. Each distinct profile template (roots, scratch, PATH — the nonce is a slot) runs the canary ONCE, before its first use, and the verdict is cached for the process: a write into scratch must land (the command ran under the profile), a write into a fresh temp dir outside must not, and `/usr/bin/env` (off the list) must not start a program. Judged by the files on disk afterwards; exit codes are not consulted, because 65 and 71 are what both a broken profile and an ordinary command can return. The canary proves the write and exec axes only — a profile that lost its network line would still pass it; the profile is a fixed template, pinned by `TestTheProfile`. A process-level canary at server start would prove a DIFFERENT profile from the one each chat uses, so the canary is per profile instead. `TestTheCanary`.

**Unavailable ⇒ no cardless shell.** Attended (`origin == "user"`): the agent asks the shell approver for a CARD through the late-bound `get_card_reason` (`Agent.shell_card_reason`, forwarded by hand on claude-max), the card says what was observed (`sandbox_note` on the web card, a ⚠ line in the terminal), and the record's `preview` carries the same sentence. Unattended: refused before any card (`SANDBOX_UNAVAILABLE_UNATTENDED`, decision `rejected`). On Linux CI the whole path runs against `tests/fake_sandbox.py`'s `UnavailableSandbox`. `TestFailClosed`.

## The typed verdict and the seam (L7, inverted polarity)

- `tools.run_command` and `tools.start_background` take `confinement` as a REQUIRED keyword. `tools.Unsandboxed(why)` is the only value that runs with the owner's rights; anything else is launched as a confinement. A caller that forgets to decide gets a TypeError, never an unconfined command. The three S1 reasons: `OWNER_TYPED` (a `!` command), `CARD_APPROVED` (a click — sandboxed from S3), `ALLOWLIST_RULE` (a prefix rule — sandboxed from S2). `TestTheSeamHasNoDefault`.
- Both shell approvers return `approval.AutoApproved(command, by_rule=…)` on the auto path instead of the bare string a click returns. `by_rule` defaults to False, and the agent runs a cardless command unsandboxed ONLY when the verdict says a rule was needed AND the command is not read-only on the classifier's word — so a verdict that says nothing is sandboxed, and a rule claim on a read-only command is sandboxed anyway. `TestWhatRunsInTheSandbox`.
- The agent decides Tier R BEFORE the approver (`_would_run_cardless`: read-only and auto-approvable with no prefixes, under the workspace roots), because when the sandbox cannot take it the approver must be told to draw a card. An approver that answers `AutoApproved` although a card was asked for is overruled: `SANDBOX_FAILED_CLOSED`.
- `background: true` and Ctrl-B detach stay sandboxed (the kernel's sandbox is inherited); refusals are not read for a detached job and its result says so.

## The refusal record and what the model is told

After a sandboxed run aish reads `log show --style ndjson --predicate 'process == "kernel" AND eventMessage CONTAINS "<nonce>"'`. Measured: the denial and the nonce arrive as ONE entry, `Sandbox: proc(pid) deny(n) op target\n<nonce>`, visible to `log show` immediately after exit (5/5 serial runs). `process == "kernel"` is in the query because a sandboxed `logger` can write user log lines.

**A file name cannot forge a refusal (design review finding 1).** The kernel writes the denied PATH into the same entry, and a path may hold a newline: a file named `.envq\nSandbox: injected(7) deny(1) network-outbound evilhost:443` produced exactly that, and the first parser — line-based, "a denial whose next line is the nonce" — accepted the injected line as a refusal of its own. `parse_refusals` now takes one ndjson entry at a time, requires it to begin with the denial and END with `\n<nonce>`, and treats everything between the operation and that line as the target, newlines shown escaped. Re-measured: the injected text stays inside the `cat … file-read-data` target. `TestTheRefusalRecord`.

Distinct (process, op, target), capped at 20 with the total kept, **labelled a sample**: the kernel collapses repeats and drops lines under a flood, and under a 6-way parallel replay `log show` missed lines a serial rerun found. A run that FAILED with nothing found is therefore read once more after 0.5 s (`log_reads: 2`); the exit code only decides whether to look twice, it is never read as a refusal. Cost: one `log show` per sandboxed command, median 774 ms, p90 899 ms (corpus replay below), against a median of 14 ms for the sandboxed command itself (same replay). `log stream` was measured as the alternative and has no readiness signal (it missed the denials when the command ran at 0 ms).

**When the read happens — the owner's decision (2026-10-26).** A run that FAILED (nonzero exit, or none) is read BEFORE the result returns, with the re-read above: the note may be what tells the model why it failed. A run that SUCCEEDED (exit 0) returns at once and its refusals are read in the background. **The model is not told about refusals on a successful run.** Measured on the corpus below: 2 of the 233 commands that succeeded under the sandbox carried a refusal (`which a || which b || …` — the fallback ran), so that is what the model no longer hears about; the record still holds it, and the command is still remembered for a card if proposed again.

The late read lands as its own record, `sandbox_refusals` (contract §3.21), joined to the run's `tool` step by `turn` + `call` — both captured when the run was dispatched, so a record that arrives several calls later still names its own step. The step itself says `deferred: true` (with the nonce and start time) instead of carrying the sample. It is renderless, live and on cold replay alike (`session.RENDERLESS_STEPS`), so the two render identically: nothing on screen changes when it arrives. Three bounds keep it honest:

- **Bounded concurrency** (`sandbox.DeferredReads`): two reads at once, sixteen waiting; past that a run's record says `read: false, why: "too many refusal reads were already waiting"` at once, rather than queueing without end.
- **Settled at the end of the task** (`Agent._settle_refusal_reads`, in `run_task`'s `finally` and claude-max's): the task waits up to 10 s for its own reads, so the records land within the turn and in the log the turn was written to — the CLI switches logs on `/new` and `/resume` between tasks, so a read delivered later could land in the wrong chat. A read not done by then is recorded `read: false` (`SANDBOX_READ_NOT_SETTLED`), and its worker, if it finishes afterwards, delivers nothing: each read is delivered exactly once.
- **Shutdown** (`WebServer.shutdown`): every read still in flight is recorded `read: false, why: "aish stopped before the read finished"` and no new one is taken — aish-web ends in `os._exit`, which would otherwise kill a worker mid-read with nothing said. A `deferred` step with NO such record means the record was never written, and aish does not know which of two things happened: the process ended before it could be written (SIGKILL, power), or writing it failed — the delivery swallows a write error (a log moved away, `SessionLogMoved`) so a closed log cannot kill the reader thread, and that leaves no trace anywhere. The settle is exception-safe: a Ctrl-C during the wait still marks its reads not read, so a worker finishing later cannot deliver into whatever log the CLI has switched to by then (delivery review F2).

**A FAILED run whose refusal arrives late** (delivery review F1, proven with an empty log): both reads before it returned found nothing, so the model got no note — and before this, the record stayed empty and the identical re-proposal ran sandboxed again and failed the same way instead of carding. Now an empty result with no read error ALSO queues a background read: the step carries its empty sample and `deferred: true`, and a refusal found later lands in a `sandbox_refusals` record and arms the card. The model is still not told on that run. `TestAFailedRunWhoseRefusalArrivesLate`, `TestTheDeferredReaderEdges`.

**Stated behaviour (delivery review F5), not defects:**

- Stop, or any task end, after a successful sandboxed run waits for its read still in flight — measured 1.4 s; at worst 10 s when the pool is busy.
- The 16-read waiting limit is process-wide: one chat flooding cardless commands can push another chat's reads to `read: false` (`too many refusal reads were already waiting`).
- After `abandon_all` at shutdown, reads already queued in the pool still run; each is already marked done, so it delivers nothing.

`TestRefusalsOfASucceededRunAreReadLater` pins all of it, including the interleaving: the model's next call happens while the first run's read is still blocked, and the record arrives after the step, joined to it.

The record is an additive `sandbox` key on the existing `tool` step (contract §3.4: extend `tool`, no new kind) — for a failed run `{confined: true, tier, refused: [{process, op, target}], refused_seen, sample: true, log_ms, log_reads, nonce, started, log_error?}`, for a succeeded one `{confined: true, tier, deferred: true, nonce, started}` with the sample in its `sandbox_refusals` record (the nonce and start time let anyone read the log again later) — and every other `run_command` step that ran says `{confined: false, why: card|allowlist}`, a cardless one refused for want of a sandbox `{confined: false, unavailable: <observed>}`, so on a step that ran absence is never the evidence. Contract §3.4. The model-facing note (`SANDBOX_REFUSED_NOTE`, failed runs only) is a harness note on the turn (`_note_in_result("sandbox", …)`), also streamed into the terminal block: what the sandbox allowed, what the kernel refused, that the list is a sample, and that the model may propose the command again — it will be carded and, if approved, run outside the sandbox. When the log names nothing, NOTHING is said: that is not a claim nothing was refused. When the log cannot be read, it says aish does not know. A refused `which` adds that `type` works inside.

**The re-proposal is carded.** A command the sandbox refused something to is remembered for the chat (`_sandbox_refused`, cleared by `restore_workspace` like the rest of session scope, L4); proposing it again draws a card naming the earlier refusal, and an approval runs it as Tier C does today. Unattended, that card is held like any other. `TestTheRefusalReachesTheTurn`, `TestTheWebCard`.

## `ps` and "is X running" — the `processes` tool

`ps` is setuid; the kernel refuses a setuid program inside any sandbox, so it could only ever fail as a cardless command. It left `SAFE_COMMANDS` (it cards like any unlisted command) and aish answers the question itself: `processes(name)` runs `/bin/ps` with a fixed argv (no shell, nothing the model wrote reaches it) and returns pid, executable name and running time. **It never prints arguments or environment** — another program's command line can carry `--api-key=…`, and that is not something the owner expects a read-only check to read out. Arguments are still MATCHED (aish-web's executable is `python3`), but only by case-insensitive equality with the last path part of a whole word, so it cannot be driven as a substring oracle to read an argument out a character at a time. What remains, stated: it is a boolean existence oracle for an EXACT guessed word. A native tool rather than a rewrite of `ps` commands, because a rewrite would be aish silently running something other than what the model asked for. Ranked, not core (`docs/tool-menu.md`). `TestProcesses`.

## Measured against the owner's own history

The corpus: every distinct command aish ever auto-approved in the owner's session logs (`~/.local/state/aish/*.jsonl`, `kind:"command"` with decision `auto`), rebuilt 2026-10-26 — **1,101 distinct commands**, 812 with a recorded exit code, 736 originally exit 0. The epic's earlier run of 767 commands used a harness whose files did not survive in the scratchpad (macOS cleaned the temp dir), so this is a fresh corpus and harness, not a re-run of that one.

Originally exit 0 AND Tier R under the old list: 370. Thirteen of those are `ps` pipelines, which now card instead (one of them, `ps aux | grep "user-data-dir=.*aish/browser"`, matches a substring of another program's arguments — the `processes` tool deliberately cannot answer that one). Tier R today and originally exit 0: **357**. Each ran in its original cwd under the real profile, roots rebuilt from the log (its `cwd` and `trust_dir` records plus the process-owned stores; for logs older than the `cwd` record, the first of `~/aish`, `~/dev/aish`, `~` under which the classifier still auto-approves it), writes going to a fresh scratch. Paired with a baseline run under a write-guard-only profile (no write outside scratch, nothing else denied), so environment drift is separated from sandbox effects without running any corpus command with full rights. Commands naming the iCloud vault were NOT replayed — a remote-control session froze on that tree twice.

## Reviews

Design review (before building) and delivery review (after), adversarial, each finding proven on this Mac. Design: the refusal record could be forged by a newline in a file name (fixed: ndjson, entry must end with the nonce); `/dev/ttysN` was writable (removed); `sort -o<path>` glued slipped the classifier (now carded; the kernel holds regardless); the metadata oracle and the `(allow default)` coupling (stated below). Delivery: no containment hole found across 17 probes; three should-fixes, all fixed — a Ctrl-B detach recorded a partial refusal sample as the whole run (now `refusals_read: false` like a background job), the note said "start only aish's read-only commands" while the list also holds the shell and mkdir/touch/rm (reworded), and the new session the signal rule rests on was unpinned (now a test).

## Residuals — stated, not contained

- **A chain mixing a prefix-rule segment with read-only segments runs unsandboxed, as before S1** (Tier T is S2's). The classifier now also cards glued and bundled one-letter unsafe flags (`sort -o<path>`, `sort -ro<path>`; design review finding 4), which closes the spelling the exploit used in such a chain, not the class.
- `(allow default)` leaves unnamed operations open (iokit, sysctl reads, other processes' info, POSIX IPC). They are reachable only by the listed programs (the shell, the read-only commands, mkdir/touch/rm); **the exec list is the real fence**, and adding a program with an exec, plugin or network capability to `SAFE_COMMANDS` hands it every default-allowed operation. Review that coupling with any change to the list.
- `(allow file-read-metadata)` everywhere is an existence/size/mtime oracle, including for `~/.ssh/id_rsa` (review finding 3). Kept because closing it breaks `ls -l` in every project with a `.env`.
- `test -x` (a builtin) answers "not executable" for programs off the exec list without a log line.
- Reads outside `/Users`, `/Volumes`, `/private/tmp`, `/private/var/folders` stay open (`/etc`, `/Library`, `/opt/homebrew`), as they were.
- The refusal record is a sample, and a detached job's refusals are not read.
- The model is not told about refusals on a run that succeeded (2 of 233 in the corpus); they are in the record only.
- Pre-existing hardlinks inside a root reach their targets (epic evidence).
- Card-approved commands (S3), owner-allowed tools (S2), unattended grants (S4) and plugin wrappers / `tool_plugins.py`'s own `subprocess.run` (S5) are not sandboxed by this slice.
