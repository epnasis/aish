## The Bridge and multi-connection sessions

- **`server.py`** — `aish-web`: the same Agent behind a Starlette WebSocket instead of a TTY. `Bridge` is the core mechanism: `run_task` runs via `asyncio.to_thread`, callbacks emit JSON events through `call_soon_threadsafe`, and the approval callbacks block the worker on a `queue.Queue` slot until the browser answers — the approval gate is unchanged, only the transport differs. The process holds many open `Session`s (each its own Agent + SessionLog + Bridge + busy flag, capped at `MAX_OPEN_SESSIONS` with idle eviction) and serves many connections at once (**multi-connection, #102**): each socket is a `Client` (its own `ws`, `outbox`, `sender`, and independently-chosen `viewing` session), tracked in `WebServer.clients`; per-connection state that used to be singletons on `WebServer` (`self.ws`/`self.sender`/`self._active`) now lives on the Client. `Bridge._put` fans each event out to EVERY viewer's outbox (`Session.viewers`, owned by the bridge), and each Client's own sender coroutine drains its own outbox to its own socket — the transcript-append + all viewer-outbox pushes happen on the loop thread (via `call_soon_threadsafe`/`_show`), so no locking is needed (the invariant that kept replay snapshots race-free). **Session firewall (#182):** the fan-out stamps every LIVE delivery with the bridge's session name (never overwriting an event's own `session`, e.g. `session_state`), and the client's `ws.onmessage` drops a stamped event naming a session other than `currentSession` (`foreignSessionEvent`, `// [SESSION-FIREWALL-START/END]` in app.js) — closing the client-side switch window (prefetched swipe, offline-mirror tap) where the OLD session's live tail kept rendering into the new view until the server processed the resume. Exempt: `hello` (the switch mechanism itself), `session_state` (sent only to non-viewers by design), `session_renamed` (by-name, idempotent). The stamp rides ONLY the delivery — the recorded transcript stays byte-identical to `reconstruct_events` (hot/cold parity), and replayed events bypass the gate anyway (the replay loop feeds `handle()` directly, which is also why the drop lives at `ws.onmessage`, like the `viewDirty` mark). Pinned by `TestSessionStamp` + `tests/js/test_choreo_session_firewall.js`. Connections coexist WITHOUT preempting — `_attach` no longer closes the previous socket (the old single-client `CLOSE_REPLACED` path is gone); a bare connection (no `?session=`) lands on the default startup session (`WebServer._default`), a named one on `?session=`. Background sessions keep running, their events buffering into their transcript; switching a Client's view = hello + full transcript replay (`_show`), which is also what makes phone lock/unlock lossless. Control is **last-actor-drives**: every action handler calls `_claim(client)` first, stamping `Session.controller` and (when it changes) broadcasting a NON-recorded `role` event (`{controller, you}`) to that session's viewers; view messages (switch, files, jobs, dequeue, reconnect) never claim. There is no locked role and no disabled UI — the approval card fans out to all viewers, any may answer, and the asyncio loop serializes messages so exactly one `answer()` reaches the blocked worker (`Bridge.answer`'s pending-slot guard drops the duplicate). On disconnect (`_detach`→`_leave`) the Client leaves its session's viewers and, if it was controller, releases control (`role` → `controller:null`). `_evict_idle` never closes a busy session, one with viewers, or the default. **Session-row directory:** each row in the sessions list is labelled with its working directory (`_send_sessions` → `_row_cwd`) — read LIVE from the agent for sessions open in memory (it may have moved since the last recorded `/cd`) and otherwise from the log's last `kind:"cwd"` record (`SessionInfo.cwd`, picked up in `_parse`'s existing single pass), so the label no longer depends on the accident of which few sessions survived the `MAX_OPEN_SESSIONS` sweep. A session sitting in the server's launch workspace (`WebServer.base_cwd`, set by `create_app`) shows NO label: stamping the same path on every row is noise, so the chip's presence *is* the signal "this chat is somewhere else". The `role` event is never recorded, so cold replay re-derives control from live membership. The `active` property survives only as a representative-session helper for HTTP endpoints (no socket context) and tests; `/file` scopes to the union of all open sessions' roots. A session that fell out of memory (idle-evicted or after a restart) is reopened cold from its log and reconstructed into the same replay event stream (`SessionLog.reconstruct_events`), so its activity trace looks identical hot or cold. **Removing an exchange (#202)** is `_redact_turn`: refused while the chat is busy (the turn may be the one running, its records are still being written, and `agent.messages` belongs to the worker thread), then log → model context → transcript. The transcript is REBUILT from the scrubbed log via `reconstruct_events` rather than edited in place — that function is DEFINED to produce what a live session shows, so leaning on the parity invariant both repaints correctly and guarantees no residue survives in memory for the next viewer to replay — and the fresh `replay` goes out through the BRIDGE so every viewer repaints (a removal on the phone must not leave the laptop showing the text). That replay carries `seen: true`, true by construction because it reaches only clients currently VIEWING the chat: without it the removal, which counts as activity so every mirror refetches, would come back as an unread dot for the person who just made it. The vanilla-JS frontend lives in `aish/static/` (no build step, iOS-styled, inline SVG icons). Standalone PWA mode hides Safari's chrome, so a stalled socket has no browser refresh to fall back on (#18): `reconnect()` in `app.js` force-closes the current `ws` (even one still reporting `readyState OPEN` — a "zombie" socket the browser hasn't noticed died) and reconnects immediately, bypassing the backoff ladder. It's reachable from the session-title `⋯` menu ("Reconnect") and by tapping the existing `#connbar` "reconnecting…" bar itself. `requestNewChat()` wraps New Chat's `send({type:"new"})` to reconnect-then-retry when the socket is in a *detectable* dead state (CLOSING/CLOSED/CONNECTING) instead of silently no-op'ing; a zombie socket isn't detectable client-side, which is why the manual Reconnect control exists as the general fix. Pull-to-refresh was considered and skipped: `messagesEl` already runs a hand-rolled horizontal swipe-paging gesture with delicate vertical-vs-horizontal disambiguation (touchstart/touchmove/touchend near the bottom of `app.js`), and layering a vertical pull gesture on the same element risked fighting that logic for a case the menu/connbar controls already cover. **Session rail (replaces the #169 working-set deck and the swipe pager).** Chats are switched from a LEFT SLIDE-OVER panel (`// [RAIL-START]…[RAIL-END]`, `#session-rail` + `#rail-scrim`), opened by a rightward drag ANYWHERE ON THE TRANSCRIPT that follows the finger (`// [RAILSWIPE-START/END]` — the pure `railSwipeOpens` decision; the wiring sits on `messagesEl` beside the touch-freeze) or the top-bar button, dismissed by the scrim, the button or Escape. It shipped edge-only first and that was wrong: an edge drawer is the platform default, but this app is navigated between chats constantly and a 24px strip is a fiddly one-handed target. What made an edge tempting — transcript children that scroll sideways (unwrapped command output, code blocks, tables) — is handled by `scrollsHorizontally`, standing down when the pan STARTS inside one; that is the same test the old swipe pager used on this exact surface, so it is a solved problem rather than a reason to shrink the target. The listener is PASSIVE and never `preventDefault`s (a blocking touchmove on the scroller is the phone's biggest jank source); `#messages`'s `touch-action: pan-y` is what actually stops the browser scrolling a horizontally-started gesture, and the scrolling children opt back in with `pan-x pan-y`. The keyboard guard reads `body.kb-open`, NOT "an editable has focus" — the composer holds focus indefinitely on a desktop, so the focus test meant the gesture never armed there at all (a phone hides that, because the two coincide). There is deliberately NO drag-to-close on the list — a leftward drag on a row is already swipe-to-delete, and two recognizers on one surface is the exact collision that cost #169 its per-row delete. `begin/dragTo/endRailDrag` are the drag's whole lifecycle and `endRailDrag` ALWAYS hands the panel back to the stylesheet (`clearRailDragStyles`), because a gesture that can end with an inline transform still on the element leaves the rail resting somewhere no CSS class accounts for — the same failure shape as the pager's parked transcript. **One panel, two widths:** past `RAIL_DOCK_MIN` (900px) it simply stays open as a sidebar and the app shell is inset. The inset goes on `body`'s padding — and the rail needs NO counter-offset, which is the counter-intuitive part: `body` carries `transform: translateZ(0)` so it IS the containing block for its fixed descendants, but a fixed child resolves offsets against the containing block's PADDING BOX, whose left edge is body's border edge (0). Padding moves the flex children and leaves `left: 0` where it was. Measured, not reasoned: "compensating" with `left: calc(-1 * var(--rail-w))` put the rail entirely off-screen. A full-screen list was rejected on purpose: it would be a separate SCREEN, i.e. a second navigation model to reconcile with the desktop sidebar later, and it has no sliver of chat to say "this is temporary". Pinned by `tests/js/test_session_rail.js`.

## Triggered sessions and ingress

**Triggered sessions (#160):** a `Session` carries an `origin` (`user`|`schedule`|`email`|`webhook`) + `trigger_meta`; non-`user` origins are persisted via a `kind:"origin"` log record (`SessionLog._parse` returns it 4th — the working directory rides along 5th, see the session-row directory below — `SessionInfo.origin` surfaces it, the `session_list` payload carries it) so a cold-reopened automated session keeps its provenance, and the rail marks provenance with a tinted glyph in the row's icon slot. It used to SPLIT them into Recent / Automated **tabs**; that partition is gone (see the rail's own notes — attention, not provenance, is the axis people navigate by, and the tabs' own design admitted it by computing counters for the hidden tab). The rail keeps the iOS 15+ Safari model for its search field — docked at the BOTTOM (`.rail-searchbar`, within thumb reach), where `body.kb-open` already shrinks the fixed body to the visual viewport so it rides above the keyboard with no extra JS — and the New-chat button shares that bar. A row's `origin` still rides the listing (`SessionLog._peek` reads the `kind:"origin"` record in the same single pass that peeks the title, so `pager_titles` returns `(name, title, origin)`) — it is what draws the provenance glyph on a rail row. The loopback+token-gated **`POST /trigger`** (`handle_trigger`) is the programmatic ingress: it `open_session(None, origin, meta)`s, `add_session`s, and launches the prompt via `_run_task` on the session's own bridge (no client — events buffer into the transcript, observable when the owner opens it).

**Trigger ingress hardening (#178 P1-10):** three guards run after the token/origin gates and BEFORE any session exists — `meta.dedup_key` idempotency (a repeat POST answers 200 with the existing session name + `deduped: true`; the map is a bounded in-memory LRU+TTL, `TRIGGER_DEDUP_TTL`/`TRIGGER_DEDUP_MAX` — durable cross-restart dedup deliberately stays at the SOURCE, the poller's Gmail label; no key → every POST fires, so existing clients are unchanged), a per-`origin` token bucket (`TRIGGER_RATE_CAPACITY`/`TRIGGER_RATE_REFILL_S`), and a cap on concurrently RUNNING triggered sessions (`MAX_CONCURRENT_TRIGGERED`, counted as origin != user AND busy) — both limits answer 429 + `Retry-After` (`TRIGGER_RETRY_AFTER_S`), safe by the poller's contract (a message is marked processed only AFTER a successful trigger, so a 429'd delivery retries next poll). The three knobs are create_app-injectable (`trigger_rate_capacity`/`trigger_rate_refill_s`/`max_concurrent_triggered`) for tests (`TestTriggerHardening`).

**Per-trigger model override (#186):** the payload may name a `model` — `open_session(model_override=…)` builds it FIRST (before `SessionLog.new`, so a bad spec leaves no orphan log) and swaps chat/model/provider on the fresh Agent, same mechanics as the resume-model restore. It exists for privacy-scoped automation (built for curation v1; curate v2 now calls the backend directly and no longer triggers sessions, so this remains a GENERAL capability for any future email/webhook automation whose prompt carries private data) and therefore FAILS CLOSED: an unbuildable override answers 503, never a silent fallback to the server's (possibly cloud) default — that fallback would be exactly the leak the override prevents. Resumed sessions ignore it (their recorded model wins); a claude-max server refuses it.

- **`email_poll.py`** — the Gmail→`/trigger` poller (#161, in-repo since #178 Gate 3; console entry point `aish-email-poll`). Polls the bot mailbox via the `gws` CLI for inbox mail FROM the owner's addresses, requires `dmarc=pass` from Gmail's own Authentication-Results (anti-spoofing — SPF alone validates the envelope, not From), builds the recipient-scoped-autonomy prompt (answer the owner via a NEW `gmail_send`, never a threaded reply; everything else draft-and-hold), and POSTs origin=email with `meta.dedup_key` = the Gmail message id (pairing with the server's idempotency). Durable dedup is the `aish-processed` label, applied ONLY after a successful trigger — a failed POST or a 429 (rate/concurrency refusal, logged with its Retry-After) leaves the message unlabelled so it retries next poll; a label-ensure failure aborts the whole run to avoid a re-fire loop. Token from the Keychain (service "aish", account AISH_WEB_TOKEN) with an env fallback. Testable by construction: the two effectful edges — the `gws` subprocess runner and the HTTP POST — are `run_poll(gws=…, post=…)` parameter seams (plus `token=` bypassing the Keychain), so `tests/test_email_poll.py` fakes both with no subprocess and no network. Its `trigger()` helper takes an `origin` param (default `"email"`) so other automation entry points reuse it — `curate.py` posts `origin="schedule"`.

## Execution, security, transport

**A refusal is not a failure (`WebServer._refuse`).** An `error` event said two unrelated things and the client could only assume the worse one. A TURN FAILURE (the model died, a tool blew up) ends the turn: the live trace closes, busy clears, Retry appears. A REFUSAL of the request the user just made says nothing about the turn at all — but it went out in the same shape, so `_redact_turn`'s correct "can't delete a message while this chat is working" **tore down the running turn's card**, taking Stop and Retry with it and stranding a task with nothing on screen to reach it. The refusal was right; the collateral was total. The split already existed in the code and simply was not carried across the wire: a turn failure goes through `session.bridge.emit` (recorded, fanned out to every viewer, part of the transcript), a refusal goes down the ONE socket that asked and is never recorded. `_refuse` stamps `code: "refused"` at the site that knows, because the far end cannot re-derive which channel an event came from; every direct-to-client error now goes through it, and the client shows a toast without touching turn state ([ERROR-KIND] in app.js). `_gone_error`'s `no_such_session` is the pre-existing instance of the same idea and keeps its own richer handling. `TestRefusalIsNotAFailure` pins both halves — including that no `bridge.emit` error ever carries the code, which would downgrade a real failure to a toast and hang the turn busy forever.

**The queue strip is backend-authoritative, all of it.** A queued-message chip names a message ONE chat's agent is holding, and its Remove button dequeues from whatever session the client is VIEWING. It used to be sent only to the client that typed it — "the requesting client's own composer echo" — which holds right until that client looks at a different chat: the chips live outside the transcript, nothing cleared them on a switch, and they followed the viewer into the next chat. There Remove dequeued from THAT session (a no-op) while the real message went on running where it was queued, so cancelling silently cancelled nothing; Edit pulled the text into the new chat's composer while the old chat still held its copy, one send away from running it twice in two places. The pending-cd card in the same strip had been reconstructed on attach since #92 — half the strip was already right. Now `_show` re-sends the real `session.queue` after the replay (so a second device sees the queue at all, which it never did), `_start_task` emits `queued` through the BRIDGE so it carries the session stamp the firewall (#182) needs to drop it, and `_dequeue` announces `dequeued` the same way, mirroring `cwd_dequeued` — a cancel on the phone takes the chip off the laptop. Both are `record=False`: a waiting message is live state, not transcript, and `reconstruct_events` emits neither. `TestQueueIsBackendAuthoritative` pins it.

**Dedicated worker executor (#178 Gate 3):** `WebServer.worker_pool` (`ThreadPoolExecutor`, `WORKER_POOL_SIZE`=32, threads named `aish-worker-*`) runs the AGENT WORKER calls — `run_task`/`run_user_command` via `WebServer._in_worker` — because a held approval PARKS its thread indefinitely (Bridge.ask blocks on a queue.Queue), and on the shared default to_thread executor a few parked workers starved the `_show`/parse/peek calls a client needs to attach and answer them: livelock, restart-only recovery. Short ops stay on the default pool BY RULE — never route anything through `_in_worker` unless it can block on an approval or run user-command-long. 32 = several times MAX_OPEN_SESSIONS + MAX_CONCURRENT_TRIGGERED + restart-resumes; idle threads are near-free. `shutdown()` releases it with `shutdown(wait=False, cancel_futures=True)` AFTER the deny loop has unblocked every held approval, so shutdown never deadlocks on a parked worker (`TestWorkerPool` pins the routing both ways). The **capability policy** (`_triggered_safe` + a branch atop `approve_tool`, wired through `make_web_approvers(..., get_origin=…)`) is draft-and-hold built out of the existing gate: in a non-`user` session, SAFE mutations (`TRIGGERED_SAFE_TOOLS` = relabeling; and `gmail_send` — draft OR live — when **every recipient is the owner** — `_all_recipients_owner` vs `OWNER_ADDRESSES`/`AISH_OWNER_ADDRESSES`, the **recipient-scoped autonomy** that lets aish answer the owner without approval since a send that can only reach the owner's own inbox carries no prompt-injection exfiltration risk; a reply with no explicit `to` is NOT auto-safe — its recipient isn't verifiable from args) auto-run with no card, while every other mutation (any send or draft addressed beyond the owner, trash, filter-create, drive share) falls through to the normal card, which simply BLOCKS pending until the owner opens the automated session and answers.

**Recipient validation is a parse, never a regex find (#178 P0-3):** `_parse_recipients` uses `email.utils.getaddresses`, rejects quoted/multi-`@` local-parts and any field that re-serializing doesn't reproduce (residue), and any unclean parse counts as not-owner — the old `findall` passed `"pawel@wenda.eu"@evil.com` (valid RFC 5322, routes to evil.com) as owner-only; drafts are checked like live sends because a fully-addressed draft is one tap from sending (`test_adversarial_recipients_never_pass_as_owner` pins the table).

**Egress hardening (#178 P0-2):** `SecurityHeaders` (pure-ASGI middleware, every HTTP response) stamps `Content-Security-Policy` (built by `content_security_policy(host)`; `img-src` = self/data:/`CSP_IMG_HOSTS` — the YouTube-thumbnail + static-maps whitelist mirroring export.py — killing the zero-click `![](https://attacker/…)` channel; the SAME whitelist is enforced in the renderer itself (#178 P1-12) — `imageFetchAllowed` + `IMG_FETCH_HOSTS` in app.js (`// [INLINEIMG-START/END]`, kept in lockstep with `CSP_IMG_HOSTS`, pinned by `tests/js/test_image_fetch_whitelist.js`), so a non-whitelisted remote image renders as a tappable non-embedded link on every path (offline replay, export preview) instead of relying on the header being present; `connect-src` names `ws://`+`wss://` of the request's own Host, sanity-checked by `_HOST_OK_RE`, so the socket works behind the wss proxy; `script-src 'self'` holds because index.html has no inline scripts — pinned by `TestSecurityHeaders`) plus `Referrer-Policy: no-referrer`; WebSocket scopes pass through untouched. The Agent carries the session's `origin` too (`common` passes it in `open_session`): in a non-`user` session, `read_url`/`web_search` to a host outside the conversation's **provenance** hold on the `approve_tool` channel, and `recall` skips the past-session archive (see agent.py notes below).

**Load-path weight:** `GZipMiddleware` (outermost, min 512 B) compresses every HTTP response — the critical path was 560 KB raw (app.js 421 KB) and now ships ~172 KB, which matters because the SW's 3 s network-first navigation race decides fresh-vs-cached-shell on exactly that first fetch; and `index.html` links `style.css` in BODY below the boot loader, not HEAD — a pending HEAD stylesheet blocks the FIRST paint entirely, so the inlined spinner never showed on a slow link (in-body, only content after the link waits, and the opaque loader covers it; no CSP-hostile `onload` swap). The token gates `/trigger` unconditionally (#178 P1-2 — the old loopback fallback is gone: a same-host reverse proxy makes every request look loopback, so it proved nothing). The access token itself always exists — `WebServer.__init__` generates a random per-run one when none is configured, `main()` prints it in the launch URL, comparisons are constant-time (`_token_ok`/`hmac.compare_digest`), and every gated surface (`/ws`, `/file`, `/upload`, `/export/*`, `/dirs`, `/offline/*`, `/trigger`) requires it. `origin_allowed` additionally rejects any browser request (WS handshake, `POST /trigger`) whose `Origin` host:port differs from the request's own `Host` — a missing Origin (curl, the poller) passes, since browsers always send one on the cross-origin requests that are the drive-by vector. Cold opens are single-flight (`WebServer._opening`, #178 P1-5): concurrent `_open_by_name` callers on one name share one Future/Session, so a racing resume + reconnect can't orphan a session whose approvals could never be answered. `add_session` takes keyword-only `default` with no default value (#178 P1-6); `handle_trigger` passes `default=False` so an overnight trigger never becomes the bare-connect landing session.

## Notifications and recovery

**Push notifications (#163):** `notify.py` sends Pushover (creds `PUSHOVER_TOKEN`/`PUSHOVER_USER` from the Keychain via `secrets.get`; unconfigured or failing = silent no-op, NEVER raises into the approval path). Two triggers, both only for non-`user` origins: (1) a HELD approval — `Bridge.ask` calls its `on_wait(event, has_viewers)` hook right before blocking; the `notify_hold` closure (wired in `open_session`) pushes a **priority-0** notification with `_describe_hold(event)` as the body ONLY when nobody is viewing (an open tab already shows the card), on the worker thread inside `ask`'s try/except. Both notifications are priority 0 deliberately: Pushover's priority 1 is the ONE level that ignores quiet hours and always sounds, which turns an overnight hold into a 2am alarm — and since a held worker waits indefinitely, the hold is still there in the morning (nothing is lost by respecting quiet hours). Priority 2 (the only level that actually re-alerts until acknowledged) requires `retry`/`expire` and is never used. (2) a triggered session FINISHING — `_run_task` awaits `_notify_done`, a **priority-0** push offloaded via `asyncio.to_thread` so the loop never blocks; it is gated on `session.viewers` exactly like the hold notification, because without that every message the owner types INTO an automated session pushes a phone notification for work he is watching live. Both carry a `url` deep-link `{public_url}/?session={name}` (`AISH_PUBLIC_URL` / `create_app(public_url=…)`, on `WebServer.public_url`; empty → no link, still notifies). This is what makes draft-and-hold safe: a held worker thread waits indefinitely, so the notification is the owner's signal to come approve.

**Restart recovery (#164):** an in-flight task is bracketed on disk by `SessionLog.task_start(prompt)` / `task_end()` written from `_run_task` (web only — a CLI session dies with its terminal and must never be resurrected; the `!` user-command path writes NO marker, since re-running the user's own shell command unattended is a risk, not a recovery). A killed process cannot write anything, so an UNMATCHED `task_start` IS the interruption evidence — no heartbeat, no timer. `WebServer.startup` fires `_resume_interrupted` as a background task (never on the startup path): `SessionLog.interrupted_sessions` scans the state dir newest-first within `RESUME_WINDOW` (12 h), each candidate is cold-opened through the SAME `_open_by_name` a user's session-switch uses (so the resumed session replays its full prior transcript), and the task is relaunched via `_run_task` on its own bridge with no client — identical to a trigger. The resumed turn is `RESUME_NOTE`, NOT the original prompt: the request and the partial work are both already in the restored history, so re-issuing the prompt would invite the model to redo side effects it may have completed (an email already sent). The ONE exception is a run killed before its own user message was logged (`history` has no user role) — there is nothing to continue from, so the recorded prompt is re-issued. Two things make "continue" real rather than nominal: the resumed run passes `keep_history=True` to `Agent.run_task`, which swaps the eager per-task tool-output trim (200-char stubs — it would gut exactly the results the resume exists to preserve) for `_trim_history_to_budget`, an oldest-first trim that runs only as far as the char budget demands; and `pending_task`'s `in_flight` list (a `tool_start` trace record with no matching `tool`, matched by name because read-only calls run in parallel) is appended to the note, naming the steps whose effect is genuinely UNKNOWN. That is the honest boundary of the guarantee: a completed step logged its result, an in-flight one may or may not have taken effect, so the model is told to verify those specifically instead of re-running the task. Bounds keep it safe: `RESUME_MAX_ATTEMPTS` (3, counted as `task_start`s since the last `task_end`) means a task that keeps killing the server is abandoned instead of crash-looping it, and `RESUME_MAX_SESSIONS` (3) stops a mass restart stampeding the backend. Applies to user chats AND triggered sessions — a triggered one is the load-bearing case, since the email poller marks a message processed on trigger and will never fire it again. `web_usage_context` tells the model imperatively what a `[automatic resume]` message means (verify what completed, never repeat a send/write/change).

## Mid-task steering and output

**Mid-task steering (#95):** a `/cd` or a message typed while a task runs is applied/injected BETWEEN steps, not only after the task. The agent's step loop polls two get/drain callbacks at the top of each iteration (`check_pending_cwd`, `check_pending_messages`, wired from `open_session` over `session_holder`; lock-free — the event loop is the sole setter, the worker thread the sole consumer). `check_pending_cwd` get-and-clears `Session.pending_cwd` and the agent `rebase()`s + rebuilds `messages[0]` for the new dir; `check_pending_messages` drains the text-only items of `Session.queue` and injects each as a mid-task user turn (echo + a distinct `injected` trace step that renders live AND replays via `reconstruct_events` — the text is appended straight to `self.messages`, NOT logged as a conversation `message` record, so cold replay does not split the turn; trade-off: injected steering is not carried into `--resume` history). Queued items carrying attachments — and `!`-prefixed terminal commands (#105), which must run through the user-direct path, not as model prompts — stay in the queue and run as a normal follow-up at `_finish_turn` (the safety net for anything left, e.g. queued after the final step). Every cwd move — mid-task, immediate `/cd`, or the post-task drain — now flows through the single `on_state("cwd", …)` handler, which is the ONE place that emits the timeline `workspace` marker AND (record=False) retires the #92 queue card (`cwd_dequeued`) + refreshes the top-bar chip (`cwd_changed`); `_cd`/`_finish_turn`/`run_user_command` no longer emit those manually. claude-max runs its own loop, so mid-task polling does not apply there (its inner Agent's post-task `/cd` still flows through the unified path).

**Live-output coalescing (#109):** `StreamCoalescer` batches run_command's per-line output into fewer `stream` events (flush at 50 lines / 16 KB / 0.1 s or command end) so huge output can't lock the tab with per-line DOM appends; it is LIVE-ONLY — logged `tool` output and cold replay are untouched, the frontend re-splits on `\n`, so hot/cold trace parity holds.

## Feedback and export endpoints

**Feedback → GitHub issue (#110/#130), two flavours:** text-only web `/feedback` uses the BLOCK flow — the model emits the finished issue as one ` ```aish-issue ` fenced block (line 1 `title:`, optional `---`, body verbatim; parsed by `parse_issue_block`, mirrored in app.js `issueDraftCard`) and never runs `gh issue create`; the frontend renders it as a review card and on confirm the backend files it VERBATIM on the pinned `ISSUE_REPO` (user-direct action, no approval gate). CLI feedback, and web feedback carrying attachments, use the CLASSIC flow — the model drafts in rendered markdown and runs `gh issue create` itself through the approval gate (it must upload assets, which the backend path doesn't handle). Attachments are published to a PUBLIC release, so consent is explicit: the draft lists every file with a per-file exclude chip (`FEEDBACK_ASSETS_RULES`), and a block-flow draft that gains attachments mid-adjustment auto-switches to classic via `FEEDBACK_SWITCH_NOTE` (appended server-side, model-only). `parse_feedback` in `cli.py` takes `block_flow`/`attachments` flags; the CLI always passes neither.

**PDF export** endpoints (`handle_export_answer` / whole-session) call `export.py` with `_image_roots()` — the union of open sessions' roots — as the local-image trust boundary. Approval-card accents are classified client-side (#107): only destructive-looking commands (`looks_destructive` in app.js — sudo/rm/mv/kill/--force) get the orange danger accent; everything else uses the calm blue — the gate itself is unchanged. Voice (#97) is frontend-only: mic dictation into the composer (SpeechRecognition, hold-to-switch language), auto read-aloud of replies to dictated messages (speechSynthesis, per-paragraph language detection), read-aloud controls docked in the composer row, and a `/mic` diagnostic — no server involvement.

## The global console

**Global "Quake console" (#148):** ONE persistent interactive pseudo-terminal (`aish/pty_session.py`) for the WHOLE server — not per-session — for TTY-reading programs (`gcloud auth`, `ssh`, `sudo`) the non-interactive `!` path can't drive. Openable from any chat three ways: the top-bar terminal icon (`#console-btn`), a `⌘/Ctrl+\` shortcut (`toggleConsole`), and the ＋ menu's "Interactive shell". It floats above whatever chat is shown and is untouched by chat-switches. Message shapes: `console_open` (no command — the console's command is fixed) / `console_in{data}` / `console_resize{cols,rows}` / `console_close` (HIDE — stop viewing, keep running) / `console_kill` (explicit destroy) / `console_share{text}` from the client; `console_started{command,cwd}` / `console_out{data}` / `console_exit{code}` / `console_error{text}` / `console_shared{text}` out. **tmux-backed for restart survival:** the console PTY runs `tmux new-session -A -s aish-console` (`TMUX_CONSOLE_SESSION`) — attach-or-create, so the shell lives in tmux's DETACHED server process and outlives `aish-web`; our `PtySession` is merely a tmux CLIENT. First open after a (re)start respawns the `tmux new-session -A` → REATTACHES to the surviving session and tmux redraws current state. Detected via `shutil.which("tmux")`; absent, it falls back to spawning `$SHELL` directly (global + cross-chat + cross-disconnect, but NOT restart-surviving). The single live `PtySession` is held on **`WebServer.console`** (never a Session, never the agent), with a global `WebServer.console_viewers` set.

**Lifecycle:** the console is NEVER killed on viewer-leave, `console_close`, session close, `_evict_idle`, or disconnect — only `console_kill` (which also runs `tmux kill-session` so a tmux reopen can't silently reattach to the killed thing) or graceful `shutdown` (which kills ONLY the PTY = detaches the tmux client; the tmux SESSION survives) end it. The spawn command is INJECTABLE (`create_app(console_command=…)` → `WebServer.console_command`) so tests use a trivial python echo loop and need no tmux.

**Broadcast:** one PTY, many viewers — `console_in` from any client writes the single PTY; `_console_out` fans `console_out` to every client in `console_viewers` (pushed straight to each Client's outbox on the loop thread, never through a session bridge → never recorded in any transcript). A second viewer of an already-running console gets a `tmux refresh-client -t <slave-tty>` poke (`_console_refresh`, off-loop, tmux-only) so its blank xterm is repainted with current screen state; `PtySession.tty` exposes the slave device path for this. Multi-viewer resize is **last-resize-wins**: tmux has a single client (our PTY) and sizes the pane to it, so a differently-sized viewer sees a mis-sized pane until it (or another) resizes.

**Load-bearing security invariant:** the model has NO write path to the console — `PtySession.write` is reached ONLY from `_console_in` (the user's own socket), and `agent.py`/`tools.py` never reference the PTY layer (asserted by `tests/test_pty.py`; `tests/test_server.py::TestGlobalConsole` covers the web wiring + globalness + survival + broadcast). All PTY reads run on a dedicated reader thread and marshal back via `call_soon_threadsafe` (Bridge discipline); console I/O stays private — never in a transcript, cold replay, or model context — UNLESS the user selects text and taps "Share", which injects it via the CURRENTLY-VIEWED session's `agent.add_user_context` (the same user-message path as `!`, logged for `--resume`, no task launched). The frontend renders `console_out` through **vendored xterm.js** (`static/vendor/xterm.js` + `xterm-addon-fit.js`, plain globals) — a real VT emulator with full cursor-addressing/erase/scroll, so an interactive shell's line-editor redraw (themed prompt, autosuggestions), `gcloud auth`, and simple TUIs render correctly. xterm captures keystrokes via its own textarea and forwards them through `consoleTerm.onData` → `console_in` WITHOUT local echo (the PTY echoes, so password prompts mask for free); hardware Esc HIDES the overlay (`hideConsole`, does not kill), `⌘/Ctrl+\` also toggles it closed, while the on-screen "esc" chip still sends `\x1b`; Share reads `consoleTerm.getSelection()`. The fit addon derives `cols`/`rows` for `console_resize`. On socket reconnect `onHello` re-sends `console_open` if the overlay is open, so tmux redraws current state into the (surviving or respawned) console.

- **`pty_session.py`** — `PtySession`: a subprocess on a `pty.openpty()` pair with `start_new_session=True` (setsid → controlling TTY), streamed over `on_output`/`on_exit` callbacks the class guarantees to invoke on the event-loop thread. Reader thread uses `select` with an idle-flush to coalesce bursts + an incremental UTF-8 decoder (multibyte chars can't split across reads). `write()` is the sole input path (issue #148 invariant — see server.py). `kill()` signals the whole process group, closes the master fd (idempotent), and reaps; `on_exit` fires exactly once. `.tty` exposes the slave device path (captured before the slave fd is closed) so the tmux-backed global console can `refresh-client` this exact client. No agent/model reference by construction. Used for ONE global console, not per-session (see the Quake-console paragraph above); killing the PTY of a `tmux new-session -A` detaches the client while the tmux SESSION survives on the tmux server.
