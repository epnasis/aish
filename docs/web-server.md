# Web server — aish-web

`server.py` (~4.4k lines), `pty_session.py`, `email_poll.py`. The same Agent behind a Starlette WebSocket instead of a TTY.

**How to use this file.** The laws come first — six invariants that explain most of the code, cited by the sections below instead of re-argued. Then the four objects (`Bridge`, `Session`, `Client`, `WebServer`), the wire protocol, and one section per subsystem, each naming the test class that pins it. `tests/test_server_docs.py` fails if a route or a `Test*` class is documented nowhere.

Frontend behaviour is in `docs/web-frontend.md`; the Agent's own gates are in `docs/agent-core.md`. Full narrative history is in git.

## The laws

**L1 · The transport changes, the gate never does.** The web is a different way to *reach* the approval callbacks, not a different policy. `make_web_approvers` mirrors `cli.make_approver` exactly for a `user` session — denylist first, also on edited commands; auto-approval scoped to the live roots; per-session prefixes on the session's Agent; "Always allow" writing the same file the CLI's `a` writes. If a change would make the web approve something the CLI would prompt for, it is wrong. The one deliberate divergence runs the other way: in a non-`user` origin the consulted prefix set is NARROWER than the CLI's (§Capability policy), which only removes approvals — the CLI has no non-user sessions to mirror.

**L2 · The loop thread owns shared state; the worker thread only computes.** Agent work runs off-loop and every callback marshals back with `call_soon_threadsafe`. Because the transcript append and all viewer-outbox pushes happen on the loop thread, there is no locking anywhere in the fan-out — that is what keeps a replay snapshot race-free. A new callback that touches a `Session`, a `Client` or the transcript from the worker thread breaks this silently.

**L3 · A parked worker must not starve the server.** A held approval blocks its thread indefinitely (`Bridge.ask` waits on a `queue.Queue`), so anything that can block on an approval or run user-command-long goes through `WebServer._in_worker` and its dedicated pool. Everything short stays on the default executor **by rule** — a few parked workers on the shared pool starved the very calls a client needs to attach and answer them, which is livelock with restart-only recovery.

**L4 · Live state is not transcript.** `SessionLog.reconstruct_events` is *defined* as "what a live session shows", so hot and cold must agree. Anything that is momentary — control role, the queue strip, cwd chips, a rename, a refusal — is emitted with `record=False` and re-derived on attach. Anything recorded must replay identically.

**L5 · The site that knows stamps it.** Provenance is written where it is known and read downstream, never re-derived: the fan-out stamps each live delivery with its session, `_refuse` stamps `code:"refused"` because the client cannot tell which channel an event came from, `kind:"origin"` records how a session was started, `_turn_event` mints the turn id. A consumer guessing from prose or shape is the bug this prevents.

**L6 · Fail closed, and unattended is not attended.** The access token always exists (a random one is generated when none is configured) and gates every surface; an unbuildable per-trigger model answers 503 rather than falling back to the server default; an unclean recipient parse counts as not-owner; a missing approver refuses. Origin is the axis: a `user` session behaves exactly as it always did, everything else is scoped.

## The objects

### `Bridge` — one per session, the thread boundary
`run_task` runs via the worker pool; callbacks emit JSON events through `call_soon_threadsafe`; the approval callbacks block the worker on a `queue.Queue` slot until a browser answers (L1, L2). `emit` is the recorded path, `record` appends to the transcript, `_put` fans out to every viewer's outbox and stamps the session name (L5) without overwriting an event's own `session`. `answer`'s pending-slot guard drops the duplicate when two viewers answer the same card. `ask` calls `on_wait(event, has_viewers)` right before blocking — the hook hold notifications hang off (`TestBridgeOnWait`).

### `Session` — Agent + SessionLog + Bridge + busy flag
Carries `origin` + `trigger_meta`, its `viewers` set (owned by the bridge), its `queue` of messages typed while busy, `pending_cwd`, `controller`, and `open_turn` (which mints the turn id `[REDACT]` needs while the turn is still live). Capped at `MAX_OPEN_SESSIONS` with idle eviction — `_evict_idle` never closes a busy session, one with viewers, or the default.

### `Client` — one per socket
Its own `ws`, `outbox`, `sender` coroutine and independently chosen `viewing` session, tracked in `WebServer.clients`. Connections coexist WITHOUT preempting: `_attach` does not close the previous socket, a bare connection lands on `WebServer._default` and a `?session=` one on that session (`TestMultiConnection`, `TestConnect`). Per-connection state that used to be singletons on `WebServer` lives here; `WebServer.active` survives only as a representative-session helper for HTTP endpoints, which have no socket context.

### `WebServer` — the process
Holds the sessions, the clients, the single console, the worker pool, the trigger guards and the token. `create_app` injects everything tests need to vary (console command, trigger limits, public URL, base cwd).

## Threading and scheduling

Three thread contexts, and mixing them is the recurring defect: the **event loop** (owns all shared state, L2), the **worker pool** (`WORKER_POOL_SIZE`=32, threads named `aish-worker-*`, reached only through `_in_worker`, L3), and the console's **reader thread** (marshals back with `call_soon_threadsafe`, same discipline). 32 is several times `MAX_OPEN_SESSIONS` + `MAX_CONCURRENT_TRIGGERED` + restart-resumes; idle threads are near-free. `shutdown()` releases the pool with `cancel_futures=True` **after** the deny loop has unblocked every held approval, or shutdown deadlocks on a parked worker (`TestWorkerPool` pins the routing both ways).

Cold opens are **single-flight**: concurrent `_open_by_name` callers on one name share one Future and one Session (`WebServer._opening`), so a restart-recovery resume racing a reconnecting PWA cannot orphan a session whose approvals could never be answered (`TestConcurrentColdOpen`).

## The wire protocol

Two kinds of client message, and the distinction is the control model. **Action** messages call `_claim(client)` first, stamping `Session.controller` and broadcasting a non-recorded `role` event when it changes. **View** messages never claim.

| | messages |
|---|---|
| **action** | `task` · `command` · `step` · `stop` · `retry` · `approval` · `write` · `tool` · `import` · `cd` · `add_dir` · `new` · `fork` · `rename_session` · `set_objective` · `plan_action` · `delete_session` · `restore_session` · `purge_session` · `redact` · `set_model` · `create_issue` · `console_*` |
| **view** | `resume` · `peek` · `history_more` · `sessions` · `models` · `files` · `jobs` · `dequeue` · `dequeue_cwd` · `share_drop` · `trash` · `render_error` · `client_debug` · `browser_watch` |

**Receipts (`rid` → `ack`, #210).** A client cannot tell a request that was handled from one that was never heard: the socket reports OPEN long after it died, accepting everything and answering nothing. So any message may carry a client-minted `rid`, and `_handle` echoes `{"type":"ack","rid":…}` once the handler returns. Three properties are load-bearing. It is stamped at the **dispatch point, not in each handler** — a handler that forgets is a silent hole, and this way a new message type is receipted before anyone thinks about it. It is sent **after** the work, so a client that hears the receipt knows the events it was owed have already gone out, and a handler that RAISES sends none — an action that blew up did not happen, and the client must hear that as loudly as one that never arrived. And it is a **delivery** fact, never a semantic one: "handled", not "succeeded", including for a refusal (a refusal is an answer, and the client must stop waiting on it). What actually happened stays with each feature's own events. The client half — which requests must carry one and what an unreceipted one undoes — is `[ACK-LEDGER]` in `docs/web-frontend.md`.

Control is **last-actor-drives**: no locked role, no disabled UI. The approval card fans out to every viewer, any may answer, and the asyncio loop serializes messages so exactly one `answer()` reaches the blocked worker. On disconnect (`_detach` → `_leave`) the client leaves the viewers and, if it was controller, releases control. The `role` event is never recorded (L4) — cold replay re-derives control from live membership.

Switching a client's view is `hello` + full transcript replay (`_show`), which is also what makes phone lock/unlock lossless. A session that fell out of memory is reopened cold from its log (`_cold_open`) and reconstructed into the same event stream, so its activity trace is identical hot or cold.

### A client that vanishes mid-send (#315)

A socket dying is the ordinary end of a connection, seen from two directions: starlette raises `WebSocketDisconnect` on RECEIVE, uvicorn raises `ClientDisconnected` (an `OSError`) out of SEND. Only the receive half had a handler, so a tab closed while `_show` was still replaying logged a full unhandled-ASGI traceback. The effect was nil — the client is gone — but the cost was the *signal*: "no tracebacks in the daemon log" is a cheap post-deploy check, and a recurring benign traceback trains you to skim past exactly what that check exists to catch. `CLIENT_GONE` names both, `handle_ws` catches it and logs ONE line at **debug** — not silence, because a *frequent* disconnect is a symptom of something else and has to stay visible somewhere. `_send_loop`'s catch is split for the same reason it is narrow: a disconnect ends the loop quietly, anything else (a serialization error, a broken frame) is a bug in what we are *sending* and is logged with its traceback rather than swallowed alongside a closing tab.

**The load-bearing half was where `_attach` sat.** It ran OUTSIDE `handle_ws`'s `try/finally`, so a raise during the replay skipped `_detach` and left a ghost in `session.viewers` with no sender task, for the life of the process. That is not merely a leak, it is a **policy input**: the viewer set is the test for "somebody is looking at this", so a ghost silences both Pushover triggers (`notify_hold` and `_notify_done` each gate on it), pins the session against `_evict_idle`, and grows an outbox nobody drains. `_attach` is now inside the try, which also cleans up after a failure that is *not* a disconnect.

**The approval card cannot be lost or forced this way, and the reason is structural rather than defensive.** `Bridge.ask` never touches a socket. It emits into each viewer's OUTBOX and blocks on its own `queue.Queue`; the socket is written later by that Client's own sender task, on a different stack. So a client vanishing at the instant a card is emitted cannot raise into the parked worker, cannot skip the gate and cannot answer for the owner — the request stays in `pending` and in the transcript, and the only thing that ever moves it is an `answer()` (a live one, a Stop, or the shutdown deny loop). The fan-out is all-or-nothing for the same reason: `_put`'s loop is one `put_nowait` per viewer and nothing in it can fail, so one of three sockets dying costs the other two nothing. And the record stays honest on the #306 axis — `held_ms` is the gate's own clock, `shown_ms` comes only from a browser that reported RENDERING the card — so a card no screen ever showed records no screen time rather than a zero. `TestClientVanishes` pins all of it, including a source-level assertion that `Bridge` names no socket verb at all; without that the invariant would go quiet the moment someone moved the line, which is how this codebase has lost properties before.

## Sessions

**Open, list, switch.** `_hello` carries model, session scope, recency list, busy/role and peeks (`TestConnect`). `_send_sessions` labels each row with its working directory (`_row_cwd`) — read LIVE from the agent for open sessions, otherwise from the log's last `kind:"cwd"` record, so the label does not depend on which few sessions survived the eviction sweep. A session sitting in `WebServer.base_cwd` shows NO label: stamping the same path on every row is noise, so the chip's *presence* is the signal "this chat is somewhere else". Rows also report waiting-for-approval state (`TestSessions`). `_peek` answers another session's transcript snapshot WITHOUT switching or claiming — nothing recorded, a miss answers `gone` on the peek rather than the resume path's error (`TestPeek`).

**New, fork, rename, delete.** A new chat inherits the model the client is currently using, like the consumer apps; the saved default applies only at server start (`TestModels`). `_fork_session` branches into a NEW session seeded with the conversation up to a point, and sets `retitle_forced` so the fork earns its own name instead of wearing its parent's (`TestFork`, `TestAutoTitle`).

**Where a fork branches from is an IDENTITY, not a position (#229).** `fork` carries `answer` — the id of the assistant record, minted at write time by `SessionLog.message` and resolved by `truncate_at_answer_id`. It used to carry an ordinal, and the only party who could supply one was the browser, counting answers as it rendered them; the first paint is capped, so on a trimmed chat the browser's sixth answer was the log's twentieth and the fork branched fourteen answers early, silently. The live path publishes the id it just wrote (`logref.last_answer_id`, cleared at `task_start` so a cancelled turn cannot hand out the previous turn's), and `reconstruct_events` re-derives the same id on replay — so hot and cold name the same record. `after` remains only for a cached page built before ids existed. Client half: `[FORK-ANCHOR]` in `docs/web-frontend.md`.

**Reading further back than the first paint (#228).** `_history_more` answers a `replay` built from a WIDER window of the log — re-read via `reconstruct_events`, because `bridge.transcript` is the bounded hot copy and by definition does not hold the part being asked for. Refused while the chat is working: a running turn's tokens are not on disk yet, so a rebuild from the log would paint the answer being written out of the view. Every replay now carries `total` (what the chat holds) beside `truncated` (whether this is all of it), which is what lets the client say how much is missing rather than only that something is. A `history_more` reply adds `more`: whether asking AGAIN would get you any further. At `TRANSCRIPT_WINDOW_MAX` — a replay is one JSON frame, and past some size the frame is itself the problem — `more` is false while `truncated` is still true, and the client says where the rest is instead of offering a control that would do nothing. A ceiling nobody is told about is the same defect #228 was. `TestHistoryMore`; client half `[BACKFILL]`. `_rename_session` works on cold sessions from disk too, rejects empty titles and path escapes, and the latest rename wins across a reconnect (`TestRename`). `_delete_session` takes the conversation AND its command history off every listing — the ONE sender is the frontend's shared confirmation modal (`TestRedactTurn` covers the finer-grained alternative below). Since #177 it MOVES the log to the trash rather than unlinking it; see **Recently deleted** below, and `docs/session-log.md` for the mechanism. It also takes the chat's scratch workspace with it, and it is the only thing that does: since #258 that directory is keyed on the chat's log rather than on whichever Agent happens to be alive, so closing a session no longer collects it (`docs/agent-core.md`). The other half is in `WebServer.__init__` — `prune_chat_scratch` sweeps workspaces whose log is gone, deliberately BEFORE `create_app` opens the default session, because a chat that has not yet written its first record is indistinguishable from an orphan once it is open.

**Recently deleted (#177).** The trash itself is `docs/session-log.md`; what the server owns is three things. `_purge_trash` runs as a **background** task in `startup`, beside `_resume_interrupted` and the evidence sweep and for the same reason — one listdir and a filename parse, never on the startup path, and a failure that can never keep the server from coming up. `_trash_rows` is what a client can render — the entry to act on, the chat's name, its title and when it was deleted — built off the loop, because reading it peeks a title out of every trashed log. And `_restore_session` / `_purge_session` are the two things that change it.

**The list is PUBLISHED, not polled, for the roster plane's reason.** `_broadcast_trash` goes to EVERY client after a delete, a restore and a permanent delete: a chat restored on the laptop must not sit in the phone's Recently deleted list waiting to be restored a second time. Reading it (`trash`) is a VIEW message — looking at what you deleted changes nothing and claims nothing; the two that change it are actions and carry a receipt like any other (`[ACK-LEDGER]`). What rides the **hello** is deliberately only the NUMBER, `trash_keep_days`: the client needs it to say what a delete costs, there must be exactly one statement of the policy (a copy in `app.js` would go on saying 30 the day this stopped meaning it), and the list itself is asked for so its file reads stay off the attach path.

**A restore is a broadcast too** (`session_restored`), and it has to be: the offline mirror dropped this device's copy when the chat was deleted ([MIRROR-FORGET]), deliberately, because the server is the one holding the bytes. That decision is #177's "interaction that will bite if ignored", and it was taken the other way from the issue's first option **on purpose**. Having `/offline/index` list trashed chats behind a flag would make `mirrorOrphans`' rule — *an absence in the catalogue is a real absence* — false, and every consumer of that index (the rail paint, offline search, the eviction planner) would need a trashed filter it does not have today; one missed filter puts a deleted chat back on the list, which is the exact failure the whole cheap-because-invisible design avoids. Nothing is lost by evicting: the bytes are on the server for 30 days, a restore is an online action (sending offline is refused on purpose), and the mirror refetches straight after one. What a device loses in the window is the ability to READ a chat it asked to delete, which is not a loss.

`_delete_session` moves the file FIRST, before any viewer is moved off the chat or the live session is closed, so its refusal ("its log file would not move") describes a delete that genuinely did not happen; nothing in the viewer hand-off writes to the doomed log (`_leave` only touches viewer sets), which is what makes that order safe. `_restore_session` shows the ONE condition `restore_session` observed (`RestoreRefused`'s message) — the trash entry gone, a live chat already holding the name, the rename failing — never a summary of the three: "no longer in Recently deleted" was being said for a chat that still was, because a live log held its name. And a chat some OTHER client has open cold — resumed, nothing written yet, no handle — cannot recreate the log under the live name once it is trashed: `SessionLog` refuses that first write (`SessionLogMoved`, `docs/session-log.md`), `_run_task` reports it as the turn's error and ends the turn, because the stub would have blocked the restore until the purge destroyed the only full copy. Every OTHER write — a rename, a rating, whatever is added next — is caught ONCE at `_handle`, the seam every message passes through, and turned into the same refusal with the client left connected and the receipt still sent; left to propagate, the exception closed the websocket, which is the method being wrong rather than a site. The task path keeps its own catch because `_run_task` runs as its own future and never surfaces in `_handle`. `test_a_rename_on_a_chat_another_client_trashed_is_refused_not_dropped` fails against the pre-fix server with a closed-socket error from the test client. It is otherwise unchanged, **including what it destroys outright** — the scratch workspace, the evidence blobs, the pin entry (a restored chat comes back unpinned; every surface that says where it lands says so). Deferring those to the purge was considered and rejected: a trash that also held the entire footprint of every deleted chat for 30 days is not a trash, and the conversation plus its audit trail is the part a delete destroys that nothing else has a copy of. Every surface offering the restore says which half it gives back. `TestRecentlyDeleted`.

**Redact a turn** (`_redact_turn`): refused while the chat is busy — the turn may be the one running, its records are still being written, and `agent.messages` belongs to the worker thread (L2). Order is log → model context → transcript. The transcript is REBUILT from the scrubbed log via `reconstruct_events` rather than edited in place: that function is defined as what a live session shows (L4), so leaning on the parity invariant both repaints correctly and guarantees no residue survives in memory for the next viewer. The fresh `replay` goes out through the BRIDGE so every viewer repaints — a removal on the phone must not leave the laptop showing the text — and carries `seen: true`, true by construction because it reaches only clients currently viewing, without which the removal (which counts as activity, so every mirror refetches) comes back as an unread dot for the person who just made it. `TestRedactTurn`.

**Titling** (#175). Two halves, split on purpose (#397). `_title_request` decides at the end of a successful task whether the turn earns a titling call — gated by `_retitle_due`: never when a hand-typed name exists, always when `retitle_forced`, otherwise at turns 1, 3, 7, 15 … and only when the chat has drifted from its current title — and it is the ONLY reader of `agent.messages` in the titler, so it runs synchronously while the turn still owns them (L2) and hands back a copy of the source. `_retitle` then runs off the turn, from that copy: `_title_source` names from the first two and last two messages, not the whole transcript; `_model_session_title` calls `agent.chat` directly — no `run_task` — so the naming turn never enters the conversation or the log, and every failure path keeps the existing name. The new name broadcasts as `session_renamed` with `record=False` (L4). `TestAutoTitle`.

**The chat is idle while the titler thinks, so the owner can act on it meanwhile, and each act outranks the answer (#397).** `Session.title_gen` is the generation of the chat's name; a `TitleRequest` carries the generation it was asked under. Bumped by: `_title_request` when it issues a request (a newer titling supersedes an older one whichever answers first), `_rename_session` on an open chat (before its own write), `_redact_turn` before the rewrite (whether or not an auto title turns out to exist — the SOURCE the titler was handed may quote the removed turn, which is exactly what the scrub deletes auto titles to keep out of the name), and `_launch_retry` (the answer being named is the one being discarded). The stamp is checked three times and each check has a job: after the model call (cheap, drops most stale answers before the log is touched); INSIDE the write — `SessionLog.set_title_if` runs the check under the log's write lock, the lock every other writer of the file takes, so nothing can land between the check and the append; and once more on the loop before the in-memory name is set, for a bump that landed after the append (that act's own record follows ours, so file and memory agree on it). The locked check also confirms the session is still open, so a chat evicted or deleted meanwhile gets no write; and `SessionLog.close` drops its handle (as the rewrite paths do) so any write that does reach a closed log takes the lazy-open path — refused with `SessionLogMoved` once the file is trashed, never a stub recreated. A stale answer is dropped silently: the owner's newer intent stands, and `retitle_forced` is left as that intent set it. `TestTurnEndsAtDone`, `TestWriteAfterClose`.

## Turns

`_launch` routes typed text three ways, checked in this order: a `!` prefix runs it directly as the user's own shell command — no model, no approval gate, mirroring the CLI's `!` escape — so a general `!command` never reaches the model (`!cd` stays the `/cd` alias and is dispatched inside `_run_user_command`); then slash handling; then the model task path (`TestBangCommands`). `/learn` and `/feedback` are rewritten server-side into their flow prompts while other slash text passes through verbatim (`TestLearnCommand`).

**A request the owner made carries his browser's identity; background work carries none (#360).** The bank tools claim PSD2 PSU-present access (lifting the bank's unattended fetch cap) only when `AISH_BANK_PSU_UA` is in their env, and the one place that env comes from is `Agent.plugin_env` — non-secret per-session context (`docs/tools-layer.md`) that reaches a plugin tool's subprocess env and nothing else (never args, never the model). The owner's rule decides who gets it: **a request he made, or delegated ONCE at a moment, carries the UA of the browser he made it from; recurring automations, monitors and email/webhook triggers are background and carry none; the terminal is him, and reuses the last browser UA aish-web saw.** `aish/owner_ua.py` holds it: `clean` (control characters dropped, stripped, capped at 512) is applied where a UA ENTERS — the socket stamp sites — so every copy downstream is valid by construction, and `remember`/`last` keep `<state dir>/owner-user-agent` for the terminal, written through `atomic_write` only on a change (the server keeps its last value in memory, so a typed message costs a string compare, not a file read; a failed write is a stderr line, never a failed turn). Case by case, each with its enforcing line:

| Case | UA | Where |
|---|---|---|
| typed message (incl. queued, or still running after he left) | the stamping socket's — the LATEST stamping socket for the chat, since a stamp persists on the agent until the next one | `_stamp_owner_ua` in `_start_task`, before the busy check |
| Retry | the pressing socket's | `_stamp_owner_ua` at the top of `_retry_task`, before the busy check, so a deferred `pending_retry` carries it |
| chat resumed after a restart | the one the interrupted turn recorded on its `task_start` (`psu_ua`, `docs/session-log.md`); none recorded → cleared | `_resume_interrupted`, before both `_continue_task` and the re-issued `_run_task` |
| one-shot automation (`{"at": …}`) | the writing agent's `plugin_env` at write time, stored as the task file's `psu_ua` | `Agent._schedule_task` puts it into `raw` BEFORE `validate_task`/render, so the card's diff is exactly what lands; `FireRequest.psu_ua = task.psu_ua` on a scheduled fire |
| recurring automation / monitor | none | `validate_task` REFUSES `psu_ua` on a cron task (`_validate_psu_ua`), so no cron file carrying one ever loads |
| "Run now" | the pressing socket's, on the `FireRequest` only — never written to the task file | `_run_now` → `Scheduler.fire_now(task_id, psu_ua=…)` |
| email / webhook trigger | none, whatever `meta` says | `launch_triggered`'s keyword-only `psu_ua`, like `profile`/`monitor`: `handle_trigger` forwards `meta` from any token holder verbatim, so `meta` can never carry it |
| terminal (`aish` REPL and `aish "task"`) | `owner_ua.last()` when stdin is a tty, read per task; cleared when absent or not a tty | `cli.stamp_terminal_owner_ua` before each `run_task` (`docs/cli.md`) |

Two costs the owner accepted, stated so nobody rediscovers them: the UA lands in the git-backed automations folder, which is pushed to his private backup — a device fingerprint, not a credential; and the CLI writes no `task_start` (L2 in `docs/cli.md`), so `aish explain` cannot show a terminal turn's claim. `ClaudeMaxAgent` forwards `plugin_env` to its inner Agent by hand (it is the inner Agent that runs plugin tools) — #311's lesson again; before it did, stamping a claude-max chat would have raised `AttributeError` (checked: the class had neither `plugin_env` nor a `__getattr__`). `TestAttendedContext`; in `tests/test_owner_ua.py`, one class per row: `TestTheStore`, `TestTaskStartRecord`, `TestTypedMessage`, `TestRetry`, `TestResume`, `TestOneShotCarriesTheWritersUA`, `TestValidation`, `TestToggleRoundTrip`, `TestScheduledFire`, `TestRunNow`, `TestTriggers`, `TestTerminal`, `TestClaudeMaxForwardsThePluginEnv`.

`_run_task` brackets the turn on disk, emits `task_start`/`task_end`, and ends the turn at `done`. **A turn is over for the owner when it is over for the client (#397).** `done` is what the browser acts on, and `busy` is what the server acts on; they used to be separated by the post-answer work — the completion push and the titling model call were awaited between `emit(done)` and the `finally` that clears `busy` — so for as long as the titler took, the owner's next `task` was parked in the queue and a `create_issue` was refused as "this chat is busy". On a fast Mac the window was unmeasurable; CI's slow runner hit it. Now the `finally` (`task_end`, `_finish_turn`) is the end of the turn, and `_after_turn` spawns the push and the titling call as a separate task once busy has cleared, held in `_epilogues` (because `session.runner` is the next turn by then) and cancelled at shutdown. `TestTurnEndsAtDone` holds the titler open and acts in the window.

**What makes post-turn work safe** is stated precisely, because the first draft overclaimed it: **the next turn's state is read before busy clears, and everything the owner can do meanwhile outranks the epilogue by construction.** The push reads its own arguments and the viewer set. The titler reads `agent.messages` only in `_title_request`, synchronously before busy clears, so a turn starting meanwhile cannot leak into the name; its model call reads the agent's live `chat`/`model` (a model switched meanwhile just answers the naming question, harmlessly); and what it WRITES — the `title` record, `custom_title`, `title_auto`, `retitle_forced` — is shared with rename, redaction, retry and any later titling, all of which the idle chat now lets through. Those are serialised by the name's **generation** (`Session.title_gen`, see Titling): every act that makes an in-flight answer stale bumps it, and the answer is dropped when the stamp it was asked under no longer matches. Anything added to the epilogue must either read nothing shared or carry the same kind of stamp, or it belongs before `_finish_turn` with the cost of holding the turn stated where it is paid. The tests act in the window with each of those: next message, redaction, retry, rename — including a rename dropped inside the write itself. `_start_task` refuses while busy by emitting `queued` through the bridge; `_stop_task` cancels a task even when it is parked on an approval; `_retry_task` regenerates the last answer from scratch — unless the last attempt DIED with work in hand, which it continues instead (*Retry continues a turn that died*, below) — with `_rollback_transcript_to_last_user` dropping everything after the last `user` event first — and `supersede_last_turn` marking the discarded attempt in the log rather than deleting it (#339), the `retry` step it returns going into the transcript before the replay snapshot so hot and cold put the row in the same place (`TestStopAndQueue`, `TestRetry`, `TestModelError`). `_finish_turn` is the shared end-of-turn drain for both the model and `!` paths.

Approvals ride the same cards over the socket for commands, writes and mutating plugin tools, including the #81 comment semantics — a comment on deny STOPS, a comment on approve HOLDS the original and reworks it (`TestCommandApproval`, `TestWriteApproval`, `TestToolApproval`). `run_command` is framed by recorded `command_start`/`command_end` events so the browser can draw a bounded terminal block and a reconnect replays it identically (`TestTerminalFraming`).

**How long the card was up before it was answered (#306).** Two numbers on the `kind:"command"` decision record, and they are deliberately not one. **`held_ms`** is the gate's own wait — `Bridge.ask` emitting the request to `Bridge.answer` filling the slot — measured on `time.monotonic()` so a clock step or a sleeping laptop cannot author it, and stamped over anything the client sent, because the browser is not an authority on the server's clock. It is always available and it is a FLOOR, not the answer: a card can sit held for an hour with nobody attached to look at it. **`shown_ms`** is the browser's half — from the card actually being RENDERED to the tap ([CARD-LATENCY] in `docs/web-frontend.md`) — and it is the load-bearing one, because it is the number a sub-second value indicts. Trusting the reporter is fine and worth saying so nobody re-derives it: it is the owner's own page, not fetched content, and it can only over-report (render→tap is at least as long as the card was really visible), so a small value is unambiguous evidence and a large one claims nothing.

**Who was there when it went up (#348).** `held_ms` is a floor and it cannot say whether anyone was looking — a four-minute hold reads identically whether the owner ignored an open tab or had no device attached at all, and those two have opposite repairs. **`viewers_at_hold`** is the count of viewers at the moment `Bridge.ask` emitted, stamped by the server over anything the client sent, on exactly the same terms as `held_ms`. Read at the ASK rather than at the answer, because the question is who the card went TO. Zero is real and load-bearing here, so it is written down rather than dropped as falsey: it is the reading that says the card reached no screen at all. It exists because the 2026-09-01 lot.com hold could not be diagnosed from its own record — `shown_ms: 11824` beside `held_ms: 255630` says the device that answered rendered the card 11.8s before the tap and therefore was not attached when it was raised, but nothing recorded whether some OTHER device was. `TestWhoWasThereWhenTheCardWentUp` pins it: zero survives to the record rather than being dropped as falsey, the count is read at the ask, and a client cannot author it.

**And a hold now pushes for owner-started sessions too (#348).** `notify_hold` gated on `origin == "user" or has_viewers`; `has_viewers` was always the whole test, and the origin clause suppressed the push in exactly the case that cost 256 seconds of a 641-second task — he started the work and put the phone down. Having asked for something is not evidence of watching it happen. Two things travel with that: the body of a user-origin push is **terse** — the tool, and the host if a url argument names one, never the card's `preview` — because an owner-started session's cards are the ones quoting his own data and a push body leaves the machine for a third-party service, which is #252's argument one rung further in; and `_notify_done` deliberately did NOT change, because a hold is aish stopped and waiting on him while a finished answer keeps. That asymmetry is stated at both sites so it does not read as an oversight.

The reason this exists rather than being assumed: every design in this area leans on the claim that SOME cards are still worth spending — the rare, checkable-at-a-glance ones — and nothing measured it. What the record held was the negative, that an eleven-line grant card is one he scrolls past and a five-cards-per-search flow trained the tap that lost a purchase. A card tapped blind is WORSE than no card, because it converts a missing control into a *recorded consent* — the trace then says he approved it. Latency collapsing across a card class is the early warning that the class has become a reflex, which is the moment to convert it into a refusal, a specification field or a record line.

**`shown_ms` is absent when it is unknown, never zero and never inferred.** A client that did not report it, a verdict sent for a card this page never drew, a card force-denied at shutdown or by Stop — none of those have a screen time, and a zero would state the exact finding the field exists to detect. A decision no card was drawn for at all (a denylist block, an auto-approval, a triggered-session policy run) carries neither number: a duration for a question never put is a claim the code cannot check. A value that cannot have been measured — a negative — is DROPPED rather than clamped, and the difference is not pedantry: clamping writes a zero, and zero is the most damning reading this field can hold, so clamping would manufacture the finding out of a broken input. A real zero is kept, because that one IS the finding. `card_latency` is the one parser, `TestCardLatency` pins both halves and the absences.

**Driving a page is carded over the same socket, and it had no test at all (#290).** `TestBrowseApproval` drives the site grant end to end: a scripted `browse` OPENS free (reading is free by any route — `docs/browser.md`), the first `browse_act` draws the `approve_tool` card whose preview is the sentence about acting *as him*, approving it presses exactly once and the grant covers the next press, and denying it presses nothing. Browser functions are stubbed at the module boundary like every other tool in this suite; the gate, the card, the bridge and the agent loop are real.

The reason it was believed undrivable is worth keeping, because the evidence read the other way round. A verification run scripted a `browse`, saw the socket go quiet after `session_changed`, found the session log ending at the `call` trace record with no `gate` step, and concluded the card had been requested but never delivered. Neither half supports that: `call` is emitted BEFORE the whole of `_dispatch` — gates and execution — and the `gate` step is a RULES-engine record, not an approval one, so "a call with no gate step" is equally the shape of a tool that is simply still running. It was: with nothing stubbed, `browse` reached a real, headful Chrome.

**And that Chrome was the OWNER's.** `browser.profile_dir()` hangs off `AISH_STATE_DIR`, resolved from the environment at call time, and `create_app` resolved its own `state_dir` without ever publishing it — so a server built with an isolated `state_dir` still opened the profile holding the owner's live sign-ins, and `signin` and `secrets` read their real stores the same way. `create_app` now writes the resolved value back into the environment: the server becomes the single owner of "where state lives", and in production the value is the one it was just read from. Same shape as #254 (`docs/knowledge-layer.md`) — the argument said isolated and the environment decided. `test_the_apps_state_dir_owns_the_browser_profile`.

**The write-back is the permanent design, and only for child processes (#312, decided 2026-10-01).** In-process code never reads `AISH_STATE_DIR` itself: every consumer asks `paths.state_home()`, the one accessor beside `config_home()` (#254), which resolves at call time. `create_app` still writes its resolved `state_dir` into the environment, because a subprocess (the email poller, a curate run, a tool's script) has no other way to learn it. The cost was weighed and accepted: the last `create_app` built in a process wins, which matters only if one process builds two servers, and production never does. A new module that needs the state folder calls `state_home()`; it must not re-read the variable.

**Live watch — a read-only window onto the page a chat is driving (#289 slice 2).** `browser_watch{action: start|stop}` is a **view** message: watching costs nothing and consents to nothing, so it claims no control (#295 P1). It names no chat — the chat is `client.viewing`, because a chat a client is not looking at is one it has no business photographing. `Client.watching` is the whole subscription and `_leave` clears it, so a session switch and a disconnect both end a watch through the one place they already share. `_watch_browse` is **one task per watched chat**, poll-only, ending the moment nobody watches that name: otherwise every background flow pays a screenshot tax on a box that also runs a VM. Frames go straight to each watcher's outbox rather than through the `Bridge` — a live frame is not transcript, is never recorded, never replays and never reaches a viewer with no sheet open, the same reasoning that keeps console I/O out of transcripts — and are **stamped with the session** so app.js's existing firewall drops one belonging to a chat that has left the screen (L5). Identical bytes are dropped before the socket. A client already `BROWSE_WATCH_MAX_BACKLOG` deep is **skipped rather than queued behind**, because the outbox is unbounded and a frame is ~67 KB; `_to_watchers` returns how many took it and the watcher advances "what is on screen" only when somebody did, so a dropped frame stays offerable instead of leaving a slow client on a blank sheet once the page stops changing. Absences are one line and always get through. The capture itself, and the read-only guarantee it rests on, are `docs/browser.md`. `/browser` outranks it and says what it kills: on a deliberate `open`, `browse_tab_count()` rides back on the frame as `closed_pages`. `TestBrowseWatch`.

**Attachments split in two (#231), and a file can be named anywhere in the text (#233).** `_message_attachments` is the reconciliation: files NAMED IN THE MESSAGE first, then anything the composer attached that the text never mentioned. Naming a file the composer also sent is one attachment, not two — the ordinary case now, since ＋ writes the embed into the text. A name matching nothing on disk is not an attachment at all. That also merges two half-mechanisms: `@` completed a path into your sentence with no delivery, ＋ delivered but only as a trailing line.

`_classify_attachments` decides what this backend can take natively and returns the **guidance** — the sentence per file telling the model whether it may look, may read, or must open. That goes to the model. What the browser is shown, and (via `run_task`) what the log keeps, is the **record form** from `to_record_form`: `![[cat.png]]`. One pure function produces it on both sides, so the copy painted and the copy stored cannot drift. `hello` carries `uploads_dir` because only the server knows where its own folder is, and without it the browser cannot turn a bare name into a `/file` request. See `docs/session-log.md` for why the two forms exist and `[ATTACHMENT-NOTES]` for the client half. `TestAttachmentNoteFormat`.

**Narration (#212).** A turn delivers more than once, so `on_delivered` emits a **recorded** `delivery` event ending each interim message the model wrote alongside its tool calls. Recorded, not live-only (L4): `reconstruct_events` replays the same event from the assistant records, so hot and cold agree — and the merging in `_put` cannot glue an interim message onto the answer, because only consecutive `token` events merge and a `delivery` sits between them. It carries the text as well as the boundary, for the client that never saw the stream: a rule-bound turn cannot stream narration at all (Verify buffers every token), and a mid-stream replay drops the stale live tail. See `docs/agent-core.md` for the agent half and `[DELIVERY]` for the client's.

**Turn identity and time.** `_user_event`/`_turn_event` stamp `ts` (epoch seconds) on every LIVE `user` event so a browser landing mid-turn learns the origin of the clock, and mint the `turn` id the delete chip names (L5). Cold replay is deliberately unstamped — it closes every turn it replays, so it can never land a reader inside a running one (`TestTurnOrigin`, `TestTurnTimestamps`).

**Quick replies.** A final answer ending in a question with no chip gets a deterministic fallback set (`apply_quick_reply_net`); `[no-chips]` opts out and is stripped. The system prompt forbids terminating chips ("Never a chip that merely ends the chat") — the user can end a chat at any time (`TestQuickReplyNet`, `TestQuickReplyPromptGuidance`).

**The learning chip (#446).** After the net — the net skips any answer already holding an `aish-reply://` link, so appended first it would displace the Yes/No replies — `_run_task` hands the turn's own records to `learning.at_answer` on a worker thread: it reads back what the turn appended since `span_start` (the log's size, taken before `task_start`), writes a `learning` record (contract §3.19) and says whether "Save this as a lesson?" (`aish-reply:///learn`) rides on the answer. It streams as a `token` like the net's suffix and is on `done.result`; `_notify_done` gets the answer without it. `owner_sent` is the one fact the server supplies: True from `_launch` (a socket's `task`, or a queued one), a pressed Retry and a Retry-chosen continuation; False for a trigger's prompt and restart recovery, which record `withheld: "not_owner_sent"`. Cold replay re-adds the chip from the record. `docs/learning-suggestions.md`; `tests/test_learning.py::TestOnTheWeb`.

**Maths (#391).** The web prompt block says nothing about mathematics: the transcript renders a model's LaTeX with KaTeX (`docs/web-frontend.md`, *[MATH]*) and the PDF typesets it (`docs/export-pdf.md`), so this surface must never ask the model to write around a renderer it has. The Unicode directive belongs to the terminal's block alone (`docs/cli.md`). `TestMathsPromptGuidance` pins the absence here and the presence there.

## Live state, not transcript (L4)

Everything here is `record=False` and re-derived on attach; `reconstruct_events` emits none of it.

- **`role`** — who last acted. Re-derived from live membership.
- **The queue strip is backend-authoritative, all of it.** A chip names a message ONE chat's agent is holding, and Remove dequeues from whatever session the client is VIEWING. It used to be sent only to the client that typed it, which holds right until that client looks at a different chat: the chips live outside the transcript, nothing cleared them on a switch, so they followed the viewer — there Remove dequeued from THAT session (a no-op) while the real message ran on where it was queued, and Edit pulled the text into the new chat's composer while the old chat still held its copy, one send from running it twice. The pending-cd card in the same strip had been reconstructed on attach since #92, so half the strip was already right. Now `_show` re-sends the real `session.queue` after the replay (so a second device sees the queue at all), `_start_task` emits `queued` through the BRIDGE so it carries the session stamp the firewall needs, and `_dequeue` announces `dequeued` the same way — a cancel on the phone takes the chip off the laptop. `TestQueueIsBackendAuthoritative`.
- **`cwd_changed` / `cwd_dequeued`** — the top-bar chip and the pending-cd card.
- **`session_renamed`** — cold replay re-reads the title record instead.
- **`objective`** (#432) — the chat's current objective revision, or none and what the tracker last recorded (`objective.read_view`). Re-read from the log on attach and put into the attaching client's OUTBOX, so it queues in order with live events; `_announce_objective` sends it to every viewer after a tracker call writes anything, after an owner edit (`set_objective`, an ACTION), and after a Retry or a redaction that may have taken the current revision with it. `Session.objective_version` is bumped as each announcement starts, and an attach whose read overlapped one drops its own copy, which may be the older. Stamped with `session` like every chat event. `tests/test_objective.py::TestEmission`. **It carries the plan too (#433)**, as `plan` (`plan.read_view`, or null): the plan sits on the same strip, so one announcement and one ordering serve both. A plan revision the model writes mid-task announces it from the agent's thread (`announce_objective_threadsafe`: the log is read there and `bridge.emit` crosses to the loop, like every event that thread emits); the owner's `plan_action` (`drop` a task, or `replan`) writes his revision (`plan.owner_drop` / `owner_replan`, conditional on the log not having changed) and sets `Agent.plan_owner_changed` while the chat is busy, so the running task hears of it before its next model call. `tests/test_plan.py::TestTheWeb`.
- **A refusal is not a failure** (`_refuse`). An `error` event said two unrelated things and the client could only assume the worse. A TURN FAILURE ends the turn: the live trace closes, busy clears, Retry appears. A REFUSAL of the request just made says nothing about the turn — but went out in the same shape, so `_redact_turn`'s correct "can't delete a message while this chat is working" **tore down the running turn's card**, taking Stop and Retry with it and stranding a task with nothing on screen to reach it. The split already existed in the code and simply was not carried across the wire: a turn failure goes through `session.bridge.emit` (recorded, fanned to every viewer), a refusal goes down the ONE socket that asked and is never recorded. `_refuse` stamps `code:"refused"` at the site that knows (L5); the client shows a toast without touching turn state. `_gone_error`'s `no_such_session` is the pre-existing instance of the same idea. `TestRefusalIsNotAFailure` pins both halves — including that no `bridge.emit` error ever carries the code, which would downgrade a real failure to a toast and hang the turn busy forever.

**The roster plane — session state is PUBLISHED, not polled (#204).** A second event plane, deliberately separate from the `Bridge`. The Bridge carries events belonging to ONE conversation, delivered to whoever is reading that conversation, and replayable as its transcript; a roster fact — "chat A is running now" — is none of those three. Its audience is every client whatever it is viewing, the session firewall would correctly drop it as belonging to another chat, and recording it would put it in a transcript it is not part of. Not really a new channel either: the status pushes it replaces already bypassed the Bridge and wrote straight to each socket. This names it and gives it the three things it lacked.

1. **One publisher.** Every transition calls `_touch`, which builds the row, diffs it against the last row broadcast for that session, and publishes on a change. Before this, exactly two transitions were announced (a chat going idle; a chat holding with no viewers) — so a chat STARTING was never announced, nor an approval ANSWERED elsewhere, which is why a phone went on showing *Needs approval* for a card cleared on the laptop, and a triggered job showed as idle everywhere until something asked.
2. **It diffs**, which makes calling it too often FREE. That is what turns the rule into *"call it whenever you touched a session"* — a rule that survives contact with new code, unlike *"announce at exactly the right moments"*, which four repairs' worth of evidence says nobody can keep.
3. **A sequence number** on every event, on the hello and on the snapshot. A gap means a delta was lost and the client asks for a snapshot; without it the client cannot tell *nothing changed* from *I missed something*, which is the same silent drift in a new costume. The snapshot carries the seq it was taken at, so one in flight cannot overwrite newer rows.

`_roster` holds what has been BROADCAST, never what is true: a snapshot goes to one client and tells the others nothing, so seeding it from one would make the next transition diff clean and never reach them. The row carries only what the server holds IN MEMORY (`name, title, state, origin, cwd`, and `out`) — deriving the LOG-derived timestamps here would mean parsing the session's log, and a chat that just did something has just changed its file, so the parse cache is guaranteed to miss at exactly the moment a transition fires. `out` is a log-derived fact that is nonetheless in memory and therefore allowed (#275): the log keeps its own last-output stamp AS IT WRITES, by the same `_is_output` predicate the listing parses with, seeded from the parse a cold open already performs — so the live row and the listed row state one fact rather than two, and asking costs an attribute read. It is also safe to DIFF on, which a clock is not: it moves only when the chat actually says something, so a row that republishes for it republishes with news. The transition's own time is a different question and rides the EVENT as `at` (#232), never the row: the row is what gets diffed, so a clock inside it would differ every time and republish every unchanged row forever. The client used to stamp arrival instead, which was self-consistent while unread compared against THAT device's seen map — the seen ledger below is what ended that. `notice` marks the two transitions worth interrupting someone about and is never part of the diff; the client suppresses it for the chat it is viewing. `session_deleted` rides the same broadcast — a chat deleted on the laptop used to sit on the phone's list until it refreshed. `session_state` is retired; the client keeps its handler so a new client against an old server degrades rather than going silent. `TestSessions::test_background_hold_sends_waiting_notice`, `test_a_hold_someone_is_watching_is_not_announced`, plus `tests/js/test_roster_plane.js`.

**A transition is published by whoever PERFORMS it, not by whoever asks for it.** The release edge — a held approval answered — is the case that proved it (#204 follow-up). It was published from the message handler, at the instant the answer arrived, which reads as the obvious place and is a tick too early: answering only drops a value into the worker's queue, the parked worker is what actually ends the hold, and until it wakes `state()` still says `waiting`. So the row built there was the row already broadcast, the diff correctly swallowed it as unchanged — and since nothing republishes mid-turn, the chat you had just approved went on sitting in `Needs you` behind a card that no longer existed, for the whole rest of the turn. The publish now hangs off `Bridge.on_release`, fired on the loop thread from the worker's own `finally` after it drops the pending slot, which is the mirror of `on_hold` and covers every exit from a hold there is — approved, denied, or force-denied at shutdown. It also shows what the diff can and cannot do for you: it makes calling `_touch` too often free, but it makes calling it too EARLY silent, so the call belongs after the state has actually moved. A late row is never a wrong one — it states whatever is true when it runs, `idle` included. `TestSessions::test_answering_a_card_publishes_the_chat_as_running_again` pins it by holding the next model call open, so a row that only catches up at `finished` fails.

**Loading a chat is not a transition** (`add_session(publish=False)`, from `_cold_open` only — #275). Every client already holds that row from its hello pager or its list, and the only thing a load changes is liveness `""` → `idle`, which renders identically everywhere. Publishing it anyway is how merely WARMING two chats put two unread dots on the rail after every restart: the client warms the two most recent chats on reconnect so a tap paints instantly, warming cold-opens them, and in a fresh process `_roster` is empty so the first row for every chat diffs as new — while the client, whose only evidence of when a chat last spoke was when a row ARRIVED, read each as an answer it had not seen. Nothing is seeded into `_roster` either; it goes on holding what has been BROADCAST, and the next real transition publishes normally. The same fix covers the `?session=` restore, which cold-opened the reconnecting device's own chat and raised a phantom dot on every OTHER device. `TestWarmingIsNotNews`.

**The seen ledger — unread belongs to the OWNER, not to a screen (#232).** `aish/seen.py`, held in the STATE dir beside the session logs (never `~/.config/aish`, which is auto-pushed to GitHub: a record of when the owner read what has no business there). Unread used to live only in each browser, on the reasoning that looking at something is a fact about a screen — right for a product with many users, wrong for one with a single owner: a chat read on the phone whose dot is still on the laptop is the app making a false claim about the person using it. It rides the roster plane because it is the same kind of fact — belonging to no one conversation, needed by every client whatever it is viewing — and `_mark_seen` is its whole surface: merge what a device offers, `_broadcast` only what CHANGED, and answer `full` with the snapshot.

Two properties carry it. **Monotonic**: a stamp only moves forward, so every merge is a `max` — arrival order does not matter, a duplicate costs nothing, a re-send is free, and nothing can un-read a chat. That is why it deliberately takes **no sequence number** where the roster needs one: a missed roster row described a transition that already happened and is unrecoverable, but a missed mark is repaired by the next connect, when the client re-offers everything the server has not confirmed. The same property is why it needs no receipt (`[ACK-LEDGER]`). **One clock**: the stamps are the server's, and one offered by a client is clamped to `now`, so a phone running five minutes fast cannot write a seen time from the future and hide output nobody has seen — clamping can only leave something unread, which is the direction a mistake is allowed to go. `hello` carries `now` so a device can correct its own skew for the window before its mark is echoed back. A deleted chat's stamp SURVIVES, for the reason `[FORGET-SESSION]` gives on the client: dropping the look is what turns a leftover row into an alarming one. `TestSeenLedger` pins the wire; `TestMonotonic`, `TestOneClock` and `TestStorage` (`tests/test_seen.py`) pin the two properties and the file behind them. Client half in `[SEEN]`.

**The pin ledger — the same finding, for a toggle.** `aish/pins.py`, beside the seen ledger in the state dir. "Available offline" lived only in each browser's IndexedDB mirror, so a chat pinned on the laptop sat in the date buckets on the phone — a per-device copy of an owner-fact. `_mark_pin` mirrors `_mark_seen`'s choreography exactly (fold offers in, broadcast only what changed as `pin_marked`, answer `full` with `pin_ledger`), but the MERGE cannot be a max, and that difference is why **no client time is trusted here, not even clamped**: the seen clamp is safe because a max-merge has a safe direction for a clock mistake (something stays unread), while last-writer-wins has none — clamping a future stamp to now would *promote* a stale toggle to the freshest action, and honouring a slow clock would silently discard the owner's newest one. So offers carry no time, every accepted toggle is stamped as it lands, and the semantics are last-RECONNECT-wins — for one owner, indistinguishable from last-action-wins except when the same chat is toggled opposite ways on two offline devices. Two more rules carry it: a **seed** (the upgrade migrating a device's pre-sync local pins) lands only on a name the ledger has never heard of, so a device offline across the upgrade cannot resurrect a pin the owner deliberately removed elsewhere (`TestSeedsOnlyIntroduce`); and the cap drops the oldest UNPINNED tombstones first, never a pin — an entry the owner is standing on (`TestForgettingDropsTombstonesFirst`). Offers naming a chat that no longer exists are dropped before the merge (`_session_exists`), and `_delete_session` drops the entry outright: unlike the seen stamp, which survives so a leftover row cannot turn alarming, a pin entry protects nothing once its chat is gone, and pins are exactly what the trim never removes — a resurrected one would be a permanent leak. `TestPinLedger` pins the wire; `tests/test_pins.py` (`TestOneClock`, `TestStorage` and the two above) the properties. Client half in `[PIN-SYNC]` (`docs/web-frontend.md`).

**A third property: forgetting SAYS so (#378).** The map is capped at `SEEN_MAX` (300), and eviction used to be silent — which made it the very defect `[FORGET-SESSION]` was written about, arriving through the back door. Unread is *output newer than the last look*, so throwing the look away is what turns an old, read chat into an ALARMING one. The owner ran 300 stamps against **576 listed chats**, and every stampless chat had last spoken before the oldest surviving stamp — no exceptions, which is what pure age-eviction predicts and nothing else does. It presented as a deploy bug for a reason that belongs to the client and not to this file: the affected rows rank ~240th by recency and the rail's offline mirror holds 200, so only a server-fed list paints them, and a restart is what makes the client ask for one. So the ledger carries `floor`: the newest look it has ever forgotten, persisted beside the stamps, raised by `_trim` to the newest entry it dropped, and monotonic for the same reason the stamps are. It rides `seen_ledger` always and `seen_marked` only when it MOVED — a field that appears on every message stops being read as the event it is. `merge` also declines a mark below the floor for a name it does not hold: the floor already covers it, and taking it would only hand it back to the next trim. What the floor claims is exactly what the per-chat stamp claims, applied to what was dropped: *every forgotten look happened at or before this instant*, so output older than it has been read. The residue is two cases, both stated as POLICY rather than discovered later: a chat read and then written to again, both before the floor, reads as read; and a chat NEVER opened whose output predates the floor does too — its dot expires after `SEEN_MAX` other looks (about five weeks at the owner's rate) instead of standing forever. A ledger written before the floor existed and sitting at the cap is seeded on load from its oldest surviving look, because a fix that waits for the next eviction ships looking exactly like no fix at all. `TestForgettingSaysSo` (`tests/test_seen.py`) and `TestSeenLedger::test_forgetting_a_look_is_published_with_the_ledger` pin it.

**Hello rows carry liveness (#203).** Every `_show` already scans the recency list for the swipe peeks; those pages now also carry each chat's `state` from the in-memory `self.sessions`, which is what lets the client re-derive its attention count on every boot, reconnect and switch instead of only when the rail is opened. Free — one dict lookup per page, no extra disk work. `test_hello_pager_rows_carry_liveness`; client half in `[ATTENTION]`, `docs/web-frontend.md`.

**Session firewall (#182).** The fan-out stamps every live delivery with the bridge's session name and the client drops a stamped event naming anything else, closing the switch window where the old session's tail kept rendering into the new view. Exempt: `hello` (the switch mechanism), `session_state` (sent only to non-viewers), `session_renamed` (by name, idempotent). The stamp rides ONLY the delivery — the recorded transcript stays byte-identical to `reconstruct_events` (L4), and replayed events bypass the gate anyway. `TestSessionStamp` + `tests/js/test_choreo_session_firewall.js`.

**Ghost trace cards.** A record kind with no renderer does not degrade to "renders nothing" — it opens an empty live trace card with a running ticker. Renderless governance records therefore need both halves (log-only emit AND membership in `RENDERLESS_STEPS`); `TestNoGhostTraceCards` verifies it where the artefact would actually appear, live and on cold replay. See `docs/trace-records.md`.

**Render errors.** `_render_error` writes a durable `kind:"render_error"` trace record and hands the model a note ONLY when the failure was in a live turn — merely opening an old chat whose images were evicted must not grow it a turn — and drops a report identical to the last one as the backstop no client can route around (`TestRenderErrorReports`).

## Mid-task steering and output

**Steering (#95).** A `/cd` or a message typed while a task runs is applied BETWEEN steps, not only after it. The agent's step loop polls two get/drain callbacks at the top of each iteration (`check_pending_cwd`, `check_pending_messages`, wired over `session_holder`) — lock-free because the event loop is the sole setter and the worker thread the sole consumer (L2). `check_pending_cwd` get-and-clears `Session.pending_cwd`; the agent rebases and rebuilds `messages[0]`. `check_pending_messages` drains the text-only queue items and injects each as a mid-task user turn: an echo plus a distinct `injected` trace step that renders live AND replays, with the text appended straight to `self.messages` and NOT logged as a conversation record, so cold replay does not split the turn. Trade-off: injected steering is not carried into `--resume` history. Items with attachments — and `!` commands, which must run through the user-direct path, not as model prompts — stay queued and run as a normal follow-up at `_finish_turn`.

**The final answer polls too.** The loop top only runs before a model call, so a message typed while the ANSWER was being written used to miss the turn entirely: it ended blind to them, `_finish_turn` launched the first queued message as a new task, and the rest were injected into THAT one (session-20260929-214924: "add pictures" and "and links" typed during an answer — the answer ignored both, and "and links" surfaced only as a row inside a trace card that then collapsed). Now a text-only answer drains the queue before it is logged; anything there turns the answer into a step (`Agent._answer_superseded`): a HELD answer (rules bind the turn) was never shown, so it is dropped and the model told so (`ANSWER_WITHHELD_FOR_MESSAGES`); an unbound one already streamed, so it is logged as an interim delivery stamped `delivered: true`, and `reconstruct_events` keeps stamped deliveries past the one-acknowledgement cap — otherwise a reload erased an answer he had read. Either way the messages are injected and the turn goes on. **What is still queued at `_finish_turn` starts together**: `_take_queued_run` joins every plain message at the head into one prompt and retires each chip by name with `dequeued` (the joined echo matches none of them); a `!` or `/` command still runs alone, in order. The frontend draws an `injected` step as a `msg user steer` bubble as well as the trace row, so the owner's own words stay visible after the card collapses. `TestMidTaskSteering`, `test_queued_messages_left_at_turn_end_start_together`, `test_trace_inspector.js`. Every cwd move flows through the single `on_state("cwd", …)` handler, the ONE place that emits the `workspace` marker and retires the queue card. claude-max runs its own loop, so mid-task polling does not apply there. `TestReconnect`, `TestWorkspace`.

**Live-output coalescing (#109).** `StreamCoalescer` batches `run_command`'s per-line output into fewer `stream` events (50 lines / 16 KB / 0.1 s / command end) so huge output cannot lock the tab with per-line DOM appends. LIVE-ONLY — logged output and cold replay are untouched and the frontend re-splits on `\n`, so hot/cold parity holds (L4). `TestStreamCoalescer`.

**Skills are rescanned per task**, so a skill added after boot is advertised without a restart (`TestSkillsRefresh`).

## Triggered sessions and ingress

A `Session` carries an `origin` (`user`|`schedule`|`email`|`webhook`) + `trigger_meta`, persisted as a `kind:"origin"` log record (L5) so a cold-reopened automated session keeps its provenance; it rides the listing and draws the provenance glyph on a rail row (`TestOriginPersistence`). **`POST /trigger`** (`handle_trigger`) is the programmatic ingress: `open_session(None, origin, meta)`, `add_session(default=False)` so an overnight trigger never becomes the bare-connect landing session, then `_run_task` on the session's own bridge with no client — events buffer into the transcript, observable when the owner opens it (`TestTriggerEndpoint`).

**Ingress hardening (#178 P1-10).** Three guards run after the token/origin gates and BEFORE any session exists: `meta.dedup_key` idempotency (a repeat POST answers 200 with the existing session name + `deduped:true`; a bounded in-memory LRU+TTL — durable cross-restart dedup deliberately stays at the SOURCE, the poller's Gmail label; no key → every POST fires, so existing clients are unchanged), a per-origin token bucket, and a cap on concurrently RUNNING triggered sessions. Both limits answer 429 + `Retry-After`, safe by the poller's contract: a message is marked processed only AFTER a successful trigger, so a refused delivery retries next poll. All three knobs are `create_app`-injectable (`TestTriggerHardening`).

**Per-trigger model override (#186).** The payload may name a `model`; `open_session(model_override=…)` builds it FIRST — before `SessionLog.new`, so a bad spec leaves no orphan log — and swaps chat/model/provider on the fresh Agent. It exists for privacy-scoped automation and therefore FAILS CLOSED (L6): an unbuildable override answers 503, never a silent fallback to the server's possibly-cloud default, which would be exactly the leak the override prevents. Resumed sessions ignore it; a claude-max server refuses it.

### Capability policy: two reasons a mutation may skip its card

`_auto_safe(name, args, origin)` plus a branch atop `approve_tool`, wired through `make_web_approvers(..., get_origin=…)`. It returns the NAME of the policy that licensed the run, or None. There are two, and they are **deliberately not one list**, because they are safe for unrelated reasons:

**Origin-scoped — `TRIGGERED_SAFE_TOOLS` (relabeling).** Safe *because* nobody is at the keyboard. Draft-and-hold, built out of the existing gate rather than a bespoke hold flow: every other mutation in a triggered session falls through to the normal card, which simply BLOCKS pending until the owner opens the session and answers — which is what makes the notification below load-bearing rather than a nicety. In the owner's own session he still sees these cards, because there he is the one who can cheaply say no.

**Consequence-scoped — `recipients.owner_scoped_send`: `gmail_send`, draft or live, when every recipient is the owner.** **Recipient-scoped autonomy**: a send that can only reach the owner's own inbox carries no exfiltration risk. That safety is a property of the ACTION, so it holds in EVERY origin — see `docs/agent-core.md`'s recipient-scope section for why it stopped being a conjunct of the triggered policy (#377), and `recipients.py` for the parse. A reply with no explicit `to` is NOT auto-safe: its recipient is not verifiable from the args.

When either policy licenses a call, `approve_tool` returns `Licensed(policy)` rather than `True` (the CLI's approver does the same): the agent needs to know no card was drawn, because it announces every cardless change in the answer itself (`docs/agent-core.md`, *A change with no card is announced by aish*).

`TestTriggeredCapabilityPolicy` covers both halves; `tests/test_recipients.py` pins the cross-surface agreement.

**The shell gate consults an origin-scoped prefix set (epic #142 hard requirement 1).** `ask_approval` auto-approves from `consulted_prefixes()`: in a `user` session that is the persistent allowlist plus the session's grants, exactly as it always was; in every other origin the persistent `allow.txt` is never read — an entry there was approved by the owner with himself at the keyboard, and that safety argument does not travel to a session nobody watches (L6) — so only the read-only classifier and the grants the owner made on THIS session's own cards auto-run. Two corollaries keep the card honest (#265): `prefix_suggestions` is computed against the CONSULTED set, so a prefix sitting unconsulted in `allow.txt` does not hide the Session/Always buttons that could actually silence the card; and "Always allow" in a non-`user` origin also arms the session set, because the per-call `allow.txt` reload it relies on in a user session is not consulted there. `TestUnattendedShellPolicy`.

**`email_poll.py`** — the Gmail→`/trigger` poller. Polls the bot mailbox via the `gws` CLI for inbox mail FROM the owner's addresses and requires `dmarc=pass` from Gmail's own Authentication-Results (SPF alone validates the envelope, not From), builds the recipient-scoped-autonomy prompt, and POSTs `origin=email` with `meta.dedup_key` = the Gmail message id. Durable dedup is the `aish-processed` label, applied ONLY after a successful trigger — a failed POST or a 429 leaves the message unlabelled so it retries next poll; a label-ensure failure aborts the whole run to avoid a re-fire loop. Token from the Keychain with an env fallback. A message from a disallowed sender or one failing DMARC is marked processed WITHOUT triggering — dropping it silently would re-read it forever (`TestSkips`). A missing token refuses to run at all rather than posting unauthenticated (`TestTrigger`). The prompt itself is pinned by test, so the owner address and the auto-approve contract it states cannot drift from what `_all_recipients_owner` actually enforces (`TestPrompt`).

Testable by construction: every effectful edge is a `run_poll(gws=…, post=…, notify=…, now=…)` parameter seam, so `tests/test_email_poll.py` needs no subprocess, no network and no sleeps. Its `trigger()` helper takes an `origin` for other automation entry points; `curate.py` used it to post `origin="schedule"` until the judge loop moved out of sessions entirely (it now calls `backends.make_chat` directly). Nothing POSTs `schedule` today; the one producer of that origin is the in-process scheduler below (§Scheduled automations), which enters through the same seam without HTTP.

**gws credentials must come from the poller's launchd environment.** `default_gws` runs bare `gws` with inherited env, and gws's default credential store is the macOS Keychain — whose secret needs a GUI prompt a launchd child can never answer, so from launchd it presents as "no credentials" while a terminal login looks fine. From 2026-08-16 to 2026-09-05 the poller failed exactly this way every 3 minutes, visibly in its own log and nowhere else. The deployment (com.aish.email-poll.plist `EnvironmentVariables`) must therefore carry `GOOGLE_WORKSPACE_CLI_KEYRING_BACKEND=file` plus `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` pointing at a file-backend account store (this machine: `~/.config/gws-accounts/<email>/`, written by `~/.config/aish/tools/_gws/login.sh`). Any future non-wrapper gws consumer needs the same two variables.

**A component whose job is to notice mail must itself be noticeable when it stops (#362).** The outage above lasted 20 days because a failed poll and a quiet mailbox looked identical from outside the poller's own log. `record_poll_health` counts consecutive polls whose mailbox LISTING never came back — the state in which no trigger can fire, and the exact shape of that outage — in `email_poll_health.json` under `AISH_STATE_DIR` (on disk because the poller is one-shot under launchd). At `FAILURE_STREAK_NOTIFY_AT` (10, ≈30 min) it sends one Pushover push through `notify.pushover` — already a silent no-op when unconfigured, and any raise is caught, since the poll loop outranks any notification — then at most one more per day while the streak continues; a clean listing resets both the count and the notified stamp so a NEW streak notifies again. The daily stamp records the ATTEMPT, not confirmed delivery, so an unconfigured notifier costs one no-op a day rather than a credential probe per poll. No auto-remediation, and the push states only what was observed (N consecutive failed polls, and where the errors are). The notifier and clock are `run_poll(notify=…, now=…)` seams beside the existing two, so the tests use an injected fake clock and no sleeps (`TestFailureEscalation`).

## Scheduled automations (epic #142 W2, S1–S6)

`schedule.py` (the store and the time logic — pure, no server import) and `scheduler.py` (the loop). The problem it closes: mid-task, with a portal down until 22:00, the owner typed *"check after 10pm"* and aish could only set an Apple Reminder and ask him to come back. Now it proposes a one-shot automation on a card, and at that time the server runs it as an ordinary triggered session.

**An automation is one inert JSON file**, `<config home>/automations/<id>.json` (`schedule.automations_dir()`, resolved at call time through `config_home()`, so `AISH_CONFIG_HOME` and the suite's isolated home move it). Fields: `id`, `note`, `prompt`, `schedule`, `enabled`, `created`, and optionally `model`, `allow` (shell prefixes), `sites` (hosts the run may press things on as the owner), `cwd`, `roots`, and — on a one-shot only — `psu_ua`, the browser UA of the owner who delegated it (§above, #360; `to_dict` emits it only when set, so `/tasks enable|disable` round-trips it). A task has exactly one schedule shape: `{"at": "<ISO local datetime>"}` (a one-shot) or `{"cron": "<5-field expr>"}` (recurring, §Recurring automations below), optionally with `"until": "<ISO local datetime>"` (§Ending: `until`, S5) and/or `"from": "<ISO local datetime>"` (§Starting: `from`, S6) beside the cron. `validate_task` fails CLOSED: an unknown key, another schedule shape, a bare date, an empty or denylisted prefix, a bare interpreter prefix (which `_prefix_approves` would never honour, so the card would offer a grant that does nothing), a site that is not a bare host, and a `cwd`/`roots` entry containing or inside the automations folder are all refused. `load_tasks` fails per FILE: an unparseable or invalid file is skipped, logged, kept in the scheduler's `problems` and its state file, and pushed once per version of the file — a broken file is an automation the owner believes exists and that will never run, so it is never silently absent (`TestAutomationValidation`, `TestAutomationStore`). `schedule.describe` renders what the creation card says in words (`TestAutomationCardMeaning`; the card itself is §Creating one, below).

**The fired ledger is the one authority on fired-ness**: `<state dir>/scheduler/fired.json`, keyed `"{id}:{occurrence}"` — a one-shot's `at`, a cron task's individual occurrence — normalised, written whole through `atomic_write`. Because the key carries the time, an owner who hand-edits `at` has re-armed the task, and a cosmetic respelling of the same time has not. **Code never writes the owner-authored folder** — there is no `enabled: false` write-back after a fire — so the task file stays exactly what he approved and the ledger is the only place "already ran" lives. Cross-restart idempotency is therefore the scheduler's, as #187 always said it must be; the server's dedup LRU only stops a double fire inside one process. An unreadable ledger (present but corrupt) fires NOTHING until it reads again, is never written over, and pushes once — "aish does not know what fired" must not be read as "nothing fired" (`TestFiredLedgerKeying`).

**When it is due.** `next_due(task, fired, now)`: due when `now >= at`, not in the ledger, and `now − at ≤ STALE_AFTER` (24 h). A one-shot that comes due while the daemon is down fires on the next start — the loop's first tick runs at startup — and the run's prompt states both the scheduled time and the actual fire time, so a late fire is observed rather than inferred. Past the bound it is EXPIRED: recorded, pushed once, settled durably (a restart does not push it again), and never fired (`TestAutomationStaleness`).

**The loop.** `Scheduler.run` ticks every `TICK_S` (30 s) from `startup`, beside the resumer, and is cancelled in `shutdown`. A tick reloads the task files only when the PER-FILE signature (name, mtime, size) changed — a directory's own mtime does not move on an in-place edit (`TestAutomationReloadSignal`) — then fires what is due. Every stat, read and ledger write goes through `asyncio.to_thread`. One tick at a time: a second tick arriving while the first is inside an open returns at once, because two could otherwise both read a key as unfired before the dedup store is written (`TestSchedulerFires`).

**A run enters through the same seam as `POST /trigger`.** `WebServer.launch_triggered` is the post-token, post-Origin half of `handle_trigger`, extracted so the two ingresses are one function: dedup check → per-origin rate bucket → concurrency cap → `open_session` (off-loop) → `add_session(default=False)` → `_run_task`. `handle_trigger` maps its `TriggerOutcome` onto the same 200/429/503 bodies it always returned, and `TestTriggerEndpoint` / `TestTriggerHardening` are unchanged. `fire_scheduled` is the scheduler's adapter: `origin="schedule"`, `meta.dedup_key` = the ledger key, the task's `model` as the override (an unbuildable one fails closed exactly as #186's 503 does — never a silent fallback), and the task's grants as a `RunProfile`. A schedule-origin session is still never resumed (#187, above).

**Open, then mark — and the window that ordering accepts.** The ledger is written immediately after the seam reports a session was opened, the same order `handle_trigger` uses for `_dedup_store`, so a failed open never poisons the key. Marking after the run COMPLETES instead would re-fire a crashed, half-done run as a duplicate. A process killed between the open and the ledger write fires the run again after the restart; that window is accepted. If the ledger write itself fails, the key is still remembered in-process and the failure is recorded.

**A refusal is not a fire.** A rate or concurrency refusal marks nothing; the next tick asks again, and the run fires when the cap frees (`TestSchedulerRefusals` drives refused → refused → admitted explicitly). Still refused when `at + STALE_AFTER` passes, it expires with the last observed refusal in its record. An open failure (an unbuildable model, a `cwd`/`roots` entry that no longer exists — checked before the open and again when the profile is applied, `RunProfileError`, before any record is written) is recorded and pushed once, then retried every `OPEN_RETRY_AFTER` (5 min) until the deadline — the owner may fix it in time.

**What aish says about a run that did not happen** is only what was observed (L8): *"automation X did not start: model unavailable: no such model"*, *"…had not started 24 h later; it was last refused with: too many concurrent triggered sessions"*, or, when the scheduler never saw an attempt, exactly that — *"aish did not observe an attempt to start it"* — never a guessed cause such as "the daemon was down". Each such run leaves a record in `<state dir>/scheduler/state.json` and at most one push per run key and KIND — one *"did not start … will try again until …"* and one terminal *"did not run … It will not run"*, so a run that never recovers still ends on the terminal sentence. After a restart the expiry names the refusal an earlier process recorded, and says no attempt was observed only when no record exists (`notify.pushover`, a silent no-op when unconfigured, and a raising notifier is caught so it can never stop the loop). A state file that exists but cannot be read is never written over; the cost is that pushes already sent may be sent again after a restart (`TestSchedulerMalfunctions`, `TestSchedulerRestarts`).

**The run's grants are its profile and nothing else.** `RunProfile` enters at `open_session` as SESSION-scoped grants, into the same sets the owner's own live answers fill: `allow` into `Agent.session_prefixes` — the only non-read-only set the shell gate consults in a non-user origin (§Capability policy, #449) — and `sites` into `_approved_sites` through `restore_site_grants`, memory only (no `site_grant` record, so nothing about the run outlives it). `cwd` re-anchors the run unannounced (the `/cd` note would claim the owner typed it), `roots` are trusted for the session. The persistent `allow.txt` is never consulted there. `TestScheduledRuns` drives a real run: the profile's `touch` runs cardless, a `mkdir` that `allow.txt` grants to the owner's own sessions holds on a card.

### Recurring automations (S2)

`{"cron": "<expr>"}` makes a task recur. **The cron is aish's own** (`schedule.parse_cron`, `cron_next`, `cron_prev` — no dependency): five fields, minute hour day-of-month month day-of-week, each a `*`, `*/n`, a number, a range `a-b`, a stepped range `a-b/n`, or a comma list of those (`1-5,7`). Vixie semantics, including its dom/dow rule: when NEITHER day field begins with `*`, a day matches if EITHER matches (`0 9 13 * 5` is the 13th and every Friday); otherwise both must, which for a plain `*` is no restriction — so the common shapes (`0 7 * * *`, `0 * * * *`, `0 9 * * 1-5`) never meet the OR. Day-of-week 0 and 7 are Sunday. Naive local wall-clock, like `at`. Names (`MON`, `JAN`), `@daily`, a seconds field, `L`/`W`/`#`/`?` and a bare `N/step` are refused at creation AND at load, never guessed at (`test_schedule_cron.py`). **Both searches are bounded** by `CRON_HORIZON` (4×366 days) and raise `NoOccurrence` past it, so a valid-looking but impossible expr (`0 0 30 2 *`) costs one bounded scan and can never hang the tick; `validate_task` requires a next occurrence (after `now` at creation, after the loader's clock at load), so such a file is an `InvalidTask` at creation and a `LoadProblem` at load, pushed once per version of the file like any other (`TestTheHorizon`, `TestRecurringValidation`). The bound's one known edge: a leap-day-only expr cannot be validated across 2100, the one 8-year gap between leap days. A cron task never settles: `Task.key` raises for it (there is one key per occurrence, `Task.key_for`), so any site still asking for THE key fails loudly rather than misfiring. `Task.deadline` is None for every cron task, because its occurrences are given up one at a time as the next arrives; one with an `until` does END, but that ending is derived in `due()` every time and stored nowhere (§Ending: `until`).

**When it is due** (`schedule.due`). Due iff the LATEST occurrence at or before now is unfired — so at most the latest missed occurrence ever fires, which is #5's "at most one immediate run per task missed during downtime". There is no staleness clamp: lateness is observed, and the run's prompt states the occurrence and the actual fire time (*"Scheduled for 2026-10-15 09:00 (recurring: `0 9 * * *`); fired at 2026-10-15 13:00:00"*). Two floors keep "the latest occurrence" honest, and both are additions to the reviewed spec, made because without them the rule misfires. (1) **`since`, when this schedule began to exist**: without it, a `0 9 * * *` task approved at 10:00 would fire at once, since today's 09:00 is unfired. It is the task file's mtime when the scheduler first sees that (id, expr), capped at now, kept in the state file's `cron` map, and never the free-text `created`. The card's commit writes the file, so the mtime is the approval; a task written at 08:59:59 and first ticked at 09:00:20 still owns 09:00. Editing the expr or re-enabling the task sets a new `since` (that edit's mtime), so an edit re-arms the task and never back-fires an occurrence that passed under the old expr or while it was disabled. **Editing `until` or `from` does NOT re-seed it — deliberately**: the key is (id, expr), and `_note_cron_schedules` ignores both window fields. So moving either edge to admit occurrences that already passed fires ONE bounded downtime-style catch-up (the latest in-window occurrence, late, both times in the prompt) plus a `skipped` record — §Ending's extension and §Starting's edited-earlier `from`. Do not "fix" this by re-keying on the window: that is a design choice, kept because it is bounded and recorded, not an oversight. A deleted or disabled task forgets it; a file that is only transiently INVALID (a typo saved mid-edit, a `LoadProblem` while its file still exists) keeps it, because forgetting would re-seed `since` at the fix and silently drop the slot the typo spanned. An entry whose `since` does not parse, or that is not an object at all (a hand-edited `state.json`), is treated as absent and re-seeded from the mtime rather than wedging the task or failing the tick (`TestRecurringStateRobustness`). Without a `since` nothing past is provably a miss, so nothing is due — the fail-closed direction.

**Floor (2), the last fired occurrence**: an occurrence at or before the newest one the ledger holds for the task is never due. This floor is what makes the pruning below safe, and it is what makes the fall-back hour fire once at any interval (below). Accepted: a file copied in with its mtime preserved (`cp -p`) gets an old `since`, and its latest past occurrence fires at once — bounded at one run, exactly as a downtime catch-up is. Also accepted: a wall-clock rollback larger than the DST hour leaves `since` or the last fired occurrence in the local future, and the task's cron runs are silent until the clock re-passes them — fail-closed and self-healing (`TestRecurringDue`, `TestRecurringFires`).

**Skipped occurrences leave a record and no push.** When the latest occurrence is due and older ones in `[since, latest)` that come after the last fired (or already-recorded) occurrence will now never fire — the daemon was down over several slots, or a rate/capacity refusal outlasted its occurrence until the next one arrived — the scheduler appends ONE `kind:"skipped"` record to `state.json`, keyed by the range (`<id>:skipped:<from>/<through>`, with `count`, and `count_capped` past `SKIP_COUNT_CAP`), and advances the task's `skipped_through`, so a restart, a re-tick or a later range never re-records it. The scan starts at the floor — `max(since, from)` (S6) — and never goes further back. (The record's own `"from"` key is the start of the skipped RANGE, a different object from `schedule.from`; grep for one finds the other.) No push: the run that fires instead, or the open-failure streak, is what reaches the owner. **Known gap, stated rather than absorbed:** a cron task refused on rate or capacity at EVERY occurrence pushes nothing — it leaves a skip record per range and no notification, because S1's rate/cap refusals never pushed and a cron task has no expiry to end on.

**Per-occurrence ledger, pruned in its one writer.** `_mark_fired` prunes inside the same read-modify-write that records the fire (`schedule.prune_ledger`), so the ledger keeps its single writer. For a CRON task it keeps the newest `LEDGER_KEEP_PER_CRON_TASK` (4) keys of that exact id, matched exactly (`eon` never touches `eon-invoices`), and leaves unparseable keys alone. Safe because the last-fired floor means an older key is never consulted. **A one-shot key whose task file exists is never pruned** (`protected`): a pruned one-shot key would read as never-fired, then EXPIRED, then push a false *"did not run"* about a run that ran — `test_a_live_one_shot_key_is_never_pruned` shows the bug that pruning it would cause, and that the code refuses to. `_fired_here` (the in-process copy) is pruned the same way. The in-memory `_retry_open_at` / `_last_refusal` entries for an occurrence are dropped once a later occurrence becomes the latest (`_forget_superseded`), because nothing reads them after that (`TestRecurringLedger`).

**Open failures push per TASK as a streak, never per occurrence** — the email poller's failure-streak pattern (#362, above). The first open failure of a streak pushes; further failures push at most once per `STREAK_RENOTIFY_AFTER` (1 day), stamped on the attempt; a successful open ends the streak, so the next failure is a new streak and pushes again. The streak lives in `state.json`'s `streaks`, never in `notified`: a per-occurrence key there would flood the 200-entry list and evict unrelated dedupe entries, such as an interruption's (`test_occurrence_keys_never_reach_notified`). The push names the next occurrence, never a deadline: *"automation X did not start: model unavailable: … aish will keep trying this run until its next scheduled time, 09:00 Fri 2026-10-16. Runs of it have failed to start 3 times in a row since 2026-10-15 09:00:10."* — what was observed, and nothing about why. A one-shot keeps S1's per-key *"will try again until …"* push unchanged (`TestRecurringStreakPushes`).

**Daylight saving: the actual behaviour, nothing refused.** The clock is naive local time, and so are the occurrences and the ledger keys. *Spring forward* (e.g. 02:00 → 03:00): a slot in the skipped hour (`30 2 * * *`) is the latest occurrence at the first tick after the jump, so it fires then, late, and the prompt states both times (scheduled 02:30, fired 03:00:00). *Fall back* (03:00 → 02:00): the repeated hour fires ONCE. A daily slot inside it fires once because both real passes are the same naive occurrence, so the same ledger key. A sub-hourly slot (`*/5`) fires once per slot because, on the second pass, every occurrence is at or before the last fired one (02:55 from the first pass), and that floor holds even after K=4 pruning has dropped the early keys. The tables are `TestDaylightSaving`, which builds the naive datetimes directly and needs no tz database.

**The card** says the expr AND the next two occurrences in local time (*"Runs on the schedule `0 9 * * 1-5` — next: Fri 2026-10-16 09:00, Mon 2026-10-19 09:00 — each time in a new chat with nobody watching"*), the same profile-in-words as a one-shot, and, in place of the one-shot's give-up time, what happens to runs that cannot start or were missed. The owner approves the behaviour, not the syntax. `schedule_task` takes `cron` as the alternative to `at`, exactly one of the two (`TestRecurringCard`, `TestScheduleTaskRecurring`). The LATER section of the core prompt is unchanged: "for something later or at a time" already routes "every weekday at 9" to the tool, and the tool's own description names the recurring case.

### Ending: `until` (S5)

The defect (#456): a daily Paris-trip monitor was created with *"expires after Nov 14 — performs no actions after"* on its card and in its prompt, while the stored schedule was a bare `0 9 * * *` that fires forever — a guarantee in aish's voice that nothing enforced, with each run's model reading the date out of its own prompt where structure belongs. **`"until"` is that end as a field**: optional, cron only, an ISO local datetime read by the same rule as `at` (`parse_at`; a bare date is refused, an offset is converted), inclusive. `validate_task` refuses it beside `at` or alone. Two checks run at CREATION only, gated on `now` exactly as `at`'s "not in the future" is: an `until` already past, and an expr with no occurrence after now and at or before `until` (a card that could never run). Neither is ever a load problem: a loaded file past its `until` is an automation that ENDED, and making it a `LoadProblem` would push "not runnable" per mtime and list a PROBLEM row for every ended file (`test_a_past_until_is_a_creation_error_and_never_a_load_problem`, `test_the_scheduler_loads_an_ended_file_with_no_problem_and_no_problem_push`). `Task.until` is threaded through `Task.schedule` and so `to_dict`, because `/tasks disable`→`enable` rewrites the file through validate→replace→render and a missing arm would silently strip the field (`TestRoundTrip`).

**ENDED is derived, never stored.** `settled` still holds one-shot keys only, and no code writes one for a cron task. `due()` searches at or before `min(now, until)`, so an occurrence strictly after `until` is never the answer and one exactly at it is (no off-by-one code: it falls out of `cron_prev`). Before `until` nothing changes. Once `now > until` every arm is `ENDED` — outranking `DISABLED` and every PENDING-shaped arm, which would read as alive — except one: **the final occurrence keeps the one-shot's grace.** The latest occurrence at or before `until`, if still a provable miss (enabled, at or after `since`, after the last fired one), stays `DUE` through `until + STALE_AFTER` (the same 24 h and the same reason: the covered period's work is still wanted, late), and fires with both times in its prompt, which now also names the end (*"Scheduled for 2026-11-14 09:00 (recurring: `0 9 * * *`, until 2026-11-14 23:59); fired at 2026-11-15 02:00:00"*). The arms at `now > until`: final fired → ENDED; unfired inside the grace → DUE; unfired past the grace → ENDED with `final_missed`; `since` None or the final before `since` → ENDED; the final at or before the last fired one → ENDED; no occurrence inside the horizon → ENDED; disabled → ENDED (`TestDueAtTheEnd`). Skip scans never cross `until`, because the occurrence they run up to never does. Open-failure retries stop at the grace edge — a run that can never become due is never asked for again — and the task's open-failure and monitor streaks are dropped with the ending (`test_retries_and_the_streak_stop_at_the_grace_edge`); a streak push about the final run names the grace edge, not a next occurrence that will never come.

**The ending is pushed ONCE, unconditional of `notify`** — lifecycle class, the expired push's carve-out (§Monitors: `never` suppresses completion pushes only): for an `on_change` monitor, lawful silence and stopped-for-good would otherwise be indistinguishable, which is exactly what this slice is for. `Scheduler._ended`: `_push_once` keyed `{id}:ended:{until-ISO}` (the `{key}:expired` pattern) with one `kind:"ended"` record. The wording is only what is enforced: *"automation paris ended as scheduled: its until (23:59 Sat 2026-11-14) has passed."* A final run that never started appends the `_expire`-shaped observed sentence — *"Its final run, scheduled for 09:00 Sat 2026-11-14, did not start: it was last refused with: …"* or *"…: aish did not observe an attempt to start it"* — and leaves a `kind:"final_not_started"` record keyed by that occurrence. A disabled task ends and pushes too: the sentence is as true for it. The key carries `until`, so extending it and ending again is a fresh push (`test_extending_until_catches_up_once_and_ends_afresh`). **Accepted, stated:** the push is deduplicated through `notified`, capped at `MAX_RECORDS`, so after heavy churn the ending can be pushed once more — bounded, the same class as an expiry's; the `ended` and `final_not_started` records are not repeated while the `ended` record survives the (also capped) record list (`test_a_notified_eviction_may_repeat_the_push_but_never_the_records`). The card's and README's "notified once" do not carry that caveat. `_ended` returns without a word for a task a mid-tick `fire_now` reload replaced, so an `until` just extended never ends under its old value (`_fire`'s guard, mirrored). The scheduler's arms are `TestTheEnding`; `run_now`'s refusal past `until` is `TestRunNowPastTheEnd`; the `/tasks` toggles' refusals are `TestToggles` (`docs/cli.md`); the tool's `until` and the card reading it from the field are `TestScheduleTaskUntil`.

**Extending `until`** on the same expr keeps `since` (`_note_cron_schedules` keeps an entry whose expr is unchanged), so the next tick inside the new window fires ONE downtime-style catch-up — the latest occurrence — and records the gap since the final run as one `skipped` range. Honest and bounded; changing the expr instead re-seeds `since` and fires nothing past.

**Everything that lists what is coming clips at `until`** through one helper, `schedule.upcoming`: the card's next two (the second could otherwise lie past the end), `/tasks`' next occurrence, `enabled_words`, and the streak push's "until its next scheduled time". `when_words` — the one humanizer, shared by the card and `/tasks` — renders *"on the schedule `0 9 * * *` until Sat 2026-11-14 23:59"*. The card adds the end from the FIELD: *"Its last run is Sat 2026-11-14 09:00, then it ends: no occurrence after Sat 2026-11-14 23:59 is ever run. If that last run cannot start on time (or aish is down), it may still start late, until 23:59 Sun 2026-11-15, and never after. When it has ended you are notified once, whatever the notify setting"* — so a wrong attended reading of *"po powrocie"* shows as a wrong date he can deny (`TestRendering`). `schedule_task` takes `until` (its one MUST: set it when the user names an end); the LATER section of the core prompt is unchanged. `/tasks`, `/runs` and `run_now` are in §Consumption surfaces and `docs/cli.md`.

### Starting: `from` (S6)

The defect (#457), the mirror of S5's: *"sprawdzaj codziennie od 7 listopada"* had no structural home — the cron began at the file's creation (the `since` floor), so a future start could live only in the prompt's prose, where nothing enforces it. **`"from"` is that start as a field**: optional, cron only, an ISO local datetime by `parse_at`'s rule (a bare date refused, an offset converted), inclusive. **Naming: the JSON key is `from`, the Python field is `Task.start`** (`from` is a keyword) — `Task.schedule` maps one to the other, so `to_dict` emits it and `/tasks disable`→`enable` keeps it (`TestRoundTrip`). Allowed shapes: `{"at"}`, `{"cron"}`, `{"cron","until"}`, `{"cron","from"}`, `{"cron","from","until"}`; `from` beside `at` (or alone) has its own refusal sentence.

**Validation.** `from` must be strictly before `until`, ALWAYS — at load too: that window is empty whatever the clock says, so a `LoadProblem` is the honest answer, and no file predating S6 carries the field (so S5's "an ended file is never a problem" still holds by construction). The no-occurrence-in-window check generalizes to `[max(now, from), until]` and stays creation-only (`now is not None`); it probes from a microsecond before `from`, because `cron_next` is strictly-after — an occurrence exactly AT `from` is the first run, matching `until`'s inclusive edge. **A `from` already past at creation is allowed and inert**: `since` already keeps a new schedule from firing retroactively, and refusing would force the model to special-case *"od dzisiaj"* and drop the owner's words from the structure (`TestValidation`).

**Enforced at one site, in `schedule.py`.** `_a_provable_miss` refuses an occurrence before `from`. That one function answers both `due()`'s live arm (before the start the task is PENDING — no status of its own, because `/tasks`' law is "derivable from file + ledger + clock", and `from` vs now is exactly that) and `_ended_or_final`'s grace arm, so a hand-edited file whose FINAL occurrence lands before `from` ENDS rather than fires, with no `final_not_started` record — there was never a final run to miss (`test_a_final_occurrence_before_from_ends_and_never_fires`). `from` only RESTRICTS: it never substitutes for `since`, so with no `since` nothing is a miss (fail-closed kept), and the effective beginning is `max(since, from)`, falling out of the two independent floors (`TestDueAtTheStart`). Skip records floor at the same `max(since, from)` inside `skipped_before`: a record claiming pre-start occurrences were "skipped" would say runs were missed that were never in the window. Daemon down over the first slots (created Oct 20, `from` Nov 7, down Nov 7–10) fires Nov 10 only, late, and records Nov 7–9 as skipped, never anything earlier (`TestTheStart`).

**Edited-earlier `from`** keeps `since` (§Recurring, above): moving the start back past occurrences that already passed fires one catch-up and one `skipped` range — byte-for-byte extend-`until`'s semantics (`test_an_edited_earlier_from_fires_one_catch_up_with_a_skip_record`). Disable→enable across `from` needs no code: the re-enable re-seeds `since` at its mtime and `max(since, from)` is right in both orders (both pinned).

**`run_now` before `from` is REFUSED** — one rule with S5's: a run by hand chooses WHEN only inside the task's own window `[from, until]`. A manual fire runs the task's PROFILE (cardless prefixes, site grants) at a time the approval card never described, and aish cannot tell a harmless early check from *"start emailing them from Nov 7"* run early. The refusal names the start and the way on: ask aish in a chat, where every change gets its card, or ask it to re-save the automation with an earlier start (`TestRunNowBeforeTheStart`). At `from` exactly it runs.

**Rendering — the clip lives in one helper.** `schedule.upcoming` skips occurrences before `from` (inclusive) as it clips at `until`, so the card's next two, `/tasks`, `enabled_words` and the streak push inherit it. `final_occurrence` returns None for a final before `from`, so `/tasks`' "may still start it, late" (`_final_may_still_run`) can never name a run `due()` will never fire. `when_words` states the window plainly — *"on the schedule `0 9 * * *` from Sat 2026-11-07 00:00 until Sat 2026-11-14 23:59"* (a past `from` is a statement, never a promise). The card's start line comes from the CLIPPED upcoming, never the field raw, so a garbled past date still shows a sane first run: *"Its first run is Sat 2026-11-07 09:00: no occurrence before Sat 2026-11-07 00:00 is ever run."* (a replacing card says *next*, since a replaced task may already have run). The run prompt's parenthesis states it: *"(recurring: `0 9 * * *`, from 2026-11-07 00:00, until 2026-11-14 23:59)"*. `schedule_task`'s confirmation to the model uses the clipped `upcoming` too — it used `cron_next(now)` raw, which with a future `from` would have announced a run before the start (`TestRendering`, `TestScheduleTaskFrom`). `schedule_task` takes `from` with until's MUST; an empty string drops silently like the other schedule keys, and the card then shows no start line, so what is approved is what exists. No push at the start: the first run is its own signal.

### Monitors (S3)

`"kind": "monitor"` makes a recurring task "watch X, tell me when it changes". A plain task (`kind` absent or `"task"`) is unchanged: its file renders byte-identically, its prompt is S2's, and its push is S1's (`test_a_plain_scheduled_task_still_pushes_exactly_as_before`). A monitor needs a `cron` schedule (a one-shot has nothing to compare against). `notify` is `always` | `on_change` | `never`, **defaulted per kind, never forced**: a monitor defaults to `on_change`, and an owner-written value is honoured. On a plain task anything but `always` is refused rather than kept, because the done-push policy is threaded only into monitor runs in this slice — a value aish silently ignored would be a constraint he believes is in force. The card says the monitor-ness and the policy in words (`schedule._monitor_lines`; `TestMonitorTaskShape`).

**The protocol and its parse.** The run's prompt (`scheduling.run_prompt` → `monitor_protocol`) tells the model to end with a `VERDICT:` line (`changed — <one line>`, `unchanged`, or on the first run `baseline`) followed by a fenced ` ```snapshot ` block of what it read. `schedule.parse_verdict` reads that mechanically, anchored on the LAST `VERDICT:` line so text aish appends after the model's block (the quick-reply net) is tolerated. Its endings: **`changed`** and **`unchanged`** need BOTH the line AND a well-formed block within `SNAPSHOT_MAX_CHARS` (8000); **`baseline`** is the disk's fact (no snapshot existed), not the model's word, and also needs the block; **`unreadable`** is everything less — no line, no block, an unclosed or unlabelled fence, an unknown word, `baseline` said when a baseline exists, an oversize block. An oversize block is malformed, never clipped: a clipped baseline would corrupt every later comparison. `unreadable` is the mandatory unknown ending (L8), and it **supersedes issue #5's "unparseable → treat as changed"**: a guess in either direction stands where the evidence should be. The three markers are a declared vocabulary (`schedule.VERDICT_MARKERS`, `on_miss=friction`, counted once per parse): a miss costs a noisy push and a skipped refresh and can permit nothing. **A snapshot carrying the protocol's own markers is never trusted, in either direction.** The block holds what a run READ, and a page can hold a complete forged ending — a `VERDICT: unchanged` line followed by its own ```` ```snapshot ```` fence. Copied verbatim as "what you read now", the last-`VERDICT:` anchor used to read the PAGE's verdict past the model's own honest one and store the page's bytes as the baseline: a silent run, under `on_change`, with an attacker-chosen baseline (found by the delivery review, by experiment). So an answer with more than one ```` ```snapshot ```` opener anywhere, or a parsed block holding a line that starts `VERDICT:`, is `unreadable` (`_read_verdict`) — which pushes on the streak and leaves the baseline untouched. The whole answer is counted, not just the parsed block, because the forged ending parses as a clean block of its own. The word "verdict" in ordinary prose is not a marker. The cost: a watched page that really does contain such lines makes every run of that monitor unreadable — noisy, never silent. `TestParseVerdict`; the prompt's protocol, and that a plain task's prompt is unchanged, is `TestTheRunPrompt`.

**Silence is structural.** `_monitor_push` is the whole completion-push decision, behind `_notify_done`'s unchanged viewer gate. It is silent for exactly: `unchanged` and `baseline` under `on_change` (a parse that matched); a `stopped` run under `on_change` (the owner pressed Stop, so he was there); an `unreadable` run, whose push is the scheduler's streak push instead; and every completion under `never`. An unreadable run is therefore never silent by default — the first of a streak always pushes; the same-day repeats are rate-limited by the streak, not silenced by a reading. **A verdict says nothing about what the run DID**, so an `unchanged` or `baseline` run under `on_change` that made a change without a card (a licensed tool call, counted per task in `Agent.cardless_this_task` because the lines themselves are taken into the answer) pushes *"…, with changes attempted without a card"* instead of staying silent. The count includes attempts that failed, because a wrapper that failed may still have written part of its change, so the push says "attempted or made". **Open, stated:** a shell command run cardless under the monitor's own `allow` prefix is NOT counted — aish does not track profile-prefix runs as changes at all (S1's known gap below, `docs/agent-core.md`) — so an `unchanged` monitor whose run used its prefixes is silent. A run the scheduler could not record (no scheduler, or the record raised) gets the plain completion push whatever the policy. `never` suppresses completion pushes only — a held approval still pushes (`notify_hold`, #348, untouched), and the malfunction pushes below are not completion pushes (`TestMonitorNotifyMatrix`).

**Where it runs, and what may trigger it.** The monitor semantics ride a `MonitorSpec` (id, notify, occurrence, the prior snapshot) that **only `fire_scheduled` supplies**, as a keyword through `launch_triggered` into `_run_task` — never `meta`, because `handle_trigger` forwards `meta` from any token holder verbatim and accepts `origin="schedule"`, so meta-carried fields would let anyone with the token mint monitor outcomes and snapshot writes (`test_http_trigger_with_monitor_shaped_meta_gets_no_monitor_handling`). The parse runs iff `_run_task` was handed the spec; it is never inferred from `session.origin` or `trigger_meta`, because the owner typing into the monitor's chat later enters `_run_task` with the same origin, and his answers must never be parsed or replace the baseline (`test_the_owner_typing_into_the_monitors_chat_is_never_parsed`). The spec is not stored on the `Session` for the same reason. It is **frozen at fire**: an edit to the task file mid-run cannot change how that run's answer is handled. The parse, the snapshot write and the record happen in `_run_task`'s success arm where `finished` is set — not in `_notify_done`, which returns early for a viewer or unconfigured Pushover, and not in the post-turn epilogue, which shutdown does not await. A stopped run (`CANCELLED_RESULT`) records `stopped` and writes no snapshot, exactly as titling skips it. A run that FAILED (an exception or `ModelUnavailable`, `finished` stays None) records `monitor_run_failed`. Every record and push goes through a `Scheduler` method (`report_monitor`, `report_monitor_failed`), as `report_interrupted` does; `_run_task` never writes `state.json`. The full cycle through the real app is `TestMonitorCycle`; the stopped, failed and unrecorded endings, driven through `_run_task` with the spec handed as `launch_triggered` hands it, are `TestMonitorEndingsThroughRunTask`.

**The snapshot store.** `<state dir>/scheduler/snapshots/<id>.md`, written whole through `atomic_write`; the path is built only from an id that `TASK_ID_RE.fullmatch`es — `fullmatch`, because `$` also matches before a trailing newline, and `validate_task` now uses it too (an id `"x\n"` used to load). One file per monitor holding the last good baseline only. Each refresh writes a one-line stamp INTO the file (`<!-- aish monitor snapshot: saved <ISO time> by <session> -->`), and records carry that stamp — the mtime is destroyed by unchanged refreshes. A snapshot file that exists and cannot be read (no stamp, bad time, over the cap) is an open failure on the S2 streak, never a first run: running it as one would overwrite a baseline aish cannot read. **A deleted automation's snapshot is removed** (`_remove_orphan_snapshots`, on every reload of the folder): the baseline belongs to the task, and a new task under the same id must start from its own first run. A disabled task, one that is merely invalid, or one switched back to a plain task still has its file, so its snapshot is kept; nothing is removed while the folder itself is missing (`TestSnapshotStore`, `TestMonitorFire`). A run still in flight when its task is deleted writes no snapshot if the scheduler has already seen the deletion, and otherwise leaves one file that the next reload removes.

**The snapshot is OUTSIDE CONTENT, even though aish wrote the file.** It is what a previous run distilled from whatever it read — a hostile page included. So it is never placed in the task string: `Agent.run_task` folds every host in the task string into `_owner_hosts` (`note_owner_hosts`), which the egress gate treats as owner-named, so a URL a hostile page planted in one run's snapshot would become cardless unattended egress on the next. Instead `launch_triggered` delivers it after the session opens through `Agent.add_outside_note` (and `ClaudeMaxAgent.add_outside_note`, same text): `provenance.disarm_markers`, wrapped in `web.UNTRUSTED_NOTE` under an `[aish: …]` heading, never `note_owner_hosts` (the `add_system_note` precedent, #178 P0-2), and the taint raised explicitly — no tool call fires to raise it otherwise. The raise is staged (`_outside_note_pending`) and applied inside `_reset_task_state`, because that reset clears the taint at the start of every task; it applies to exactly the one task the note was delivered for. The prompt carries only the stamp, re-rendered from the parsed time. Pinned: `TestSnapshotDelivery` (the task is tainted at its first model call; a host named only in the snapshot is not in `_owner_hosts` and unattended `read_url` to it is still a novel host; the control case shows the same host in the task string WOULD be laundered).

**Consequences per status**, recorded as `kind:"monitor"` with `status`, the model's own word (`said`), `prior_saved_at` and the new `saved_at`: `baseline` — snapshot written, silent. `unchanged` — snapshot refreshed, no push. `changed` — snapshot refreshed, push *"aish monitor <id>: changed"* with the model's one-line summary. `unreadable` — snapshot NOT replaced, record keeps the `reason` and the answer's last 600 chars. Unreadable and failed runs push on a per-monitor **streak** (`monitor_streaks` in `state.json`, S2's `_streak_failed` shape): the first bad run pushes, then at most once per `STREAK_RENOTIFY_AFTER` (1 day), stamped on the attempt; any readable parse ends it (`TestMonitorStreak`). It is a separate map from the open-failure `streaks` because every monitor run that opens ends an open-failure streak. The push states only what was observed — *"the run ended without a verdict aish could read (<reason>)"* or *"the run did not finish: <failure>"*, never "the monitor ran" (a stall-stopped run reaches the same parse) — and names the **baseline's age**: *"still comparing against the baseline from 09:00 Wed 2026-10-14"*, or *"there is no baseline yet"*. Under `always`, an unreadable run the streak did not push still gets a completion push with that sentence.

**The false-silence direction is UNGUARDED, and measured.** A model that says `unchanged` about something that changed is silent, and no parse can tell. What exists is instrumentation: every readable verdict records `snapshot_identical` (the new block byte-equal to the baseline the run was handed) and `verdict_matches_bytes`, so unchanged-but-differs and changed-but-identical are counted from day one. It changes no behaviour; whether it ever should is a decision for when there are counts (`TestMonitorReports`).

**Accepted gaps, stated.** A monitor run interrupted by a restart is reported by `report_interrupted` (S1) and does not advance the monitor streak. The vocabulary tally from the server-side parse lands on the next task that flushes, as any consultation outside a task does (`docs/vocabularies.md`).

### Creating one, and the fence around the folder

**`schedule_task` is the only writer the model has**, and it exists only in the owner's own chat. The handler in `agent.py` refuses outright in every non-`user` origin (`SCHEDULE_ONLY_FROM_OWNER`, blocked, no card — a triggered session must never author the thing that triggers sessions), runs `validate_task` with the time required to be in the future, renders the JSON itself (the model never writes it), and materialises it as `files.plan_write(<automations>/<id>.json)` through the existing `approve_write` card. The card's `note` — the slot rule writes use, rendered above the diff on both surfaces — is `schedule.describe`: when it runs in words (*"Runs ONCE, at 22:05 today (Thu 2026-10-15)…"*), the WHOLE prompt, never truncated, what may run without asking (the prefixes) and which sites it may press things on as him; the JSON diff stays underneath. Reusing an id is an edit on the same card (*"Replaces automation …"*). Deny, deny-with-comment and approve-with-comment mean what they mean on every write card (`TestScheduleTaskCreation`).

**Every other write into the folder is unapprovable, in every origin** — the charter fence's two-net shape (`docs/roles.md`), pointed at `schedule.automations_dir()`. File tools: `_is_automation_file` in `_dispatch_write`, through `files.contains`, so a symlink from a session root into the folder is the folder. Shell: `_command_touches_automations`, which is the charter fence's four nets (`_command_names_a_store`, shared) — the literal spelling anywhere, every path-shaped token resolved with `~`/`$HOME` expanded, a dynamic token that could expand into the folder, and the coarse floor of the word `automations` or `AISH_CONFIG_HOME` in any command the shell will rewrite. Both return `blocked` before any approver is asked, so there is no yes button on the path. The accepted cost, as for charters: `cat`/`jq` on a task file is refused too; `read_file` still reads one. The owner's own `!` commands and his editor are not model calls and are untouched (`TestAutomationFence`). **What the fence does not reach, stated because a delivery review found it.** The fence reads command TEXT and file-tool PATHS; `load_tasks` validates a file's shape, never who wrote it. So (a) a mutating plugin tool approved on its card, and (b) an approved command — including one run cardless under a profile prefix such as `./sync.sh` — whose script BODY writes into the folder, can create a task file that the next tick fires with whatever `allow`/`sites` it carries and no further card. That second step is an escalation from one approved grant to arbitrary unattended grants, and it is OPEN in S1. (c) The shell nets are the charter fence's, known-incomplete against composed spellings (`V=auto; W=mations; … $V$W/…`); such a leak lands on an ordinary card or a hold, not silently. The fix that closes all three at one chokepoint is an admission ledger: `schedule_task`'s approved write records the file's digest, and `load_tasks` fires only files whose digest was admitted (or that the owner re-admits) — the digest-binding shape roles already use (`docs/roles.md`). Not built in S1.

**The run's site grants are what they say** — `sites` makes the per-site press card already answered on a profile host, while a press on any other host still asks, and a control that draws its own card still draws it (`TestTheRunsSiteGrants`).

**What S1 deliberately does not do.** A run that has nothing to say still ends with the ordinary completion push (§Notifications): a model-declared "nothing to report" would also silence shell commands that ran under a profile prefix, which aish does not announce (`docs/agent-core.md`, *A change with no card is announced by aish*, known gaps). S3's monitors are the one place a run may now be silent, and only on a parsed verdict — with that same prefix gap still open (§Monitors). ### Reading and changing one from a chat (#459)

**The session that filed it.** Asked (in Polish, one line) to move an existing automation's cron, the model had only `schedule_task`, whose reuse of an id REPLACED the file from the call's arguments. It searched for the task with the shell — `ls` of a guessed folder, then a `grep -rn` over `~/.config ~/.local` that ran 120 s (neither names the word `automations`, so the fence's nets did not apply) — read it through a read card held 346 s, and re-sent every field, adding an `until` nobody asked for. Reading the handler then showed the replace also wrote `enabled: true` and `created: now`, so **changing a paused automation silently resumed it**.

**`automations` — the model's read.** No `id`: the `/tasks` listing, the same `automation_admin.task_lines` (one function, two surfaces). With an `id`: that task's lines plus its stored file as `Task.render` writes it — what an edit names its changes against. A problem file is named as one with its error and the way on. No card: it reads aish's own config into the context, as `recall` reads past chats; that is NOT "nothing leaves the machine" — the content enters a context whose `web_search`/`read_url` inputs are cardless egress, the same exposure `recall` already has. Refused in every non-`user` origin (`AUTOMATIONS_ONLY_FROM_OWNER`): a triggered run has no use for the other automations' instructions. In `CORE_TOOLS`, because ranking already failed `schedule_task` on a Polish one-liner and the filing message was another (`docs/tool-menu.md`). The folder fence is unchanged: the shell is still refused, `read_file` still reads a task file on its card.

**An existing id is an EDIT, never a replace.** `schedule.edited` starts from the FILE's validated task and overlays only the arguments passed; `clear` (`schedule.CLEARABLE`: from, until, allow, sites, model, cwd) drops optional fields by name, and set-plus-clear of one field is refused. `enabled` and `created` are the file's unless named. Rejected: a separate change tool (a second verb for the model to choose and ~1k chars on every menu) and an explicit `change: true` flag (a model that forgets it gets the replace back, which is the bug). Rules the merge enforces:

- **A shape change never silently drops a bound the owner approved**: `at` on a cron task with `from`/`until` is refused unless `clear` names them.
- **`psu_ua` is minted only at creation.** An edit keeps a one-shot's, and a task that becomes recurring loses it (validate_task requires that); a cron task turned one-shot gets none — background work never becomes a presence claim by being edited.
- **`roots`** has no `schedule_task` argument: an edit keeps it and cannot drop it.
- **A kind change takes the new kind's `notify` default** unless `notify` is named (a plain task refuses every policy but `always`).
- **The creation-time checks apply only when the schedule moved**: `validate_task(now=…)` when the schedule dict changed, `as_of` otherwise, so a note edit on a fired one-shot is not refused for its past time.
- **Nothing to change → no card**, and the model is told so.
- **A problem file is not edited field by field** (the `set_enabled` precedent: a field of a file that does not parse cannot be changed without guessing). A complete task (prompt and `at`/`cron`) replaces it; `delete=true` removes it.

**The card leads with what changes.** Its note is `Changes:` and one line per field from `schedule.changes(old, new)` — computed from the two tasks, never from anything the model said about its call — then `describe(new, replacing=True)`, the whole resulting automation in words, grants included, so a grant inherited from the file or added by the edit is on the card. `describe` now states **PAUSED** for a disabled task: an edit keeps `enabled`, and a card listing next runs of a paused task would read as live.

**What the scheduler does with an edit** (`scheduler.py`, `since` keyed per id and cron expression): a NEW cron expression re-seeds `since` at the file's mtime, so a run the old expression missed is gone and the new one never back-fires; an UNCHANGED expression keeps its `since`, so a run already due and not yet started starts with the edited version. The edit's result says which. A tick already iterating the old task can still fire it: `_fire` re-checks only that the task is still among those the scheduler last loaded (`task not in self.tasks`), and the folder is re-read at a tick's start or by `fire_now` — so the exposure is the tick in progress when the card is approved.

**Pause, resume, delete.** `enabled` (strictly a boolean or the string `true`/`false` — models send the string `"false"`, which is truthy) rides the edit path and its card; enabling or disabling past `until` is refused by `automation_admin.toggle_refusal`, the terminal's own rule. `delete=true` takes nothing but `id`, works on a problem file too, and draws a write card with `WritePlan.remove` set: every surface titles it delete (`verb: "delete"`, *Delete file*), its note is `schedule.describe_deletion` (what it was, that it stops, that there is no way back). `files.commit` refuses a `remove` plan, so the flag is no general unlinker — the automation handler unlinks itself. **Pausing and deleting are refused once outside content entered the task** (`AUTOMATION_SILENCING_TAINTED`, on `_tainted` — taint, not origin): a disabled or deleted monitor says nothing about it ever again, so silencing one is exactly what an injected page or mail would ask for, and the owner's habit on cards is no defence. Resuming stays available on its card. Known: an edit that silences in effect (a cron that never fires in the window) is not covered by this gate; it is on a card headed by that change.

**A card left open never overwrites a change made meanwhile.** Every automation write (create, edit, delete) re-reads the file after approval and writes only if it still holds the bytes the card was planned from (or, for a create, still does not exist); otherwise `AUTOMATION_CHANGED_WHILE_OPEN` tells the model to read it again and re-propose. The write itself goes through `atomic_write.publish`. The check and the rename are not one atomic step; that last instant is not closed. `TestACardLeftOpen` (`tests/test_automations_manage.py`) holds the interleavings (an owner pause while an edit card is open, an edit while a delete card is open, a file created while a create card is open); `TestReadingThem`, `TestAnEditChangesOnlyWhatItNames`, `TestPausing` and `TestDeleting` pin the rest of this section.

**Against the admission-ledger fix named above:** an approved edit is a write through the card like a creation, so when the ledger is built it admits the edited file's digest exactly as it would a new one. The merge base can itself be a file the open gap wrote; the edit card re-shows its grants through `describe`, so an edit does not widen that gap.

### Consumption surfaces (S4)

What S1–S3 record became reachable: the terminal's `/tasks` and `/runs` (`docs/cli.md`), a silent monitor run kept out of the web's attention badge, `run_now`, and — after S4 — the web's Automations sheet (below). **The web adds no badge and no toast for runs**: the drawer's schedule glyph (row anatomy, `docs/web-frontend.md`) was already there, and the composer answers `/runs` with "terminal-only" rather than "unknown command".

**The Automations sheet — `/tasks` on the web.** Three WS view-messages (the `run_now` precedent: they act on the automations folder and edit nothing in the chat on screen, so none claims control of it — `test_the_sheet_messages_claim_no_chat`), from an authenticated socket only. `automations` answers `{type: "automations", rows, problems, notes, outcome?, error?}` to the asking client: `rows` are `automation_admin.task_rows`, built from the SAME `read_listing` the terminal reads (with the scheduler's own deny list, so a PROBLEM here is one the scheduler skips) and the same helpers as `task_lines` — id, note, kind, when-words, state (`ENDED` outranks `DISABLED` exactly as there), the stands line, last-ran words, notify, and the task's `allow` and `sites`, on the row because resuming re-arms unattended runs carrying them. `problems` are `{file, id, error}` (`id` is the stem, which is how a problem file is named for delete); `notes` carries the unreadable-scheduler-state line. The client derives nothing. `automation_enable {task, enabled}` is `set_enabled` and `automation_delete {task}` is `delete` — the terminal's own toggle and shredder, so neither can create a file or write any field but `enabled` (`test_the_writers_never_create_a_file`, `test_a_forged_enable_changes_only_enabled`) — each answered with a fresh listing plus a one-line `outcome` (`enabled_words` after an enable), or the `AdminError` text as `error`. `enabled` must be a JSON boolean: `"false"` is a truthy string, and a toggle that coerces is how a pause becomes a resume, so anything else is refused with nothing written. Only `task` and `enabled` are read. **No push**: a change made elsewhere — the terminal, another tab, the scheduler ending a task — reaches an open sheet only on its next fetch (on open, and after each of its own actions). `TestAutomationsSheet` (`tests/test_server_automations.py`).

**A silent monitor run does not demand attention.** Every monitor run is a new schedule-origin chat the owner never opens, so an every-30-minutes `unchanged` monitor kept "Needs you" permanently full — the web's attention predicate counted its unseen output like any chat's. The SERVER now states a row fact, `silent: true`, and the client's ONE predicate (`needsYou`, `[ATTENTION]`) consumes it; no second predicate exists and the client derives nothing. Where the fact comes from: `_run_task`'s success arm, right after the monitor's ending is recorded, writes a `kind:"quiet"` record into the run's OWN log (`SessionLog.quiet`, `_mark_quiet`) when `scheduling.is_quiet` holds — status `baseline`, `unchanged` or `stopped` and no change made without a card (`cardless`, the same count that keeps such a run's push from being silent). That count inherits the push's open gap (§Monitors, S1's known gap): a shell command run cardless under the monitor's own `allow` prefixes is not counted, so an `unchanged` run that used them is silent here too. `stopped` is quiet for any run that ends on `CANCELLED_RESULT` in `_run_task`'s success arm; that the owner's Stop is the only way to get there is NOT pinned — whether a shutdown cancellation can end there has not been driven by a test (any later output in that chat badges again). `changed`, `unreadable` and a failed run never get one: changed IS "needs eyes". The record carries `through`, the chat's last output stamp at that moment, and `_silent(out, quiet_through)` holds only while the chat's output is not newer — so the owner typing into the chat later, or anything the chat says after, is news again. It is written BEFORE `_finish_turn` publishes the idle row, so the first row that could badge the run already says silent; a failed write leaves it badging, the direction a mistake may go. Every publisher of a row a band can be decided from states it: the roster row (`_roster_row`), the snapshot list (`_send_sessions`), the hello pages, the offline index and the offline session payload, which the mirror's meta keeps (`docs/web-frontend.md`). A monitor run holding a card still needs him: `needsYou` checks `waiting` first.

**The bound: none from the scheduler's record cap, by placement.** The spec's named edge was that `state.json` keeps `MAX_RECORDS` (200) records, so a fact derived from them would be evicted and an old silent run would re-badge — for a 30-minute monitor, one old run re-badging per new run once ~4 days had passed, which is the flood again, delayed. The fact therefore lives in the chat's own log, beside `origin`: it is bounded by the chat's existence (it goes with a delete, comes back with a restore) and by nothing else. Stated cost: one append per silent run, and the listing parse reads one more record kind (`quiet` is not activity, `_is_activity`). `TestSilentMonitorRows` (`tests/test_server_automations.py`, including `test_the_fact_survives_the_schedulers_record_cap`); the client half is `test_attention_badge.js` §7.

**`run_now` — the owner runs an automation outside its schedule.** A WS view-message (the `share_drop` precedent: it starts a NEW chat from an automation file and edits nothing in the chat on screen, so it claims no control of it). It names WHICH automation — `task`, or the chat on screen when an automation started it (its live meta, else the `[scheduled: <id>]` prefix of its opening prompt) — and nothing else in the message is read. It routes through `Scheduler.fire_now(task_id)`, so the scheduler stays the one owner of the prompt, the `MonitorSpec`, the snapshot read and the records: `fire_now` re-reads the folder through the scheduler's own `_reload_if_changed` (a private read made a monitor run before the first tick write no snapshot — the ending is recorded against `self.tasks`), then enters the same guarded seam a fire does (`fire_scheduled` → `launch_triggered`: dedup, rate bucket, concurrency cap, the profile as a `RunProfile`) with dedup key `<id>:manual:<server time>` (`scheduling.manual_key`, a shape no ledger key can take). **It never marks the fired ledger**: the ledger states what the SCHEDULE did, and a manual run is "run it again now" — the occurrence that is due still fires on schedule; the affordance and its answer say so. A run that opened leaves a `manual_run` record; a monitor run by hand records its verdict with `manual: true` and refreshes the baseline like any run. The prompt states that the owner ran it manually and when, and that it replaces no scheduled run — never "scheduled for" (L8) — but keeps the `[scheduled: <id>]` prefix `report_interrupted` and the diagnostics read; the chat is titled *Run by hand: …*.

**What `run_now` refuses, and who can send it.** Refused before the seam, each with the reason and the way on: a missing id, a problem file, a recurring task whenever now is past its `until` — not only once ENDED, since a run by hand inside the final run's grace would still cross the owner's own bound (*ask aish for a new automation*, S5), a recurring task before its `from` (S6, §Starting: `from` — one rule: `run_now` chooses WHEN only inside the task's own window) — a disabled task (*enable it first — Resume in /tasks on the web, or /tasks enable <id> in the terminal — then run it*), and an expired or settled one-shot (*it will not run again; ask aish for a new automation, which comes on its own approval card*); a fired one-shot may be run again. An open failure is answered to the owner, who is there to read it, and is neither recorded nor pushed. Senders: an authenticated client socket only. The web sends it from a TYPED `/run-now [id]` — a chip can never reach a slash command (`[CHIP-NEVER-COMMANDS]`) — and no model tool and no `POST /trigger` field can produce it; `test_http_trigger_with_monitor_shaped_meta_gets_no_monitor_handling` stays green. `TestRunNow` pins that a forged message chooses only WHEN: extra `prompt`, `allow`, `sites`, `model`, `cwd` or `monitor` fields change nothing the run receives.

**The terminal handler — and the web sheet, which calls the same two functions — is a toggle and a shredder, never an author** — `/tasks enable|disable` (Pause / Resume) changes exactly `enabled` on an existing file, `/tasks delete` (Delete) removes one; neither can create a file, so the creation card stays the only author of automation content. The rule, the `since` re-seed a disable→enable round trip causes, and the orphan snapshot a delete leaves until an aish-web reads the folder are in `docs/cli.md`.

## Restart recovery (#164)

An in-flight task is bracketed on disk by `SessionLog.task_start(prompt)` / `task_end()` from `_run_task` — **web only**, because a CLI session dies with its terminal and must never be resurrected, and the `!` path writes NO marker, since re-running the user's own shell command unattended is a risk, not a recovery. A killed process cannot write anything, so an UNMATCHED `task_start` IS the interruption evidence: no heartbeat, no timer.

`startup` fires `_resume_interrupted` as a background task (never on the startup path). Candidates are scanned newest-first within `RESUME_WINDOW` (12 h) and each is cold-opened through the SAME `_open_by_name` a user's switch uses, so the resumed session replays its full prior transcript, then relaunched with no client — identical to a trigger.

The resumed turn is `RESUME_NOTE`, **not** the original prompt: the request and the partial work are both already in the restored history, so re-issuing it would invite the model to redo side effects it may have completed, like an email already sent. The one exception is a run killed before its own user message was logged — there is nothing to continue from, so the recorded prompt is re-issued. Two things make "continue" real rather than nominal: `keep_history=True` swaps the eager per-task tool-output trim (200-char stubs would gut exactly the results the resume exists to preserve) for an oldest-first trim that runs only as far as the budget demands; and `pending_task`'s `in_flight` list — a `tool_start` with no matching `tool` — is appended to the note, naming the steps whose effect is genuinely UNKNOWN. That is the honest boundary: a completed step logged its result, an in-flight one may or may not have taken effect, so the model is told to verify those specifically instead of re-running the task. `RESUME_MAX_ATTEMPTS` (3) abandons a task that keeps killing the server instead of crash-looping it; `RESUME_MAX_SESSIONS` (3) stops a mass restart stampeding the backend. `TestRestartResume`.

**Schedule-origin sessions never resume (#187).** A resume restores the session's RECORDED model — and a per-trigger model override is exactly how a scheduled curation run once loaded a model too big for the host and OOM-crashed it, HA VM and all. Resuming would reload that same model on every reboot: `RESUME_MAX_ATTEMPTS` bounds the loop at 3, but each attempt can take the box down, at 3 a.m., unattended. And the resume buys nothing there: a periodic job re-fires on its own cadence, and whether that re-fire redoes or skips a half-done pass is the SOURCE's decision — the server's `dedup_key` is an in-process LRU that does not survive a restart by design (`TRIGGER_DEDUP_TTL`), so cross-restart idempotency was always the scheduler's (today `aish-curate`'s own cooldown ledger, and it no longer opens a session at all). The check is one origin test in `_resume_interrupted` (`pending_task` carries the log's `kind:"origin"` value, `"user"` when none was written); of the four origins (`user`|`schedule`|`email`|`webhook`) ONLY `"schedule"` is excluded. `email` keeps resuming because the poller labels a message processed only after a successful `/trigger` and never re-fires it (`email_poll.py`); `webhook` because nothing on aish's side re-fires one — so, like a user chat, the resume is the only thing that would ever finish the task, and each keeps its recorded model (the drawer's stickiness promise). A skipped session is left exactly like one past `RESUME_MAX_ATTEMPTS`: nothing appended, and cold replay renders the interrupted turn with its Retry affordance. `test_schedule_origin_interrupted_task_is_never_resumed`, `test_user_origin_interrupted_task_still_resumes`.

**But a run that is never resumed never completed, so it is reported (epic #142 W2).** `make ship` restarts the daemon on every reinstall, which makes "killed mid-run" the ordinary way a scheduled run stops. Beside the skip, never in it (the skip still appends nothing to the session log), `_report_interrupted_schedule` hands the session to `Scheduler.report_interrupted`: a `kind:"interrupted"` record in `<state dir>/scheduler/state.json` and ONE push, *"The run of automation X in chat <session> was interrupted: aish-web stopped while it was running, and scheduled runs are not resumed…"*. That states what was observed, which is an unmatched `task_start` found at the next start. The automation id comes from the `[scheduled: <id>]` prefix the scheduler writes into the run's own prompt, because the session log persists the origin but not `trigger_meta`. With no prefix, the push says *"a scheduled run"*. The dedupe key is `interrupted:<session>:<log size>`, on disk in the state file's `notified` list. The resumer re-scans on every start and the skip leaves the log byte-identical, so the same interruption is never pushed twice, while a later, new interruption of that chat is a new key. User-origin chats are untouched. `test_an_interrupted_scheduled_run_is_recorded_and_pushed_once`, `test_a_scheduled_run_without_an_automation_id_says_so_plainly`, `test_an_interrupted_user_chat_pushes_no_interruption`.

**A hang is not a death — but no hang has ever been observed (#336).** `attempts` counts every `task_start` with no ending, so a live process that went quiet would spend the allowance kept for dead ones. A `stall` record and a raw-start backstop were built to separate the two and withdrawn: the stranded starts that prompted it were #338's Retry rewind, and nothing has ever been seen to hang. See `docs/session-log.md`.

**What made the budget run out was not hangs, it was Retry (#338).** Every Retry called `rewind_last_turn`, which cut at the turn's user `message` — so it kept the `task_start`/`rule_eval`/`binding`/`context` preamble written before that message and dropped the `task_end` after it. A turn that ran to completion came back as a pending crash with a stranded `task_start`, and four retries of one prompt permanently excluded that chat from recovery. The boundary now walks back to the turn's own `task_start` (`_turn_opens_at` in `session.py`), which is the fix; nothing else was needed.

**#338 bought that by deleting the whole turn; #339 stopped paying.** `_launch_retry` now calls `supersede_last_turn`, which MARKS the discarded turn instead of removing it and appends a `retry` record saying so (`docs/session-log.md` L7, `docs/trace-contract.md` §3.11). `pending_task` skips superseded records, so recovery sees exactly what it saw when they were deleted — and a `task_start` that is NOT marked is still the killed-process signal, so a genuinely dead process resumes as it always did. The evidence the whole recovery argument was reasoned from — the retried attempt, its `model_error`, its `task_end` — is now still on disk to be read back.

**Recovery runs through the same primitive a continuing Retry uses (#387)** — `_continue_task`, below. So a restart resume now inherits the dead attempt's provenance too: before it, `_reset_task_state` handed a resumed web-read task an untainted fence and a disarmed stop gate, because nothing restored either cold.

## Retry continues a turn that died (#387)

Retry is one button with two acts, and a recorded fact picks between them. **Regenerate** (#60) — rewind the model's context, supersede the attempt, roll the transcript back, rerun the prompt from scratch — is right for a *delivered* answer he dislikes. It is wrong for an attempt that never delivered one: the motivating session had four finished tool results, one refused model call, and four presses that each threw the results away and re-ran the discovery. So an attempt that **died with work in hand** is **continued**: nothing is rewound, superseded or rolled back, and a continuation runs on top of the attempt's live records, fed its completed results as history. The mainline for a busy quota is still the in-attempt hour (`docs/rate-limits.md`); this is the fallback for what outlives it — the hour's backstop, the attempt cap, a transient failure's two minutes, a crash, a process killed past recovery's bounds.

**The decision is `retry_decision(SessionLog.last_task(path), native)`, read from the log**, so a press a second after the failure and one on a chat reopened the next morning take the same act:

| last attempt `ended` | Retry |
|---|---|
| `ok`, `stopped` (ended `ok` on `STOPPED_ANSWER`), `none` (no bracket at the question), `unrecorded` (statusless `task_end`) | regenerate — unchanged |
| `failed`, `model unavailable: …` with a give-up `retryable: true` | continue |
| `failed`, `model unavailable: …` with `retryable: false` or no give-up record | regenerate — the refused request would be refused again; retryability unknown is not retryability |
| `failed`, `task failed: …` (a crash) | continue |
| `failed` with neither prefix | regenerate — an unrecognised ending is not evidence to continue |
| `unknown` (a `task_start` nothing closed) | continue |

**Stop then Retry regenerates**, and so does a Retry pressed while busy (it stops the attempt first, and a stopped attempt regenerates): Stop is a verdict on the work, and a note saying "everything above already happened" would tell the model to build on what he rejected. v4 designed a busy-press continuation; it dissolved because `app.js` refuses Retry while the client is busy. claude-max keeps today's Retry (`isinstance(session.agent, Agent)` precedes the table): its SDK holds its own session and nothing asserts what it retains. A question whose typed message never reached the log regenerates — there is nothing to continue from.

**The bound**: continue while `chain_attempts <= RESUME_MAX_ATTEMPTS` (3), where `chain_attempts` counts the LIVE `task_start`s at the question — the original attempt and every continuation, automatic or pressed. Past it Retry regenerates and the record says `bound: "attempts"`; the regenerate starts a new chain, so a later death there is continuable again. The chain is read off the start records: its first is the latest start whose prompt is not a `RESUME_MARKER` note (extended back over a start restart recovery re-issued with the same prompt); recovery's own `attempts` counter is untouched and neither reads the other.

**`_continue_task(session, last, by=)`** is the one primitive, shared with restart recovery: the note is composed from the RECORDED ending (`continuation_note` — `CUT_OFF_NOTE` quoting the `task_end.error`, or `RESUME_NOTE` for a death, plus the in-flight list); `SessionLog.carried_work` is handed to `run_task(continuing=…)`; a pressed Retry writes its `retry` record (`record_retry`, `continued: true`) BEFORE the continuation's `task_start` and emits it right AFTER `open_turn(note)` — both through `emit`, so they arrive in order — which is where `reconstruct_events` puts it cold. Synchronous up to the launch, like the supersede: no other turn can start between the decision and the act.

**The approval story.** Reusing a result is not re-running a command: the dead attempt's calls and outputs go back as history and nothing is re-dispatched, so nothing bypasses `approve()`; everything the continuation proposes meets `_dispatch` and its gates. A denied or held call stays in the history as the denial or hold it was, and is not carried as done. What IS carried is restriction only (`Agent._adopt_carried`, `docs/agent-core.md`): taint, links that arrived by mail, an armed stop gate, typed page values — never a grant.

**Regenerate after continuations** discards the whole chain as one: `rewind_last_task`, `supersede_last_turn` and `_rollback_transcript_to_last_user` all walk back over aish's own user messages (a continuation note, an `[aish: …]` nudge) to the question the owner TYPED, so the note is never re-run as a prompt. `retry` records are never marked, and the rollback keeps the chain's `retry` rows, so hot and cold both read question → earlier presses → this press → the rerun.

**Interim costs, named** (#286 slice 1 closes them): a continued question is one question rendered as two or more turns, so `redact_turn` on the typed turn leaves the continuation's turn holding the answer, and a Fork on a continuation's answer forks at the note's turn. `TestRetryContinues`, `TestRetry`, `TestLastTask` (`tests/test_session.py`).

## Shipping a new build (#221)

`make ship` (`scripts/ship.sh`) is the ONE local path from a checkout to the running service: guard → lint → tests → `launchctl bootout` → `uv tool install` → `launchctl bootstrap` → health-check. `scripts/deploy-web.sh <host>` is the remote equivalent.

**The guard is the reason it is a script at all.** `uv tool install` builds the wheel from the **WORKING TREE, not from HEAD** — verified, not assumed: an uncommitted line in `aish/static/app.js` was found inside a freshly built wheel. So a bare install silently ships whatever happens to be uncommitted, and there is nowhere to put a check when the ship step is a command pasted from a doc.

That is not hypothetical. On 2026-08-11 the installed `app.js` hash matched a **dirty** checkout rather than any commit — another session had installed its in-progress frontend to test it live. A routine reinstall from that tree would have shipped 129 uncommitted lines that were simultaneously failing two doc-gate tests, and reverted the live UI under the session driving it. The near-miss was caught by comparing hashes by hand, which is exactly the check a machine should be doing.

So: a dirty tree **refuses**, naming the files and separating those that land in the wheel (`aish/`, `pyproject.toml`) from those that do not — a refusal that cannot tell a stray README from a modified module just teaches people to reach for `--dirty`. Untracked files count, and are the sharper case: hatchling packages off disk, so a new uncommitted module ships like any other while `git diff` shows nothing. A non-`main` branch warns but does not block. `--dirty` is the deliberate override.

The remote script keeps working-tree shipping as its normal mode — that is the point of a remote dev loop — but prompts when the tree is dirty, and with **no tty to prompt on** it refuses rather than treating silence as consent. That non-interactive branch is the one that matters: the failure above happened while nobody was watching a terminal.

`--check` runs the preflight and stops before anything is installed or restarted, which is what makes the guard testable — `TestShipGuard` drives the REAL script against throwaway git repos, never a Python restatement of its logic.

**The install runs with the job OUT of launchd (#411).** `com.aish.web` is `KeepAlive`, so while it is loaded launchd may start it at any moment — including while `uv tool install` is replacing the env it runs from. On 2026-09-24 the log for the install window held respawns failing against a half-written env (an ImportError inside `wcwidth`, then `aish-web: No such file or directory`); after the install, ship's `kickstart -k` and its 10 s window, `launchctl print` showed `spawn scheduled`, and one more `kickstart -k` brought it up in ~4 s. Why the first kickstart was not enough was never established, and nothing here claims it. The sequence is changed so the question does not arise: `bootout` before the install, `bootstrap` after it. Booted out, the job cannot be started mid-install; bootstrapped, it is a fresh job (`runs = 1` in `launchctl print`) that starts because the plist sets RunAtLoad, with no restart to race. Two launchctl behaviours it depends on, both observed on macOS 26 against a throwaway label, never the live service:

- `bootout` returns 0 while the process is still exiting (`state = SIGTERMed`, `print` still finds the job), and a `bootstrap` in that window fails with `5: Input/output error`. So ship polls `print` until the job is gone (up to 60 s) before installing; if it never goes, ship installs nothing and prints the recovery command. Only exit 113 (`Could not find service`, observed) counts as gone — any other `print` failure says nothing about the job and is polled through, never read as gone. The 60 s is a bound, not a measurement: the plist sets no ExitTimeOut, and how long aish-web takes to exit was not measured.
- `bootstrap` returns 0 for a plist whose program does not exist — it means *loaded*, not *running*. Only the health check says running, and on failure it prints what `launchctl print` reports (`state`, `last exit`) as an observation.

Every exit after the bootout puts the job back (an `EXIT` trap): a failed install bootstraps the install that is on disk and health-checks it, but ship still exits non-zero. If uv had already replaced part of the old env before failing, what is on disk is neither build and that job may not start — the health check is what reports it. A failed `bootstrap` says the service is DOWN and prints the exact `launchctl bootstrap gui/<uid> <plist>` to run. A job not loaded at the start is loaded after the install.

The trap is written so nothing can stop it before the bootstrap. It turns `set -e` off and ignores SIGPIPE, INT, TERM and HUP first: under `set -e` a failing command inside an `EXIT` trap ends the trap, and once the terminal has gone (a dropped ssh session: SIGHUP mid-install) even the `echo >&2` announcing the restore fails — which, before this, ended the trap one line short of the bootstrap. It also runs the same gone-poll before bootstrapping, because an interrupt can land while the booted-out job is still exiting, and bootstrapping then fails with 5.

`TestShipRestart` drives the real script past the preflight against PATH stand-ins for `launchctl`, `uv`, `netstat`, `curl` and `sleep`, with a throwaway HOME — including runs with stderr closed, a SIGHUP sent from inside the install, and a SIGINT sent during the gone-poll.

Health-checking probes whatever address the kernel says is listening rather than assuming loopback: this service binds the LAN address, so a `127.0.0.1` probe reports a false failure on a perfectly healthy restart.

## The global console

**ONE** persistent interactive pseudo-terminal for the WHOLE server — not per-session — for TTY-reading programs (`gcloud auth`, `ssh`, `sudo`) the non-interactive `!` path cannot drive. It floats above whatever chat is shown and is untouched by chat switches. Held on `WebServer.console` with a global `console_viewers` set — never on a Session, never on the agent.

Message shapes in: `console_open` (no command — the console's command is fixed) · `console_in{data}` · `console_resize{cols,rows}` · `console_close` (HIDE, keep running) · `console_kill` (destroy) · `console_share{text}`. Out: `console_started{command,cwd}` · `console_out{data}` · `console_exit{code}` · `console_error{text}` · `console_shared{text}`.

**tmux-backed for restart survival.** The PTY runs `tmux new-session -A -s aish-console` (attach-or-create), so the shell lives in tmux's detached server process and outlives `aish-web`; our `PtySession` is merely a tmux CLIENT, and the first open after a restart reattaches to the surviving session. Detected via `shutil.which("tmux")`; absent, it spawns `$SHELL` directly — still global, cross-chat and cross-disconnect, but not restart-surviving. The spawn command is injectable, so tests use a trivial echo loop and need no tmux.

**Lifecycle.** NEVER killed on viewer-leave, `console_close`, session close, eviction or disconnect. Only `console_kill` (which also runs `tmux kill-session`, or a reopen would silently reattach to the killed thing) or graceful `shutdown` (which kills only the PTY — the tmux SESSION survives) end it.

**Broadcast.** One PTY, many viewers: `console_in` from any client writes it, `_console_out` fans out to every client in `console_viewers`, pushed straight to each outbox on the loop thread — never through a session bridge, so console I/O is never recorded in any transcript. A second viewer of a running console gets a `tmux refresh-client` poke so its blank xterm repaints with current state (`PtySession.tty` exposes the slave device path for exactly this). Multi-viewer resize is last-resize-wins: tmux sizes the pane to its single client.

**Load-bearing security invariant: the model has NO write path to the console.** `PtySession.write` is reached ONLY from `_console_in` — the user's own socket — and `agent.py`/`tools.py` never reference the PTY layer (asserted by `tests/test_pty.py`). Console I/O stays out of transcripts, cold replay and model context UNLESS the user selects text and taps Share, which injects it through the currently-viewed session's `agent.add_user_context` — the same user-message path as `!`, logged for `--resume`, launching no task. `TestGlobalConsole` covers the wiring, globalness, survival and broadcast.

**`pty_session.py`** — a subprocess on a `pty.openpty()` pair with `start_new_session=True` (setsid → controlling TTY), streamed over `on_output`/`on_exit` callbacks the class guarantees to invoke on the loop thread (L2). The reader thread uses `select` with an idle-flush to coalesce bursts plus an incremental UTF-8 decoder, since multibyte characters can split across reads. `write()` is the sole input path. `kill()` signals the whole process group, closes the master fd idempotently and reaps; `on_exit` fires exactly once. No agent or model reference, by construction.

## HTTP surfaces

| route | what it serves |
|---|---|
| `/` · `/index.html` | the app shell (`serve_index`), stamped with the asset revision |
| `/ws` | the WebSocket |
| `/static/{path}` · `/fonts/{name}` | assets; fonts via `serve_config_font` |
| `/file` | one image, scoped to `_workspace_roots()` |
| `/frame` | one evidence frame, scoped to the frame store — narrower than `/file`, never wider |
| `/pdf/info` · `/pdf/page` | a PDF's page count, and one page rasterised — same scope |
| `/download` | one file of any type, saved to the device — same scope plus aish's two download stores |
| `/upload` | `POST ?name=<filename>`, raw body |
| `/share` | `POST ?name=&text=&source=`, raw body — the share-sheet inbox |
| `/dirs` | the folder browser |
| `/explain` | one turn's dossier — see below |
| `/export/answer` · `/export/session` | PDF |
| `/offline/index` · `/offline/session` | the offline mirror |
| `/trigger` | programmatic ingress |

**Gates.** The token always exists — generated randomly per run when none is configured, printed by `main()` in the launch URL, compared with `hmac.compare_digest` — and EVERY surface above except the shell and its assets requires it (`TestTokenGate`, `TestUnconditionalToken`). `origin_allowed` additionally rejects any browser request (WS handshake, `POST /trigger`) whose `Origin` host:port differs from the request's own `Host`; a missing Origin (curl, the poller) passes, since browsers always send one on the cross-origin requests that are the drive-by vector — WebSockets are exempt from same-origin and a text/plain POST needs no preflight, which is what makes this necessary (`TestOriginGate`). `/trigger` is token-gated unconditionally: the old loopback fallback is gone, because a same-host reverse proxy makes every request look loopback (L6).

**Security headers.** `SecurityHeaders` (pure-ASGI, every HTTP response) stamps `Content-Security-Policy` and `Referrer-Policy: no-referrer`; WebSocket scopes pass through untouched. `img-src` is self/data:/`CSP_IMG_HOSTS` — the YouTube-thumbnail and static-maps whitelist mirroring export.py — which kills the zero-click `![](https://attacker/…)` channel; the SAME whitelist is enforced in the renderer itself (`[INLINEIMG]` in app.js) so a non-whitelisted image degrades to a link on every path rather than relying on the header being present. `connect-src` names `ws://`+`wss://` of the request's own Host, sanity-checked by `_HOST_OK_RE`, so the socket works behind the wss proxy; `script-src 'self'` holds because index.html has no inline scripts. `TestSecurityHeaders`.

**Load-path weight.** `GZipMiddleware` (outermost, min 512 B) compresses every HTTP response — the critical path was 560 KB raw and now ships ~172 KB, which matters because the service worker's 3 s network-first navigation race is decided on exactly that first fetch. `index.html` links `style.css` in BODY below the boot loader, not HEAD: a pending HEAD stylesheet blocks the first paint entirely, so the inlined spinner never showed on a slow link.

**`/file`** serves images the model generated so they render inline, scoped to `_workspace_roots()` — `roots` + the media store + the scratch dir — which is the ONE boundary the PDF exporter uses too. They disagreed before #188: the exporter trusted the scratch workspace and `/file` did not, so a file the model wrote where it is TOLD to write throwaway files printed fine in a PDF and 403'd in the chat with nothing saying why (`TestFileEndpoint`, `TestImageRootsAgreement`).

**`/frame`** serves the picture of a page aish drove (#289), and it exists because those bytes left the workspace boundary in #318. They used to live in the media store, which is inside `Agent.workspace_roots` — and being inside it is what let the MODEL name a frame to `show_image` and put a picture of a hostile page into its own context, bannerless and untainted (`docs/browser.md`). The bytes moved; the display could not, because a record the owner cannot see is not a record (#295 P6). So this endpoint applies every `/file` rule that is about handing bytes off the machine — token, absolute path, an image type, symlinks resolved BEFORE containment — and changes the one that is about *which* bytes: containment is asked against the frame store, so `/frame` cannot serve a project file. The converse is true in the arrangement that matters and no more strongly than that: `/file` cannot reach a frame because the store is outside the workspace boundary — except where a session root happens to contain the state directory, which puts every store aish owns back inside it, and which costs nothing here because both doors answer to the same token and the same owner. **What must not become true is either door growing into a superset of the other**, and the model's side deliberately does not rest on this at all (`Agent._is_evidence_frame` asks about the store directly). `_is_frame` also accepts an open session's media store, because that is where frames landed before #318 and where the trace rows of every chat already on disk still point — serving one there grants nothing `/file` already refused the same token, and blanking his existing chats would be taking the record away to protect it. `/download` asks the same predicate, so the Save button on a frame's picture viewer still saves. Frames are content-addressed under a digest, so the response is `immutable` like an upload's. `TestFrameEndpoint`.

**`/pdf/info` and `/pdf/page`** (#218) let an attached PDF be looked at, not just read about: `info` answers `{name, pages}` and `page` rasterises one page as a PNG, which the client shows in the photo viewer it already has (`[PREVIEW]` in `docs/web-frontend.md`). Both go through `_pdf_target`, which applies the `/file` rules unchanged — token, absolute path, symlinks resolved BEFORE containment, inside `_workspace_roots()` — plus a `.pdf` suffix and the `%PDF` magic bytes, the same guard `read_pdf` applies to a fetched file, because a `.pdf` that is not a PDF is usually a login wall. **One helper for both**, so a rule cannot be enforced on the page and forgotten on the count. Rendering runs in `asyncio.to_thread` (PyMuPDF is CPU-bound and the loop serves every socket), and pages are **never stored**: the media store holds what the MODEL was shown, and a page somebody swiped past is not that. Repeats are cheap because the answer caches — an upload's bytes cannot change, so its pages are `immutable`; anything else revalidates on an ETag carrying the file's mtime. A page that cannot be produced (out of range, encrypted, corrupt) is a 404 naming which, so the client can show words instead of a broken-image glyph. `TestPdfPreview`.

**`/download`** is how a file gets off the chat and onto the device — the same gate as `/file` (token, absolute path, symlinks resolved before containment) over `_download_roots()`: `_workspace_roots()` plus the two stores aish fetches INTO for the owner, browse downloads and `tool-downloads/` (mail attachments, Drive exports). **Within that scope any file of any type is saved.** It used to be narrower — images and PDFs, the uploads dir, browse downloads — on the argument that the roots are a project tree nobody was ever shown and a `.env` there should answer 415 as it does on `/file`. That narrowness is what left a mail attachment fetched by `tuta_attachments` as a chip that would hand over a PDF and nothing else, and the owner chose the wider door (2026-10-08): he holds the token, the roots are his own machine's folders, and a file in them reaching his own device is not a leak. Outside the roots stays 403. The two stores are named outright rather than only through an open session's roots because a chip in a chat reopened after a restart has no live session behind it, and the file is still his (`test_a_tool_download_is_saved_with_no_session_open`). Every response is `Content-Disposition: attachment` + `nosniff`, so an `.html` is saved rather than rendered as same-origin markup; the filename is sent in both forms (`_attachment_disposition`), the quoted ASCII one REPLACING what it cannot represent rather than dropping it — a name reduced to `----` says nothing about what you just saved — and that same pass is what keeps a quote or a newline in a filename from ending the header early. `TestDownloadEndpoint`.

**`/upload`** takes a raw body with the filename in the query — no multipart, so no extra dependency — rejects bad names, lands the file in the session's roots, and `_classify_attachments` splits the result into native images, native documents and text notes, with only files inside the uploads dir eligible to go native (`TestUpload`). The note text it appends to the turn is written for the MODEL and must never be rendered to the owner; the frontend parses these exact strings to strip them (`[ATTACHMENT-NOTES]` in `docs/web-frontend.md`), which makes the format a cross-language contract with no shared code behind it — so it is pinned from both ends, by `TestAttachmentNoteFormat` here and `test_attachment_notes.js` there.

**`/share`** is the iPhone share sheet's way in (#213). iOS cannot register a PWA as a share target — Web Share Target is Chromium-only and Safari implements only the outbound half — so there is no manifest entry to add and no amount of frontend work that would produce one; sharing to aish is a **Shortcut** with "Show in Share Sheet" that POSTs here (recipe in the README). `name` decides how the raw body is read, and that is the whole interface: WITH a name it is a file (exactly as `/upload`), WITHOUT one it is text, capped at `SHARE_TEXT_MAX` with an announced truncation. The second form exists because Safari shares a URL rather than a file, and percent-encoding a shared link into a query string inside Shortcuts works right up until the link contains an `&`. `chat=new` marks the item as wanting a chat of its own — advisory, recorded here and acted on by the client, because iOS gives no way to open an installed web app at a chosen URL. The query also carries optional `text` (fine for short things) and a free-form `source` label; either a file or text is required and both may be sent. `_store_upload` is the single writer shared with `/upload`, so a shared file is indistinguishable from a picked one everywhere downstream.

**What arrives is PARKED, never run** — that is the whole security argument for the endpoint. It stores the item, prunes the inbox (`SHARE_MAX_ITEMS`, `SHARE_TTL_S`) and broadcasts the list; it opens no session, calls no model and executes nothing. The share sheet stages work for the owner to pick up, and does not become a way for any app on the phone to start an unattended agent (contrast `/trigger`, which does exactly that and is rate-limited and origin-gated for it). The inbox is persisted to `<state_dir>/shares.json` because the normal case is a share arriving with nothing connected and aish-web restarting under launchd before it is claimed; an unreadable file starts an empty inbox rather than failing to start. `hello` carries the list for that same reason — the broadcast alone would only reach a tab that happened to be open. `share_drop` (a VIEW message: it acts on the server's inbox, not on any chat, so it must not claim control) removes an item — sent, or dismissed with ✕, and the file stays in uploads either way — a claimed share is now an attachment the composer holds by path. `TestShareInbox`.

**What was received is logged, because nothing else keeps it (#393).** The item is deleted the moment it is claimed and no access log covers `POST /share`, so a Shortcut that never carried `chat=new` and a client that dropped it were indistinguishable afterwards. Two stderr lines now record it — `[share] <id> received: file|text, source=…, chat=new=yes|no` on arrival and `[share] <id> left the inbox, chat=new=…` on the drop — and they state only what arrived, never a cause; the shared text itself stays out of the log. Not a trace record: a share belongs to no session, so there is no session log for one to go into. `test_the_fresh_flag_is_logged_on_arrival_and_on_claim`.

**Caching on `/file`** splits by whether the bytes at a path can change. An UPLOAD is immutable by construction — `_store_upload` never overwrites, it appends `-1`, `-2` … — so it is served `private, max-age=31536000, immutable`. Everything else is the model's own output, where a regenerated `chart.png` at the same path is exactly what a long max-age would leave stale on screen, so those keep ETag revalidation and no `Cache-Control`. This is what makes the composer's thumbnail a prefetch rather than a duplicate download: an upload is fetched once while the owner types and costs nothing when the sent bubble renders it. Before it, pressing send began a 4.2 MB download of the original at the one moment the owner was watching (`TestFileCaching`).

**`/dirs`** lists folders and files by name for the picker, filtered by `dir_ignore`, and runs its walk in a separate killable process (`_run_fs_child`) with a timeout answering 504 — a hung filesystem must not take the server with it (`TestDirListing`). `list_files` backs @-mention completion with the same walk, cap and scoring as the TUI (`TestFilesAutocomplete`).

**PDF export** calls `export.py` with `_workspace_roots()` as the local-image trust boundary. The answer export's title is written by the answer's OWN model via `_answer_title` (`agent.chat` directly, off-loop under `TITLE_TIMEOUT`, never entering the conversation), with `derive_title` as the deterministic fallback for every failure path including a rambling reply — a title is a nicety and must never fail or block an export (`TestExportEndpoints`, `TestExportAssembly`, `TestExportMedia`).

**Offline endpoints.** `GET /offline/index` (rev + every session's `name/title/snippet/ts/origin`) and `GET /offline/session` deliberately construct NO Agent and take NO session slot, mirroring `handle_export_session`'s token-check + name-safety + `asyncio.to_thread` shape. `/offline/session` has three "don't resend what they have" layers, cheapest first: a matching `If-None-Match` against a weak mtime+size ETag → **304, empty body**; a `since`/`sig` pair whose prefix still verifies → only events after it; otherwise the whole stream. `sig` is `_prefix_sig`, a hash of the first `since` events computed by the SERVER both times and echoed back opaquely, so there is no cross-language canonical-JSON agreement to get wrong. It exists because reconstruction is NOT purely append-only: a command still running at sync time later reconstructs as `command_start → stream → command_end`, splicing events mid-stream, which a naive `since` would silently corrupt. `offline_events()` caps bulk output on `stream.text` and `step.output` — the conversation stays verbatim, the noise shrinks ~10x, and that asymmetry is what makes a full local archive affordable; a pre-trace log falls back to the flat `history` blob. `TestOfflineMirror`. Client half: `docs/web-frontend.md`.

## `/explain` — one turn's dossier (#243)

`GET /explain?session=<name>&turn=<id-or-ordinal>&raw=1`, token-gated like every other surface, returning `explain.dossier()` as JSON.

**A deliberate endpoint, not transcript events.** The trace contract §8.7 anticipated this and named the three reasons: the frontend opens a trace card *before* it dispatches on step kind, so pushing renderless kinds down that channel draws empty cards with running tickers rather than nothing; **the offline mirror writes transcript events into IndexedDB on every device**, and reasoning quotes fetched pages, file contents and mail bodies, which must not land on a phone's disk; and the transcript is the hot path while a dossier is not.

**Two client caches, and `NEVER_CACHE` closes only one.** That list makes the service worker *pass the request through* — the response then meets the browser's ordinary HTTP cache and the bfcache. `no-store` is what closes the second, exactly as the three offline-mirror responses already do. `TestExplainEndpoint` asserts both, because asserting the service-worker list alone tests half the claim.

**Turns are addressed by the `#202` string turn id**, with the ordinal kept only for logs written before ids existed and for typing a number at a terminal. A browser cannot count turns: its first paint is bounded (`TRANSCRIPT_KEEP` = 500 events), so the turn a long chat shows fourth is not the log's fourth — the same trap `[FORK-ANCHOR]` fixed, where *an id cannot be counted wrong*. With no `turn` at all the endpoint answers the LAST turn, which is what the panel opens to.

**`running` is stamped by the endpoint, into the envelope.** A turn with no `task_end` was either interrupted or is still going, and the log genuinely cannot tell the two apart — only the live server knows. Putting it in the dossier would teach the reader to ask about live state, which is precisely what its purity test exists to prevent.

`load()` re-parses the whole file, mid-write, so the build runs in a thread. Raw records are opt-in and capped at `EXPLAIN_RAW_RECORDS`, reporting what they elided: the section exists so a rendering can be checked against its own source, and a truncated list presented as the whole would defeat that.

**The dossier's `sent` section carries a capability per blob (#352).** Each digest a recorded request references — every provider message, the tools payload, a hoisted system text — is stamped with a `sig` by `_sign_evidence` on the way out: an HMAC over (chat name, digest) keyed by the access token. Minted by the SERVER and never by the reader, because it is a fact about this server and not about the log. Keyed by the token so it survives a restart; a holder of the token can call `/explain` anyway, so deriving from it adds no reach.

## `/evidence/{session}/{digest}` — one blob from a chat's evidence store (#352)

`GET /evidence/<session>/<digest>?sig=…&token=…` serves one blob from `<state_dir>/turns/<chat>/` (`aish/turns.py`, `docs/diagnostics.md`): a message exactly as the provider saw it, the tools payload, or the system parameter. Token-gated like `/explain`, and additionally by the `sig` `/explain` minted — so a tap on the step screen is a file read and not a re-parse of a multi-megabyte log, and a digest nobody was handed answers 403 whatever it is. Scoped to the chat by the path: the digest is looked up in that chat's directory only, and a valid sig for chat A is a 403 on chat B. The chat name goes through `safe_session_path`; the digest must be 64 hex characters (400 otherwise) before anything touches the filesystem.

**Two absences, told apart on purpose.** `410 Gone` with the body *evidence for this chat was evicted on <date>* when the chat's directory holds the store's tombstone — the whole chat went to the budget sweep — and `404` with *no such blob in this chat's evidence* when the bytes are simply not there: purged by a redaction, or never written. A client that collapsed the two would be reporting a redaction as a capacity event, or the reverse.

Served as `text/plain; charset=utf-8`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, and `/evidence/` is in the worker's `NEVER_CACHE`: the bytes are what a model was handed and can quote anything a page, a mail or a file said, so they are downloaded rather than rendered and never land in a cache. Deleting a chat deletes its directory (`_delete_session` → `turns.delete_chat`), and the sweep that bounds the store runs from `startup` and from `_finish_turn` — never inside a tool call (`TestTurnsSweepWiring`: a two-tool-call task sweeps once at start and once when the turn ends). `TestEvidenceEndpoint`.

## Feedback → GitHub issue

Two flavours. Text-only web `/feedback` uses the **block flow**: the model emits the finished issue as one ` ```aish-issue ` fenced block (line 1 `title:`, optional `---`, body verbatim), parsed once in the backend by `parse_issue_block` and mirrored in app.js, and never runs `gh issue create` — the frontend renders a review card and on confirm the backend files it VERBATIM on the pinned `ISSUE_REPO` as a user-direct action with safe argv, no approval gate (`TestIssueBlockParsing`, `TestIssueCreation`).

CLI feedback, and web feedback carrying attachments, use the **classic flow**: the model drafts in rendered markdown and runs `gh issue create` itself through the approval gate, because it must upload assets. Attachments are published to a PUBLIC release, so consent is explicit — the draft lists every file with a per-file exclude chip, and a block-flow draft that gains attachments mid-adjustment auto-switches to classic via a server-appended, model-only note (`TestFeedbackAttachmentSwitch`).

## A wire test that waits for a card must be able to FAIL

`recv_until(ws, "approval_request")` blocks until that event arrives, with no bound. That is right when the card is the fixture and wrong when the card is the thing under test: #295 M4 stopped an inert press drawing one, and `TestBrowseApproval` — which pressed a plain `Faktury` button — stopped at that call and hung the whole suite. The run looked identical to a slow machine, and the failing test was found by sampling the blocked process rather than by reading a failure.

So a wire test whose SUBJECT is whether a card appears reads events into a list up to a bound and asserts on the list — `_run_to_done` in `tests/test_server.py`. It also asserts what reached the page, because "no card" and "nothing happened" are different outcomes and only one of them is the feature.
