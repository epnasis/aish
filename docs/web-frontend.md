# Web frontend — `aish/static/`

`app.js` is ~10k lines organised around **fenced regions** (`// [NAME-START] … // [NAME-END]`). A fence means: this code holds an invariant that is not visible from reading it, and breaking it produced a bug someone reported. (No count here on purpose — a number in prose rots the next time someone adds a fence; `tests/test_frontend_docs.py` knows the real one.)

**How to use this file.** Find the fence you are about to touch, read its entry, then read the law it cites. The entry says what the region owns and what breaks; the law says why the shape is what it is, so you do not have to re-derive it. A new fence gets an entry here — `tests/test_frontend_docs.py` fails otherwise.

Full narrative history is in git; this file keeps only what a future edit needs.

## A card that lists values has to render as a list (#251)

`.tool-preview` carries `white-space: pre-wrap`, and that is load-bearing rather than typography. A batch approval card is a LIST — one line per value going into the form — and its entire claim to be *more* oversight than the twenty unseen keystrokes it replaces is that the owner can read those values before he taps. With the default `white-space` the newlines collapsed, and measured in real Chrome at 390px it rendered as one run-on line: `fill in this form on lot.com and send it: 'Skąd' ← 'WAW' 'Dokąd' ← 'Paryż' press 'Szukaj'`.

No JS test would have caught it. The preview string was always correct; the stylesheet threw its shape away — which is the standing reason this project drives a real browser rather than trusting the unit tests it already has. `overflow-wrap: anywhere` stays alongside it: `pre-wrap` must not become `pre`, or a long value pushes the card sideways off a phone. `TestACardThatListsValuesRendersAsAList` pins both.

## The laws

Seven rules explain most of the fences. Every entry below cites one instead of re-arguing it.

**L1 · One owner per fact.** State that must change together changes in exactly ONE function. Every incident behind these fences was a second writer holding a different subset of the same facts — a boot paint that reset no fingerprint, three replay paths each hand-rolling the same zeroing. `tests/js/test_ownership.js` enforces the manifest: `ws` → `[CONNECT-WIRE]`+`[RETIRE]`, `currentSession` → `[SESSION-ENTER]`, `seenAt` → `[SEEN]`, `viewFp`/`viewDirty` → `[SESSION-ENTER]`+`[CONNECT-WIRE]`+`[REPLAY-LANDING]`, `answerEl` → `[TURN-RESET]`+`[ANSWER-OPEN]`+`[ANSWER-CLOSE]`, `currentTrace` → `[TRACE-OPEN]`+`[TRACE-CLOSE]`. Adding an owned variable is one manifest line; deliberately not every variable — over-fencing turns the lint into noise.

**L2 · Hot and cold render identically.** A replayed transcript must produce the same DOM as the live turn that wrote it (`SessionLog.reconstruct_events` is *defined* as "what a live session shows"). So a new live-only field either replays too, or renders nothing. Omit empty keys rather than writing them, and old logs keep replaying byte-identically.

**L3 · Live and replayed are different events.** The same message means different things by arrival path. Anything that is a fact about *this turn happening now* — the clock origin, the seen stamp, a render-error report, scrolling to the answer — must be gated on live, or merely opening an old chat fabricates activity.

**L4 · A claim must be earned.** A fingerprint claims that what is on screen equals something authoritative, which entitles a later path to skip work. Only a path that can honestly make the claim may stamp it, and a fingerprint compares rendered thing to rendered thing. A wrong claim is worse than no claim: it is a silent no-op. Corollary: DOM the server never sent (an un-acknowledged bubble, a mirror paint) can never be filed under a server fingerprint — the fingerprint cannot see it.

**L5 · Recognizers claim or yield explicitly.** Geometry cannot distinguish a flick-scroll from a drawer-open; the zones overlap. Every recognizer records what it decided a touch IS — both when it stands down and when it claims — and eligibility for a window-level gesture is read at **touchstart**, never touchend: a window listener runs last, after element handlers have already mutated the state it would read.

**L6 · The phone is the constraining device.** One-handed, thumb-reachable, and the finger covers the control it is pressing — which is why arm-then-confirm is gone, and why a state change under the thumb is not feedback. Widths are phone widths: an always-reserved gutter costs title text that matters more.

**L7 · A local action never waits on a round trip, and the screen never lies.** Anything the device can already do happens on the tap: identity, title and URL move before any server answer, and the best copy this device holds fills the gap. Drafts survive reloads, un-acknowledged sends come back to the composer, and a screen that cannot show the truth *says so* — a stalled load, a stalled send, an offline bar — rather than leaving the previous chat up pretending to be the new one. Both halves were invisible on a LAN and both were reported from a phone on a bad connection.

## Rating an answer (#207)

👍/👎 with an optional reason, in the answer's tool row. It exists because the rules engine is about to start checking answers before it delivers them, and the only honest test of that machinery is whether the owner is **still correcting turns that passed every rule they were subject to** — a signal aish could not detect at all before this.

Three properties are load-bearing, and each is pinned:

- **One tap does one thing, even mid-sentence.** The chips decline focus (`onmousedown` preventDefault) and commit the open reason themselves. Without that, tapping a thumb while typing blurred the field first, blur committed and removed it, the row lost its height, and the tap landed on a thumb that had **moved** — so the first tap appeared to only close the box. Toolbar controls beside a text field decline focus for exactly this reason; the commit still happens, in an order we choose rather than the browser's.
- **The words survive switching and withdrawing** — kept in `ratingDrafts`, a per-turn map that lives only as long as the tab. Switching thumb carries the reason onto the new verdict (so the latest record is always verdict *and* reason together) and reopens the box pre-filled to edit; withdrawing keeps the text in memory but **does not write it**, because a comment with no verdict attached is not a rating. A replayed reason seeds the draft too, so editing after a reload starts from what was written.
- **The reason commits on the way out, however you leave** — Return, tapping elsewhere, dismissing the keyboard. Blur used to keep the text and send nothing, so a comment typed and then tapped away from was silently discarded; the log held the tap with `comment: ""` and the owner reported, correctly, that his comment had vanished. On a phone, tapping away IS how you finish typing — especially once the box scrolls itself to mid-screen, away from the keyboard's return key. Committing is idempotent, because the browser fires blur after the field is removed.
- **The reason is read back on render.** It was written to the log and replayed with the rating from the start — and then dropped on the floor, because the handler read only `event.rating`. A lit thumb with no words is worse than no comment at all: it reads as though the note was lost. It now renders under the answer, tapping it reopens the box pre-filled (the thumbs toggle the verdict, so without that there is no way to correct a note), and withdrawing takes the words with it. `TestRateAnswer` pins that hot and cold replay carry the identical event.
- **Tapping the lit thumb withdraws it** — `none` written after `down`, never a deletion, so the log stays append-only and readers taking the last record simply stop counting it. A verdict you cannot take back is one you hesitate to give.
- **The reason box is its own row**, under the tool strip rather than inside it. As a flex item competing with eight 40px chips it collapsed to nothing on a phone: the keyboard opened onto a field with no width, which reads as a broken button.
- **And it keeps itself above the keyboard.** Full width was not enough — focusing is not the end of the story on a phone, because the keyboard opens *after* focus and `syncKeyboardInset` then clamps `body` to the visible strip, leaving a box that was on screen when tapped sitting a thousand pixels below the fold. Measured with the clamp simulated: an answer at y≈1420 with the keyboard line at 377 put the box completely out of reach. It now scrolls itself into view on open **and on every viewport change while it holds focus**, because the keyboard arrives, animates and settles across several events rather than one — landing at y≈272, above the keyboard, at full width.
- **The tap records immediately**, before any comment is typed. A rating that waits for a reason is a rating that mostly does not happen, and the *count* is what the metric needs; the reason box opens after and sends a second record for the same turn, last one winning. `tests/js/test_rating_chip.js`.
- **Delivered exactly once.** Recording and delivering were two calls that both fanned out, so every viewer received each rating twice — invisible on screen, wrong in the transcript. The transcript append and the delivery are now separate, and only the delivered copy carries `seen`.
- **It is keyed by the turn id `#202` already mints** for removal — stable live and on replay, so no second identity scheme. The answer element carries it in `data-turn`, populated from `currentTurnId`, which `addUserMsg` sets on both the live and the replay path exactly as `prompt` and `answerTiming` already are.
- **Ratings replay LAST.** `reconstruct_events` defers them to the end of the stream: a rating decorates a turn rather than being one, it is applied by id rather than position, and it can be written long after the turn it names. In file order the frontend would receive a decoration for a turn it has not rendered yet. `TestRateAnswer`.

### The card says why, not just what (#252)

A card showed the action and nothing else, so the owner reverse-engineered its purpose from a tool name and its arguments. One wrong guess held a legitimate verification step and left a fabricated answer in its place (`docs/agent-core.md` for the incident and the agent half). `intentBlock` renders the model's own words for the step, on the `tool` and `command` cards, from the request's `intent` key.

- **Its own box, never the preview.** `.tool-preview` is ground truth the tool computed (#157); this is the model's word for it. They get different visual registers — a labelled, neutral-ruled quote versus the blue-accented fact — because one box for both would lend the claim the authority of the fact.
- **Attributed.** The label says *aish says*, so the card reads as quoting a claim rather than stating a reason.
- **Facts first.** The command (or the args) precede it and the comment field follows it: the owner sees what will happen, then what it is claimed for, then the box that acts on the answer — the comment being how a misread became a refusal in the first place.
- **Absence is rendered.** No reason produces *"It gave no reason for this step"*, not a missing box. That tells the owner he is back to guessing, and it is what makes the silence visible if the model ever stops narrating — narration exists because of an installed rule, not a prompt, and measured 0/0/0 narrated turns with that rule off.
- **Never truncated — a long one FOLDS.** The 120-character snippet the trace keeps cuts the incident's sentence at an abbreviation and drops the entire reason, which is why the card needs its own copy. Past `INTENT_FOLD_CHARS` the block clamps with a *Show more* control, but the clamp is CSS and the whole text is always in the DOM: nothing is destroyed, which is what keeps "never truncated" true after the fix for "sometimes it is a wall of text". The threshold sits at double the incident's own length, so the case the feature exists for never needs a tap.
- **On a task's FIRST step the same words appear twice** — once as the delivered bubble, once on the card — and that is deliberate. Suppressing the card's copy when the bubble already showed it would reintroduce the exact failure this fixes: the owner cannot tell *it gave no reason* from *the reason is somewhere above*, and the bubble scrolls away while the card stays. Redundancy on one step is cheaper than ambiguity on all of them.
- **Every card kind, one gate.** Command, tool, write, read and import all carry it. A reason on some cards and not others is worse than none, because the owner cannot tell *it gave no reason* from *this kind never shows one*. Placement follows the same rule everywhere — after that card's facts (the diff, the path, the args), before its comment field — except the import card, where it goes ABOVE the file listing: the consolidated review (#139) shows whole files, and a reason under them is a reason nobody scrolls back up from.

`tests/js/test_card_intent.js`.

### `[CARD-LATENCY]` — a sub-second tap is a blind tap

The consent design rests on the claim that SOME cards are still worth spending — the rare, checkable-at-a-glance ones. Nothing measured it. What the record held was the negative: an eleven-line grant card is one he scrolls past, and a five-cards-per-search flow trained the tap that lost a purchase. A card tapped blind is **worse** than no card, because it converts a missing control into a *recorded consent* (#306).

`markShown` stamps the card at the moment it goes on screen and `shownExtra` puts the elapsed milliseconds on the `approval` message; the server writes it beside its own `held_ms` (`docs/web-server.md`). Only the browser can know this one — the server's wait says how long the card was HELD, which is an hour of nothing when nobody is attached.

- **`performance.now()`, never `Date.now()`.** A phone waking from sleep, an NTP step or a timezone change must not be able to author a plausible number. Monotonic time cannot go backwards.
- **It measures render → tap, which is an over-count**, never an under-count: a card in a background tab or scrolled out of view still accrues time. That asymmetry is the point — a small value is unambiguous evidence the card cannot have been read, and a large one claims nothing.
- **A card this page never drew reports NOTHING.** A verdict sent after a reload, for a card whose element is gone, carries no `shown_ms` at all. A zero would state the exact finding the field exists to detect, so an unknown travels as an unknown and the server writes it down as one.
- **The stamp happens at render, not at answer time.** Deferring it would make every tap measure zero — the finding, manufactured.

`tests/js/test_card_latency.js`.

### The approval card for a rule shows what it MEANS

A write approval card renders the plan's diff. For a rule that diff is YAML **the owner did not write** — the model named field values and the harness rendered the file — so approving the diff would mean approving an implementation detail he has no reason to audit. The card therefore carries an optional `note`, the compiled meaning in English (*when this, then that*) plus which of his recent turns the rule would have bound, and it renders **above** the diff rather than instead of it: the YAML stays one glance away for anyone who wants it. Set as text, never markup — the words are the owner's own description coming back to him. An ordinary file write sends no note and is unchanged, with no empty box. `tests/js/test_rule_card_note.js`.

**A rule is not a file, to the person approving it.** The card said "Create file", showed a path, counted lines, and led with YAML — so the owner read it as aish having bypassed its own rule tools to hand-write the file. He was deciding about a behaviour and the card described a text edit. A rule write now titles itself by what it is (new rule / rule change / retire rule), names the RULE rather than the path, drops the line counts (nobody decides about a rule by how many lines it is), and folds the file behind one tap. Folded, not removed: the file is still the truth, it is just no longer the first thing. `tests/js/test_rule_card_note.js`.

**Nothing acts on it.** No model reads it, it claims no control of the chat, and the comment never enters the conversation — making a feedback control steer the running session would turn it into a lever the model can be pointed at. It is evidence for the weekly pass (`curate.scan_ratings`, `TestRatingLedger`) and for the owner.

## Connection, identity, and painting a view

### `[CONNECT-WIRE]` — builds the socket and wires its handlers
**L1.** The only assignment of `ws` besides `[RETIRE]`. Every entry to `connect()` (boot, backoff timer, `reconnect()`, foregrounding) goes through it. — `test_choreo_socket_replace.js`

### `[RETIRE]` — disposes the socket being replaced
**L1.** Assigning `ws` does not dispose its predecessor: an orphaned OPEN socket keeps delivering into `handle()`, so every live bubble and step rendered once *per surviving socket* (replay was immune — it `replaceChildren()`s — which is why only the live state doubled). Null the handlers first so no stray `onclose` schedules another connect, then close. Idempotent on any readyState. — `test_socket_retire.js`, `test_choreo_socket_replace.js`

### `[SESSION-FIREWALL]` — drops live events belonging to another chat
**L1.** The server stamps each live delivery with its bridge's session; `ws.onmessage` drops a stamped event naming anything but `currentSession`, closing the switch window where the old chat's tail kept rendering into the new view. Exempt: `hello` (the switch mechanism itself), `session_state` (sent only to non-viewers), `session_renamed` (by name, idempotent). The drop sits at `onmessage`, not in `handle()`, because the replay loop calls `handle()` directly. — `test_choreo_session_firewall.js`

### `[SESSION-ENTER]` — the only writer of "the view is now chat X"
**L1.** Sole writer of `currentSession`, sole caller of `deepLinkSession` and the `aish-session` key. Fixed order: stash outgoing view → reset fingerprint **iff the name changes** → identity → provenance (`offlineViewing`, from `source`) → title → guarded persistence → URL → mirror MRU + pin. The "iff" is load-bearing both ways: a prefetched swipe moves identity ahead of its hello on purpose, so the hello reads as same-session and no-ops instead of rendering twice. `onHello` keeps only what a hello knows (model, recency, workspace, busy/role, peeks). — `test_choreo_session_switch.js`, `test_pending_view.js`

### `[PENDING-VIEW]` — the transcript between chats
**L7.** `resumeSession` leaves ALWAYS: `enterSession` fires on the tap, then `awaitPaint` fills the gap in a fixed order — the offline mirror FIRST (it holds nearly every chat, and was previously consulted only when the socket was DOWN, so on the one connection where it helps most, up-but-slow, it sat unused), then the server's replay through `onReplay`, then a placeholder saying what is happening. `paintFromMirror` re-enters as `source:"mirror"` so the paint claims no fingerprint (L4) and the replay rebuilds over it. `awaitingPaint` IS the race guard, cleared by `paintLanded()` at the top of `onReplay`, so a mirror read resolving after the authoritative paint silently cancels itself. `PENDING_VIEW_SLOW_MS` stops the spinner and offers Reconnect — the zombie-socket case. Broke: the tap did nothing visible until the server answered, so the rail slid away over the chat you had just LEFT — indistinguishable from a tap that never registered, and the common case for anything below the top `PREFETCH_TARGETS` (2). — `test_pending_view.js`

### `[PREFETCH]` — warm peeks of the recency head
**L4.** After each hello settles, `peek` the top `PREFETCH_TARGETS` chats (a view message: no claim, no hello, nothing recorded; a miss answers `gone` on the peek, never the resume path's error, whose toast would blame the user). `resumeSession` paints the peek synchronously after a successful resume send; the authoritative replay then no-ops on the matching fingerprint. A stale peek just misses into a rebuild. Aimed at the MRU head, not swipe neighbours — that is what keeps A↔B instant. Server half: `_peek` / `TestPeek`. — `test_choreo_session_switch.js`

### `[VIEWCACHE]` — stashes a clean idle view's rendered DOM
**L4.** A switch otherwise rebuilds every answer (markdown + hljs). Correct by construction: the transcript is append-only while open, so any change moves `replayFp` (event count + truncation + last event) and every mismatch rebuilds — the cache can make a switch faster, never wronger. Only a CLEAN view is stashed, and `viewStashable` refuses a view holding an un-acknowledged bubble: that is DOM the server never sent, so no server fingerprint can describe it. `viewDirty` is marked at the `onmessage` dispatch, deliberately NOT inside `handle()` (the replay loop calls it too); `VIEW_SAFE_EVENTS` lists what never touches the transcript, so over-dirtying is the safe failure. — `test_view_cache.js`

### `[REPLAY-LANDING]` — the one authoritative repaint
**L4.** `replayLanding` picks `noop` (same fingerprint, clean view, DOM present — the phone-unlock re-replay and the second half of a prefetched swipe keep the DOM *and* the scroll position), `reuse` (stash hit), or `rebuild`. It refuses `noop` over an un-acknowledged bubble, same reason as `viewStashable`. **A mirror paint claims no fingerprint** (`viewFp = offlineViewing ? "" : fp`): mirror events come from IndexedDB, capped and possibly in an older event shape. Proof it matters — adding a `turn` field to `user` events moved neither the count nor the last event, so the replay no-op'd over a chip-less mirror DOM and the delete control was missing from every chat not used since the deploy. A prefetch keeps its claim (peek data IS server data). A session-switch hello resets `viewFp` so a cross-session collision cannot keep the wrong DOM. — `test_choreo_midstream_replay.js`, `test_choreo_trace_switch.js`

### `[SCROLLPOS]` — reading position across a rebuild
**L4.** Remembers an ANCHOR, not a `scrollTop` (a lie the moment any height differs): the top-visible child's index + on-screen offset, in `localStorage["aish-scroll"]`, bounded `SCROLL_MAX_KEPT`, written debounced plus on `pagehide`/`hidden` (the phone case is a teardown inside the debounce window). Keyed on `transcriptFp()` — the transcript ON SCREEN — deliberately not `viewFp`, which a live turn never updates, so the flow this exists for (ask, scroll up to read, come back) would always find it stale. A mismatch falls through to `scrollToEnd(true)` BY DESIGN: something arrived while you were away. — `test_scroll_memory.js`

### `[BACKFILL]` — reading further back than the first paint reaches
**L1.** The replay is bounded (`TRANSCRIPT_KEEP`, 500 events) because a replay is one frame on a socket and a long chat is megabytes. For a long time that bound was the whole story: above it sat "… earlier events trimmed …", a line that said the chat had been damaged when in fact the log was whole and only the frame was small. A 1314-event chat opened at its 815th event, and its first two thirds — six answers and three photos — could not be reached from the app at all (#228).

The marker is now a CONTROL. It asks for a wider window of the same log (`history_more`, a view message: no claim, nothing recorded) and **the ordinary replay path repaints from it** — no second rendering path, no prepending into a live DOM, nothing that can disagree with what a normal replay would draw. The price is re-rendering what is already on screen, paid once, on a deliberate tap.

Holding the reader's place across that repaint is deliberately NOT `[SCROLLPOS]`'s anchor: that anchor is a child INDEX, and every index shifts when a thousand events are inserted above it. **Distance from the BOTTOM** is the quantity that does not move when content is added to the top, so that is what is measured and put back — and it is consumed once, so an ordinary replay afterwards falls through to the remembered reading position like any other.

Past the server's per-request ceiling there is genuinely nothing more to fetch (`more: false` while `truncated` stays true), and the row becomes a plain line saying where the rest is — a control that would do nothing is the same dead end in a friendlier font. A missing `more` reads as "yes": that is an older server, or a mirror paint, and neither should lose the control.

The row is a read that makes a CLAIM ("loading…", disabled), so it goes through `act` rather than a bare `send`: the ledger exists so a claim about the server can be undone when the server never answers, and a zombie socket would otherwise leave the control saying "loading" forever. `endBackfill` is called by the ledger's `lost`, by the refusal path, by every replay, and by a session switch — a backfill in flight belongs to the chat being LEFT, and its reading position must never be applied to the one arriving. Server half: `_history_more` / `TestHistoryMore`. — `test_backfill.js`

### `[WAKE]` — the foregrounding reconciliation
**L1.** The most defect-dense moment in the client: deferred work never ran and the socket may be dead without having said so. Reconciles two subsystems (mirror, connection) in one NAMED function rather than an anonymous listener — a listener you cannot call is a listener you cannot test. The file's other `visibilitychange` listeners (viewport snap, read-aloud wake lock) are unrelated and deliberately untouched. — `test_choreo_wake.js`

### Reconnecting by hand (unfenced)
**L7.** Standalone PWA mode hides Safari's chrome, so a stalled socket has no browser refresh to fall back on. `reconnect()` force-closes the current `ws` — even one still reporting `readyState OPEN`, the zombie the browser hasn't noticed died — and reconnects immediately, bypassing the backoff ladder. Reachable from the session-title `⋯` menu and by tapping the `#connbar` "reconnecting…" bar itself. `requestNewChat()` wraps New Chat's send to reconnect-then-retry when the socket is in a *detectable* dead state (CLOSING/CLOSED/CONNECTING) instead of silently no-op'ing; a zombie is not detectable client-side, which is why the manual control exists as the general fix. Pull-to-refresh was considered and skipped: `#messages` already runs a hand-rolled horizontal gesture with delicate axis disambiguation, and layering a vertical pull on the same element risked fighting it for a case these controls already cover.

### `[OPEN-NEW]` — `?new` starts a fresh chat instead of resuming
For a Home Screen icon or a Shortcut that should always start clean — a shared photo landing in its own chat rather than on top of yesterday's conversation. The whole of it is **consuming the parameter exactly once**: it is read at module load and `replaceState`d out of the URL before anything else looks at it, because a launch parameter left in the address bar opens a new chat on every reload, on every rev-mismatch reload the app performs *on itself*, and on every relaunch of a PWA that restores its last URL — one intent becoming an endless drip of empty chats. For the same reason the flag is cleared **before** the `new` is sent rather than after: `ws.onopen` runs on every reconnect, and a flag still set there opens a chat each time the phone wakes up. On that one load it also suppresses the remembered session and the offline first paint, or the old chat is painted and then replaced, which reads as a glitch.

The rewrite preserves everything else on the URL — the token above all, plus the mount path and hash. Note the flag must be *defined* wherever `offlineFirstPaint` runs: that function reads it inside its own `try`/`catch`, so an undeclared name does not throw, it silently skips the first paint (which is how three choreography sandboxes failed). — `test_open_new.js`

### `[BOOTLOADER]` — dismisses the first-paint spinner
**L7.** Idempotent, fired by whichever path gets there first (hello, mirror paint, token gate), with a 10 s backstop so a wedged boot can never strand the user behind a spinner.

## The live turn

### `[TURN-RESET]` — closes a live turn as a unit
**L1.** A replay is reachable mid-stream from three paths (socket `replay`, mirror tap, warm peek) that each hand-rolled the same zeroing — leaving a half-streamed bubble while its tail arrived into a fresh one, and never closing `currentTrace` at all, so a live trace survived into the NEXT chat and kept its ticker running. `resetLiveTurn(landing)` closes answer bubble + stable-prefix bookkeeping + approval cards + `renderedAnswers` + `finishTrace`, called from `onReplay` and `onHistory`. Two decisions live in it:

1. **A `noop` landing resets NOTHING** — the DOM already IS this transcript (the re-replay every phone unlock produces on a chat that may still be working). Safe only because `[SESSION-ENTER]` drops the fingerprint on any name change, so a SWITCH can never land there.
2. **A mid-stream landing abandons the answer.** `answerAbandoned` encodes: *drop the stale LIVE tail; REPLAYED content is authoritative and re-opens the turn.* Both halves are load-bearing. The server replays merged token events, so `onToken` rebuilds the bubble from the replayed token and the live tail flows on into it — nothing lost or doubled. A stale live token alone would paint a truncated answer AND (via `sawAnswer`) suppress the `done` render carrying the whole text, so it is dropped; worst case is "no live streaming until `done`", never wrong content.

— `test_choreo_midstream_replay.js`

### `[DELIVERY]` — narration is its own bubble (#212)
**L1/L2.** A turn says several things: what it found, what it is going to do next, and finally the answer. Each of those is a **delivery**, and `delivery` closes one — so they land as separate bubbles instead of a single paragraph that grew for four minutes. Three decisions live here.

**The event carries the text as well as ending the bubble**, the same shape `done` uses with `sawAnswer`, because the tokens may never have arrived: a rule-bound turn cannot stream them at all (Verify buffers every token, and whether a turn is the *answer* is knowable only once its tool calls arrive — a token cannot be retracted), and a mid-stream replay drops the stale live tail. In both cases `sawAnswer` is false and the event is the only copy. It clears `answerAbandoned` before painting, because unlike a lone live token this text is **complete**, so the guard that exists to stop a truncated fragment does not apply to it.

**An interim bubble gets no tool row.** That row belongs to the deliverable: the fork ordinal counts *final* answers (`truncate_at_answer` defines them the same way, by not being followed by a tool message), regenerate re-runs the prompt, and a rating must bind to the **turn** — spreading 👍/👎 across however many times the model spoke would fragment the one corpus #207 exists to build. So `closeAnswer(true)` marks the bubble and attaches nothing.

**Both flags it resets describe the bubble, not the turn.** `sawAnswer` and `answerAbandoned` go back to false so the next delivery — and the answer itself — stream into fresh bubbles. `resetLiveTurn` still closes mid-stream bubbles the ordinary way: whether an open bubble is interim is unknowable until the delivery boundary arrives, so there is nothing better to do there. — `test_delivery_bubble.js`

### `[ANSWER-OPEN]` / `[ANSWER-CLOSE]` — the answer bubble's lifecycle
**L1.** One region per stage; with `[TURN-RESET]` (the disorderly end) these are the only writers of `answerEl`. Open claims `turnAnchorEl` — **the anchor is the ANSWER, never the trace card**, which is what used to pin the progress box to the top of the screen for a whole turn. "Scroll while it fills, then stop" is a CONSEQUENCE of `anchorAnswer`'s clamp, not a mode: the target clamps to the bottom while the turn is shorter than a screen, then stops moving once the answer's top can reach the top of the viewport, and content only ever appends below it. Hence no follow flag. The forced `anchorAnswer(true)` is gated on `!replaying`, read at SCHEDULE time (inside the rAF the loop has already reset the flag), or a reload lands at the top of the last answer. Close flushes pending tokens, highlights fences once (safe only when settled), and attaches the copy/read-aloud row. — `test_choreo_midstream_replay.js`, `test_trace_tail.js`

### `[PENDING-SEND]` — your message on screen before the server confirms it
**L7.** Drawn on SEND in a pending state, RECONCILED by the server's echo. The server's version always WINS: it carries the `at` stamp, the `turn` id the delete chip needs, and any attachment notes the server appended. A `queued` event resolves it the other way, into a chip. Matched by TEXT with an oldest-first fallback, because two sends inside one round trip can come back in either order and the echo is not always byte-identical. A `!` command is exempt — its terminal block already carries the command, and a bubble would be the duplicate that was removed once already. `PENDING_SEND_SLOW_MS` turns "Sending…" into a Reconnect offer. Broke: between the composer clearing and the echo arriving the message existed nowhere visible, and a long one read as lost.

**The recovery rule is the load-bearing half, and it is HOLD-THEN-ADJUDICATE.** A bubble whose DOM is destroyed while still un-acknowledged (`clearPendingSends`, from `onReplay`, `renderLoadingTranscript`, `ws.onclose`) has its text HELD — never auto-resent, since the send may well have arrived and a duplicated instruction to an agent that runs shell commands is worse than retyping. It used to go straight back to the composer, and that is a second, quieter way to produce the same duplicate: **"the DOM is going away" is not "the message did not arrive"**, and the rebuild that destroys it is usually a RECONNECT — whose very next act is to replay the transcript the server holds. The recovery fired one moment before the definitive answer, the answer was "I have your message", and the owner, looking at a toast saying it was not confirmed with the words back under the cursor, sent it again. So the replay adjudicates: a transcript containing the message drops it silently, one without it puts the words in the composer with the toast. Matched on EXACT text and on the chat it was sent in — never the oldest-first fallback the live path may use, because a replay carries every message the chat ever had and a positional match would "confirm" a send using something written last week. Held text is persisted (`aish-held-sends`, its own key — a draft is text you are WRITING, and only one of the two may be silently dropped when it turns out to have arrived), and `HELD_RELEASE_MS` hands back anything no replay ever settled, because holding forever is losing what you typed by a slower route. — `test_pending_send.js`

### `[ERROR-KIND]` — a refusal is not a turn failure
Two different things arrive in the same `error` shape. Everything below the guards is written for one of them — your TURN failed — and ends the turn: close the answer, close the live trace, clear busy, red dot, Retry, push notification. A REFUSAL of the request you just made says nothing about the turn, and is a toast: transient feedback about an action, the same register as every other refused action here. Told apart by the machine-readable code, NEVER the prose — the server stamps `refused` at the site that knows (`WebServer._refuse`), because a turn failure travels through the bridge and a refusal down one socket, a distinction the client cannot re-derive. An UNCODED error still ends the turn, unchanged. Broke: asking to delete a message while the chat was working produced the correct refusal AND tore down the running turn's card, taking Stop and Retry with it. — `test_error_kind.js`

### The queue strip belongs to its transcript
Every chip above the composer names a message THIS chat's agent is holding, and its Remove dequeues from whatever session the client is viewing — so `clearQueueChips` runs wherever the transcript is replaced (`onReplay`, `renderLoadingTranscript`). The server re-sends the real queue on attach, so clearing loses nothing: what comes back is the queue of the chat you actually landed in. Broke: only the message chips survived a switch (the pending-cd card was already dropped there, so one half of a strip behaved differently from the other), leaving a chip above the new chat's composer whose Remove dequeued from the WRONG session. — `test_queue_chips.js` (pins the clearing AND the wiring — a chip outliving its view is a wiring bug, not a logic one)

### `[MSG-STAMP]` — when a turn happened
**L2/L3.** Rides `at`, never `ts`: on a live event `ts` means "this turn starts now" and drives the trace clock, and cold replay must never look like a running turn. Sent as EPOCH SECONDS — the log's ISO stamp carries no timezone and a browser would read it as local time, silently showing the wrong hour on a phone away from the server (`record_epoch`; unparseable → None → nothing rendered, never a wrong time). Rendered on the turn's OPENING message only: the two halves are seconds apart, and the answer's row already carries how long it took. ABSOLUTE format — a rail row re-renders so "2m" stays true there, a transcript line is written once and read months later. A read, not a migration: every record has been stamped since the first version of `session.py`. — `test_synthetic_user_turn.js`

### `[SYNTHETIC]` — logged user messages that are not your bubble
**L2.** `_user_event()` tags a live `user` event with the classification `session.synthetic_kind` will reach on replay; `addSystemMsg` renders it as a quiet system row. The only producers are the resume note and `/trigger` — what you type is never routed through it. A synthetic turn IS a real turn (all `case "user"` side effects stand) except that it seeds neither the chat title nor the composer's prompt history. **A resume row prints a fixed sentence, not the note's own text (#285):** the note is written for the model — do not repeat completed steps, and here are the tool calls that were cut off mid-flight, by name and raw URL — and rendering it verbatim put a paragraph of `read_url: https://…` above the answer, in the one place he actually reads. None of it is his to act on. The row says the single fact that explains the half-finished transcript above it; the note survives in full in the log, for `aish explain`. — `test_synthetic_user_turn.js`

### `[RULE-VERDICT]` — aish's verdict is not a paragraph of the answer
**L2.** When a rule fails, the harness goads the model a bounded number of times and then delivers the answer anyway rather than wedging the turn, carrying a line it writes itself: `[aish] rule 'X' not followed: …`. That line is the point — `_verify_answer` records it as the reason: a rule that was tried and failed must be visible to the OWNER, not only to automation.

It rendered in the same font, colour and paragraph flow as the answer, so it read as though the model had said it — an accusation in the voice of the accused, and the owner circled it in a screenshot and asked why it was in his answer (#250). Everything else aish says in its own voice is marked and rendered as a system row (`[SYNTHETIC]`, via `synthetic_kind`'s `[aish: ` marker); this one spells its marker `[aish]`, square bracket and no colon, so it matched nothing.

A block-level rule in `renderMarkdownBlocks`, not a new event on the wire. The prose is not a display string that leaked — it IS the record, in the session log and in the model conversation — so a structured field would describe only turns logged after today while this parser would still be needed for every older one. Two owners of one fact, which `[ATTACHMENT-NOTES]` already settled the other way. — `test_rule_verdict.js`

### `[FILE-LINK]` — a link to a file on this machine is the file
**L2.** aish drives the owner's signed-in portal, presses *Pobierz e-fakturę*, and the invoice lands in its downloads folder — and the answer could only say WHERE it was. `/download` would have served it the whole time; nothing in an ANSWER could ask, because `INLINE_RE`'s plain-link branch is http-only and a local path matched no branch at all.

An absolute path with a file extension now becomes the file. It hands off to `attachmentChip`, so there is ONE answer to what a file looks like and what tapping it does — a PDF opens onto its pages, an image is a picture, anything else saves. Three details are load-bearing: **spaces are allowed** inside the parentheses, because the site names the file and `faktura 09-2026.pdf` is what a real invoice is called; a **file extension is required**, so a site-relative link the model wrote by hand (`[the docs](/help)`) stays text rather than becoming a chip for a file that does not exist; and **`file://` is accepted and thrown away** — aish never writes it, but a model reaching for "a link to a file on your machine" reaches for it unprompted and did, seven inert links in one real answer, and a chat log is never rewritten. — `test_file_link_chip.js`

### `[FORK-ANCHOR]` — which answer a fork branches from
**L2.** The fork point NAMES the answer: the id of the assistant record behind it, minted where it was written and carried on `done` both live and on replay.

It used to be a POSITION, counted twice, by two parties, over two different lists — the browser counting answers as it rendered them (`++renderedAnswers`), the server counting them again over the whole log (`truncate_at_answer`). Those agree only if the browser rendered all of them, and it had not: the replay is capped (`[BACKFILL]`). The arithmetic of the report is exact — a 25-answer chat whose view began at answer 15, a Fork tapped on answer 20, sent as 6, cut at the log's 6th. Fourteen answers of context and three photos short of what was tapped, silently, twice (#229). A second divergence sat underneath it: `reconstruct_events` and `truncate_at_answer` do not even count the same answers (a delivery followed by a tool message is one to the first and not the other), so the two numbers could differ on a fully-rendered chat too.

An id cannot be counted wrong: it either names a record in that log or it names nothing, and naming nothing is a refusal the owner sees. The ordinal survives only as the fallback for a transcript with no ids at all — a pre-trace log replayed as a flat `history` blob, where nothing identifies a record because the records were never written to be identified. Server half: `truncate_at_answer_id` / `TestFork`. — `test_fork_anchor.js`

### `[REUSE-PROMPT]` — reuse restores the message, not just its words
**L1.** Copy and reuse both read the body of the split (`[ATTACHMENT-NOTES]`), because the attachment lines are not part of what was typed. For copy that was once the end of it. For reuse it was a silent hole: the composer has an attachment zone, and a prompt sent WITH a photo came back without one, so pressing send asked the model to look at something that was not there and nothing on screen said so (#230). Reuse now re-attaches the files (skipping any already in the composer). A file since deleted is not filtered out — the chip fetches through the same token-gated `/file` endpoint the transcript's thumbnails use, and falls back to naming it, which stays true. Copy also changed, one step later (#231): it hands back the SOURCE, body plus `![[cat.png]]`, so a copied message keeps its pictures. — `test_reuse_prompt.js`

### `[REDACT]` — delete an exchange
**L6.** The chip is on the PROMPT (a turn is named by its prompt) and at the START of the chip row, so copy and reuse — tapped constantly, without thinking — keep the trailing edge a thumb lands on by habit. What replaces the turn is a quiet, UNDATED `Message deleted` row: an answer above a silently-removed prompt reads as a reply to nothing, but a time ON that row reads as "deleted at", which is not what the only available number means (it is the deleted message's own stamp) — its POSITION between two timestamped turns says when. The tombstone keeps `at` on disk as the audit trail. The word is DELETE everywhere the user sees it: "remove" reads as "taken off this screen", and here the text stops existing. — `test_redact_turn.js`

## The trace card

### `[TRACE-OPEN]` / `[TRACE-CLOSE]` — the live card's whole lifetime
**L1.** Created lazily by the first step that needs it, one per turn; destroyed by `finishTrace` whatever ends it — finished turn, error, stop, or the replay that replaced the transcript it was drawn into (`resetLiveTurn` calls `finishTrace` rather than nulling the variable, so the interval timer and every still-spinning row are finalized on all of those paths). A third writer is how a trace from one chat ended up collecting another's steps. Collapsed while live: the header IS the status line, so `open` on a live card can only mean the reader tapped it. — `test_choreo_trace_switch.js`

### `[TRACE-STATUS]` — the header's status line
**L1.** Priority chain in `traceStatusLine`: Stopping > Waiting for approval > Answering > running tool (the model's own words beat the deterministic `TOOL_STATUS`; parallel reads add `· +N more`) > streaming thinking gist > Thinking… > last turn's words > Working…. The split that matters: step handlers write DATA onto `t` only (`turnSay`/`turnGist`/`liveGist`/`running`/`waitingApproval`/`answering`/`stopping`) and ALL display strings derive inside the fence — the choreo sandboxes load the handlers with `updateTraceHead` stubbed, so string-building in a handler crashes them. `markStopping` is state + `updateTraceHead`, never a one-shot DOM write, or the 1 s ticker repaints "Working…" over it. Keys are omitted when empty, so old logs replay identically (L2). — `test_trace_status_line.js`, `test_trace_thinking_gist.js`

### `[TRACE-TAIL]` — the live card is the turn's last child
**L1.** A turn reads prompt → what the model wrote → what it is doing now, so the live card is the LAST transcript child, sticky to the bottom, where Stop can never scroll out of reach. That order cannot be chosen at creation (the card exists before the answer bubble, since steps arrive first), so `keepTraceLast()` re-establishes it from `scrollToEnd` — the funnel every content-adding path already goes through, which is what makes ONE enforcement point cover appends nobody has written yet. It reads only the `live` class, so a finished card stays put as a footnote under its answer (no end-of-turn reshuffle under the reader). Header order is `status · text · chevron ——— Stop`: the chevron follows the label it opens, because two affordances sharing the trailing edge made the expand tap land on Stop. — `test_trace_tail.js`

### The turn clock
**L3.** `turnStart` is owned by the `user` case — the card is built by the first STEP and destroyed by every rebuild, so it can never be the origin. A browser landing mid-turn is TOLD the origin: live `user` events carry `ts`, read back by `replayedTurnStart`. The step-sum back-date in `accountStepTime` survives only as the fallback for an unusable stamp, guarded by `originKnown` — summing steps measures the WORK, but a turn is work plus every gap in it, so it always reconstructs SHORT (that shortfall is what a swipe away and back looked like: the clock did not reset, it re-derived itself from less). Cold replay is deliberately UNstamped: `reconstruct_events` closes every turn it replays, so it can never land a reader inside a running one. `answerTiming` is wall-clock and therefore gated on `!replaying`. The FINISHED header is the other reader of that same sum, and there it is not a fallback but the only source — a finished turn has no end stamp to subtract, live or replayed — so **every step that draws a row must book its seconds**, or the header contradicts the timeline printed directly under it. `thinking_cancel` did not, and it carries the LONGEST turn of most tasks: writing the answer. A turn that thought for 3.6s, ran one tool for 2.2s and then spent 23s answering summarized itself as "Worked for 5.8s" above its own "Answered in 23s" row. The agent side is the same rule — `_finish_stopped`'s wrap-up is a real answer turn and now emits its own `thinking_cancel`, so a stopped task no longer totals every turn except the one being read. — `test_trace_clock.js`, `TestTurnOrigin`

### `[TRACE-FRAME]` — what the page looked like when the model read it
**L2.** aish drives real pages the owner cannot see, and this is the row that lets him check one (#289). A browse step carrying a `frame` draws a thumbnail of the page as the model was shown it; tapping it opens the ordinary picture viewer, so it pinches and zooms like a photo with no second gesture vocabulary.

Four things are load-bearing:

- **It is a pure function of the step**, which is the whole of hot/cold parity here: a chat redrawn from its log draws the same picture the live turn did, because there is nothing else to consult.
- **`imageSrc` and nothing else builds the URL.** A frame is a picture in the transcript like any other and is bound by the same token-gated `/file` policy; a hand-built src would be a second answer to "which images may load".
- **A frame that will not load says so.** The bytes live in a bounded LRU cache (`docs/media-and-images.md`), so a record outliving its picture is the ordinary end of a frame's life. `onerror` replaces the image with a sentence — never a broken glyph, and never silence, which would read as though nothing had been captured. It says the picture *could not be loaded and the store may have cleared it*, and not that it was purged: from the browser an evicted file, a stale token and a server that is not answering are the same event. `aish explain` stats the path, so that is the surface entitled to the stronger word.
- **Absence names itself.** `FRAME_ABSENT` is three closed reasons matching `browse.py`'s `NO_FRAME_*`: the page was asking for a password (a login form is exactly the picture that must not exist), the owner was driving the browser himself, or the capture did not come back. A step with neither a frame nor a reason draws nothing at all — that is a log written before frames existed, and manufacturing a note for it would claim a capture was considered.

The row claims only that the picture is of the page **at the moment the model was shown it** — not "what the model saw", which is text and a control list, and which would be false the moment a page repaints after the shutter. — `tests/js/test_trace_frame_row.js`

### `[ANSWERING-COLLAPSE]` — collapse the timeline when the reply starts
Fires once at the transition so the answer isn't buried under a tall step list, and never fights a manual re-expand (`t.userToggled`) — which, since the card became collapsed-by-default, is the ONLY way an open live trace comes about. — `test_answering_collapse.js`

## The dossier panel

### `[EXPLAIN]` / `[EXPLAIN-OPEN]` — one turn, read back from the record
The consumption half of `aish explain` (#243). `openExplain(ref)` fetches `/explain` and draws three sections over the document the server assembled — **before it started**, **what happened**, **what it answered**. It began as four, split by record kind (given / thinking / ran / answered), and that was the first thing reported after a day of use: with the thinking in one section and the calls in another there was no way to tell which result a thought followed. Kind is how a file is organised, not how a turn is. The middle section is now the turn's **rounds** — each model call's reasoning beside the calls it issued and what came back — with steering, mid-task trims and brief changes shown between them. `docs/diagnostics.md` carries the grouping rules and the three states. Nothing here re-derives: the ranking, the three states and the summaries all arrive as data, so the panel and the terminal can never disagree about what a log says (`docs/diagnostics.md`).

Four things are load-bearing:

- **Everything is set as TEXT.** This panel renders the untrusted half of the machine: reasoning quotes fetched pages, a tool result is whatever a command printed, and the system text carries the owner's own rules. One `innerHTML` here executes a page aish read. `test_explain_panel.js` asserts no node's `innerHTML` is ever written.
- **The three states are never a blank.** *Not recorded* / *recorded and empty* / *recorded, then deleted* route to three different repairs, and a blank cell reads as the first whatever the truth was. There is a fourth for a log predating the full reasoning record, which kept only a fragment — shown as a fragment, because a snippet presented as "the reasoning" is how someone concludes the model barely thought.
- **The empty notes list never says the turn is fine.** It names how many checks ran. A checker knows only the classes somebody coded, so "nothing unusual" would state the opposite of the truth on the one turn whose cause is an uncoded class — above the evidence.
- **The skeleton is open, the bodies are folded.** Round headers and one-line call rows render immediately; reasoning, arguments and tool output fold behind "show all". The skeleton IS the flow, so if reading it cost a tap per round the reorganisation would have bought nothing.
- **Section bodies are built on first open.** One turn's system text alone is tens of thousands of characters; laying out four sections of it up front costs a visible beat on the phone this is for.

Long bodies are **folded, not truncated** — the record's whole point is that it is whole, so only the first look is short. A note deep-links to the exact round or call it was computed from, not the top of the section — landing at the top of a long stream makes the citation decorative.

**The jump sets `scrollTop` on the panel's own scroller, never `scrollIntoView`.** That call scrolls every scrollable ancestor, including the transcript behind the sheet, and its smooth behaviour turns a long jump into an animation: measured on a real turn, an 8000px jump had not arrived a second and a half later, which reads as a dead control. Navigating inside a panel should be instant and should move exactly one thing.

The check that let a broken deep-link ship asserted a note **had** a click handler without ever calling it, so a jump that reached nothing passed. `test_explain_panel.js` now invokes the handler and asserts where the panel ended up — which is why the fake element grew a `click()` and a small `querySelector`. `xpAbort` cancels an in-flight read when a second turn is opened, and a failed fetch **says so** (L7) rather than leaving the spinner up; offline is the ordinary case, since the transcript paints from the mirror while `/explain` cannot be served. — `test_explain_panel.js`

### A trim marks the turn it prepared
The one governance record that draws a row (#243). Every other one describes a decision you can look up; this one **contradicts what is in front of you** — the transcript above still shows the whole page while the model was handed 200 characters of it, and the transcript is what you are reading.

The row says how many earlier results were shortened and whether the model can read them back on demand; it never says why, and it never names the results — which ones, and their keys, are in the full record one tap below. Singular and plural are distinguished, and it books a step like every other row, or the finished header contradicts the timeline printed under it (the turn clock). — `tests/js/test_trim_row.js`

### The door is the finished trace card
The card is already the turn's footnote, it already replays cold, and it already means "what it did", so it gains one row — `Full record ›` — rather than the answer's tool row gaining a tenth chip for something that is not about the answer.

**The row is added in `finishTrace` and nowhere else.** Both the live path and cold replay reach that function, which is what makes hot and cold render identically (L2); adding it from the `done` handler instead would miss every replayed card and still pass the node checks. It writes DOM only — `currentTrace` stays owned by `[TRACE-OPEN]`/`[TRACE-CLOSE]` (L1).

The card carries the turn id it was **created** with, so the row addresses a turn by id rather than by a position the browser would have to count — the first paint is bounded, so the fourth card on screen is not the log's fourth turn ([FORK-ANCHOR]: *an id cannot be counted wrong*).

**A step-less card is no longer dropped.** It used to be removed unless it carried token usage (#84), which is right when the box only shows steps and wrong once the box is also the door: a turn that answered without running anything is exactly the one worth asking about. It is kept whenever there is a turn to open, and its finished header reads `Answered` rather than `Worked for 0.0s · 0 steps`, which reads as a broken card. `/explain` in the composer is the second door, for turns older than the bounded first paint and for logs written before cards existed.

## The session rail

### `[RAIL]` — the slide-over chat list
**L6.** One panel, two widths: past `RAIL_DOCK_MIN` (900px) it stays open as a sidebar and the app shell is inset. The inset goes on `body`'s padding and the rail needs NO counter-offset — `body` carries `transform: translateZ(0)` so it IS the containing block for its fixed descendants, but a fixed child resolves offsets against the containing block's PADDING BOX, whose left edge is body's border edge (0). Measured, not reasoned: "compensating" with a negative `left` put the rail entirely off-screen. A full-screen list was rejected on purpose — it would be a separate SCREEN, i.e. a second navigation model to reconcile with the desktop sidebar, and it has no sliver of chat to say "this is temporary". No drag-to-close on the list: two recognizers on one surface is the collision that cost the old pager its per-row delete. The search field is docked at the BOTTOM (`.rail-searchbar`, within thumb reach) on the iOS 15+ Safari model, where `body.kb-open` already shrinks the fixed body to the visual viewport so it rides above the keyboard with no extra JS; the New-chat button shares that bar. The "you are here" mark is repainted by `refreshRailCurrent` from `enterSession`, and `renderSessions` prefers `currentSession` over the server's `event.current` — otherwise the next `session_list` (which arrives right after every switch) undoes it, and on a docked rail the row you LEFT goes on claiming to be current. — `test_session_rail.js`

**Docked is TWO facts, and for a year it was one.** The viewport has room (`railDocked()`), and the owner has not put the list away on this screen (`aish-rail-hidden`, localStorage — the laptop's sidebar has nothing to say about the phone's, so this is one of the few genuinely per-SCREEN facts). Only the width used to count, and the whole docked layout was written unconditionally inside the media query, so the class the JS was flipping meant nothing there: the topbar chats button and ⌘O both route through `closeSessionRail`, which refuses while docked, and on the only screens wide enough to dock there was no way to give the chat the full window at all. The showing rules now hang off `body.rail-open`, which is what makes the button real.

**The two writers stay separate, and that is the load-bearing half.** `closeSessionRail` is the SLIDE-OVER's dismiss — the scrim, Escape, picking a chat, starting a new one — and still refuses when docked, because none of those mean "put the sidebar away"; if it wrote the preference, every tap on a chat row would file the desktop sidebar away for good. `fileRailAway` is the one deliberate act and the only writer in that direction; an explicit `openSessionRail` (the toggle, `/resume`, `/delete`) is the only writer back. Both the module-load class and the resize handler read the preference rather than forcing open, or the decision is undone by the next reload or the next drag of a window edge.

Docked, the rail overlaps nothing, so `openSessionRail` stands NO sheets down there — showing the list must not close the dossier you opened it beside. On a phone it covers them and still does. The toggle animates nothing: the shell's padding cannot move in step with the panel's transform (a transition on `body`'s padding fires on the class set at module load, i.e. on every cold load), and half an animation reads worse than none.

**And the button shows the state it is about to change.** This is design Screen 0 (#57), built at last: the layout was taken from that mock and the control was not, which is how it ended up a dead button that also could not have said anything if it worked. One button, two glyphs, chosen by width — because the panel it drives is two different things by width:

- **Slide-over** — a hamburger with the word beside it. The panel is an OVERLAY, the platform affordance for "a list is behind this", and the scrim and a swipe also close it, so the button is not the toggle and `aria-pressed` would describe a switch the owner does not have.
- **Docked** — a sidebar glyph whose left pane is drawn FILLED while the pane is on screen and empty while it is away, tinted `--dim` when showing and the accent when hidden (an accent means "there is something here to get back"), with the word gone: a labelled button in a two-pane layout is naming the pane it is standing next to. `aria-pressed` here, and the name is what the tap will DO — *Hide chats* / *Show chats*.

A transforming hamburger→X was rejected on the same distinction that picked the glyph: an X says *this is covering your work, dismiss it*, which is true of the overlay and false of a pane sitting beside the chat.

**The split between CSS and JS is the invariant.** Everything visual — which glyph, the fill, the tint — derives from `body.rail-open` in the stylesheet, so it cannot hold a different opinion from the panel about which state is painted. `syncRailToggle` sets only what CSS cannot: the wording and `aria-pressed`. It is a READER of the fact, called from every path that writes `rail-open` (open, hide, resize, module load) — including a resize that opens and closes nothing, because crossing the breakpoint changes what the control IS. — `test_session_rail.js`

### The UI says CHAT; the machine says session
The button said *Sessions* and the panel it opened said *Chats*. The split ran much wider than that one control — *Session roots*, *Session exported*, *Allow this session*, *no such session*, *sessions persist* — and it has one cause: **`session` is the machine's word.** It names a log file, an entry in `WebServer.sessions`, a process lifetime. Those are real things, which is exactly why the word keeps leaking outward into text about the thing the owner is actually looking at, which is a **chat**.

So the line is drawn by AUDIENCE, not by file: the wire protocol (`approve_session` is still the action `make_web_approvers` reads), the log format (`session-*.jsonl`), the CLI, the Python identifiers and every comment go on saying `session`. Everything a person reads in the web UI says chat — including `web_usage_context`, because that is the model describing this UI back to its owner and it has to use the owner's words or it is describing an app that does not exist.

Two things a find-and-replace would have broken, and the reason this is pinned by `tests/test_chat_vocabulary.py` rather than done once with a sed:

- **One "session" on screen is not a chat at all** — the browser sign-in note, where it means a cookie jar. It is allowlisted by exact string.
- **The approval echo is display text AND a matcher.** `✓ session-allowed:` is what the server emitted and what the trace card matches to suppress a line it already shows. The server now emits `chat-allowed`, and the matcher accepts BOTH — every log written before the rename carries the old spelling, and a replay must render as the live turn did (L2).

The approval card's middle scope is now **This chat**, which is also more true than the old *Session*: it is scoped to this conversation's approver, and "Session" was being read as "until the server restarts".

### A sheet belongs to the chat, not to the window
Sheets are `position: fixed`, so they never saw the shell's inset and went on centring themselves over the whole viewport. On any window narrower than roughly 1300px that slid the sheet under the docked rail, which is painted above it (z-index 30 vs 20) — reported as the full record sitting *"in the middle and behind the session list"*. The docked query gives `.sheet` and `#backdrop` the same left inset the shell has, which centres them on the chat and makes the overlap impossible rather than layering out of it: the rail is this app's navigation and a picker should never bury it. The dim layer moves with them, so it stops at the sidebar's edge and reads as deliberate. Scoped to `.rail-open`, so a put-away sidebar hands the full width back. `tests/test_desktop_layout.py`.

**And the full record is sized as a DOCUMENT.** Every other sheet is a short list of rows, where the 560px desktop cap is generous. The dossier carries a turn's reasoning, its tool arguments and whatever a command printed; at picker width on a desktop it reads through a letterbox with most of the screen empty. It takes `min(1040px, 100%)` and 92% of the height when there is room — a cap, not a fixed size, so a short record is still a short sheet.

### `[RAILSWIPE]` — the open gesture
**L5.** A rightward drag ANYWHERE on the transcript, following the finger — not edge-only, which is the platform default but a fiddly one-handed target in an app navigated between chats constantly. Transcript children that scroll sideways are handled by `scrollsHorizontally` standing down when the pan STARTS inside one. The listener is PASSIVE and never `preventDefault`s (a blocking touchmove on the scroller is the phone's biggest jank source); `#messages`'s `touch-action: pan-y` is what actually stops the browser scrolling a horizontally-started gesture, and scrolling children opt back in with `pan-x pan-y`. The keyboard guard reads `body.kb-open`, NOT "an editable has focus" — the composer holds focus indefinitely on a desktop, so the focus test meant the gesture never armed there at all (a phone hides that, because the two coincide). `endRailDrag` ALWAYS hands the panel back to the stylesheet, or a gesture ends with an inline transform resting somewhere no CSS class accounts for. — `test_session_rail.js`

### `[SEEN]` — "the owner has read this chat"
**L3.** `seenAt`/`seenSince` (`aish-seen`) is written ONLY by `markSeen`, and nothing ever UNSEES a chat ([FORGET-SESSION] is where that last tried to happen). Called from `[SESSION-ENTER]`, at `done` on a LIVE turn, and on SEND (`addPendingSend` — your own message is a message in the chat, so without it a chat you had just typed into flagged itself unread for a sentence you wrote, and it showed for the whole time the turn ran). That second call is load-bearing: a turn keeps writing to the log after the hello that stamped it, so without it every chat you had just used came back unread the moment you left, and the band became the whole list. `sessionUnread` is pure and takes `current` — the chat on screen can never be unread. It compares the seen stamp against the row's **`out`**, the last thing that went into the CONVERSATION, not `ts`, which is the last thing that happened at all: a running turn writes trace records, so reading `ts` meant a chat that was merely thinking marked itself unread with nothing new to show (`_is_output`, `docs/session-log.md`). An absent `out` — an older server, a mirror row written before the split — falls back to `ts`, never to zero, which would read as "nothing here is ever new". Unread is the rail's organising axis: `Needs you` (holding an approval, or output the owner has not seen) > `Active now` > `Pinned` > date buckets. — `test_session_unread.js`

**It belonged to the SCREEN, and that was wrong here (#232).** The map used to live only in this browser, on the reasoning that *"I looked at it" is a fact about a screen, not about the server* — right for a product with many users, and wrong for one with a single owner and a single pair of eyes. A chat read on the phone whose dot is still on the laptop is the app making a false claim about the person using it, and the attention band, whose entire value is being short and true, fills with chats they already know about. The ledger is the server's now (`docs/web-server.md`) and this map is a **cache plus an outbox**: written optimistically the instant a chat is opened (so reading one offline is immediate and the mirror-painted rail still knows), reconciled with the server's whenever there is one. `pendingSeen` is the outbox half — marks the server has not confirmed, persisted beside the map, offered on connect and retired by `applySeenMarks` when a stamp comes back. A map stored **without** a `pending` key was written by a build that kept unread to itself, so all of it is offered once: the upgrade seeds the ledger from whichever device connects first, with no migration flag to forget.

**Everything rests on merging by MAX, in both directions.** A stamp only moves forward, so arrival order does not matter, a duplicate costs nothing, a re-send is free, and nothing can un-see a chat. That is also why marking seen is deliberately NOT an act in `[ACK-LEDGER]`: the repair for a lost mark is the next connect, which re-offers it, and re-offering can only be right. Replace-instead-of-max anywhere and an older stamp arriving late from the other device flips a chat you just opened back to unread.

**Sharing the stamps forced ONE CLOCK, and that is what moved `[ROSTER]`'s.** A device used to compare its own clock (the seen stamp) against its own clock (the roster row, stamped on arrival by deliberate choice) — self-consistent, and it stopped being true the moment the ledger was shared. So the server stamps the ledger, the roster transition carries `at`, and the hello carries `now`, from which `clockSkew` puts this device's optimistic marks in the server's frame. A phone five minutes fast would otherwise write a seen time from the future and hide an answer in that chat permanently. The clamp is server-side too, so a device that lies still cannot: a mark is never accepted later than now, and never-accepted is always the *unread* direction.

**`seenSince` stays a fact about THIS device**, on purpose. It answers "what has this screen had a chance to show me" — without it a new phone renders the entire archive unread — and it can only ever move something toward READ, never resurrect a dot. Mark-as-unread is deliberately absent: monotonicity is the property that makes the sync safe, so if it is ever wanted it is a SECOND stamp, also monotonic, not a relaxation of this one. — `test_seen_sync.js`

### `[ROSTER]` — the stream of "chat X is now …"
**L1.** Every client hears every chat's transitions, whatever it is viewing. It replaces a PULL: the list and its states refreshed only when this client asked, which it did on opening the rail, so between opens the roster decayed — and the four repairs before it each widened *when it re-asks* instead of making the server tell it. Never announced at all: a chat STARTING, an approval ANSWERED elsewhere (so a phone kept showing *Needs approval* for a card cleared on the laptop), a chat renamed or deleted elsewhere. A row is applied whole and is idempotent, so a duplicate costs nothing and a missed one is repaired by the next row for that chat. `seq` is what makes "nothing changed" and "I missed something" different observations — a gap asks for a snapshot instead of leaving a stale row up forever. **A hello re-baselines it, and a mismatch there marks the roster STALE**: deltas emitted while the socket was down can never be re-sent, so a client that quietly adopts the new sequence carries wrong rows forever. That flag is what let the rail stop asking — `requestSessions` now sends only for a SEARCH (a ranked answer no local state holds) or an incomplete roster (a fresh connection knows only the hello's recency head; a reconnect knows it missed something). Opening the rail is otherwise a local act with no round trip (L7), where it used to be the refresh mechanism — which is why the list was only ever as current as the last time you looked at it. A row carries everything the server already holds about a chat it is RUNNING — title and preview both derive from the in-memory conversation, so the rail's preview line moves with the turn instead of with the last full list. An empty field on a row means "no opinion", never "it is empty now" — a row derived mid-turn has no preview to give and must not blank the one this device can still show. The heads-up is deliberately not the row: every client gets the row, only a client not looking at that chat is interrupted. Server half in `docs/web-server.md`. — `test_roster_plane.js`

**The transition's time rides the EVENT (`at`), never the row.** The row is what `_touch` diffs, so a clock inside it would differ every time and suppress nothing — the plane would republish every unchanged row forever. It used to be stamped on ARRIVAL here, because unread compared it against this device's own seen map and one clock was enough; `[SEEN]` becoming the owner's ended that, since the last-output stamp and the last-look stamp now have to be in the same frame (#232), and the publishing instant is the one arrival was approximating anyway, minus the skew. The LOG-derived stamps stay off the row for the original reason: the server would have to parse a session log to know them, and a chat that just did something has just changed its file, so its parse cache is guaranteed to miss exactly then.

### `[ATTENTION]` — the count on the rail button
**L1.** The badge and the rail's `Needs you` band answer the same question, so they share ONE predicate (`needsYou`, in the partition block) and the badge is a pure function of (authoritative rows, seen map, chat on screen), recomputed by its single owner whenever any of the three moves. Rows arrive three ways: the `session_list` the rail requests, the recency rows every hello already carries (which include each chat's liveness — `_hello` stamps `state` from `self.sessions`), and a pushed `session_state` for one chat, stamped with THIS device's clock because that is the clock the seen map uses. Reading a chat decrements it inside `markSeen`, on the tap (L7). The chat on screen is never counted whatever its state — an approval it holds is a card in front of you, not somewhere else to go. Broke: two writers on two clocks — a `session_state` push ADDED, a `session_list` REPLACED — and a `session_list` was requested only when the rail opened, so between opens the count kept chats you had read, never learned about a chat that stopped for approval, and started EMPTY after a reload; opening the rail refreshed it, so the number you acted on and the list you checked it against could never be caught disagreeing. — `test_attention_badge.js`, plus `TestSessions::test_background_hold_sends_waiting_notice`

**What it counts: an approval you owe or OUTPUT you have not seen — never a turn in progress.** Liveness outranks the stamp inside `needsYou`: a chat that is working is not asking for anything, and will say so itself when it finishes or stops for you. It keeps its unread DOT when an earlier turn's output really is unread — the row says so, it just does not send you somewhere with nothing for you yet.

**Three rounds, and only the third one split the fact.** The count and the list disagreed (round 1); a running chat inflated the count (round 2); a mirror-painted rail could not show what the count named (round 3, `railRows`). Every one of those patched a READER of `ts` — one field moonlighting as "when did anything happen" (ordering) and "when did something readable appear" (unread). The fix that ends the series is `_is_output` in `session.py`: a second stamp, `out`, carried on session rows, hello pages and the offline index, which `sessionUnread` reads instead. The `needsYou` liveness guard survives on its own meaning, no longer load-bearing against steps.

**Round four: WHEN a chat last spoke is the server's fact, not the row's arrival (#275).** Splitting `out` off `ts` fixed which stamp unread READS; a pushed row still had to invent the value, because the only thing a delivery tells you is that it arrived. So `noteAttention` stamped `out = now` for every non-`running` row — right for the case it was written for (a background turn finishing must raise a dot before the next list arrives) and wrong for every other reason a row is published. Every restart put exactly TWO already-read chats in `Needs you`, stamped "just now": the two this client WARMS on reconnect, each of which the server announced because its roster cache is empty in a fresh process. A rename on another device did the same with no restart at all. The server no longer publishes for a load and states `out` on the rows it does publish; the client prefers it and keeps its own clock ONLY as the fallback for a server too old to send it — which is what keeps the #203 case working against an old server and for a chat that has never spoken. — `test_attention_badge.js` §8, `TestWarmingIsNotNews`

**And the count's own rows are always renderable (`railRows`).** The mirror is refused as a SOURCE (its `ts` lags, it cannot see liveness at all, so a cached paint claims nothing — L4), as is a ranked search result (a subset would under-count) — but the traffic runs the other way: the count's rows are laid OVER the cached paint, because a count naming a chat the visible list does not contain is a worse lie than either. A mirror-painted rail has no `Active now` band at all and misses whatever moved since the last sync, and waiting does not fix it: on a phone the socket is usually still reconnecting when the rail opens, and `requestSessions` does not even ASK while it is down. So authoritative rows overlay `state` and `ts`, unsynced ones are appended (the merge re-sorts, or the date buckets below stop descending), and the mirror keeps everything the server row has no opinion about — snippet, cwd, pin. Search is exempt from the append half only: a row that does not match the query is not an omission.

### `[FORGET-SESSION]` — what this device drops when a chat is gone
**L1.** One function for "chat X no longer exists", called from all three ways of learning it: `session_deleted`, a `no_such_session` error, and a warm peek that misses. It drops the warm peek, the stashed DOM, the roster row — **and the mirrored copy** ([MIRROR-FORGET]), which is the one that decides whether the row is still on screen at all. Since `[ROSTER]` made opening the rail a local act, the rail paints from the MIRROR: a chat left there is a chat still in the list however cleanly the server deleted it, until a later sync happens to prune it, and never if it was pinned. **The seen stamp deliberately SURVIVES.** It used to be dropped here too, and that is what turned a stale row into an alarming one — unread is "output newer than this device's last look", so forgetting the look made the leftover row UNREAD, and the chat you had just deleted came back at the TOP of the list under `Needs you`, counted on the badge, answering a tap with "that chat no longer exists". Learning that a chat is gone must never make it MORE prominent; there is nothing to reclaim by forgetting, since `[SEEN]` is capped and session names are never reused. `onSessionDeleted` awaits the eviction BEFORE repainting the rail, or the repaint races the delete and paints the chat straight back. — `test_forget_session.js`

### `[ACK-LEDGER]` — handing a request to the socket is not the same as it happening
**L4.** `send()` returning true means the browser took the bytes, nothing more: **a WebSocket reports OPEN long after it died**, accepting everything and answering nothing (`FakeWebSocket.zombie()` models it; a phone that has been asleep is where it lives). The client treated that as *done* everywhere, and the UI said so — the approval card greyed out, the queue chip vanished, the header said "Stopping…", the title changed. Every one of those was a claim about the SERVER made on the strength of a local function call, and against a zombie socket every one was false: the gate stayed parked holding a command, the message you withdrew RAN, the task went on. A delete is how it surfaced (#210): the log file was still there hours later.

So an **act** is a request that changes something over there, and it stays outstanding until the server RECEIPTS it. The receipt is generic — the server stamps one for any message carrying a `rid`, at the dispatch point rather than in each handler, so no request type can be forgotten and a new one is covered before anyone thinks about it (`_handle`, `docs/web-server.md`). It says *handled*, never *succeeded*: what happened is still carried by the events each feature emits, and those still drive the UI. A refusal is receipted too — it is an answer.

What an act owes the user when it goes unreceipted is a `lost` callback: **undo whatever the UI claimed**, and a claim that cannot be undone must not be made. That is why the call sites hand over their own repair (re-enable the card, put the chip back, un-say "Stopping…", give the title back) instead of this block guessing. One sweep reports all of them together — N toasts in one toast slot say less than one sentence — and the wording is "may not have reached aish", because an act whose receipt died on the way back DID happen. **It never retries**: re-issuing an approval, a stop or a delete on a guess is worse than the failure being fixed, and every act is one the user can simply repeat.

Reads (`sessions`, `files`, `models`, `jobs`, `peek`) are deliberately not acts — a lost query paints nothing and asking again is free. `task` and `resume` keep their own stronger guards (`[PENDING-SEND]`, `[PENDING-VIEW]`), and the console is its own continuous receipt. Those exceptions are a MANIFEST in the test, so a new message type on bare `send()` fails until someone answers the question. — `test_choreo_ack_ledger.js`, `TestReceipts`

### `[CONFIRM]` — the one modal for every irreversible action
**L6.** Replaced arm-then-confirm everywhere, because that guard **communicates by changing the control the finger is covering** (an ICON turning red under a thumb is functionally one tap) and because the confirming tap lands on the SAME PIXEL as the arming one, so a double-tap habit commits. The modal states CONSEQUENCES ("the log file on the server", "the copy mirrored to your devices", "cannot be undone") — a verb and a red button say what you are doing, never what it costs. Invariants: nothing runs until Confirm; every dismissal (Cancel, tap-outside, Escape) is a NO that DROPS the pending action; the action closes over what it was asked about (captured at ask time, never read back at confirm time); Cancel takes focus, never the destructive button; Escape is claimed AHEAD of `escapeExit()`, since the modal can be raised over any surface. Centered with its own dim layer, not a bottom sheet — a sheet is a picker you browse, this is a question you answer. Deliberately no undo: an undo buffer is a copy of the thing just asked to be destroyed. — `test_confirm_modal.js` (also fails if a second bespoke confirmation appears)

### Row anatomy (unfenced)
**L6.** The status icon answers ONE question — what state is this chat in: running (green spinner) > waiting (orange alert) > automated (tinted origin glyph: clock / envelope / bolt) > plain chat mark. It used to answer two badly, with a blue TICK for "the chat you are in" (which the row's own highlight already says, and which reads as *done*) and provenance only when nothing else was showing — so a screen of ordinary chats was a column of identical grey marks and automation was invisible. "Current" is deliberately not an icon. Unread is a badge CORNERED on that icon, not a leading column: the mail convention needs mail-row width, and a reserved gutter spends title text on a state most rows do not have. Bold titles alone were measured on a real phone and found illegible — the dot is the signal, the weight step is support. The pin sits BELOW the timestamp and is `--dim`, NEVER the accent: blue on a rail row is the attention vocabulary (it is exactly what the unread dot is), so an accent pin read as "this one is new", the one thing a pin never means. No per-row trash and no swipe-to-delete — deleting is the chat menu's row, the ONE sender of `delete_session`.

### Reach and consistency (unfenced)
**L6.** New chat exists in TWO places on purpose: the rail's bottom bar (thumb range, where you already are after swiping) and the app header (findable without knowing the rail exists) — same glyph, same styling, because a filled tint on one copy made one action read as two different buttons. The rail button is 44×44 with real separation from the session-title menu, which is `flex: 1` and therefore huge: a near-miss did not just fail, it opened the wrong thing. The pin lives in the chat menu (a rarely-touched per-chat setting was competing for the scarcest space in the app) and its glyph carries the state — upright + solid = pinned, tilted back + hollow = not — because having to read On/Off is not a state indicator. Tilted-and-blue read backwards: a pin at an angle is one that is NOT pushed in.

## Composer, gestures, and reading

### `[COMPOSER-SLOT]` — what sits in and beside the field
**L6.** Split by WHAT THEY ACT ON — the rule to keep when the next affordance arrives. The FIELD owns its content, so clearing is a control inside the field, shown only when there is something to clear; the ROW owns actions on the message, so paste is a button beside attach/dictate/send and is ALWAYS present. One shared slot (paste when empty, clear when not) failed the actual flow: you type a few words and THEN paste ("review this: <url>"), so it hid paste exactly when it was wanted. Mutually exclusive on screen is not mutually exclusive in use. Full-width (`tall`) at the SECOND line, decided by `composerLines()` against the computed line-height — a pixel constant means "two lines" at one reading size and "three" at another. — `test_composer_slot.js`

### `[COMPOSER-FILES]` + `[FILE-DROP]` — the three ways a file gets in
**L1.** The ＋ picker, a **paste**, and a **drop** all end at `uploadFile`, and the name a file is stored under is decided in `uploadName` for all three. That last part is not a tidiness point: a pasted screenshot arrives as a Blob with an EMPTY name (Chrome's `image.png` is barely better — every screenshot you ever paste is then the same file), and `/upload` refuses an empty or dot-leading name, so without it a paste failed with "invalid file name" and read as "paste isn't supported here". The composer chip is then named from the path the SERVER returned, not from the local file: a second `cat.png` is stored as `cat-1.png`, and a chip still saying `cat.png` names the wrong file.

Paste is **additive and never calls `preventDefault`**. Copying a chart out of a spreadsheet, or an image off a web page, puts an image AND text on the clipboard; taking the image by swallowing the event silently drops text the owner may have been after. The field is a `<textarea>`, where a file paste has no default behaviour to suppress, so both survive — files become attachments, the browser's own text paste still runs. The paste BUTTON (`[COMPOSER-SLOT]`) tries `navigator.clipboard.read()` first for the same reason and falls back to `readText`: on a phone there is no Cmd+V, so that button is the only route from clipboard to composer, and text-only made a copied image unpasteable.

The composer chip shows a **thumbnail** for an image, which does two jobs: a name like `IMG_4021.jpg` identifies nothing when you are about to send one of three photos, and the `<img>` fetches the bytes through the same `/file` URL the sent bubble will use — so the picture appears the instant you press send instead of starting a multi-megabyte download at the one moment you are watching for a result (measured at 4.2 MB on the wire after the click, which over a tunnel is seconds). It only works because `/file` marks uploads immutable; see `docs/web-server.md`.

Drop is bound on the **window**, not the composer — a one-line box is a poor target, and the full-window `body.dropping` overlay says so. Every dragover carrying files is prevented: a file dropped on a page NAVIGATES to it by default, which would replace the chat with the image and take the draft with it. `dragenter`/`dragleave` are depth-counted because they fire per element crossed, not per window. — `test_composer_files.js`

### `[ATTACHMENT-NOTES]` — a message has two forms, and files sit where they were written
**L1.** A message that carried a file says so with an **embed**: `![[cat.png]]`, wiki-link style as in Obsidian. Name alone for a file aish keeps (the uploads folder is the only place one can be, and names there are made unique on write, so the name IS the address); full path for a file living anywhere else, where nothing could derive it back. That is the **record form**: what the log stores, what the bubble renders, what copy writes back out, what reuse re-attaches from.

**An embed means the same thing wherever it sits (#233), and every one of them draws the same (#234).** A file between two clauses pushes them apart and sits full size in the gap:

```
This image ![[shot.png]] you should check.

    This image
    ┌──────────────┐
    │              │
    └──────────────┘
    you should check.
```

That is what Obsidian does with an embed, and it is the version that works: the position is kept AND the picture is legible. The first attempt sized a picture to the height of the words beside it — position kept, picture lost, which is backwards. A screenshot two lines tall is unreadable, and being read is the only reason a screenshot is sent. It also removed a heuristic that had to decide when a trailing picture "belonged to the sentence"; with one size there is nothing to decide.

`messageParts` returns the message as an ordered SEQUENCE of text runs and files, which is what lets `addUserMsg` draw each file where the owner put it. Files written together stay together — two photos sent at once are one side-by-side group, as they always were; a run of words between them ends the group. `ownLine` on a file part is about how it was WRITTEN, not how it draws, and only the source derivations read it: a reference written inside a sentence stays in the words, one written alone is re-appended by `recordSource`, and that is what makes copy round-trip.

The whole-line rule this replaced existed so a `![[…]]` the owner TYPED was not eaten — and it mattered because a matched line was REMOVED from the bubble and redrawn as a thumbnail, so a false match deleted their words. A reference rendered in place cannot do that. The rule is now about the outcome instead of the syntax: **a reference that resolves to nothing stays as plain text.** Only the server can decide that — the browser cannot see the disk — so the `user` event carries `files`, the references in THAT message which name a real file, and `reconstruct_events` re-derives the same list so a chat reopened cold draws the identical bubble.

**Empty and absent are different answers and both are needed.** `[]` is "I looked, and none of these is a file", which is what makes prose about the notation render as prose. A missing field is "nobody looked" — an older server, a mirror written before this — where every reference is taken at face value, the behaviour from before and never worse than it. Collapsing the two is not hypothetical: sending the field only when non-empty made "no real files" indistinguishable from "old server", and a chip was drawn over the words of someone writing about wiki-links. The browser found it; no unit test could have.

**Two derivations, and the difference is the audience.** `messageBody` drops the attachment LINES and keeps inline references verbatim — it is what reuse puts back in the composer to be sent again. `stripAttachmentNotes` is the DISPLAY derivation and reads an inline reference as its file name: a title showing `![[shot.png]]` is showing notation, and one that dropped it reads *"the error in , the fix like "*, with its subject taken out. Both mirror `message_body` / `strip_attachment_notes` in `session.py`.

What a MODEL is given is the **guidance form** — a sentence per file saying whether it may look, read, or must open. Built at hand-over and never stored (`docs/web-server.md`, #231). The two used to be one string, written for the model, which meant that sentence was the ONLY record a message had a photo: it was rendered verbatim in the blue bubble, it titled the chat, and every owner-facing surface had to undo it.

**Copy hands back the SOURCE** (`recordSource`), so a message pasted into notes carries its pictures and comes back the shape it left — a file already named inline is not appended a second time. A message read in the OLD prose form still copies out as embeds: one format leaves this app, whatever shape it was read in.

`uploadsDir` arrives in the hello: only the server knows where its own folder is, and without it a bare name is not loadable. Before it lands a name resolves to itself, the thumbnail fails, and the chip names the file — the fallback a deleted file already had.

The three bracketed prose forms are still parsed and always will be: a chat log is never rewritten, so every message written before #231 is in that shape for as long as the chat exists. — `test_attachment_notes.js`

### `[EMBED-AT-CARET]` — a file joins the message where you are typing
**L7.** ＋ writes `![[name]]` under the cursor rather than appending it, so attaching mid-sentence reads as attaching mid-sentence.

**A caret at the END appends a BLOCK — its own line, its own full thumbnail.** That is not a special case, it is the ordinary one: writing a question and then tapping ＋ leaves the caret at the end, which is how essentially every attachment has ever been made. The first version treated it as "inside the sentence" and put the reference on that line, so a plain photo came out rendered at text height — a smudge where the thumbnail used to be, reported as *"embedded photo does not show bigger like before"* (#234). Inline is what a cursor genuinely in the middle of the text gets, which is a deliberate act and the only case position was ever the point of.

Two rules keep the inline case from being annoying: it never lands mid-word (a space on whichever side lacks one, existing spacing not doubled), and an EMPTY composer gets nothing — a photo sent with no words is a whole message by itself, the server appends the reference on send, and typing one in just to delete it is a step nobody asked for. The caret ends after the insertion so typing continues where the sentence does. — `test_embed_at_caret.js`

### `[SHARES]` — what the iPhone share sheet handed over
**L1/L4.** iOS cannot register a PWA as a share target (Web Share Target is Chromium-only; Safari ships only the outbound half), so sharing to aish is a Shortcut that POSTs to `/share`, and what arrives is **parked, never run** — see `docs/web-server.md`. The server owns the inbox: this reconciles the composer against whatever the last `hello`/`shared` said and keeps no local copy, because two devices claiming from one inbox is the ordinary case (the phone shares, the laptop uses) and a local list would drift the moment the other one claimed something.

**A share goes into the composer. There is no strip and nothing to tap.** A file is attached; text is appended. It was a chip you tapped first, on the theory that a share landing mid-sentence must not join a message you were already writing — and that theory cost a real send twice, reported from a phone both times: *"I can see 'shared from iPhone' on the composer but adding a prompt and pressing send does not send the attachment, just the prompt"*, and then the same again for links. The strip sits in the composer's attachment zone, so it READS as already attached. Every app that shares into a compose surface — Messages, Mail, WhatsApp, Slack — pre-fills the field; the chip was the odd one out, and a "tap to add" caption would only have made a pointless step discoverable. The safety property was never the tap: it is that a share starts NOTHING (no session, no model call), enforced on the server and untouched by any of this.

Text is appended at the **end**, on a **line of its own**, and does **not** steal focus. The line break is not cosmetic: what arrives is somebody else's words landing in the middle of yours, and a URL spliced onto the end of a sentence is hard to read back out of a long prompt (trailing spaces are taken with it, so the line you were writing keeps no invisible tail). Not at the cursor: this is an arrival, not something the owner just asked for with a keystroke, so inserting at the cursor could split a word and focusing would throw the keyboard up on a phone unasked. Appending cannot destroy — whatever was typed is still there with the link after it. Terminal mode is skipped entirely (that composer is a shell command line) and the item stays in the inbox for the next repaint.

**When an item is consumed differs by kind, from one principle: consume it once it is somewhere it cannot be lost.** A FILE is released on send (`releaseSentShares`), because an attachment chip is not persisted and a reload would lose it — so a tab closed without sending leaves it waiting rather than silently spent. That release is a plain `send`, not an `act`: if it is the request that goes missing the item is simply offered again, which is what "we don't know whether it was used" should look like, whereas quietly spending a share that never went anywhere has nothing on screen to notice. TEXT is consumed on arrival, because the draft IS persisted.

Both paths need a **ledger** (`textTaken`, `freshHonoured`) rather than trusting the inbox to shrink: `hello` repeats it on every connect, and a `share_drop` that never lands leaves the item exactly where it was — so without one, a link appends on every reconnect. **✕ on an attachment must tell the server**, or the next repaint puts it straight back and the button reads as broken. An arrival **while you are looking** toasts; the first paint is silent, or every reload would announce what was already there.

**`chat=new` gives a share its own conversation.** The intent rides on the ITEM, not on the launch URL, and that is forced: iOS will not open an installed web app at an address of your choosing — `webapp://…/?new` launches the app and drops the query (confirmed on device) — so `[OPEN-NEW]` can only ever serve a browser tab or a second Home Screen icon. Recorded on the share, it works however the app was opened. Three rules keep it from becoming a chat mill: every fresh id is marked the first time it is seen; the whole batch opens ONE chat rather than one each; and an already-empty chat is not worth leaving, or you get a spare row in the rail that reads as a misfire. The attachment is not re-done afterwards — attachments deliberately survive a session switch, which also makes it failure-tolerant: if the new chat never arrives the file is still attached where you are. — `test_shares.js`

### `[ENTER]` — bare Enter sends only in terminal mode; the chord sends anywhere
**L7.** In the PROSE composer bare Enter inserts a newline: autocorrect, IME and dictation all emit Returns that used to fire half-written messages, and a `<textarea>` never implicitly submits its form, so nothing else can. Bare-Enter-to-send survives only in `!` terminal mode (a shell prompt, where running the command is the point), on both the desktop keydown branch and iOS's `beforeinput`/`insertLineBreak` branch. The suggestion popup still accepts a partial completion with Enter; an exactly-typed slash closes the popup instead of falling through to submit. That asymmetry is deliberate — don't "fix" it back into symmetry.

**Cmd/Ctrl+Enter sends in either mode**, and it does not weaken any of the above: the three things that made bare Enter unsafe are all *text input* — none of them can hold down a modifier, so the chord is unmistakably a human pressing send. Without it a desktop had no keyboard send path at all, which is the wrong end of the trade on the pointer that HAS modifier keys (a phone keyboard doesn't, which is why the button remains the universal path and stays the only one on touch). It is checked BEFORE the suggestion popup: with a modifier down the intent is send-what-I-typed, never complete-it. `altKey` is excluded rather than ignored — Alt+Enter is a newline on several platforms, and a send key must not be reachable by a near-miss. The chord is invisible to a reader, so `#send`'s tooltip names it on `FINE_POINTER` only, with the platform's glyph. — `test_composer_enter.js`

### `[TOUCH-FREEZE]` + `[VV-SETTLE]` — selecting text while composing
**L5.** iOS WebKit will not establish a document selection while an editable holds focus, so a long-press on an answer could never copy part of it. Transcript touchstart now blurs the focused editable (the keyboard dismisses — the platform chat convention; a touch INSIDE the focused element, e.g. a card's feedback field, never blurs it) and FREEZES viewport settling until touchend, because those settle steps ran on the dismissal's visualViewport events and moved the text under the still-held finger, cancelling the long-press. Freezing alone is not enough: the dismissal animates `visualViewport.offsetTop` back to 0, and a fixed body still pinned at the old offset slides DOWN by exactly that much — so while frozen `trackViewportPan` keeps `body.style.top` glued to the moving `offsetTop` (top only; the kb-open class, height and every scroll stay frozen). An established selection also suppresses `scrollToEnd` on later viewport events, so it is never yanked to the bottom. — `test_transcript_select_guard.js`

### `[PREVIEW]` — tap a picture, see the picture
Opened from three places that each used to do something else: a composer attachment chip (inert), an attachment on a sent message, and an inline image the model produced — the last two called `window.open`, which from an installed PWA means leaving the app for Safari to look at your own photo. Local images now preview in place; a REMOTE whitelisted image keeps its anchor, because reaching the real URL by an explicit tap is exactly what that link is for.

Two details are load-bearing and easy to tidy away. The **image is not a dismiss target** — long-press on it is how iOS offers Save Image, and a tap handler there makes that fiddly, so the surround, the ✕ and Escape close it instead. And **closing clears the `src`**, or a stale picture flashes when the next one opens and the bytes are held for the life of the page. `closePreview()` returns whether it acted, because the Escape chain reads that: it takes the key ahead of `[CONFIRM]` (nothing can be raised over the preview, since the preview is opened from everything else), and a closed one must not swallow Escape from the sheet behind it. A missing overlay is a no-op, never a throw — the caller is a chip's `onclick`.

**`[PREVIEW-GESTURE]`** is the rest of what a photo viewer is: double-tap to zoom (and again to fit), drag to pan while zoomed, pinch, and — at fit — a drag DOWN that carries the picture with your finger and lets go of it. The transform is a **pure model** over `{scale, x, y}` with the DOM binding kept thin, because the failures that matter here are not "does it move" but "does it move to the RIGHT place", and those are invisible in a screenshot:

- a zoom is anchored at the tapped point, so double-tapping a face enlarges *that* face rather than the middle;
- panning is bounded by the **picture**, not by the element — `object-fit: contain` letterboxes a wide photo, and element bounds let you drag it off into the black margin;
- a drag while **zoomed** pans and never dismisses, or a picture falls out of the window the moment you look at its bottom edge;
- a pinch is measured from where the pinch STARTED rather than compounding each frame, which drifts.

Pointer events, not touch events: a mouse gets the same behaviour free (double-click, drag, wheel) and two fingers are just two pointer ids. **`draggable="false"` + `-webkit-user-drag: none` on the image are load-bearing**, not tidiness — dragging an `<img>` starts the browser's native image drag-and-drop, which fires `pointercancel` and ENDS the gesture, so exactly one move was ever applied and a 220px drag registered as 18px. Nothing throws and nothing logs; the drag just quietly does a fifteenth of what you asked. **iOS needs a second pinch path.** Safari does not hand a two-finger pinch over as two pointer streams — it claims the gesture as page zoom and reports it through WebKit's own `gesturestart`/`gesturechange`/`gestureend`, whose `scale` is the spread since the gesture began. So the pointer-pair path (what Chrome and Android give) is not enough on the one device this feature exists for, and pinching there did nothing at all. `preventDefault` on those events is half the point: without it Safari zooms the PAGE, leaving the app scaled up with no way back inside a standalone PWA. Chrome never fires them, so the wiring is verified by dispatching them synthetically.

**The measurement is layout geometry, never `getBoundingClientRect()` on the image.** That call returns the box AFTER the transform, so every clamp was measured against a "screen" that grew with the zoom: at 6x the bounds were six times too generous and a pinch could fling the photo right off, leaving a screen of black — reported as "pinch pans the photo out of screen" and "panning lets me move it beyond its borders". The model tests cannot catch it (the model is handed a correct view and was never wrong), and it reads as the obvious way to get an element's size, so `test_preview_gesture.js` guards it at the SOURCE level instead. `#preview` is fixed and untransformed, which makes it both a trustworthy origin and the image's `offsetParent`.

**Swiping pages between the pictures in one message.** The set is that bubble's own images (or the composer's), passed to `openPreview` as a group — not everything the chat ever carried, which is not what is in front of you. Horizontal only at FIT: zoomed, a sideways drag stays a pan, because stealing it would make a close-up impossible to examine. **No wrap** — the ends give (`PREVIEW_END_DRAG`) rather than looping, since wrapping saves one swipe and costs you the knowledge of where you are in a set of three. The axis is committed once by `previewAxis` and then kept, or a drag re-decides mid-gesture and wobbles between paging and dismissing. `previewShow` is the one writer of what is displayed (src, name, counter, index move together — a half-applied step showing a new picture under an old name is exactly the thing that defeats telling two photos apart), and the counter is hidden for a lone picture, where "1 / 1" would imply a swipe does something.

**`previewPaint` is the enforcement point, not each gesture.** Every path clamps its own result, and that was not enough: it made "the picture stays on screen" a property of five call sites agreeing, so one new path — or one running before the image has loaded and knows its shape — could put the photo somewhere unrecoverable. Clamping in the paint makes an out-of-bounds transform *unwritable* rather than merely unwritten (the dismissal drag and a swipe in progress are the deliberate exceptions — both are *supposed* to have the picture outside its bounds). The pre-load window is real and invisible on a desktop: until the bytes arrive `naturalWidth` is 0, `previewContent` falls back to the element's shape, and a pinch inside that window is bounded against the wrong picture — so `load`, `resize` and `orientationchange` re-clamp. On a laptop the image is there before a finger can move; on a phone fetching a 3 MB photo it is not.

**Two fingers do two things**, and both must be honoured: they scale by their spread AND carry the picture by the pair's travel. `previewPinch` takes the midpoint where the pinch BEGAN and where it is NOW — it finds the content coordinate under the fingers when they landed and puts it back under them. Anchoring on the current midpoint alone (as it first did) gives a **reversed two-finger pan**: the correction is `(to - centre)(1 - ratio)`, which turns negative the moment you are zooming in, so the picture slides the opposite way to the hands moving it. Unmistakable in the hand, and invisible to every pinch test that keeps the midpoint fixed — which is exactly why it shipped, on both the pointer and the WebKit path.

`reportViewport` carries the preview's state when it is open — scale, offset, measured view, natural size, the painted rect and `complete`, beside the `rev`. A misplaced picture is otherwise only describable in words, and the numbers that would settle it live on the device it happened on. It is **snapshotted at the end of each gesture and kept after the preview closes**: the report is reached by typing `/debug` in the composer, which the preview covers and which closing resets, so a live-only reading could never be taken for the one case it exists for.

The image is **full-bleed** with the bar floating over it on a gradient, rather than the bar taking a strip out of the top. A viewer should give the whole screen to the picture, and a bar that owns its own band leaves a black stripe you can pan the picture away from — which reads as the picture escaping even when the clamp is right.

There is deliberately **no `setPointerCapture`** either: capturing on a transformed element lost the capture a frame later with the same result, and the overlay is full-screen with the listeners on it, so the pointer has nowhere to escape to. `touch-action: none` on both the overlay and the image, or the browser claims the gestures first. The `settling` transition is added only when letting go — during a drag it makes the picture lag the finger, which reads as the app being slow. `previewReset()` runs on open and close, or a new photo appears already halfway into the last one's corner. — `test_preview_gesture.js`

**A PDF previews as its PAGES** (#218), through this same viewer — the pages ARE the pictures, so swipe turns a page, pinch reads the small print, and the counter is the page number, with no second gesture vocabulary and no PDF renderer shipped to the client. Two alternatives were weighed and rejected: an `<iframe>` at the file gives a real PDF viewer on a desktop and fails on the device this is for (iOS Safari renders only the FIRST page of an embedded PDF, and a standalone PWA has no browser chrome to escape to), and a client-side renderer is a megabyte of library for something the server already does — aish depends on PyMuPDF, and `read_pdf` rasterises an unreadable page for exactly the same reason (`docs/documents-and-pdf.md`).

Three things make it behave like a picture rather than like a download:

- **Page 1 goes up on the TAP** (L7). The count arrives afterwards from `/pdf/info` and only decides how far a swipe may go, so opening an attachment never costs a round trip. `previewAdoptPages` is guarded on the document still being the one open — the answer lands from a `fetch`, and the tap that closed the preview or opened another file has no way to cancel it. A count that never arrives leaves a readable one-page document, which beats an error over a page the owner can already see.
- **The overlay says what it is doing.** A photo is already on the device; a page is RENDERED when it is asked for, and black screen during that reads as a preview that opened onto nothing. `#preview-status` says `Rendering page N…` after `PREVIEW_STATUS_MS` (a page that renders quickly shows no spinner at all — the flash is more noticeable than the wait) and names the failure when the page cannot be produced. It is `pointer-events: none`, or it would swallow the gestures of the picture under it.
- **Neighbouring pages are prefetched, photos are not.** A photo's bytes are already here (the bubble or the composer chip fetched them); every page is a render nobody has asked the server for yet, and a swipe that waits for one feels broken.

`previewShow` stays the one writer and now moves the status line with everything else, skipping the `src` write when it has not changed — re-setting it restarts the load of the page already on screen. It compares against `previewSrc` rather than reading the DOM back, because the DOM returns an absolutised URL that a relative one can never match. Chips open from both ends: the composer's (deliberately without a page-one thumbnail — that would rasterise a page for every PDF being held, and unlike `IMG_4021.jpg` a document's name usually says which one it is) and a sent message's, decided by the PATH rather than the note's `kind`, since a PDF outside the uploads dir is logged as a plain `[attached file: …]` and is just as readable. — `test_preview_pdf.js`

### `[ATTACH-SAVE]` — getting the file, not just a look at it
**L1.** Looking at an attachment is not having it: the preview could pinch a photo and page through a PDF, and there was still no way to put either in Files. Four decisions:

- **It saves the FILE, never what is on screen.** For a PDF that is the document, not the page being read — a long-press on a page would save that page's PNG, which is the wrong object and silently so. Every page item therefore carries the same `file`, and `previewSaveTarget()` is read at the moment of the tap, since a swipe moves the file under the button.
- **One saver.** The bytes go to `saveBlob`, the same function the PDF export already saves through, because "put a file on this device" is one behaviour and two of them would diverge on the phone first.
- **The name comes from the chat, not the response header.** The server's quoted fallback is an ASCII transliteration, and the client already holds the real name — `Zażółć.pdf` must not land as `Za____.pdf`.
- **A refusal says so.** A file deleted since it was sent, or a server that cannot be reached, toasts with the name and the reason. A tap that quietly does nothing is indistinguishable from a tap that missed.

The button lives in the preview bar, before the ✕ (which keeps the trailing edge a thumb lands on by habit), and is hidden when nothing is behind the picture. Its tap had to be exempted from "a tap on the surround closes": the button's own handler runs first, and the close scheduled behind it tore the viewer down at the moment you asked it to save something. Chips act too — a PDF's opens the preview, and **everything else SAVES**, because a chip that names a file and then refuses to hand it over is worse than no chip; the `title` says which, since the two look identical. — `test_download.js`

### `[ATTACH-SHARE]` — sending the file on, not just filing it
Save answers "put this on my device", and on a phone that is the *less* common want: after reading a document you send it to somebody, and doing that from Files means leaving the app, finding the file again in a second app, and sharing from there. iOS's own share sheet is one tap and reaches Messages, Mail, Photos, AirDrop and every other app at once, and the Web Share API can hand that sheet a real `File`. Four decisions:

- **The button is drawn only where FILES can be shared.** `navigator.share` alone is text-and-URL sharing, which every desktop browser has — offering the button on the strength of it would open a sheet with nothing in it, and a picture that "shared" as no picture is the worst of the outcomes. `canShareFiles()` probes with a dummy `File` through `canShare`, once per page (the answer cannot change under it), and the button is hidden where the answer is no. It is asked a SECOND time with the real file at the moment of the tap, because a browser can share files in general and refuse a particular type.
- **The bytes are the FILE's, never the screen's** — the same object and the same `previewSaveTarget()` Save reads, so a PDF shares as the document rather than as page 7's PNG, for the reason `[ATTACH-SAVE]` gives. The `File` carries the chat's name (the header's is an ASCII transliteration) and the response's content type, because the receiving app picks itself from both.
- **The fetch starts on the PRESS, the sheet opens on the release.** iOS only opens a share sheet for a tap that is still current, and a multi-megabyte PDF arriving over the tunnel outlives that window — so `pointerdown` primes and `click` hands over an already-resolved `File`. When the timing loses anyway (`NotAllowedError` on the one tap that had to wait), the file is now in hand and the toast says *tap share again*, which is an instruction rather than an error; the same refusal on a tap that waited for nothing reports a plain failure instead of sending the owner round a loop that already happened. A cached FAILURE would be the opposite mistake — a fetch that failed is a server that was unreachable a second ago — so only the File is kept.
- **Dismissing the sheet says nothing.** `AbortError` is a decision, not a failure. Everything else — unreachable server, deleted file, unshareable type — toasts with the name and what happened, and the type case points at Save, which still works.

It sits before Save, which keeps the ✕ on the trailing edge a thumb lands on by habit, and it needed no exemption from "a tap on the surround closes": that rule already spares any `<button>`. — `test_share.js`

**File names are shortened from the MIDDLE** (`shortName`), on both the composer chip and a sent message's chip, with the full name on `title` and in the preview's own bar. The end of a name is where it differs — `IMG_4021` vs `IMG_4022`, `-final` vs `-final-2`, and the extension — so a plain trailing ellipsis removes exactly the part that tells two files apart, which is what "the names are cut so I can't distinguish some of them" was about. — `test_preview.js`, `test_composer_files.js`

### `[ANSWER-TOP]` — jump to the start of an answer
The chip lives ON the answer (that is what "this answer" means) at the far right of the tool row, apart from the cluster that acts on the answer, because it navigates. One arithmetic trap worth the comment: `#messages` is a SIBLING below `#topbar`, not underneath it, so an element at the scroller's own top is ALREADY clear of the header; subtracting the header height as clearance (which reads as obviously right) overshoots by exactly the header, and on a short transcript lands at 0 — which looks like a working scroll-to-top button and is not the feature. It HIDES itself when the answer is no taller than the viewport: if it fits, then whenever you can see its tool row you can already see its first line, so tapping scrolls nowhere, which reads as broken rather than as "nothing to do". Height-vs-viewport is the whole test (scroll position never enters it), re-evaluated by a ResizeObserver because images, fonts and the reading-size stepper all change an answer's height after it is built. — `test_answer_top.js`

### `[ACTIVE-APPROVAL-CARD]` — which card a keystroke acts on
The last card still awaiting a verdict, newest-first so stacked cards clear bottom-up, matching where the eye is. `CARD_SHORTCUTS` is data (A=approve/install, D=deny, T=trust dir, E=edit); a key acts only when the active card actually HAS that button, is routed through the button's own onclick so edit/scope/feedback handling is unchanged, and never fires while typing in a comment field. On desktop (`FINE_POINTER`) a pending card takes focus and verdict buttons show `.key-badge` chips, not just tooltips. — `test_approval_shortcut.js`

### Card accents and voice (unfenced)
Approval-card accents are classified **client-side**: only destructive-looking commands (`looks_destructive` — sudo/rm/mv/kill/`--force`) take the orange danger accent, everything else the calm blue. The gate itself is untouched by this — it is a reading aid, not a policy, and must never become one. Voice is frontend-only with no server involvement: mic dictation into the composer (SpeechRecognition, hold-to-switch language), auto read-aloud of replies to *dictated* messages (speechSynthesis, per-paragraph language detection), read-aloud controls docked in the composer row, and a `/mic` diagnostic. iOS dictation rebuilds each recognition session's transcript from all its results on every event rather than appending, which is what fixes cumulative duplication.

### `[ESC-EXIT]` — what Escape leaves
Escape leaves `!` terminal-input mode and deliberately does NOT touch the global console: there Escape is a real key (vim/tmux/less) and passes through to the PTY — close the console with its button or `Ctrl+\`. `[CONFIRM]` claims Escape ahead of this. — `test_escape_exit.js`

## Rendering

### `[INLINEIMG]` — which remote images may load
A non-whitelisted remote image renders as a tappable non-embedded link on every path (live, offline replay, export preview), so the zero-click `![](https://attacker/…)` channel stays closed even if the CSP header is ever absent. `IMG_FETCH_HOSTS` is kept in lockstep with `CSP_IMG_HOSTS` in server.py. Arbitrary image sources work through `show_image` instead, whose fetch is server-side — security preserved by RELOCATING the fetch, not by loosening policy. — `test_image_fetch_whitelist.js`

### Markdown and rich content (unfenced)
`renderMarkdown` is hand-written — there is no build step and no markdown library on the client — so its rules are pinned individually. Every external http(s) link carries `target="_blank"` + `rel="noopener noreferrer"` so it opens in the system browser; the in-app `aish-reply://` scheme stays a `<button>` and is never turned into an anchor (those are the quick-reply chips the model is told about in `web_usage_context`, and they rendered as raw markdown text until the inline-syntax regex learned the scheme). The list parser absorbs an item's continuation — blank lines and lines indented under the marker — instead of terminating the list, or a multi-paragraph item silently ends its own list. `YOUTUBE_RE` matches all three URL shapes including Shorts, and its `group(1) || group(2)` id read is kept in lockstep with `export.py`'s `_YOUTUBE_RE`. Live terminal blocks are capped by `appendTermLines`/`capTermLines`: a command with huge output otherwise grows the block unboundedly and freezes the tab (the server-side half is `StreamCoalescer`). Slash commands need a case in `handleSlash` as well as an entry in `SLASH_COMMANDS`/`SLASH_ALL` — a missing case falls through to "unknown command", which is how a shipped slash command can exist everywhere except the web. — `test_markdown_links_lists.js`, `test_quick_reply_render.js`, `test_youtube_shorts.js`, `test_term_stream_cap.js`, `test_session_slash.js`

### Rich embeds and the poster form (unfenced)
A whitelisted YouTube or Google Maps link becomes an inline card in the WEB transcript only (#50); the CLI keeps a plain markdown link. Only strictly-matched ids/queries reach an iframe `src`, decoded then re-encoded, and every frame is sandboxed, cross-origin and referrer-stripped. `MAPS_RE` accepts exactly two shapes — `?q=`/`?query=` for a place and `saddr`+`daddr` for a route — so a tool that emits a `?cid=` or a `/maps/@lat,lng` link silently gets a flat hyperlink instead of a map. That is not a rendering nicety: it is the contract a map-producing plugin tool has to hit, which is why the installed google maps tool's own check script asserts its emitted links against this very regex.

`[![alt](image)](url)` — an image that is also a link — is the one nested inline form the renderer parses. It is matched by `IMAGE_LINK_RE`, deliberately kept OUT of `INLINE_RE`: that regex's plain-link branch would read a remote-hosted poster as a link labelled `![alt`, and adding a branch would renumber ten capture groups the renderer indexes by hand. `inlineMd` tries it first at each position and a tie goes to the nested form.

Its payoff is the **poster-backed card**: the picture a tool already produced paints immediately, and the live iframe is built only on tap. Beyond saving a frame load, the poster is same-origin and already stored, so it is what stays visible when the frame cannot load at all (offline, or the host blocked) — where an eager iframe leaves a black box. A poster resolves through `imageSrc`, the same whitelist `inlineImage` applies, so a poster can never become the zero-click fetch `[INLINEIMG]` exists to close. A bare maps link with no poster keeps loading eagerly. — `test_image_link_embed.js`

**A video card takes a poster too, and its still survives the player.** Both halves are #217. The poster was accepted by `embedForLink` and then silently dropped on the YouTube path, which re-fetched `i.ytimg.com` instead — a second copy of bytes already on disk, and the wrong copy: `/file` images are in the service worker's cache and the offline mirror, `i.ytimg.com` is in neither, so a chat read on a plane showed a black card where the picture had been. And activation used to `replaceChildren(frame)`, throwing the still away at the one moment it becomes the only fallback left; the frame is now laid OVER it. A cross-origin frame cannot be asked whether it worked — `load` is the only signal it gives and a frame that never loads gives none — so silence past `EMBED_FRAME_SLOW_MS` (8000 ms) is read as failure: the still comes back with *Couldn't play here — Open on YouTube*, the card is tappable again, and the anchor stops its own click from bubbling into a retry (L7 — the screen says what it cannot do). Generous timeout on purpose: being early yanks a player that was merely slow. — `test_video_card.js`

### `[EMBED-HANDOFF]` — what a tap on an embed card looks like while the frame arrives
Reported from the phone as *"clicking loads the frame but does not start it so I have to click twice"*, for the video card **and** the map. Two different things, one cause.

**The second tap on a video is real and cannot be removed** while the video plays in place. `autoplay=1` is on the frame's URL, but a user gesture does not cross into a **newly created cross-origin iframe**, so on iOS the player arrives paused whatever it asks for; the working play button is YouTube's own. The alternatives were weighed and rejected: handing off to the YouTube app is one tap that LEAVES the app (the same thing `[PREVIEW]` exists to stop for pictures), `mute=1` autoplays silently and buys a tap to unmute instead, and loading every frame eagerly is a megabyte-plus of third-party player per card plus a request to YouTube for a video nobody played. Preloading on scroll-into-view would genuinely be one tap and is the owner's call, not a default.

**What was actually broken is the FIRST tap having no visible result.** The video card kept the same still with our badge swapped for a loading frame; the map card was worse — it `replaceChildren`'d its poster away and left an empty box for as long as Google took, then painted a live map that looks like the poster it destroyed. A tap whose only outcome is the same picture reads as a tap that never registered (L6: the change under the thumb is not feedback; L7: the screen says what it is waiting for — the same law behind the pending-send bubble). So the badge goes **at once**, a spinner with words takes its place over the still, and it clears on the frame's `load`, leaving the player's own controls as the only thing to press — never two play buttons at once. The map's poster now survives the swap exactly as the video's still does, and `playsinline=1` keeps an iOS play from throwing the video into the native fullscreen player, which is a *third* way for a tap to feel like it left the app. The overlay is `pointer-events: none`: the card owns the gesture, and a tap landing on the overlay instead would silently do nothing. — `test_video_card.js`, `test_image_link_embed.js`

### `[ONE-CARD]` — one playable card per video per answer
A turn about a video produces the still AND a link to it — `show_image` on the thumbnail, then "here is a summary of [the video](…)" in the prose — and each became its own card, so the answer opened with the same picture twice, once with a play button on it (#217; the transcript that reported it also shows the two stills fetched from *different* CDN hostnames for the same id). The first occurrence wins, later ones degrade to a plain hyperlink, and `imageLink` degrades to a **link rather than to its picture** — the whole point is not painting the still twice, in either order. The agent side removes the cause rather than relying on this: `_show_image` hands back the composed poster line for a thumbnail, so the model emits one construct (`docs/media-and-images.md`). This stays as the backstop, because the prose link is a separate decision the model makes on every turn.

**The scope is the ANSWER, not the render call** — and while a turn streams those differ: `renderAnswerNow` freezes a growing prefix and re-renders the live tail on every token. So the set is the caller's (`answerCardIds`, reset with the other answer-bubble state in `[ANSWER-OPEN]`/`[TURN-RESET]`): the prefix commits into it, the tail is handed a **copy**, or a card would demote itself to a plain link one token after appearing. `renderMarkdown` is the scope's only writer, restoring the enclosing one on the way out so nested renders (list items, blockquotes) inherit rather than start fresh — a card inside a list item would otherwise be blind to the one beside it. An unscoped render (a tool result, an issue draft) claims freely: there is no answer for it to duplicate within. — `test_video_card.js`

### `[RENDERERR]` — telling the model an image didn't render
**L3.** The browser is the only place that knows something failed to render, and it used to keep that to itself. Failures are batched (debounced, capped) and reported with the model's ORIGINAL target — never the rewritten `/file?…&token=` URL, which would put the access token in the session log. `noteRenderError` returns early when not `live`: a failure to render is a fact about the turn that WROTE the image, so a replayed report is ledger noise that COMPOUNDS — one chat accumulated 53 identical records and was marked unread by the act of being read. The gate sits in that ONE function so a future call site cannot forget it; the server dedupes as the backstop no client can route around. — `test_render_error_report.js`, plus `docs/trace-records.md`

## The console

### `[XTERM-LAZY]` — the terminal emulator is not on the boot path
xterm.js (~285 KB) is needed only when the console opens, which most sessions never do. Loaded on first open, stamped with the page rev so devices cache immutably and a deploy busts them (the old static `<script>` tags were unversioned — a known stale-after-update gap). The big half of the white-screen fix. — `test_xterm_lazy.js`

### `[CONSOLE-LINKS]` — clickable URLs in terminal output
Reconstructs a logical line by joining a row with its neighbours whenever the row is packed to the right margin (the geometry signal for a hard wrap tmux did NOT mark) or xterm flagged the next row `isWrapped`, then maps matches back to buffer coordinates. Capped at `MAX_ROWS` so a screenful of full lines cannot run away. — `test_console_links.js`

### `[CONSOLE-LINK-TARGET]` — which browser a console URL opens in
There are two browsers now: this device's own, and aish's remote Chrome — the one that screenshots a page and holds the owner's signed-in sessions (`docs/browser.md`). Which one is wanted depends on the link (an auth URL wants the browser aish will later read that site as; a doc link wants the phone's), so a tap follows a **remembered default** and a **hold offers the choice**.

**The hold is the whole design problem, because it was already spoken for.** A stationary hold on the console means Select mode — the copy gesture, since a terminal has no selectable DOM to long-press. So it is claimed **only when the press landed on a URL** (L5: a recognizer states what it decided the touch is); everywhere else the gesture is untouched, and `consoleHoldAt` is the one place that decides, returning `"select"` for the caller to act on rather than half-entering either mode.

**One answer to "is that a link".** The hit test maps the point to a terminal cell (a uniform grid inside `.xterm-screen` — no private xterm API, no per-row elements, so it is testable with no layout engine) and then asks `[CONSOLE-LINKS]`, the same provider the tap goes through. A second URL scanner would offer the fragment printed on the pressed row for any URL wrapped across rows — which is most of the ones worth opening from a console, since they are auth links.

**The lift belongs to the hold, and the menu refuses to act until the hold is over.** A touch that raises the menu is still down; the lift then synthesises a click on whatever is under the finger — which is now the scrim the menu just raised. Every hold dismissed its own menu instantly, and the fake-DOM checks could not see it: no scrim to hit and no layout to hit it at.

It took three goes, and the owner's two reports are the diagnosis in both cases.

**`preventDefault` on touchend** is the textbook fix and was applied first — *"long press opens menu but when finger released menu disappears unless I move while holding."* WebKit synthesises that click only for a touch that did not MOVE, so jiggling suppressed it; touchend is not always cancelable on a real iPhone, so preventing it did not. It is still applied, but nothing here may depend on which events a platform decides to send.

**An arming window** came next: `consoleHoldAt` disarms the menu the moment it opens one, the end of the touch arms it `CONSOLE_LINK_MENU_ARM_MS` later, and until then the scrim and every row answer nothing. A menu raised with no gesture in flight (desktop right-click) is live at once; a touch whose end never arrives arms on the `CONSOLE_LINK_MENU_LOST_MS` backstop, because a menu nothing can dismiss is worse than a slow one.

**And a window was still not it** — *"it works [when] the keyboard is shown but when hidden long press without finger drag makes menu disappear."* That split is the tell: iOS spends the lift's click on dismissing the keyboard when there is one, so the click only reaches the page when there is not — and then it can arrive well after any window short enough to keep the menu responsive. So the lift's click is identified by **where** it lands rather than when: at the point the finger was, `CONSOLE_LINK_MENU_SLOP` px, and there is exactly ONE of it, so it is swallowed **once** whenever it turns up. `CONSOLE_LINK_MENU_STRAY_MS` only stops that expectation lingering into a later deliberate tap on the same spot. Everything else stays instantly answerable, which is what a long arming delay would have cost. `openConsoleLink` additionally drops a call with no explicit target while the menu is up.

Layers, on purpose: near the bottom of the screen the menu is clamped *up* under the finger, where that stray click lands on a ROW — a dismissal is a lost menu, but this would be an action nobody chose.

The node test drives both rules on a controllable clock and controllable timers. The real-Chrome run reproduces the lift's own click at the point the finger was — and had to **stage** the late case rather than replay it, because Chrome delivers its compatibility click immediately, so a click fired 700 ms after a real touch is a *second* click and the guard correctly lets it through. Staging it (open the menu, tell the shipped code the hold ended, let one real click land late) is what makes the assertion about the phone's behaviour instead of Chrome's. Both runs also check the menu is not *stuck*: the next tap dismisses it.

**The browser opens OVER the console, not instead of it.** Sheets paint at z-index 20 and the console overlay at 60, so the first version hid the console to be seen at all — which threw away the reason the link was worth opening: for a sign-in, the command that printed it is *still running*, and you come back to the prompt waiting for the code. The sheet and `#backdrop` are raised past the overlay while `body.console-open` (64/63), scoped to that class because a backdrop permanently above 60 would cover the popover menus that live there. Two things follow from the terminal still being alive underneath: xterm's helper textarea keeps the keystrokes unless it is blurred, so a URL typed into the address bar would land in the shell — and it gets focus back on the way out only if it *had* it, hung off `bvEndIfOpen` (the funnel every dismissal already goes through) so a phone with the keyboard down does not get one summoned. `consoleReflowViewport` also stands down while the sheet is up: it would resize the remote PTY to whatever the *browser's* keyboard left, repainting a program nobody is looking at.

The menu brings **its own scrim**, because `#backdrop` is at 19, under the console, and could never catch the dismissing tap. Setting the default is its own row rather than a side effect of choosing once, or one experiment would silently send every later tap somewhere nobody asked it to go; and the default is **per device** — "your browser" is a different browser on the phone than on the Mac, while the aish browser is one shared Chrome, so this is a fact about the screen it was set on. — `test_console_link_menu.js`

### `[PAD-DRAFT]` / `[PAD-HISTORY]` / `[PAD-HISTORY-RENDER]` / `[PAD-SEND]` — the dictation scratchpad
**L7.** iOS keyboard dictation REWRITES the whole field on every recognition update, and a PTY cannot retract bytes already written — so speech typed straight into xterm arrives as every interim revision CONCATENATED. The pad is a staging textarea that only writes to the PTY on Send. Return in it is a NEWLINE, never a submit (a stray Return must not fire a half-finished command at the terminal); ONLY Send submits. It FLOATS above the key row rather than taking flex space, so opening it never re-fits xterm and resizes the remote tmux pane. The unsent text is persisted like the composer's draft — saved on every change *including* from `renderDictation`, since setting `.value` fires no input event — plus on `pagehide`, and the ✕ deliberately KEEPS it: a mis-tapped close losing a spoken sentence is the failure the pad exists to prevent. History renders OLDEST-first so the newest sits nearest the textarea and your thumb. The pad keeps default iOS autocorrect — deliberately the opposite of `!` terminal mode — because what you speak into it is prose, not keystrokes. — `test_dictation_pad.js`

### Console UI (unfenced)
The key row is Blink-SmarterKeys-style: sticky-left `esc`/`ctrl`/`tab`, sticky-right arrows/keyboard, only the middle scrolls; symbol keys tap for the primary glyph and swipe-down for the grey secondary; `ctrl` is a 3-state chip (tap = armed one-shot, double-tap = LOCKED until tapped off). The arrow pad is ONE key you DRAG for direction with distance-scaled auto-repeat after a 450 ms delay — and double-tapping it opens the dictation pad (free real estate: a tap without a drag did nothing, and a drag sets `pressed` so it cannot be mistaken for a tap). Touch scroll dispatches a real `WheelEvent` on the touched element so mouse-mode apps (tmux/vim/less) scroll identically to the desktop wheel. The overlay top is pinned to 0 rather than following `visualViewport.offsetTop`, or an arrow-drag rubber-bands it. When the shell or tmux exits the console auto-respawns in place, crash-loop guarded (a second death within 1.5 s stops and offers retry). Desktop copy arrives as OSC 52 from tmux (`set-clipboard on`); a `?` read request is REFUSED so the clipboard is never leaked back, and paste is left to xterm's native handler (intercepting Cmd/Ctrl+V double-pasted). — `test_choreo_console_status.js`, `test_osc52_clipboard.js`

### `[CHIP-NEVER-COMMANDS]` — a chip is a message, never a command

A chip's label and payload come from **model output**, and a chip sends on ONE TAP. `submitInput` routed any leading `/` through `handleSlash`, so under prompt injection a hostile fetched page could render a friendly *"Sign in to continue"* chip that opened aish's own remote-browser login sheet pointed at a credential-harvesting URL — borrowing precisely the trust that sheet is designed to have. ## Remote browser view

### It is a browser, so it looks like one

The sheet was built as a sheet with browser parts bolted on, and every widget that came from "sheet" rather than "browser" was wrong:

- **A title row reading "Browser on the Mac"** — a whole row of chrome spent stating something visible from the content, and false the moment aish runs anywhere but a Mac. Deleted; the address bar carries the identity, as in every in-app browser.
- **A "Go" button beside the address bar** — no browser has one. The field is `type="url" inputmode="url" enterkeyhint="go"`, so the phone keyboard offers **Go**, and Enter blurs the field so the keyboard gets out of the way.
- **A blue "Close" in the bottom bar** — blue is the primary-commit style, so closing read as the most important action in the sheet and was pressed by accident, with nothing to undo it. Close is now a quiet ✕ at the top right, which is where an in-app browser puts it and where the sheet's own close already lived.
- **Back and Refresh stay** — both earned their place in use.

The result gives the page **74% of the sheet** (549px of 738 on a 430×900 phone) where the old fixed 44vh slot gave it 396px.

The heuristic, learned the slow way across three rounds of feedback: **if a mobile browser or a remote-desktop client does it with a gesture on the content, do not add a widget.** Widgets are for what has no gesture — the address, Back, Refresh, Close.

### `[BROWSER-VIEW-END]` — a dismissed sheet must not leave a browser running

A sheet can be dismissed four ways: the Close button, the ✕, the backdrop, and a swipe down the grabber. Only the button told the server. The other three left a real Chrome running on a machine nobody is sitting at — and because a read REFUSES while the owner is driving the view (`docs/browser.md`), a stray swipe meant aish could not read **any** page until the 15-minute idle cap expired. `bvEndIfOpen` therefore hangs off `closeSheets`, the one funnel every dismissal already goes through, rather than off each dismissal in turn.

### The page fills the stage

`bvViewportSize` asks for the remote page at **exactly the stage's shape**, so `object-fit: contain` has nothing to letterbox. Asking for a taller page was a measured regression: a 390×828 page shown in a 430×549 stage fits by HEIGHT and renders at 0.66 scale with black bars down both sides — about 60% of the width wasted, which the owner photographed. Matching the aspect also means scale 1.0, so the page is shown at its own size rather than shrunk.

### On a desktop the sheet is not a picker (#259)

`.sheet` caps at 560px past 700px wide, which is right for the model, folder, mic and workspace pickers — short lists of rows, where more width buys nothing. This one is a BROWSER, full height by design, and it was rendering a real page down a 560px column with the rest of a 1280px window empty beside it: the same class as *A sheet belongs to the chat, not to the window*, one sheet further on. Past 700px it takes `min(1280px, 100%)`.

**The `100%` is the CHAT COLUMN, not the viewport** — the docked query already gives every sheet the shell's left inset, so "what the window has" arrives for free and centring stays centred on the chat.

**And the cap is the frame's own width, which is the only number here that means anything.** `browser.VIEW_DESKTOP_WIDTH` captures every page at 1280 CSS px whatever the client asks for; the stage only ever chose the frame's SHAPE (above). So width buys legibility and never more page, and the useful ceiling is parity — below it the sheet is shrinking what was rendered, above it is magnifying a picture it already holds at native size. It also stops being free at that point: `bvRequestDetail` asks for a sharpening patch once the stage needs more than the frame's own density, so a stage wider than the frame would spend a round trip on every idle glance, which is precisely what an overview frame exists to avoid. `test_the_desktop_cap_is_the_frame_s_own_width` pins the two numbers to each other so they cannot drift apart in silence.

**Nothing vertical is touched, and that is deliberate.** The whole of #226 — the top safe-area inset, the stage's 44px tap-target floor, the toolbar standing down beside an open field, the `max-height: 500px` landscape rules — is a column-height argument, and it is the half no unit test can see. `scripts/check-browser-sheet.py` returns coordinates identical to the ones before this change at all ten device cases, landscape phones included (they are past 700px wide, so they widen too, and every row lands where it did).

### `[BROWSER-VIEW-EDIT]` — tapping a field opens an editor

The first design put a text field permanently in the sheet with **Type** and **⏎** buttons. Owner feedback after real use, and every clause of it is a distinct defect:

- *"there was no feedback that I highlighted a field so I did not know what field I have highlighted"* — a tap gave no sign of what it selected.
- *"I didn't know how to open up the keyboard"*, then *"the type at the bottom was actually not visible because it doesn't fit the screen"* — measured: at the 543px visual viewport the keyboard leaves, `bv-text` sat at 505–545 and `bv-type` at 503–548. **Tapping the field opened the keyboard that pushed that field off the bottom.**
- *"I cannot edit the value in the field once I enter it, since it only adds to the values"* — Type sent keystrokes, so there was no correcting and no clearing.
- *"I still don't understand the button type versus the enter button."*

So: a tap on a field opens an editor carrying the field's **name** and its value. It began as a modal with Cancel / Set / Set & submit and a paragraph of explanation, which was too much furniture for "type into a field" — the owner asked for something "not modal-like, more like a focus". It is now a row in the sheet above the nav bar: the label, the value, an inline clear and (for passwords) a reveal, and nothing else.

**It behaves like a field on a page, because that is the model it is borrowing.** Tapping the page LEAVES the field and keeps what was typed, as blurring a real field does — and that tap is spent on leaving rather than forwarded as a click, so dismissing cannot also press something. Enter submits; Escape discards. There is no Done button, which also answers the old Type-vs-⏎ confusion by deleting both sides of it.

A row is safe here only because the sheet is a fixed column: the previous in-sheet bar was pushed under the fold by the keyboard, which is what made a modal look necessary in the first place. `bvPaintFocus` outlines whatever the page has focused, supplying the missing "what did I just select".

**It opens only when the tap landed ON the field** (`focus.tapped`, decided server-side by hit-testing the click against the focused element's rect). Focus also moves as a *side effect* — pages autofocus their first input, dismissing a cookie banner can leave focus in one — and popping an editor then would rebuild the exact surprise this replaces.

**A password is never pre-filled**, and that is a transmission decision, not a display one — see `docs/browser.md`. The eye toggle reveals only what the owner is typing now, and the input is cleared and reset to `password` on close, because a value left in a DOM node outlives the dialog. Commit sends BEFORE clearing: `bvSend` refuses while an interaction is in flight, and clearing first silently destroyed the text — usually a password — with nothing on screen to say so.

### `[BROWSER-VIEW-DETAIL]` — when zooming is worth a round trip

A frame is an **overview**, and it is sharp only up to `zoom == its own density`. Past that the phone is enlarging a JPEG — which is what the owner reported above 2.5×, and which no density setting fixes: zoom goes to 4×, so serving it from the frame would mean a 1.3 MB capture on every glance and scroll to serve the one moment he stops and reads. The server side, with the measurements, is in `docs/browser.md`.

So the deep end is fetched for the rectangle he is actually looking at. The client's whole job here is **deciding when to spend a trip**, and every rule is one:

- **Density is read off the PICTURE** (`naturalWidth / bvFrame.width`), never held as a copy of the server's setting — one fewer number that can fall out of step with the thing it describes.
- **The scale asked for is what THIS screen can show**: stage CSS width × its own `devicePixelRatio`, over the page width visible. A 2× phone therefore asks for less than a 3× one at the same zoom, and nothing on the server has to know about anybody's hardware. Past parity the extra pixels are invisible.
- **No trip while the frame can already show it.** Zooming within the frame's own density is what "zoom is free" means.
- **No second trip for ground already covered** — the patch is captured wider than the screen (`BV_DETAIL_PAD`) so small pans stay sharp — and the covered scale compared is the one the **server captured**, not the one requested. Believing the request would leave a patch claiming a sharpness it does not have, after which no further trip is ever made.
- **Only once the gesture has stopped** (`BV_DETAIL_SETTLE_MS`), so a pinch in three parts costs one trip rather than three.
- **Not through `bvSend`.** That guard exists so *frames* stay ordered, and a patch is neither an interaction nor something the page can change under. Behind the guard, a sharpening would swallow the next tap. Ordering is handled instead by a **token**: every frame bumps `bvFrameSeq`, each request carries it, and a patch that comes back stamped with an older one is dropped. A sharp rectangle of a page that has moved on is worse than a blurry one of the page in front of him, because it looks authoritative.

`bvVisiblePageRect` reads the **live transformed geometry** rather than `bvZoom`, for the same reason `browserViewPoint` does — the browser has already applied the transform, so inverting one uniform scale cannot drift out of step with it. It clamps at the page edges instead of refusing there: a rounding error should cost a few pixels of coverage, not the capture.

The patch is positioned in **page coordinates inside the layer's untransformed box**, and the layer then carries the frame's own transform string — so the two can never diverge under zoom or pan, and there is one geometry rather than two. The layer is `pointer-events: none`, because the frame underneath owns the coordinate mapping and a tap must reach it. — `test_browser_view_detail.js`

### `[BROWSER-VIEW-COORDS]` — where a tap actually lands

The `/browser <url>` sheet shows aish's own Chrome (running on the headless Mac) as a letterboxed `<img>` and turns a tap into a click at the same point on the real page. `browserViewPoint` owns that translation.

It must map against the **rendered image**, not the element box. `object-fit: contain` letterboxes the frame, so on any aspect ratio that does not match, the element is larger than the picture in one axis; mapping against the element is then off by the letterbox margin, increasingly so toward the edges. Nothing about that failure is visible — the frame still looks correct, the click simply lands elsewhere — and it is worst on a small login field on a phone, which is the entire reason the view exists. A tap in a letterbox bar returns `null` and is dropped, rather than being mapped to a plausible-but-wrong point inside the page.

Two client-side rules go with it. `bvSend` refuses a second interaction while one is in flight, so frames cannot arrive out of order and paint a stale page. And the text field is cleared the instant it sends: the owner types real passwords through this sheet, and a value left in a DOM node outlives the sheet. Nothing typed here is logged, client or server (`docs/browser.md`).

The site's markup never enters this document — the `<img>` is the whole rendering surface, so a hostile page cannot script the app or reach the access token.

`tests/js/test_browser_view_coords.js` drives the shipped function through exact-fit, vertical- and horizontal-letterbox, offset-element, and zoomed/panned cases.

### `[BROWSER-VIEW-ZOOM]` — pinch, pan, and why a drag is not a dismissal

Zoom exists for one job: hitting a small field — a password box on a phone — accurately. Everything about the gesture set follows from that, and it deliberately differs from the photo lightbox next door:

- **A drag PANS, and never dismisses.** In the lightbox a drag down closes the picture; here the picture is a live page the owner is aiming at, so closing on a drag would be losing their place mid-login. `Done` closes it.
- **A press that did not move is still a click on the page** (`BV_TAP_SLOP`), so tapping a field works whether or not the finger wobbles.
- **A tap waits `BV_DOUBLE_TAP_MS` (300) before it clicks**, so a double-tap can mean zoom and *only* zoom. The original code sent the click immediately, arguing a wait "would make the view feel broken" and a stray click "costs a frame, not data". Both halves were wrong: the round trip is already 1–3s so the wait is imperceptible, and a stray click follows links, toggles controls and focuses fields — state that costs a round trip to discover and may be unrecoverable mid-login. It is also what made double-tap useless in practice: the first tap clicked the page, so the page changed under the zoom. 300 ms is the platform's own number, used by mobile browsers for exactly this case. A tap marker paints instantly so the wait is never silence.
- **Zoom state is a READOUT, never a control.** The old `1:1` button merged them and the owner read a badge sitting on content as status — correctly — and never pressed it. `.bv-zoom` is `pointer-events: none` and fades; double-tap is the reset, which is both the convention and what he asked for.
- **Double-tap toggles 1× ↔ 2.5×, about the tapped point**, so the thing being aimed at stays put rather than sliding out from under the finger. Pinch does the same continuously.
- **The frame is `draggable="false"`, and that is load-bearing.** Dragging an `<img>` starts Chrome's native image drag-and-drop, and the browser taking over the gesture fires `pointercancel` — so a swipe died one move in, leaving no scroll and a stale drag behind. Measured on a real mouse: `pointerdown`, ONE `pointermove`, then silence. A `dragstart` preventDefault backs it up.
- **The gesture ends on the RELEASE's own coordinates, and on a window-level `pointerup` too.** Chrome coalesces and drops moves under load, so trusting the last one seen measures a shorter swipe than the finger made; and a release that drifts off the frame would otherwise never end the drag at all. (Pointer *capture* is the usual fix and is deliberately avoided — on an `<img>` it silently breaks drags, the same lesson `previewDown` records.)
- **A swipe scrolls the page.** At 1× there is nothing to pan — the frame already fills the stage — so a drag did nothing at all, which wasted the most natural gesture on a phone and left the ▲/▼ buttons as the only way down a page. Zoomed in, the drag has already panned and must not also scroll. The delta is converted through `bvPageScale`, the same `contain`-fit geometry the tap mapper inverts, so a swipe moves the page by what it looks like it moves rather than by a fraction of it.
- **A single tap is not debounced against the double-tap window.** Waiting 300 ms to act on every tap would make the view feel broken; a stray extra click costs one frame, not data.

`bvClamp` is the one writer of the transform, and it clamps there rather than at each gesture: at 1× the picture exactly fills the stage and cannot be panned at all, and zoomed in it can never be panned past its own edge. Making an out-of-bounds pan *unwritable* rather than merely unwritten is the same discipline `previewPaint` uses, and for the same reason — five call sites agreeing is not an invariant. `tests/js/test_browser_view_clamp.js`.

**The view drives one of TWO profiles, and which one has to be on screen.** `/browser <url>` opens the owner's browser — every session he has — and `/browser anon <url>` opens the profile `web_search` reads results pages with, which is signed into nothing (`docs/browser.md`, *The second identity*). The two are pixel-identical on screen and mean opposite things, so `openBrowserView` names the search profile in the status line rather than only in the socket message: a password typed into the wrong browser is a mistake nothing else on the page would reveal. The profile is sent by the CLIENT and never inferred server-side from the URL — signing the search profile into Google happens at `accounts.google.com`, the same address the owner would use for his own. It is also stored beside the Resume address (`aish-bv-last-profile`), because reopening a search-profile page in the owner's browser would silently swap which sessions are attached. Bare `/browser anon` is a question, not an open, so it goes to the sheet as text like the other bookkeeping verbs.

**The empty view lists where the browser has been** (`[BROWSER-VIEW-RECENT]`), one row per site, newest first, asked for over the socket rather than read from `localStorage` — the list is a fact about the one Chrome on the Mac, not about the device looking at it (`docs/browser.md`). Each row reopens in the profile it was opened in and names that profile when it is the anonymous one. — `test_browser_search_profile.js`

**Zoom must not move where a tap lands**, which is why `browserViewPoint` reads the element's transformed `getBoundingClientRect()` instead of tracking zoom state of its own: the browser has already applied the transform, so the mapper inverts one uniform scale and stays correct under any zoom or pan. The frame is captured at 2× device scale so zooming shows detail rather than an enlarged blur, while coordinates stay in CSS pixels. `tests/js/test_browser_view_coords.js` pins that a page point keeps its coordinates at 1× and 2×, panned and unpanned.

**The sheet sends the SHAPE of its stage, and the server renders at desktop width.** `bvViewportSize` measures the stage so `object-fit: contain` has nothing to letterbox; `view_size` then scales that shape up to `VIEW_DESKTOP_WIDTH`. Serving the phone's web to a phone-shaped viewport was tried and measured backwards — a mobile home page is banners and navigation, so reaching content cost a round trip per scroll — and it split the browser's identity besides. The rationale, the numbers and the frame-size measurements are in `docs/browser.md`; do not reintroduce a mobile viewport here. A rotation or a keyboard re-lays-out the remote page rather than stretching the frame. No user-agent is spoofed either way: width is what responsive CSS keys on, and a UA disagreeing with the profile's own would risk the session later reads depend on.

**The sheet's own layout is load-bearing and is NOT covered by those tests**, because the node harness has a fake DOM and no layout engine. Three separate incidents have now shipped green through it, all the same shape — a control off the bottom of the screen: the Done button at y=899 on a 430×900 viewport, the text field pushed under the keyboard that types into it, and the password input a hundred pixels below a landscape keyboard (#226).

The column is a fixed stack in which **`.bv-stage` is the only elastic row**, which makes its `min-height` a floor on every control below it — that was the landscape bug, and it is why the floor is now a tap target (44 px) rather than a picture (150). `#browser-sheet` is `height: 100%` with `padding-top: calc(6px + env(safe-area-inset-top))`, and `.bv-body` must stay a flex CHILD that can shrink (`flex: 1; min-height: 0`). Sized by its content instead, the whole stack overflows invisibly, because the overflow is hidden rather than scrolled — on purpose: a scroll position that can hide a control is what produced two of the three.

**Changes here need a real browser at a phone viewport, not a unit test** — so there is one: `uv run python scripts/check-browser-sheet.py` drives this file and `index.html` through a real Chrome at ten device/orientation/keyboard combinations, with genuine safe-area insets, and fails if anything is unreachable. Run it after touching any `.bv-*` rule. The full rationale is in `docs/browser.md`.

## Offline mirror (client)

The server half — `GET /offline/index`, `GET /offline/session`, `_prefix_sig`, `offline_events` — is in `docs/web-server.md`.

The mirror is cheap because it reuses two invariants rather than adding a second renderer: rendering is already a pure function of an event array, and `reconstruct_events` is already a pure `path → list[dict]`. IndexedDB `aish-offline` keeps SEPARATE `meta` and `events` stores, so the rail and search read metadata without ever deserializing transcripts. Sync is resumable **by construction, not bookkeeping**: newest-first, one session at a time, each committing atomically, and the next pass recomputes the work from the same timestamp comparison — so a pass cut off by a tunnel simply continues. It runs on connect, ~2 s after each `done`, and on a 5-min idle tick; `navigator.storage.persist()` is requested once there is something worth keeping. `offlineFirstPaint()` runs BEFORE `connect()` so the last chat paints from IndexedDB while the socket is still opening, checking `serverPainted` so an authoritative replay always wins the race. Offline mode is decided by the SOCKET, not `navigator.onLine` (hotel wifi with no route home is "online"). `deepLinkSession()` keeps `?session=` in step, without which regaining signal yanks you back to whatever chat the last hello pinned in the URL. **Sending offline is refused ON PURPOSE** — an outbox would dispatch an agent that runs shell commands with nobody watching and an approval gate answered by someone who has moved on.

### `[OFFLINE-INDEX]` / `[OFFLINE-SEARCH]` — the local index and its ranking
`[OFFLINE-INDEX]` owns WHAT is searchable, `[OFFLINE-SEARCH]` owns HOW it ranks; they are fenced separately because each has a twin in `session.py` (`visible_messages`, `SessionLog.rank`) that must say the same thing, and they drifted once already (#266).

#### the index
Built from `user`/`done` text only: command output is noise in a search index and the bulk of the bytes. The server now indexes the same thing (`visible_messages`, `docs/session-log.md`) — it used to index every record, tool results included, so the two halves of one search disagreed about what a chat contains and the online half returned chats the word appears in nowhere on screen (#266). The `history` branch is the flat blob a log too old to reconstruct falls back to, so the role filter has to be applied there by hand.

#### the ranking
`offlineRank` ports `SessionLog.rank`'s tiers so offline search ranks like online search, including the rule that matters most: the approximate tier is a FALLBACK for a query nothing matched (`offlineClosest`, capped, candidates length-compatible with the query word), never a contributor to a search that worked. It is the ranking actually on screen for the first paint of every keystroke, so a divergence here is not a degraded-mode detail. `offlineRanked` returns the rows AND whether they are only the closest (`offlineRank` is the rows alone, mirroring `SessionLog.rank`/`ranked`), and `offlineMatchLine` quotes the line a row matched on under exactly the server's rule — including not quoting the title back when the chat is named after the question. A searching list renders flat with no date bands (relevance order would make them lie about why a row is where it is) and carries `No exact match — closest chats` when the answer is approximate. The mirror's `text` is stored in the case it was written in, because a row now quotes it; matching lower-cases where it compares, and metas written before that heal on their next sync. — `test_offline_search.js`

### `[SEARCH-HIGHLIGHT]` — the searched words inside the row
`paintMatch` rebuilds a row's title and quote with each hit in its own `<mark>`, styled as colour and weight rather than a highlighter block. It exists because the quote alone was not enough: a rail row is ONE truncated line, so on a phone the excerpt's run-up filled the visible width and the word typed never appeared on screen at all (#266) — the excerpt window was shortened for the same reason (`SNIPPET_LEAD`). Text nodes plus one element per hit, never `innerHTML`: the text is a chat's own contents. — `test_offline_search.js` covers the excerpt it paints; the painting itself is DOM assembly with no branch worth a harness.

### `[OFFLINE-EVICT]` — what to drop when over budget
Lowest value first: pinned NEVER (the user's promise to themselves that a reference chat is always there — a promise about the BUDGET, never about a chat that has been deleted; see [MIRROR-FORGET]), then the session on screen, then most-recently-opened *on this device*, then most-recently-active anywhere — that last tier is what makes a chat started on the laptop readable on the phone without opening it first. — `test_offline_evict.js`

### `[MIRROR-FORGET]` — dropping this device's copy of a deleted chat
**L1.** ONE function for "the server does not have this chat any more", because there are two ways to learn it — the sync notices the catalogue no longer lists it, and the socket says so outright ([FORGET-SESSION]) — and a chat half-forgotten by one of them is a ghost the other never gets to clean up. **Gone is gone, PIN INCLUDED.** The prune used to exempt pinned chats, reading a pin as "keep it even if it no longer exists"; a pin means "keep this copy against EVICTION" (`[OFFLINE-EVICT]`, the budget sweep), and the delete confirmation says in as many words that the copy on your devices goes too. What the exemption bought instead was a row no sync could ever remove. `mirrorOrphans` is the pure half — cached names the server's index does not list — so the rule is testable without a fetch. Safe because `/offline/index` lists EVERY non-empty session, uncapped: an absence there is a real absence, not a page boundary. — `test_forget_session.js`

### `[OFFLINE-PIN-STATE]` — reading the pin
**L4.** Read from the STORE on every paint, never from the in-memory `offlineMeta` mirror: that mirror is empty for a moment after every reload, so reading it showed a pinned chat as "Off" and a tap to "pin" it silently UNPINNED it (the toggle flips the real value). Until the read lands the icon shows a dimmed `unknown` state rather than claiming either answer. There is deliberately NO bulk "clear offline copies": the mirror self-manages (capped, least-useful-first eviction, server-side deletions dropped as soon as they are heard of — [MIRROR-FORGET]), and the action that existed also wiped the SW shell cache, breaking "the app always opens offline" until the next successful load. — `test_offline_pin_state.js`

### `[OFFLINE-RELOAD]` — the self-update guard
**L7.** A rev mismatch means this page runs older code than the server serves, and with a service worker in front of `index.html` that is one bad cache entry from a loop: reload → SW serves the same stale HTML → same stale rev → reload. Two independent guards, because a loop here bricks the app on the device it happens on: purge the cached shell first so the reload is guaranteed to re-fetch, and refuse more than `RELOAD_MAX` (3) reloads per `RELOAD_WINDOW_MS`. One revision behind is a papercut; an app that reboots forever is unusable. — `test_reload_throttle.js`

### `sw.js` — `[SW-ROUTE]`
Navigation is **network-first** (3 s timeout, cache fallback) because the page compares its own `?v=<rev>` against `hello.rev` and a stale cached `index.html` would loop forever. `?v=`-stamped assets are cache-first-immutable (the URL names exact bytes, so new HTML can never pair with stale JS); other statics stale-while-revalidate; `/file` images get a bounded LRU. `/ws`, `/offline/*`, `/upload`, `/trigger`, `/export/*`, `/dirs` are NEVER cached. — `test_sw_routes.js`

## Removed — do not reintroduce

- **The working-set deck and the horizontal pager.** They bet on SPATIAL memory in a surface that never showed a map: one page at a time, order in per-device `localStorage`, a wrong guess costing a full transition plus a transcript rebuild, and nothing ever teaching you the right one. Worse, the deck was a SECOND source of truth about which chats matter, permanently reconciled against the server's real list — seeding, idle eviction, phantom pruning, fork anchoring and the park/unpark/watchdog choreography were all that reconciliation. Recency ordering is a pure function of the logs the server already has, so phone and laptop finally agree. What the pager was genuinely good at — bouncing between two chats — recency does BETTER: the other chat is permanently row one. **Do not reintroduce a client-side membership set.**
- **Recent/Automated tabs.** Attention, not provenance, is the axis people navigate by — and the tabs' own design admitted it, computing counters for the HIDDEN tab so it could still flag things, while search dropped the split entirely because it lies about relevance. A held email-triggered session and your own unattended long-running task want you identically; a three-week-old triggered chat is just an old chat. Provenance is now a glyph in the row's icon slot.
- **The composer swipe-up, the bottom search bar's swipe-dismiss, and `answerFilling`.** The first two were gestures competing on surfaces that already had one; `answerFilling` was a mode replaced by a consequence of `anchorAnswer`'s clamp.
- **Two-tap arm-then-confirm.** See `[CONFIRM]`.

## Testing this file's subject

Node checks in `tests/js/` extract the REAL function from `app.js` by source markers and run it in a `vm` against a minimal fake DOM — the shipped code is tested, never a hand-copied duplicate. `tests/test_frontend_js.py` runs them inside pytest (skipped when node is absent).

Those checks verify DECISIONS. Every one of the four #181 incidents had a correct decision function and a broken feature, because the defects live in the **choreography** — when a decision is consulted, what happens if a step is skipped, what happens when two sources race. `tests/js/harness.js` (a plain CommonJS module, NOT a test — the runner globs `test_*.js`) is the shared, **hostile-by-default** world for new choreography tests: page hidden unless asked otherwise, `requestAnimationFrame` callbacks collected and never fired, timers as `{fn, ms}` data the test fires by predicate, the lying element (computed transform tracked apart from the inline style, because "the DOM lies" was itself a bug), and `FakeWebSocket` — records sends, `deliver()`s messages on demand, fires `onclose` out of order, and goes `zombie()` (readyState OPEN, silent, `close()` observably nothing — the failure no event announces). Existing tests deliberately keep their own copies; harness.js is for NEW tests.

**Convention: a race fix ships with its interleaving as a test, not just its decision function.**
