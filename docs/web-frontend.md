# Web frontend — aish/static/app.js

The rail, the transcript, ownership fences, the trace card, the console UI, the offline mirror. These invariants are NOT obvious from the code — the fenced regions exist because each one was a bug.

*Split out of `CLAUDE.md`. Read this before changing the code it describes.*

## The session rail

**Why the deck went (#169's premise was wrong).** The deck bet on SPATIAL memory — chat X is always two swipes left — in a surface that never showed a map: you saw one page at a time, the order lived in per-device localStorage, a wrong guess cost a full page transition plus a transcript rebuild, and nothing ever taught you the right one. Worse, it was a SECOND source of truth about which chats matter, permanently reconciled against the server's real session list — seeding, 48h idle eviction, phantom pruning (`deck_check`/`deck_gone`), fork anchoring, and the park/unpark/watchdog/landing choreography were all that reconciliation. Recency ordering is a pure function of the session logs the server already has, so all of it is deleted, and phone and laptop finally agree on the order. What the pager was genuinely good at — bouncing between two chats — recency does BETTER: the other chat is permanently row one. Don't reintroduce a client-side membership set. **Unread is the rail's organising axis (`// [SEEN-START/END]`).** The list is banded by ATTENTION, not provenance: `Needs you` (holding an approval, or activity newer than this device's last look), then `Active now` (running), then `Pinned`, then date buckets. That replaces the Recent/Automated TABS, and the tabs' own design admitted they were on the wrong axis — attention counters had to be computed for the HIDDEN tab so it could still flag things, and search dropped the split entirely because it lies about relevance. A held email-triggered session and your own unattended long-running task want you identically; a three-week-old triggered chat is just an old chat. Provenance is now a GLYPH in the row's avatar slot. `seenAt`/`seenSince` (`aish-seen`, per-device — "I looked at it" is a fact about a screen) is written ONLY by `markSeen`, called from `[SESSION-ENTER]` (entering a chat IS looking at it) and at `done` on a live turn — that second call is load-bearing, because a turn keeps writing to the log after the hello that stamped it, so without it every chat you had just used came back unread the moment you left it and the band became the whole list. `seenSince` is the first-run floor, for the same reason: without it a new device renders its entire archive unread. `sessionUnread` is pure and takes `current` (the chat on screen can never be unread). Pinning is now ONE concept — top band AND never evicted from the offline mirror — instead of two toggles for "I care about this chat". Pinned by `tests/js/test_session_unread.js`.

**The eraser is a chip on the prompt (`// [REDACT-START/END]`, #202).** It lives on the PROMPT because a turn is named by its prompt, and it deletes the whole exchange; it sits at the START of the chip row, so copy and reuse — tapped constantly and without thinking — keep the trailing edge a thumb lands on by habit. What replaces the turn is a quiet, UNDATED `Message deleted` row: a chat that silently loses an exchange leaves the answer above it reading as a reply to nothing, and a deletion you cannot see is indistinguishable from data going missing — but a time ON that row reads as "deleted at", which is not what the only available number means (it is the deleted MESSAGE's own stamp), so the row carries none and its POSITION between two timestamped turns says when. The tombstone keeps its `at` on disk, where it is the audit trail rather than a rendered claim. The word is DELETE everywhere the user sees it — "remove" reads as "taken off this screen", and what happens here is that the text stops existing (the on-disk record kind stays `redact`, which names the MECHANISM: content gone, tombstone kept). Pinned by `tests/js/test_redact_turn.js`.

**ONE confirmation modal for every irreversible action (`// [CONFIRM-START/END]`, #202).** It replaced the two-tap arm-then-confirm guard everywhere that existed, because that guard **communicates by changing the control itself, which on a phone happens under the finger covering it**. The chat menu's version got away with it by rewriting its LABEL ("Delete chat" → "Confirm delete"); the transcript's delete chip is an ICON, so "armed" was a 17px glyph turning red beneath a thumb — tap, nothing seems to happen, tap again, gone. Functionally one tap, and the owner reported it as exactly that. The second defect is geometric: the confirming tap lands on the SAME PIXEL as the arming one, so a double-tap habit or a "did that register?" retap commits. The modal fixes both and adds what neither guard had — it states the CONSEQUENCES ("the log file on the server", "the copy mirrored to your devices", "cannot be undone"), because a verb and a red button say what you are doing and never what it costs. Invariants: nothing runs until Confirm; every dismissal (Cancel, tap-outside, Escape) is a NO and DROPS the pending action, so a dismissed dialog leaves nothing half-committed; the action closes over what it was asked about (the chat name is captured at ask time, never read back at confirm time); Cancel takes focus, never the destructive button; Escape is claimed AHEAD of `escapeExit()` since the modal can be raised over any surface. It is centered with its own dim layer rather than a bottom sheet — a sheet is a picker you browse, this is a question you answer over whatever raised it. Deliberately no undo anywhere near it: an undo buffer is a copy of the thing just asked to be destroyed. Pinned by `tests/js/test_confirm_modal.js` (which also fails if a second bespoke confirmation appears).

**Row anatomy.** The status icon answers ONE question — what state is this chat in — in priority order: running (green spinner) > waiting (orange alert) > automated (a tinted origin glyph: clock / envelope / bolt) > a plain chat mark. It used to answer two badly: a blue TICK for "this is the chat you are in" (which the row's own highlight already says, and which reads as *done*), and provenance only when nothing else was showing — so a screen of ordinary chats was a column of identical grey marks and automation was invisible. "Current" is deliberately not an icon. **Unread is a badge cornered on that icon**, not a column: a leading slot is the mail convention, but mail rows are wide and this panel is phone-width, so an always-reserved gutter spent real title space on a state most rows do not have. Bold titles alone were measured on a real phone and found illegible — the dot is the signal, the weight step is support. The pin sits BELOW the timestamp (the space the row's trash used to take), not beside it, for the same width reason — and it is `--dim`, NEVER the accent: blue on a rail row is the attention vocabulary (it is exactly what the unread dot is), so a pin painted in it read as "this one is new", which is the one thing a pin never means. It shares its colour with the timestamp it sits under, which is the company it belongs in. There is no per-row trash and no swipe-to-delete: leftward on this panel closes it, and having that same drag mean "delete a chat" was the destructive reading of an ambiguous gesture. Deleting is the chat menu's row, which asks in the shared confirmation modal ([CONFIRM], pinned by `test_confirm_modal.js`) — the ONE sender of `delete_session`.

**Reach and consistency.** New chat exists in TWO places on purpose: the rail's bottom bar (thumb range, where you already are after swiping) and the app header (findable without knowing the rail exists). They are the same glyph with the same styling — a filled tint on the rail's copy made one action read as two different buttons. The rail button in the header is 44x44 with real separation from the session-title menu, which is `flex: 1` and therefore huge: a near-miss did not just fail, it opened the wrong thing. **The pin lives in the chat menu**, not the title bar (a rarely-touched per-chat setting was competing for the scarcest space in the app), and its glyph carries the state — upright + solid = pinned, tilted back + hollow = not — because having to read On/Off is not a state indicator. Tilted-and-blue read backwards: a pin at an angle is one that is NOT pushed in.

## Responsiveness on a slow link

**A local action never waits on a round trip (`// [PENDING-VIEW-START/END]` + `// [PENDING-SEND-START/END]`).** ONE rule, broken in the two places the app is touched most. Both were invisible on a LAN and both were reported from a phone on a bad connection, in the same breath.

**Tapping a chat** sent `resume` and then, on anything but a warm-peek hit, did NOTHING until the server answered: no transcript, no title, no URL. The rail slid away over the chat you had just LEFT and left it there for the whole round trip — indistinguishable from a tap that never registered, so you tap again, or you start typing into a chat you believe you have left. And only the top `PREFETCH_TARGETS` (2) chats are ever pre-warmed, so that was the COMMON case for anything further down the list. `resumeSession` now leaves ALWAYS: `enterSession` fires on the tap, then `awaitPaint` fills the gap with the best copy this device can reach — the offline mirror FIRST (it holds nearly every chat and was consulted only when the socket was DOWN, so on the one connection where it helps most, up-but-slow, it sat unused), else a placeholder that says what is happening. `paintFromMirror` re-enters as `source:"mirror"` so the paint claims no fingerprint (see "a mirror paint claims no fingerprint") and the server's replay rebuilds over it; `awaitingPaint` is the race guard, cleared by `paintLanded()` at the top of `onReplay`, so a mirror read that resolves AFTER the authoritative paint silently cancels itself. A stalled switch (`PENDING_VIEW_SLOW_MS`) stops spinning and offers Reconnect — the zombie-socket case, where the socket reports OPEN and nothing is coming.

**Sending a message** cleared the composer the instant the text hit the socket but drew the blue bubble only when the server ECHOED the turn back; between the two the message existed nowhere the user could see, and a long one read as lost. The bubble is now drawn on SEND and RECONCILED by the echo — the server's version WINS (it carries the `at` stamp, the `turn` id the delete chip needs, and the attachment notes the server appends), and a `queued` event resolves it the other way, into a chip. Matched by TEXT with an oldest-first fallback, because two sends inside one round trip can come back in either order and the echo is not always byte-identical to what we sent. A `!` command is exempt: its terminal block already carries the command, and a bubble would be the duplicate #154 removed. The recovery rule is the load-bearing half: a bubble whose DOM is destroyed while still un-acknowledged hands its TEXT BACK to the composer (`clearPendingSends`, called from `onReplay`, `renderLoadingTranscript` and `ws.onclose`) — deliberately NOT an automatic resend, since the send may well have arrived and a duplicated instruction to an agent that runs shell commands is worse than retyping.

Two cache invariants follow, pinned from both sides: an un-acknowledged bubble is DOM the server never sent, so `viewStashable` refuses to file it under a server fingerprint and `replayLanding` refuses to `noop` over it — the fingerprint cannot see it, because nothing about it came off the socket. Same rule in a third place: the rail's "you are here" mark is repainted by `refreshRailCurrent` from `enterSession`, and `renderSessions` prefers `currentSession` over the server's `event.current` — otherwise the next `session_list` (which arrives right after every switch) would undo it and the row you LEFT would go on claiming to be current on a docked rail.

Pinned by `tests/js/test_pending_view.js` + `tests/js/test_pending_send.js`, each mutation-checked, and verified against a real browser driving an isolated server over a deliberately slowed socket.

## The transcript

**When a turn happened (`// [MSG-STAMP-START/END]`, #200).** A transcript said nothing about WHEN, so an old chat surfacing in the rail was undated once you were inside it. The data was always there: `SessionLog._write_line` has stamped every record with an ISO timestamp since the first version of the file, so this is a read, not a migration — chats written long before the feature get their times back. It rides `at`, deliberately NOT `ts`: on a live event `ts` means "this turn is starting now" and drives the trace card's clock, and cold replay must never look like a running turn, so the two stay separate fields with separate meanings (`record_epoch` converts the log's ISO stamp; unparseable → None → nothing rendered, never a wrong time). Sent as EPOCH SECONDS, not the ISO string, because that string carries no timezone and a browser would read it as its own local time — a phone away from the server would silently show the wrong hour. Rendered on the turn's OPENING message only: a turn's two halves are seconds apart, so stamping the answer as well prints the same time twice, and the answer's row already carries how LONG it took (asked at 14:32, took 12s). The format is ABSOLUTE — a rail row is re-rendered every time you open the list so "2m" stays true there, but a transcript line is written once and read months later, where "2m" becomes a lie. Adding the field moves the offline mirror's prefix signature once, so mirrored sessions re-sync a single time; self-healing, and the reason the field was not squeezed into `ts`.

**Jump to the start of an answer (`// [ANSWER-TOP-START/END]`).** A long reply runs off the top of the screen while you read it, and finding where it began means scrolling back through its own body hunting for a boundary that looks like all the other text. The chip lives ON the answer (that is what "this answer" means) at the far right of the tool row — apart from the cluster that acts on the answer, because it navigates. The arithmetic has one trap worth keeping the comment for: `#messages` is a SIBLING below `#topbar`, not underneath it, so an element at the scroller's own top is ALREADY clear of the header; subtracting the header's height as clearance (which reads as obviously right) overshoots by exactly the header and lands above the answer — and on a short transcript lands at 0, which looks like a working scroll-to-top button and is not the feature. The chip HIDES itself when the answer is no taller than the transcript viewport: if it fits, then whenever you can see its tool row you can already see its first line, so tapping would scroll nowhere — which reads as broken rather than as "nothing to do". Height-vs-viewport is the whole test (scroll position never enters it), re-evaluated by a ResizeObserver because images, fonts and the reading-size stepper all change an answer's height after it is built. `tests/js/test_answer_top.js` pins the maths and the show/hide rule.

**Composer affordances (`// [COMPOSER-SLOT-START/END]`).** Split by WHAT THEY ACT ON, which is the rule to keep when the next one is added: the FIELD owns its content, so clearing is a control inside the field (the platform's clear button), shown only when there is something to clear; the ROW owns actions on the message, so pasting is a button beside attach / dictate / send and is ALWAYS present. They were one shared slot first (paste when empty, clear when not) and that failed the actual flow — you type a few words and THEN paste ("review this: <url>"), so the shared slot hid paste at exactly the moment it was wanted. Mutually exclusive on screen is not mutually exclusive in use. The composer now goes full-width (`tall`) at the SECOND line rather than the third, decided by `composerLines()` measuring against the computed line-height — a pixel constant means "two lines" at one reading-size setting and "three" at another — because the in-field clear button has nowhere sensible to sit in a two-line box still sharing its row. `tests/js/test_composer_slot.js` pins the split, plus the refused-clipboard path saying so instead of looking like a dead button. Gesture recognizers yield explicitly: the pager sets `touchConsumedByTranscript` whenever it decides what a touch IS — standing down for a vertical scroll OR claiming a horizontal page-drag — and the window-level swipe-up respects it; geometry alone cannot tell a flick-scroll from an open-the-drawer swipe (the bottom zone overlaps the transcript), and the claim used to be one-sided (scroll only), so one diagonal flick could both commit a page switch AND open the drawer over it. Eligibility for a window-level gesture is decided at **touchstart**, never at touchend (a window listener runs last, after element handlers have already mutated the state it would read).

**Two meanings of `error` (`// [ERROR-KIND-START/END]`).** Everything below the guards in the `error` case is written for ONE of them — your TURN failed — and it ends the turn: close the answer, close the live trace, clear busy, red dot, Retry, push notification. The other kind is a REFUSAL of the request you just made and says nothing about the turn, but it arrived in the same shape: asking to delete a message while the chat was working produced the correct refusal AND tore down the running turn's card, taking Stop and Retry with it. Told apart by the machine-readable code, never the prose — the server stamps `refused` at the site that knows (`WebServer._refuse`), because a turn failure goes through the bridge and a refusal down one socket, a distinction the client cannot re-derive. A refusal is a toast: transient feedback about an action, the same register as every other refused action in this app. Pinned by `tests/js/test_error_kind.js`, which also pins that an UNCODED error still ends the turn exactly as #48 built it.

**The queue strip goes with the transcript (`clearQueueChips`).** Every chip above the composer belongs to ONE chat — it names a message that chat's agent is holding, and its Remove button dequeues from whatever session this client is viewing — so the whole strip is cleared wherever the transcript is replaced (`onReplay`, `renderLoadingTranscript`). It used not to be, and only for the message chips: the pending-cd card was already dropped there, which is how one half of a strip came to behave differently from the other. A chip that survived a switch sat above the new chat's composer, where Remove dequeued from the WRONG session while the message it named ran on in the old one. The server re-sends the real queue on attach, so clearing loses nothing — what comes back is the queue of the chat you actually landed in. `tests/js/test_queue_chips.js` pins the clearing AND the wiring, since a chip outliving its view is a wiring bug, not a logic one.

## Ownership fences

**Session identity has one owner (`// [SESSION-ENTER-START/END]`, #181 phase 2):** "the view is now chat X" used to change in FOUR hand-rolled variants — a hello, an offline mirror read, the boot paint, and the warm-peek paint in `resumeSession` — each writing a different SUBSET of the facts coupled to identity, which is where the subset-drift bugs lived (the boot paint reset no fingerprint and remembered no session; an unguarded mid-hello `localStorage` write aborted the rest of the hello in private mode). `enterSession(name, {source, title, stash})` is now the ONLY writer of `currentSession` and the only caller of `deepLinkSession` + the `aish-session` key, doing every coupled write in one fixed order: stash the outgoing view → reset the fingerprint **iff the name changes** → identity → provenance (`offlineViewing`, derived from `source`) → title → guarded persistence → URL → mirror MRU + pin toggle. The "iff" is load-bearing both ways: a prefetched swipe moves identity ahead of its hello on purpose, so that hello reads as same-session and its replay no-ops instead of rendering twice. `onHello` keeps only what a hello knows (model, recency list, workspace, busy/role, peeks). `test_ownership.js` enforces the single writer; `tests/js/test_choreo_session_switch.js` pins the races (prefetch-vs-hello, mirror-vs-socket boot, private-mode throw, fork-vs-reconnect) over the REAL functions via `harness.js`'s `sessionWorld()`.

**The live turn's render state has one owner too (`// [TURN-RESET-START/END]`, #181 phase 3):** a replay is reachable MID-STREAM from three paths that never asked whether a turn was running (the socket's own `replay`, an offline mirror tap, the warm-peek paint), and each hand-rolled the same zeroing of the answer accumulators — leaving the half-streamed bubble behind while its TAIL kept arriving (the rest of the answer painted into a fresh bubble, and `done`, the only carrier of the complete text, then saw `sawAnswer` and rendered nothing), and never closing `currentTrace` at all, so a live trace survived into the NEXT chat, collected its steps, and kept its 1-second ticker running. `resetLiveTurn(landing)` is now the one place that group is closed as a unit (answer bubble + stable-prefix bookkeeping + approval cards + `renderedAnswers` + `finishTrace`), called once from `onReplay` and from `onHistory`. Two decisions live in it. (1) **A `noop` landing resets NOTHING** — `noop` means the DOM already IS this transcript, which is the re-replay every phone unlock produces on a chat that may still be working; the exemption is safe only because `enterSession` drops the fingerprint on any name change, so a SWITCH can never land there (pinned in `test_choreo_trace_switch.js` so the two halves can't drift). (2) A replay that lands mid-stream **abandons** the answer (`answerAbandoned`), and the rule the flag encodes is **abandon drops the stale LIVE tail; REPLAYED content is authoritative and re-opens the turn**. Both halves are load-bearing. `Bridge._put` records token events (merging consecutive ones), so the ordinary same-session reconnect — a phone unlock during a long answer — replays the partial answer itself, and the loop thread makes that snapshot contiguous with the live tail that follows: `onToken` rebuilds the bubble from the replayed token, clears the flag, and the tail flows on into it, so nothing is lost or doubled. A stale LIVE token is the other case — its bubble is gone, so painting it alone would show a truncated answer AND (via `sawAnswer`) suppress the `done` render carrying the whole text; it is dropped, and if the replay had nothing to rebuild from the cost is "no live streaming until `done`", never wrong content. Turn boundaries clear the flag too, but a `user` event only when LIVE — a replayed one is the rebuild of the very turn that was abandoned. The manifest gained `viewFp`/`viewDirty` (→ `[SESSION-ENTER]` + `[CONNECT-WIRE]` + `[REPLAY-LANDING]`, the fence around `onReplay` — the one authoritative repaint), `answerEl` (→ `[TURN-RESET]` + `[ANSWER-OPEN]` + `[ANSWER-CLOSE]`, one region per lifecycle stage) and `currentTrace` (→ `[TRACE-OPEN]` = `ensureTrace` + `[TRACE-CLOSE]` = `finishTrace`). The streaming hot path itself (`onToken`'s rAF batching, `renderAnswerNow`, `StreamCoalescer`) is deliberately untouched — this was an ownership change for the RESET transition, not a render rewrite.

**Rendered-view reuse (`// [VIEWCACHE-START/END]` in app.js):** a session switch replays the full transcript and rebuilds the whole DOM (markdown + hljs for every answer) — the slow half of a swipe on long chats. Leaving a CLEAN idle view (no live events since its replay, no pending cards, not busy, not mirror-painted) stashes its rendered nodes (`viewCache`, capped MRU), and a replay whose fingerprint (`replayFp`: event count + truncation + last event, capped) matches swaps them back in instead of rebuilding. Correct by construction: the transcript is append-only while a session is open, so any change moves the fingerprint, and every mismatch just rebuilds — the cache can make a switch faster, never wronger. Live events mark `viewDirty` at the `ws.onmessage` dispatch (deliberately NOT inside `handle()`, which the replay loop also calls — and which tests extract into bare sandboxes); `VIEW_SAFE_EVENTS` lists the types that never touch the transcript, so over-dirtying is the safe failure mode. `offlineFirstPaint` gained a `FIRST_PAINT_GRACE_MS` wait so a fast LAN replay wins the first paint outright instead of rendering every chat twice back to back. Pinned by `tests/js/test_view_cache.js`.

**A mirror paint claims no fingerprint (#202 follow-up).** `viewFp` is a CLAIM that the DOM on screen equals a SERVER replay — that is what lets a later replay land `noop` and keep it — and a paint from the offline mirror cannot make that claim: its events come from IndexedDB, are capped by `offline_events`, and are only re-synced when the chat's ACTIVITY stamp moves, so a chat nobody has touched keeps whatever was stored, in whatever event SHAPE the app that stored it used. `onReplay` therefore sets `viewFp = offlineViewing ? "" : fp`. The defect that proved it: #202 added a `turn` field to `user` events (what the delete chip names), which moves neither the event COUNT nor the LAST event, so `replayFp` could not see the difference — the authoritative replay no-op'd, the chip-less mirror DOM stayed, and the delete control was missing from every chat not used since the deploy. A prefetch keeps its claim (peek data IS server data; that no-op is the point of the warm peek). Pinned in `test_choreo_midstream_replay.js`, mutation-checked. `replayLanding` decides every landing: **"noop"** (same fingerprint, clean view, DOM present — the reconnect re-replay on every phone unlock and the second half of a prefetched swipe keep the DOM AND the scroll position), "reuse" (stash hit), "rebuild" (everything else). A session-switch hello resets `viewFp` so a cross-session fingerprint collision can never keep the wrong DOM.

**Warm-peek prefetch (`// [PREFETCH-START/END]` + server `_peek`):** after each hello settles, the client `peek`s the top `PREFETCH_TARGETS` chats of the server's recency list (`prefetchTargets`, from `hello.pager`, excluding the one on screen) — a VIEW message answering `{type:"peek", name, events, truncated}` (no claim, no hello, nothing recorded; a miss answers `gone` ON the peek, never the resume path's error, whose toast would blame the user). `resumeSession` paints a warm peek synchronously AFTER a successful resume send — identity moves before the hello on purpose, so the authoritative replay no-ops on the matching fingerprint and nothing renders twice; a stale peek just fingerprint-misses into a rebuild. Aiming at the MRU head rather than swipe neighbours is what keeps the A↔B case instant under recency ordering. `TestPeek` in test_server.py.

## Touch and gestures

**Passive transcript touch:** `#messages` carries `touch-action: pan-y` (inner code/tables/terminal opt back into `pan-x`), which lets the pager's touchmove listener be PASSIVE with no preventDefault — a non-passive touchmove on the scroller forced every scrolled frame to wait on main-thread JS, the biggest phone scroll-jank source; the browser's own gesture-start decision now enforces what preventDefault pretended to.

**Transcript selection while composing (`// [TOUCH-FREEZE-START/END]` + `[VV-SETTLE-START/END]`):** iOS WebKit won't establish a document selection while an editable holds focus (the console's select mode blurs for the same reason), so a long-press on an answer while the composer was focused could never copy part of it — transcript touchstart now blurs the focused editable (keyboard dismisses, the platform chat convention; a touch INSIDE the focused element, e.g. a card's feedback field, never blurs it) and FREEZES viewport settling (`syncKeyboardInset` reflow, `snapViewportHome`, `scrollToEnd`) until touchend, because those ran on the dismissal's visualViewport events and moved the text under the still-held finger, cancelling the long-press; `endSwipe` runs the deferred settle without `scrollToEnd`, and an established selection also suppresses `scrollToEnd` on later viewport events so it is never yanked to the bottom (pinned by `tests/js/test_transcript_select_guard.js`). Freezing alone is not enough: the dismissal makes iOS animate `visualViewport.offsetTop` back to 0, and a fixed body still pinned at the old offset slides DOWN the screen by exactly that much — so while frozen, `trackViewportPan` keeps `body.style.top` glued to the moving `offsetTop` (top only; the kb-open class, height, and every scroll stay frozen), and the content under the finger genuinely stays put. The busy model-dot glow animates a `::after` ring on transform/opacity, never box-shadow (which repainted — and re-blurred — the backdrop-filtered top bar every frame for as long as any task ran).

**The drawer's Recent/Automated tabs, the composer swipe-up, the horizontal pager and the bottom search bar's swipe-dismiss are all gone** — replaced by the rail above. The Sessions screen's bottom-docked search survives as the rail's own (`.rail-searchbar`), same thumb-reach argument, just narrower. Web approvers mirror `cli.make_approver` exactly (denylist first, also on edited commands; auto-approval scoped to live roots; per-session "allow this session" prefixes, held on the session agent (#176) so they die with the session; "Always allow" saves the card's shown prefixes to the same persistent allowlist file as the CLI's `a` answer).

## The trace card

**Trace-header status line:** while a turn runs, the trace header narrates the CURRENT step — priority chain in `traceStatusLine` (fenced `// [TRACE-STATUS-START/END]`): Stopping > Waiting for approval > Answering > running tool (the model's own words win over the deterministic `TOOL_STATUS` line; parallel read-only tools add `· +N more`) > streaming thinking gist > Thinking… > last turn's words > Working…. The load-bearing split: step handlers (`traceStep`/`toolStart`/`toolFinish`) write DATA onto `t` only (`turnSay`/`turnGist`/`liveGist`/`running`/`waitingApproval`/`answering`/`stopping`) and ALL display strings derive inside the fence — the choreo sandboxes load the handlers with `updateTraceHead` stubbed and `TOOL_META:{}`, so string-building in a handler crashes them. The model's words ride the persisted `thinking` step (`say` = preamble emitted alongside tool calls, `gist` = first line of its thinking text, both `_status_snippet`-capped at `STATUS_SNIPPET_CHARS`; keys omitted when empty, so old logs replay byte-identically and hot/cold parity holds by construction). Thinking text itself is captured via `ChatMessage.thinking` (backends.py: Anthropic thinking blocks; Ollama's `message.thinking`, whose streamed deltas feed a live "Thinking: <gist>" through the UNRECORDED `WebStatus.note` status channel — `status.note()` is part of the status protocol, no-op on the CLI ticker and `_NoStatus`). `_one_chat` returns a 5-tuple ending in the thinking text; claude-max emits no thinking steps, so it gets the deterministic lines only. "Thought for Xs" rows keep the gist as a subtitle on BOTH the live-finalize and replay-synthesize branches (pinned by `tests/js/test_trace_thinking_gist.js`; the priority chain by `tests/js/test_trace_status_line.js`). `markStopping` is state + `updateTraceHead`, not a one-shot DOM write — the 1s ticker used to repaint "Working…" right over it. The header gives the status line the FULL width: no right-side tokens chip (tokens ride the sub line), and the LIVE sub is `elapsed · ↑N ↓M` with no step count (what is happening matters mid-run, not how many steps so far; the finished sub keeps "N steps").

**That elapsed time counts the TURN, and the turn's origin travels on the `user` event.** The card is built by the turn's first step and destroyed by every rebuild, so it can never be the clock's origin — `turnStart` (owned by the `user` case, cleared at every way a turn ends and by `resetLiveTurn`) is, and a browser landing mid-turn must be TOLD it: `_user_event`/`_turn_event` stamp `ts` (epoch seconds) on every live `user` event, and `replayedTurnStart` reads it back. The step-sum back-date in `accountStepTime` survives only as the fallback for an unusable stamp (a transcript trimmed past its own opening turn, a pre-stamp log, a client clock behind the server's) and is guarded by `originKnown` so a known origin is never pushed into the past twice — because summing steps measures the WORK and a turn is work plus every gap between it (the step still in flight, an approval waiting, the answer streaming), so it always reconstructs SHORT. That shortfall is what a swipe away and back looked like: the clock did not reset, it re-derived itself from less. Cold replay is deliberately UNstamped — `reconstruct_events` closes every turn it replays (a cut-off one becomes an `error`, which clears the origin like `done` does), so it can never land a reader inside a running turn, and stamping it would rewrite every mirrored session's offline prefix sig for nothing. `answerTiming` is wall-clock and therefore gated on `!replaying`: since the origin is now real, the time since it is the transcript's age, not the turn's length. Pinned by `tests/js/test_trace_clock.js` + `TestTurnOrigin` in test_server.py.

**Live card is the turn's TAIL, and the answer is the anchor.** A turn reads prompt → what the model wrote → what it is doing right now, so the live card is the LAST transcript child and sticks to the BOTTOM (`.trace.live { position: sticky; bottom: 0 }`) — pinned above the composer where a chat app's status line belongs, and where Stop can never scroll out of reach (the reason the card must stay one row: it is COLLAPSED while live, `open` on a live card can therefore only mean the reader tapped the header, which is why `collapseTimelineForAnswering` now stands down on `t.userToggled`; Stop is icon-only for the same width reason). Header order is `status · text · chevron ——— Stop`: the disclosure chevron follows the LABEL it opens (`.trace-headtext` is `flex: 0 1 auto` — shrink-only, so it hugs a short status yet still takes the full width for a long one, and `.trace-chev { margin-right: auto }` hands all the slack to Stop), because two affordances sharing the trailing edge made the expand tap land on Stop; `.trace-stop`'s `margin-left` is the floor on that gap for when a long status line has eaten the slack. That ordering cannot be chosen at creation — the card exists BEFORE the answer bubble (steps arrive first) and every later append lands after it — so it is re-established by `keepTraceLast()` (`// [TRACE-TAIL-START/END]`) called from `scrollToEnd`, the funnel every content-adding path already goes through: ONE enforcement point that covers appends nobody has written yet, and it reads only the `live` class, so a finished card stays put as a footnote under its answer (no end-of-turn reshuffle shifting text under the reader). Replay runs the same handlers, so hot and cold produce the same order. `--live-trace-h` (set by `measurePinnedTrace`'s ResizeObserver, cleared by `releasePinnedTrace`; the observer is guarded because the choreo sandboxes have none) offsets the floating jump-to-latest arrow above the card, capped so an expanded timeline can't fling it up the screen.

**The anchor is the ANSWER, never the card** — `turnAnchorEl` is claimed in `[ANSWER-OPEN]` and deliberately NOT in `[TRACE-OPEN]` (a card that owned it was what pinned the progress box to the top of the screen for the whole turn). "Scroll while it fills, then stop" is then a CONSEQUENCE of `anchorAnswer`'s clamp rather than a mode: while the turn is shorter than a screen the target clamps to the bottom so the view rises with the text; once the answer's top can reach the top of the viewport the target stops moving, and since content is only ever appended BELOW that top, nothing scrolls again for the rest of the turn. Hence no follow flag and no "stop chasing" branch — the `answerFilling` freeze it replaced is gone. Pinned by `tests/js/test_trace_tail.js` (tail invariant across an interleaved text→tool→text turn, driven through `scrollToEnd` so the wiring is pinned too; the rise-then-lock arithmetic; the answer claiming the anchor).

**Reading position survives a rebuild (`// [SCROLLPOS-START/END]`).** The `noop` landing already kept the scroll by keeping the DOM; the other two landings threw it away and came back at the tail — and once the ANSWER was the anchor, `[ANSWER-OPEN]`'s forced `anchorAnswer(true)` fired for REPLAYED tokens too and landed a reload at the top of the last answer, so that call is now gated on `!replaying` (read at SCHEDULE time — inside the rAF the loop has already reset the flag) and `onReplay` alone owns the resting position. What is remembered is NOT a scrollTop (a lie the moment any height differs) but the anchor the wrap toggle already reflows around (`topVisibleAnchor`/`restoreAnchor`): the top-visible child's INDEX + on-screen offset, in `localStorage["aish-scroll"]` (per session, bounded `SCROLL_MAX_KEPT` oldest-first), written debounced on scroll plus on `pagehide`/`hidden` — the phone case is a page torn down inside the debounce window. It is keyed on `transcriptFp()` — count + last child's class + its text length, i.e. the transcript ON SCREEN — deliberately NOT `viewFp`: viewFp is stamped by the last replay, and a live turn appends to the DOM without ever replaying, so the flow this exists for (ask, scroll up to read, come back) always finds it stale. Comparing rendered DOM to rendered DOM asks the right question, "is this the screen I left?", and a mismatch falls through to `scrollToEnd(true)` BY DESIGN — something arrived while you were away and the newest of it is what you came back for. `tests/js/test_scroll_memory.js` pins both directions plus private-mode/garbage-storage survival and the replay guard.

## Console UI

**Console frontend refinements (#148):** the terminal key row is Blink-SmarterKeys-style — sticky-left `esc`/`ctrl`/`tab`, sticky-right arrows/keyboard, only the middle scrolls (symbol keys: tap sends the primary glyph, swipe-down arms the grey secondary); `ctrl` is a 3-state chip (tap = armed one-shot, double-tap = LOCKED sticky-held until tapped off); the arrow pad is ONE key you DRAG for direction with distance-scaled auto-repeat after a 450 ms initial delay (touch-only; desktop uses real arrows).

**Dictation scratchpad:** iOS keyboard dictation REWRITES the whole field on every recognition update (re-punctuating and correcting earlier words), and a PTY cannot retract bytes already written — so speech typed straight into xterm arrives as every interim revision CONCATENATED. The fix is a staging textarea (`#pty-pad`), opened by DOUBLE-TAPPING the arrows key (free real estate: a tap without a drag did nothing; a drag sets `pressed` so it can't be mistaken for a tap), which reuses the composer's #97 recognition engine retargeted via `dictateTarget` (`dictEl()` = `#input` | `#pad-input`; `setDictLang`/`setDictRecording` drive BOTH mic chips) and only writes to the PTY on Send — `padSend(true)` appends `\r`, a long-press inserts without Enter. Return in the pad is a NEWLINE, never a submit (the pad composes multi-line text, and a stray Return must not fire a half-finished command at the terminal); ONLY the Send button submits. It FLOATS above the key row (`positionPad` sets `bottom` from the row's height; 0 on desktop where the row is `display:none`) rather than taking flex space, so opening it never re-fits xterm and resizes the remote tmux pane; `resizePadInput` grows it with the text to ~40% of the overlay, then it scrolls internally. Typing a correction while the mic is live sets `dictHold` (renderDictation becomes a no-op so a result can't overwrite your edit) and, after a 700 ms settle, re-baselines `dictateBase` on the edited text and restarts recognition, so new speech appends to what you wrote. `padHistory` keeps the last 10 sends in localStorage (MRU, deduped; rendered OLDEST-first so the newest sits at the bottom, nearest the textarea and your thumb); the UNSENT text is itself persisted (`aish-pad-draft`, mirroring the composer's `aish-draft`: written on every change — including from `renderDictation`, since setting `.value` fires no input event — plus on `pagehide`), so an app update's rev-reload or a PWA relaunch mid-dictation restores it, and `padRestorePending` makes the FIRST `openConsole` of a page load reopen the pad with the recovered text (mic NOT auto-started — there is no gesture to unlock audio after a reload, and you may just want to send it). Only sending discards the draft (`closeConsolePad(true)`); the ✕ deliberately KEEPS it — a mis-tapped close losing a spoken sentence is the failure the pad exists to prevent because the annoyance being fixed is losing a long spoken line to a submit that landed in the wrong window (vim in normal mode); the pad keeps DEFAULT iOS autocorrect/autocapitalize — deliberately the opposite of `!` terminal mode (#156) — because what you speak into it is prose, not keystrokes. Covered by `tests/js/test_dictation_pad.js`. Touch scroll dispatches a real `WheelEvent` on the touched element so mouse-mode apps (tmux/vim/less) scroll identically to the desktop wheel (#151), and the overlay top is pinned to 0 rather than following `visualViewport.offsetTop` so an arrow-drag can't rubber-band it. When the shell/tmux exits or detaches the console auto-respawns in place via `openConsole` (crash-loop guarded: a second death within 1.5 s stops and shows a retry message) instead of leaving a dead overlay.

**Desktop console clipboard (OSC 52):** tmux runs with `set-clipboard on` so a server-side (mouse-mode) copy emits an OSC 52 sequence; xterm's `oscClipboardText` decodes it to the local desktop clipboard, and a `?` read request is refused so the clipboard is never leaked back. Paste is left to xterm's native handler (intercepting Cmd/Ctrl+V double-pasted); the touch paste button still uses `consolePaste`.

**Keyboard shortcuts:** global — Ctrl/Cmd+N new chat, Ctrl/Cmd+O session search, Ctrl/Cmd+P export-to-PDF (older Shift combos still work), Ctrl/Cmd+\ toggles the console. Approval cards use a data-driven `CARD_SHORTCUTS` table (A=approve/install, D=deny, T=trust dir, E=edit) — a key acts only when the active card (`activeApprovalCard()`, last unresolved, so stacked cards clear bottom-up) actually has that button, routed through the button's own onclick so edit/scope/feedback handling is unchanged and never firing while typing in a comment field. On desktop (FINE_POINTER) a pending card takes keyboard focus and verdict buttons show visible `.key-badge` chips, not just tooltips. **iOS terminal keyboard (#156):** entering `!` terminal mode swaps `#input` for a fresh `<textarea>` (id kept, listeners re-bound via `attachInputListeners`) carrying autocorrect/autocapitalize/spellcheck-off attributes from birth — iOS only reads those on first focus, so flipping them on the already-focused composer never took; exit swaps back to prose attrs (chat prose keeps autocorrect).

## Composer, replay and polish

**`!`-command replay (#154):** a user-direct `!` command is shown by its terminal block, so the redundant blue user bubble is skipped both live and on cold replay; `reconstruct_events`' `_BANG_RE` gained `re.DOTALL` so a multi-line backend-run command (feedback's `gh issue create` with a multi-line body) rehydrates as its terminal block, not a raw annotation bubble.

**Misc web polish:** user bubbles recall to the composer via an explicit pencil reuse chip in the tool row, not a whole-bubble click that clobbered drafts (#155); write/edit approval-card diffs wrap by default regardless of the global wrap toggle (#153); PDF export shows a sticky in-progress toast (`showToast(text, sticky)`/`hideToast`); `/feedback` now sends its attachments (engaging the classic upload flow) and the vision note carries the full uploads path (#152); iOS dictation rebuilds each recognition session's transcript from all its results every event instead of appending, fixing cumulative-transcript duplication (#97).

**Synthetic turns (#171)** extend that same "not every logged user message is a bubble" seam: `_user_event()` tags a live `user` event with the classification `session.synthetic_kind` will reach on replay (`_launch`'s typed messages are deliberately never routed through it — what you type is yours), the resume + `/trigger` emit sites are the only two producers, and `app.js`'s `addSystemMsg` renders the tagged event as the workspace marker's quiet system row. The turn side effects in `case "user"` are untouched — a synthetic turn IS a real turn — except that it seeds neither the chat title nor the composer's prompt history.

**Composer Enter (#170):** in the PROSE composer Enter inserts a newline and the `#send` button is the ONLY submit path — autocorrect/IME/dictation all emit Returns that used to fire half-written messages, and a `<textarea>` never implicitly submits its form, so nothing else can. Enter-to-send survives ONLY in `!` terminal mode (a shell prompt, where running the command is the point — #100/#156), on BOTH the desktop keydown branch and iOS's `beforeinput`/`insertLineBreak` branch; the suggestion popup still accepts a partial completion with Enter, but an exactly-typed slash now just closes the popup instead of falling through to submit. The asymmetry is marked in `// [ENTER-START]…[ENTER-END]` and pinned by `tests/js/test_composer_enter.js` — don't "fix" it back into symmetry.

## Offline mirror

**Offline mirror (#165):** the installed PWA opens and READS its conversation archive with no server reachable. It is cheap because it reuses two existing invariants rather than adding a second renderer: rendering is already a pure function of an event array (`onHello` + `onReplay`), and `SessionLog.reconstruct_events` is already a pure `path → list[dict]`. Server side, two read-only HTTP endpoints outside the WebSocket — **`GET /offline/index`** (`handle_offline_index`: rev + every session's `name/title/snippet/ts/origin` via `list_sessions`) and **`GET /offline/session`** (`handle_offline_session`) — deliberately construct NO Agent and take NO session slot, mirroring `handle_export_session`'s token-check + name-safety + `asyncio.to_thread` shape. `/offline/session` has three "don't resend what they have" layers, cheapest first: a matching `If-None-Match` against a weak mtime+size ETag → **304, empty body**; a `since`/`sig` pair whose prefix still verifies → only events after it (`base>0`); otherwise the whole stream. `sig` is `_prefix_sig` — a hash of the first `since` events computed by the SERVER both times and echoed back opaquely by the client, so there is no cross-language canonical-JSON agreement to get wrong. It exists because reconstruction is NOT purely append-only: a command still running at sync time later reconstructs as `command_start → stream → command_end`, SPLICING events mid-stream, which a naive `since` would silently corrupt. `offline_events()` wraps `reconstruct_events` and caps bulk output (`OFFLINE_OUTPUT_CAP`, head+tail+marker) on `stream.text` and `step.output` — the conversation stays verbatim, the noise shrinks ~10x, and that asymmetry is what makes a FULL local archive affordable; a pre-trace log falls back to the flat `history` blob so old sessions mirror too. Client side (all in `app.js`, marked blocks): IndexedDB `aish-offline` with SEPARATE `meta` and `events` stores (the sessions sheet and search read metadata only, never deserializing transcripts), a `text` search index built from `user`/`done` text only (command output is noise in a search index and the bulk of the bytes), `offlineRank` — a port of `SessionLog.rank`'s tiers so offline search ranks like online search (tier 1's difflib fuzzy is approximated by an LCS ratio), and `offlinePlanEviction` (150 MB / 200 sessions; pinned NEVER evicted, current never evicted, else least-valuable-first by `max(openedAt, ts)` — the `ts` half is what makes a chat started on another device readable here). Sync is resumable **by construction, not bookkeeping**: newest-first, one session at a time, each committing atomically, and the next pass recomputes the work from the same timestamp comparison — so a pass cut off by a tunnel simply continues. It runs on connect, ~2 s after each `done`, and on a 5-min idle tick; `navigator.storage.persist()` is requested once there is something worth keeping. `offlineFirstPaint()` runs BEFORE `connect()` so the last chat paints from IndexedDB while the socket is still opening (the speed half of the feature); it checks `serverPainted` so an authoritative replay always wins the race. Offline mode is decided by the SOCKET, not `navigator.onLine` (hotel wifi with no route home is "online"), and takes over the `#connbar` with a single `#offlinebar`. `resumeSession()` falls back to `openCachedSession` so rail row taps work offline; `deepLinkSession()` keeps `?session=` in step, WITHOUT which regaining signal yanks you back to whatever chat the last hello pinned in the URL (`connect()` prefers the URL over the last-session key). Sending offline is refused ON PURPOSE — an outbox would dispatch an agent that runs shell commands with nobody watching and an approval gate answered by someone who has moved on. `sw.js` went from notification-only to an app-shell cache: **navigation is network-first** (3 s timeout, cache fallback) because the page compares its own `?v=<rev>` against `hello.rev` and a stale cached index.html would loop forever; `?v=`-stamped assets are cache-first-immutable (the URL names exact bytes, so new HTML can never pair with stale JS); other statics stale-while-revalidate; `/file` images get a bounded LRU cache; `/ws`, `/offline/*`, `/upload`, `/trigger`, `/export/*`, `/dirs` are NEVER cached. The reload path is double-guarded: `reloadThrottled()` asks the SW to `PURGE_SHELL` first and refuses more than 3 reloads per minute — one revision behind is a papercut, an app that reboots forever is unusable. The **pin** is a row in the chat menu (`data-act="pin"`, glyph upright+solid = pinned) — it started as a header toggle and moved out when the title row ran out of space — and its state is read from the STORE on every paint (`offlineIsPinned`), never from the in-memory `offlineMeta` mirror — that mirror is empty for a moment after every reload, so reading it made a pinned chat show "Off" and a tap to "pin" it silently UNPIN the chat (it flips the real value). Until the read lands the icon shows a dimmed `unknown` state rather than claiming either answer; `tests/js/test_offline_pin_state.js` guards both the reader and the wiring. There is deliberately NO bulk "clear offline copies" action: the mirror self-manages (capped, least-useful-first eviction, server-side deletions dropped on the next sync), and the one that existed also wiped the SW shell cache — breaking "the app always opens offline" until the next successful load. Disposal and repair are covered by deleting the installed app; the SW's `CLEAR_CACHES` message went with it. Tests: `TestOfflineMirror` in test_server.py (delta, 304, truncation, token gate, legacy fallback) plus `tests/js/test_offline_search.js`, `test_offline_evict.js`, `test_sw_routes.js`, `test_reload_throttle.js`.

## Testing the frontend

**Choreography harness + ownership lint (#181).** Those checks verify DECISIONS; every one of the four #181 incidents had a correct decision function and a broken feature, because the defects live in the *choreography* — when a decision is consulted, what happens if a step is skipped, what happens when two sources race. `tests/js/harness.js` (a plain CommonJS module, NOT a test — the runner globs `test_*.js`) is the shared, **hostile-by-default** world for new choreography tests: page hidden unless asked otherwise, `requestAnimationFrame` callbacks collected and never fired, timers as `{fn, ms}` data the test fires by predicate, the lying element (computed transform tracked apart from the inline style, because "the DOM lies" was itself a bug), and `FakeWebSocket` — records sends, `deliver()`s messages on demand, fires `onclose` out of order, and goes `zombie()` (readyState OPEN, silent, `close()` observably nothing — the failure no event announces). Existing tests deliberately keep their own copies; harness.js is for NEW tests only. Pins today: `test_choreo_socket_replace.js` (#179 — replacing a socket through the real `connect()` leaves exactly one live feed), `test_choreo_wake.js` (the wake handler's two subsystems), `test_choreo_console_status.js` (the #180 follow-up, as a property over every interleaving — plus, since phase 3, `openConsole`'s own guard sequence: only a REAL open may disarm the placeholder guard, since it used to be re-armed ABOVE the early returns and an open-while-open call disarmed it for good), `test_choreo_session_switch.js` (phase 2's identity races, on `sessionWorld()`), `test_choreo_midstream_replay.js` + `test_choreo_trace_switch.js` (phase 3 — a replay landing at every position in a token stream must leave exactly ONE answer bubble holding the COMPLETE text, and a live trace must never outlive the transcript it was drawn into, while a `noop` landing disturbs neither). Convention going forward: a race fix ships with its interleaving as a test, not just its decision function. `tests/js/test_ownership.js` is the enforcement half — a manifest of `owned variable → fenced region(s) allowed to assign it`, checked against app.js, whose failure NAMES THE OWNER to call instead (`ws`→`[CONNECT-WIRE]`+`[RETIRE]`, `currentSession`→`[SESSION-ENTER]`, `seenAt`→`[SEEN]`, `viewFp`/`viewDirty`→`[SESSION-ENTER]`+`[CONNECT-WIRE]`+`[REPLAY-LANDING]`, `answerEl`→`[TURN-RESET]`+`[ANSWER-OPEN]`+`[ANSWER-CLOSE]`, `currentTrace`→`[TRACE-OPEN]`+`[TRACE-CLOSE]`). Adding an owned variable is one manifest line; deliberately not every variable, only the invariants the user can see (over-fencing turns the lint into noise) — `answerAbandoned` is deliberately OUT, its writers being the owner plus the two turn boundaries that already reset `sawAnswer`, which no honest fence covers.
