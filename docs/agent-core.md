## Backends and the claude-max exception

## - **`claude_max.py`** — the exception: routes through the Claude Agent SDK / local `claude` CLI login. It strips Claude Code to bare inference and injects aish's own tools, so the approval gate still applies. Keeps its own session state. Three invariants added by #178 P0-4: (1) the SDK owns the loop, so the inner Agent's `run_task` — where per-task state normally resets — never runs; `ClaudeMaxAgent.run_task` therefore calls `Agent._reset_task_state()` (the SHARED extraction of run_task's top: stop gate, skill gates, `_run_meta`, `task_sources`, `_cancel` — add new per-task fields THERE, never inline in run_task, or claude-max wedges again). (2) The constructor has NO `**kwargs` sink — every capability the entry points pass is either kept on the wrapper (`on_message`, `on_token`, `status`, `max_steps`) or forwarded to the inner Agent (approvers incl. `approve_tool`/`approve_import`, trace/command/state sinks, steering callbacks, `semantic`, `aliases`); an unknown kwarg is a TypeError, so a new Agent capability can never silently no-op here. Plugin tools register on the SDK MCP server (`_current_tool_defs` = `TOOL_SCHEMAS + inner._plugin_defs`, refreshed per task by `_refresh_server`, mutating ones only when a tool approver is wired). (3) SDK tool handlers may run concurrently while the inner Agent is not thread-safe: `_locked_dispatch` is the single execution path — a `threading.Lock` around `inner._call_result(... inner._dispatch ...)`, which also emits the same tool_start/tool trace steps as the native loop and contains tool exceptions. Tested by `tests/test_claude_max.py` via a FakeSDK injected at the `_load_sdk` seam (no SDK package, no CLI, no network).

## **Gemini thinking (compat layer):** `OpenAICompatBackend` requests `include_thoughts` for provider gemini (`GEMINI_THINKING_BODY`) — the compat API returns thought summaries INSIDE content delimited by `<thought>…</thought>`, so `_ThoughtFilter`/`split_thoughts` split them into `ChatMessage.thinking` on both the streaming path (stateful — tags can split across deltas; trailing partial tags held back and flushed) and non-streaming; unfiltered they would stream straight into the answer bubble and history. Known compat-layer gap probed against the live API: streaming TOOL-CALL turns omit thoughts entirely (non-streaming includes them), so on Gemini the tool phase falls back to the deterministic line and the live "Thinking: <gist>" shows on answer turns.

## Approval parsing

## - **`approval.py`** — conservative parser classifying commands as read-only for auto-approval. Philosophy: only approve what it *positively* understands; anything ambiguous falls through to a prompt. Auto-approval is scoped to session roots (launch dir + `/add-dir` + directories the user trusted at a prompt); path arguments escaping them (absolute, `~`, `..`, symlinks resolved — including a plain relative token that IS an in-root symlink pointing outside, #178 P1-1; tokens naming nothing on disk are never resolved, so patterns/flags/future files can't false-positive) prompt even when allowlisted — `escaping_dirs()` names the escapes so the prompt/card can offer "trust this directory" (`Agent.trust_root`, session-memory only). Shell path operands also get `files.is_sensitive_path` on their RESOLVED target (mirroring the read_file sensitivity prompt), so `cat link-to-ssh-key` or an in-root `.env` prompts even when containment holds. The prefix allowlist has two lifetimes: `a`/"Always allow" is durable and file-backed, while `s`/"Allow this session" lands in `Agent.session_prefixes` and dies with the session (see the roots paragraph below — one rule for both halves of the scope). When touching this file, err toward prompting.

## Session scope and workspace restoration

## **Auto-approval scope belongs to the SESSION, not the process (#176).** Both halves of that scope — the `roots` that bound auto-approval to directories, and `Agent.session_prefixes`, the command prefixes granted with `s` / "Allow this session" — live on the Agent and are reset by the SAME call, `restore_workspace`, so a session change drops them by construction rather than by someone remembering to. The approvers never own the prefix set: `cli.make_approver` and `server.make_web_approvers` both take a late-bound `get_session_prefixes()` returning the live set off the agent (same holder pattern as `get_scope`/`trust_dir`, because the agent is built after its approvers), and keep a set of their own only for an unwired approver in a test. `restore_workspace` CLEARS the prefixes and never restores them — unlike trusted dirs they are not recorded on disk, so resuming BACK to the chat that granted one asks again rather than inventing persistence the log cannot back. The persistent `a` allowlist is deliberately untouched by all of this: it is file-backed, shared by CLI and web, and outlives every session.

## `restore_workspace(cwd, trusted)` is AUTHORITATIVE, never additive: on resume/cold-open it rebuilds `roots` to be EXACTLY that session's own workspace — its recorded `kind:"cwd"` (or `Agent.launch_cwd` when it never recorded one, matching the base the web gives a cold-opened session) plus its own recorded `kind:"trust_dir"` dirs, which `/add-dir` and an approval-prompt "trust this directory" both write. Both directions are bugs, because `roots` is what scopes auto-approval: a dir trusted in the chat you LEAVE must not stay auto-approvable in the one you land in (the CLI reuses ONE live Agent across `/resume`, so this leaked; the web builds a fresh Agent per cold open and never did), and a dir this chat DID trust must come back. `/new` re-anchors the same way (`restore_workspace(agent.cwd, [])` — you are still in that directory in this terminal, but the previous chat's grants stay with it). It sets state directly, never via `rebase`/`trust_root`, so restoring emits no fresh record (a replay feedback loop). The corollary: roots a PROCESS owns rather than a session — the web's uploads dir — must be appended AFTER the call, which is why `open_session` adds it below the restore block, not at construction.

## Origin gates

## **Origin-gated egress (#178 P0-2).** `Agent.origin` (constructor kwarg, default `"user"`; the server's `open_session` passes the session's origin, cli.py passes nothing) scopes two read-side capabilities to attended sessions. In a non-`user` session: (1) `web_search`/`read_url` (`EGRESS_TOOLS` — read-only locally, but their INPUTS leave the machine) hold on the existing `approve_tool` channel when they reach a host outside **provenance** — `_owner_hosts` (extracted by `_hosts_in_text` from owner-authored text ONLY: the task/trigger prompt in `run_task`, mid-task steering in `_inject_pending_messages`, `add_user_context`, and user-role turns in `load_history`; never tool results or fetched pages, which are exactly what an injection controls) plus `_approved_hosts` (hosts vouched on an earlier egress card; a plain approve caches the host for the session). `_egress_gate` mirrors `_dispatch_plugin_tool`'s #81 verdicts, passes the novel host as the card's `preview` (zero frontend change), and fails closed: no approver → `EGRESS_NO_APPROVER`, unparseable URL → gated. `_read_needs_prompt` routes gated calls out of the parallel read path so the gate can't be bypassed. (2) `_recall` drops the past-session archive search (knowledge entries stay) and says so in the result so the model doesn't retry. `user`-origin sessions are byte-identical to before — no new prompts. `TestEgressGate` in test_agent.py pins all of it.

## **Origin-gated knowledge writes (#196).** The third capability the same axis scopes, and the one the axis was never applied to: `remember`/`forget_memory` (`KNOWLEDGE_WRITE_TOOLS`) auto-approve, deliberately, so capturing a fact costs nothing — but that reasoning is **attended-only**, and unattended the text proposing the write can be injected email while the result persists into EVERY future session and is retrieved by preflight. That makes the frictionless write a **persistence primitive reachable from untrusted input** — strictly worse than the read exposure #178 P0-2 closed, because it outlives the session. `_knowledge_gate` (called from `_dispatch` immediately before both branches; they are not in `READ_ONLY_TOOLS`, so the parallel read path can never reach them) returns on its first line for `origin == "user"`, so attended behaviour is byte-identical. Non-`user`: deletion is refused **structurally** — no card — because there is no unattended case where autonomously deleting the owner's knowledge is right, so asking would only park a worker on a question already decided (the #185 curate pass's intended path was always *proposing* retirement in its summary; v1's prompt-level `MUST NOT call forget_memory` was #190's own thesis sitting in aish's code — a policy that exists only as prompt text is a policy that does not exist). Saving **holds** on the `approve_tool` card (verdicts mirror `_egress_gate`/`_dispatch_plugin_tool` #81 exactly; no approver → fails closed), because a triggered session does legitimately learn things and the owner should see what lands in the corpus. `_triggered_safe` must never shortcut `remember` (pinned in test_server.py). Every refusal names the slug and the real destination — #190 decision 2, the harness carries the feedback so the owner doesn't have to. `TestKnowledgeGate` in test_agent.py pins it.

## **claude-max got origin (#196 side-fix).** `ClaudeMaxAgent.__init__` had no `origin` parameter while `open_session`'s `common` dict has always passed one — and with the deliberate no-`**kwargs` sink (#178 P0-4) that meant **every** claude-max web session raised TypeError at construction. It now takes `origin` and forwards it to the inner Agent, which is what makes both origin-scoped gates hold on that backend: they live in `Agent._dispatch`, and `_locked_dispatch` is the single path to it.

## Tool execution, file writes, egress

## - **`tools.py`** — `run_command` (approval-gated shell) and `read_docs` (auto-approved, so it takes only a bare command name validated against PATH — never a shell string). The denylist (unrecoverable commands blocked even with approval) lives here. Also the **tool result envelope** (#192): `ToolOutcome` + `classify_output`. The envelope exists because the runtime used to decide whether a call succeeded by sniffing a string prefix (`result.startswith("ERROR")`), which recorded `youtube_analyze` — `transcript: ""`, populated `error_log`, **exit 0** — as a green ✓ while the model silently substituted six web searches for the source the user had named. `ToolOutcome` is deliberately a **`str` subclass**: every existing caller keeps treating it as the result text, so the verdict rides along with no ripple through ~30 dispatch branches, and — the load-bearing half — the metadata travels WITH the value instead of in instance state, which is what makes it correct on the parallel read-only path where several calls are in flight at once (`_run_meta` could not have been used there). The caveat that follows from the same choice: a string operation returns a plain `str` and silently drops the envelope, so a `ToolOutcome` is always built LAST, after any `_with_feedback` concatenation. `classify_output` is the deterministic verdict — exit code, then emptiness, then declared required fields (#193's contract, empty until it ships), then a populated error channel (`error`/`error_log`/`errors`, a NAMED field the wrapper author chose, never prose). `read_tool_output` is the native read-only tool that pages a truncated result from the cache.

## - **`files.py`** — pure `plan_*` functions compute (old, new, diff) without touching disk; `commit()` writes. The gap between plan and commit is where the diff is shown and approval obtained — nothing is written unseen.

## - **`web.py`** — `web_search`/`read_url`, auto-approved but their inputs leave the machine, so every call is echoed and fetched content is wrapped in an untrusted-content banner. http/https only. `fetch_binary` is the same guarded fetch for non-text bodies (`show_image`), sharing `_require_public` + `_opener` so the redirect re-check applies. **TLS trust has ONE source (`_trust_store`, #189):** Python's default store on macOS is Apple's legacy `/etc/ssl/cert.pem` — not the Keychain system store — which is years stale and missing newer roots (GlobalSign Root R46 among them), so fetches to whole swathes of the web failed with `unable to get local issuer certificate` while other hosts worked fine; it reads as a broken SITE rather than a broken client, and it silently affected `read_url` too, not just the image fetch that surfaced it. `_opener` now carries an `HTTPSHandler` built from **certifi**'s current Mozilla root set (declared in pyproject because we import it), falling back to the default context if certifi is ever absent — a stale store still verifies most of the web, refusing everything would be worse. The `_PublicOnlyRedirects` handler stays wired alongside it (`TestTrustStore` pins both: verifying a certificate on a fetch aimed at cloud metadata is no win).
