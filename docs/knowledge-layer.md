# Knowledge layer — skills, memory, retrieval, curation

`skills.py`, `embeddings.py`, `curate.py`, `skill_import.py`, `paths.py`.

**How to use this file.** The laws first — retrieval is the part of aish where a plausible-looking change silently degrades quality without failing anything, so the thresholds and floors below are calibrated numbers, not taste. Then the store, the three retrieval paths (index, pre-flight, deliberate recall), writing, and curation. The agent-side dispatch of these tools is in `docs/agent-core.md`.

---

## The laws

**L1 · Progressive disclosure.** The prompt carries a capped name+description **index**; full bodies load on demand via `read_skill`; the long tail is reached by the `recall` tool. Nothing gets a permanent seat in the context window just for existing.

**L2 · Lexical is the floor; embeddings are an upgrade, never a dependency.** Any embedding failure (ollama down, model not pulled) makes `scores()` return `None` and every caller degrades to the deterministic lexical tiers — byte-identically. `TestLexicalFloor` asserts a measurable floor without a semantic layer at all.

**L3 · Selection must be able to abstain.** A judged audit of 481 live injections measured **46% pure noise**, because a single 0.24 floor sat below the corpus's own noise floor: the median task cleared it with 7–8 entries, so the four slots always filled. Retrieval that cannot say "nothing relevant" is not retrieval.

**L4 · Retire, don't delete.** `status: disabled` and `expires:` remove an entry from every path without removing the file, which is why curation never needs a delete verb — and why deletion has no code path there at all.

**L5 · The action envelope is code, not prompt obedience.** Where a model decides, the set of things it is *able* to do is enforced by the parser and the writer, not by instructions. A policy that exists only as prompt text is not a policy.

**L6 · Imported knowledge is untrusted.** An imported skill's instructions and scripts are what the model would go on to follow, so the review is one consolidated human decision with deterministic risk flags — enforced in code, never by asking the model to check itself. Approval installs it as **third-party** content, not as the owner's (#467): its own tree, its own index section, never preloaded, and reading it taints the task — see "The third-party tree" below.

## The store — `skills.py`

**Skills** are playbooks in `~/.config/aish/skills/`; **memory** is one fact per file, same markdown + frontmatter format, in `~/.config/aish/memory/`. Legacy `lessons.md` lines appear as synthetic memory entries until `/learn lessons` migrates them. `TestParse`, `TestListAndLoad`, `TestLoadEntriesAndCache`.

**Imported skills live apart, in `~/.config/aish/vendor-skills/`** (`VENDOR_SKILLS_DIR`, #467) — see "The third-party tree" below.

**Project scope is DISABLED by default** (#178 P0-1 interim): `./.aish/skills` and `./.aish/memory` are not discovered unless `skills.INCLUDE_PROJECT_DIRS` is set, which neither entry point does — a repository you clone must not be able to hand the model instructions. `TestProjectScopeDisabled` (skills) and `TestProjectScopeDisabledAgent` (end to end) both pin it, and no fixture flips the switch.

**A skill is either** a flat `<name>.md` **or** an agentskills.io-compatible folder `<name>/SKILL.md` bundling `scripts/`, `references/`, `assets/` — the name defaults to the directory, frontmatter still wins, and `_dir_entries` scans subdirs for `SKILL.md` only for `kind == "skill"`, so memory stays flat. `read_skill`/`load_skill` append a `_bundled_note` naming the folder's files so the model reads and runs them through the normal gated tools. `TestFolderSkills`.

### One reading of the header, one shape for a value (#209)

**`split_frontmatter` is the family's single answer to "where does the header end", and it lives here.** Skills, memory, rules and plugin tools are four artifact classes in one md+frontmatter format; `skills.py` already held the family's other shared read primitives (`lifecycle_active`, `parse_expiry`), so `rules.py`, `tool_plugins.py` and `curate.py` import this one rather than each keeping its own. The terminator is anchored to its OWN line (`^---[ \t]*$`, CRLF-tolerant): a naive `split("---", 2)` ends the header at a `---` *anywhere*, so `description: the source came back empty --- say so` made `keywords:` below it prose. `TestOneFrontmatterReader` sweeps `aish/**/*.py` for a fifth reading — both directions pinned, plus a planted offender so the sweep cannot pass by matching nothing.

Adopting it made `curate.update_entry_meta` stop *disagreeing* with `_parse`: its own regex demanded `^---\n` exactly, so one trailing space after the opening marker — the corpus is hand-editable — raised `ValueError` out of the judge loop on a file `_parse` reads perfectly well. Refusing to repair the entry the ledger just flagged.

**`frontmatter_value` is the writer half, and it is the thing that was load-bearing without being written down.** Every writer here interpolates raw (`description: {text}`), so a model-authored value carrying a newline does not produce a broken line — it produces **extra keys**. `save_memory` was safe on the description path only because it happened to flatten the fact with `" ".join(fact.split())`, and that mitigation stops being true the moment a writer preserves newlines.

It had already stopped being true on the *other* path: keywords were only `.strip()`ed, so `remember(fact="a harmless fact", keywords="alpha\nstatus: disabled\nbeta")` wrote a file that parses back `status: disabled` — the entry gone from index, preflight and recall — while the tool returned `remembered (probe): a harmless fact`, with no `[disabled]` marker. Same shape as the `_yaml_scalar` colon-newline bug in `docs/rules-engine.md`: **the artifact means something its own confirmation does not say.** The flattening is now a named function used at every single-line interpolation (`save_memory`'s description and keywords, `update_entry_meta`'s both, `create_tool`'s manifest fields), so a writer that forgets it is visible rather than merely unlucky.

**A key declared twice is the reader's half of the same bug, and the family splits on blast radius (#326).** `frontmatter_duplicates` lives here too, because "what counts as a restated key" must have one answer for the same reason "where does the header end" does — but what a caller DOES about one differs. Advice **warns and still loads**: a duplicated `keywords:` misleads retrieval, and refusing a memory over it would cost the owner more than the ambiguity does, so `_parse` says it out loud on the channel a malformed `expires:` already uses. A plugin tool's manifest is **refused**, because there the weak reading reached the approval gate — `mutating: yes` then `mutating: no` loaded read-only and auto-ran (`docs/tools-layer.md`). Note `pinned` was already the strict reading (`pinned = pinned or …`), which is the shape the tools layer generalises. `TestARestatedKeyInAdvice`.

**The rule this leaves behind: any writer that puts a model-authored value into a structured file gets a round-trip test on day one** — render it, parse it back, assert it means the identical thing. Both bugs above were invisible to reading and neither was catchable any other way. `TestFrontmatterRoundTrip` carries the shared `SMUGGLED` list — a value with `---` on its own line, with a trailing space after the marker, with CRLF, with colon-newline, with a leading `---`, and ones smuggling `expires:`, `pinned:` and `name:` — and the sibling probes in `tests/test_curate.py` and `tests/test_agent.py` import the same list. A round-trip test over benign values is not this test. The one assertion worth copying: `("[disabled]" in result) is (entry.status == "disabled")` — the confirmation and the artifact are one claim.

**The whole tree moves on one knob: `AISH_CONFIG_HOME`** (`paths.config_home`, #254). Rules, skills, memory and plugin tools are four directories under `~/.config/aish/`, and they are one thing — the owner's own corpus, read at the top of every task and WRITTEN by `remember`, `create_skill` and `import_skill`. The verify harness gave itself its own state dir, allowlist, config file and cwd, and was therefore believed isolated while it read the owner's 24 live rules and pointed every knowledge write at his real store; a scripted step that reached an approval card was one click from a permanent, hand-editable artefact. One variable rather than one per directory, because four is four chances to isolate three of them and share the fourth, and the fourth is the one that writes. Resolved at IMPORT, like `AISH_STATE_DIR` at its call sites — set it before importing aish, or rebind the constants, which is what the suite's autouse `isolated_global_dirs` does. `test_suite_never_reaches_the_real_knowledge_store` pins the readers, not the constants, and proves nothing is stubbed by writing a memory through the real `save_memory` and checking where it landed. Since #390 the knob also carries `allow.txt`, `deny.txt` and `lessons.md`, resolved at CALL time (`docs/agent-core.md`, "Where the lists live") — the verify harness's separately-named allowlist was the one file the knob had left behind.

This is the substrate for the **skills-primary, tools-as-scalpel** model (epic #141): a tool is added later only for hot, shell-fragile, reliability-critical operations a documented skill snippet cannot do safely.

## The index (L1)

`knowledge_index()` renders a capped, byte-stable name+description index that `agent.compose_system_content()` rebuilds into `messages[0]` at **every** `run_task`. That live rescan is what makes a new skill appear without a restart — **do not reintroduce boot-time caching** (`TestSkillsFreshness`, `TestKnowledgeIndex`, `TestMemoryIndexSection`).

Caps are **per type** (`INDEX_SKILLS_MAX`, `INDEX_MEMORY_MAX`, and `INDEX_THIRD_PARTY_MAX` for the third-party section), so one entry type growing large can never evict the others from the prompt.

**Standing rules (#178 P1-7).** `pinned: yes` (or `kind: policy`) puts a memory in its own "Standing rules" section under its OWN budget (`INDEX_PINNED_MAX`), exempt from the mtime-recency cap and sorted by NAME — a behaviour rule must not stop applying because newer facts rotated past it, and *which* rules render must never depend on whose mtime moved last. `remember` sets it; `save_memory(pinned=None)` preserves it on update. `TestPinnedTier`.

**The budget is a cut, and the cut is said (#442).** Exempt from recency is not the same as permanent: past `INDEX_PINNED_MAX` the alphabetically LAST pinned rules are not rendered and apply to no task (the owner's corpus reached 27 pins against 20, so 7 rules were cut by their file names, and the section header still said "apply every rule below"). The cut stays — raising the cap or choosing by relevance is experiment H2's question under #444, not a fix — but it is no longer silent. `pinned_cut` is the one answer to which pins render, shared by the index and by the admission check: a `remember` that saves a pin while the set is over the cap appends `pinned_cut_note` to its result, naming every rule the index cuts and whether the one just saved is among them (it reaches the owner through the tool-result echo, like the keyword-drop note below), and a curate `pin` verdict that lands over the cap adds `pinned_not_rendered` to its action record and logs a line. The index's own note still gives only the count. `TestPinnedCutIsSaidAtAdmission`, `test_a_pin_past_the_index_cap_records_what_the_index_cuts`.

A per-task `TASK_REMINDER` system message is re-inserted before each user message — directly, never via `_append`, so it stays out of logs and transcripts. Recency is what makes small local models actually consult skills.

**The index is an INPUT to the model, and inputs get recorded too (#208).** `knowledge_index(on_index=…)` reports what the composition selected and what it capped out; `run_task` turns that into the `context` record (`docs/trace-contract.md` §3.10). A callback rather than a changed return type, for the same reason as `save_memory(on_admission=…)`: the string return is what `compose_system_content`, cli.py and ~20 tests read.

This exists because a session once answered a question about a sick child with the owner's holiday street address, and **the owner could not find where it came from in their own session log** — correctly, because it wasn't there. The address was one memory's `description`, pasted into `messages[0]` before the first token. No tool call, no trace. The gates all behaved: `rule_eval` sees message and action shapes, not assembled context; `admission` sees writes, not reads; `knowledge` records preload, a different mechanism, and is suppressed when it selects nothing.

The live rescan two paragraphs up is exactly why this cannot be left to reconstruction. The index is a pure function of a **mutable directory at a moment in time** — mtime order, `expires` filtering — so touching one file makes yesterday's index unrecoverable. The entry in that incident carried `expires:`, so the evidence was on a timer. Names only, never descriptions: the name answers "which entry?", while for `remember`-saved memories the description often *is* the whole fact, and a log that copies it has re-leaked what it was written to explain. `TestIndexSelectionRecord`, `TestContextRecord`.

**Open, and the reason that memory's body was empty:** a `description` is both the retrieval key `recall` ranks on and the payload injected into every task. Writing one to be findable makes it a fact in every unrelated conversation. Descriptions should say what an entry is *about*, with the specifics in the body — a corpus migration plus a `remember` prompt change, not yet done.

## Pre-flight injection (L3)

`skills.preflight` picks the top entries for a task and `run_task` injects their bodies into the per-task reminder up front, capped by the `PREFLIGHT_*` constants. Oversized bodies get a teaser plus a **read gate** armed until `read_skill` loads them — lifted after bounded refusals so it can never wedge a task (`TestPreflight`, `TestSkillGate`, `TestPreflightInjection`).

**Injecting and BLOCKING do not share a confidence bar** (#238). Injection at `PREFLIGHT_MIN_SIM` buys roughly three-quarters precision, which is the right trade for a teaser: a near-miss costs some characters. Refusing the model's next tool call until it submits to reading a playbook is not comparable, and it ran on the same number — worse, on the keyword rail, which lowers that number further.

Measured on the session that produced the rule: the owner asked for his energy invoices *"for each apartment"*; `trippy_search`, a playbook for finding hotels, scored **0.282** — below the injection floor, and almost exactly the audit's median for an irrelevant entry (0.290). Its author had listed `apartment` as a keyword, so the keyword rail dropped the bar to `SEMANTIC_MIN_SIM`. And the body runs a few dozen characters past the oversized line, so the teaser came with a gate. Two `browse` calls refused, one call spent pulling a hotel playbook into a context about Polish electricity, and a sentence in the owner's chat explaining it — the one thing the refusal text explicitly forbids.

So `_gate_arms` is a second, stricter question, asked only of an oversized skill that is already being injected. **Named in the task arms it** — cosine may not veto an explicit mention. **A keyword hit never arms it on its own**: it is a prior for injection, and the whole failure was a curated word standing in for relevance it did not have. Otherwise the similarity must clear `GATE_MIN_SIM` (0.45 — the same audit's median for a *relevant* entry). In lexical mode there is no similarity to clear, so nothing but a name arms it; that is the conservative direction on purpose, because an unarmed gate costs a playbook the model may skip and an armed one costs the owner's task. The two real cases straddle the bar cleanly: 0.282 for the invoices, 0.454 for an actual apartment search.

An unarmed teaser also stops saying **REQUIRED**. A model told a read is required when nothing enforces it learns that aish's requirements are optional. `TestOnlyAStrongMatchMayBlockWork` pins the whole rule as a table.

**The waiver is a silent retry, not a speech.** Every surface used to tell the model that it could skip a truncated skill by *stating why it does not apply* — and the model's only channel for stating anything is the owner's chat, so a question about sharing PDFs into Obsidian came back with the plan plus *"(Note: the preloaded skill `ios-ssh-terminal-architecture` does not apply here because …)"*. That note bought nothing: nothing ever read the justification, the gate lifts on the refusal counter alone, so the retry always WAS the waiver. The prompts now say so and add the missing half — retrieval is the harness's bookkeeping, and which skills were or were not used is never reported to the owner (`test_waiver_is_a_retry_never_a_speech_to_the_user`, pinning all four surfaces: the teaser, `SKILL_GATE_REFUSAL`, `PRELOAD_REMINDER`, the system prompt). Positive transparency stays where it belongs — the `knowledge` trace record already shows what was preloaded.

The thresholds, all calibrated on the #183 audit (`TestPreflightPrecision`):

- **`PREFLIGHT_MIN_SIM` = 0.35** for unsolicited injection — relevant median 0.458 versus irrelevant 0.290.
- **`SEMANTIC_MIN_SIM` = 0.24** remains the floor for keyword-rail confirmation. A keyword hit is a strong PRIOR that lowers the bar, **never a bypass**: keywords are model-authored, and one generic word used to guarantee injection on a third of all tasks. It is no longer `recall`'s floor — the 0.24 bar sat below recall-shaped noise too (`RECALL_MIN_SIM` below).
- **A NAME hit is unconditional** — naming an entry is unambiguous, and short names embed poorly.
- **Pinned rules never compete for preflight slots.** They are already in every task's index; re-injecting them stole slots from actual skills.

**A playbook a rule forbids is not preloaded.** "check my emails" (2026-09-23, a local model) preloaded `gws-gmail-watch` — a Gmail Pub/Sub watcher — at 0.445, because only the identity line is embedded and "Watch for new emails" sits close to "check my emails". Every command in it was `gws gmail`, in a turn where the owner's `gmail-through-its-tools` rule forbade running exactly that, and the slot it took is the one the model needed for the fact that his primary mailbox is Tuta. So `run_task` seeds the rules BEFORE preflight, and preflight passes over a skill whose every bash/sh/zsh-fenced command (`shell_commands`) the bindings forbid (`rules.forbids`, see `docs/rules-engine.md`); the next entry takes its slot. **One runnable command keeps the skill** (the rule restricts running, not reading), and so does **naming it** — the same reason a name hit is unconditional. Memories are never withheld, the skill stays in the index and `read_skill` loads it, and a skill injected on an EARLIER turn is still in context because earlier reminders are kept — this narrows what is offered, it does not unsay anything. What was withheld is relayed as a note and recorded on the `context` record's `preload.withheld`, but only for skills that would otherwise have taken a slot. This fixes the rule collision, not the mis-retrieval: an identity line that matches the wrong task still does, and that is a retrieval-quality problem for another day. `TestWithheldSkills`, `TestRuleForbiddenPlaybookIsNotPreloaded`.

**Short tasks embed with context.** Below `PREFLIGHT_CONTEXT_TASK_CHARS` the query includes recent prior user turns (synthetic `[…]` notes filtered out), because a bare follow-up like "show on map" is hopeless alone. The keyword and name rails still scan ONLY the current message.

**Diagnostics ride the log.** `Preload.mode` (`semantic`|`lexical`) plus per-item `sim`/`rail` (or lexical `score`) go out on the `knowledge` trace step, so retrieval precision is auditable from logs alone — the #183 audit had to reconstruct all of this by hand. Keep it cheap and keep it there; the curation ledger reads exactly these records.

**What the floors turned away rides the log too (#435, epic #444).** The `knowledge` step lists admitted entries only, so a floor could be judged only by replaying tasks against a corpus that has since changed — and #435's miss (family-profile: keyword hit, sim 0.154 under the 0.24 keyword floor) was unrecoverable from any record. The keyword-language experiments then put the owner's accepted Polish residue at ~0.26–0.34, just under the 0.35 plain floor, and showed no floor value buys it back at an acceptable noise cost: the band is where the next decision has to be watched. So preflight records every entry that scored within `PRELOAD_NEAR_MISS_BAND` (0.10) under the floor that applied to it — with that floor, its kind (`keyword`/`plain`), the rail and the sim — nearest the floor first, at most `PRELOAD_NEAR_MISS_MAX` (5) per task with the overflow counted. Lexical mode records the same shape in its own units: `score` against `PREFLIGHT_MIN_SCORE`, one tier below (a fuzzy-only match; no shared word at all is not near anything). It rides the renderless `context` record's `preload` — present on every turn a selector ran, `items: []` included — because the `knowledge` step is skipped when nothing was admitted — exactly the turns whose misses matter (`docs/trace-contract.md` §3.10). It is a record only: nothing reads it to select, and `TestPreloadNearMisses` pins that selection is identical with the band at zero. `aish explain` shows it as one line under the context row; curate's ledger deliberately ignores it (an entry never injected has no engagement to measure). `TestPreloadNearMisses`, `TestContextRecord`, `TestEveryReaderParsesALogWithNearMisses`.

In lexical fallback the keyword rail is a full guarantee again — there is no similarity to confirm against (L2).

## Deliberate recall

`rank_entries` + `recall_text`: deterministic difflib tiers, two-phase, hard caps, mtime-cached parsing (`TestRankEntries`, `TestRecallText`, `TestRecallTool`). Both take `semantic` and `Agent._recall` passes it, so embeddings reach the deliberate-search path and not only preflight (#178 P1-9). Fusion keeps strong lexical hits — exact name, whole query inside the identity line — as the deterministic rail on top, and similarity orders the rest; a `None` from `scores()` degrades byte-identically to pure lexical. `TestSemanticRecall`.

**The lexical tiers match whole words (#445).** `score_entries`' phrase-in-identity (4), phrase-in-body (3) and all-words (2) tiers were `in` tests, i.e. substring tests: the one-word reply "Tak" sat inside the keyword `kontakty`, scored tier 4 and injected an unrelated skill on 11 recorded tasks. They now match on word boundaries (`_whole_word_pattern`) with the same s/es folding as the keyword rail; hyphens and punctuation are boundaries, so "gmail" still finds `gws-gmail`. A word *fragment* ("kontakt") now reaches the fuzzy tier at best, which is below `PREFLIGHT_MIN_SCORE` — inflected non-English queries are the semantic layer's job, and keywords are English (#444). Preflight's lexical mode and recall both call this function, so both changed. `TestLexicalTiersMatchWholeWords`.

**Recall must be able to say nothing matches (#369, L3 applied to search).** A ranker always has a "best", so without a floor an empty match rendered identically to a real one — in aish's own voice: `recall("Maciej LinkedIn")` returned *"Saved knowledge matching 'Maciej LinkedIn' (best first):"* followed by the owner's home-address memory and an Apple Reminders skill, zero relevance, and a small local model may act on that noise. The lexical path always had the natural floor — zero shared words means `score_entries` never ranks the entry — but in semantic fusion a word-free neighbour rode in on cosine alone at `SEMANTIC_MIN_SIM` (0.24). A pure-semantic hit now needs **`RECALL_MIN_SIM` = 0.30**; below it, `recall` says plainly that nothing saved matches. Lexical hits never consult the floor (L2) — a populated corpus with zero shared words already answered "nothing matches" before this change, and `test_a_populated_corpus_with_no_shared_word_is_no_match` now pins it — and past-session mentions still list separately: "sessions that mention it" is honest language about text search, not a relevance claim.

The number is **provisional** — not a judged audit like the one behind `PREFLIGHT_MIN_SIM`, but hand-labelled probes replayed against the live corpus (embeddinggemma, 2026-09-15): twenty genuine queries (mostly Polish, against English entries, no shared words) and ten queries with nothing in the corpus:

| | scores observed |
|---|---|
| genuine, target ranked **first** (16/20) | 0.313 · 0.348 · 0.364 · 0.367 · 0.370 · 0.382 · 0.395 · 0.416 · 0.426 · 0.430 · 0.486 · 0.501 · 0.508 · 0.511 · 0.511 · 0.612 |
| genuine, target ranked 4th–6th behind noise (4/20) | 0.209 · 0.234 · 0.267 · 0.283 (the two `trippy_search` hotel queries, google-maps for "jak dojechać", a vague "what car parts") |
| no match, top neighbour (10/10) | 0.164 · 0.217 · 0.236 · **0.259 (the incident)** · 0.262 · 0.267 · 0.268 · **0.282 ("Anna's phone number" → `user-home-address`)** · 0.286 · 0.313 ("kubernetes ingress config" → `do-not-expose-secrets-inline`) |

The distributions overlap in the 0.28–0.32 band, so no floor separates them; the choice is which error to prefer. 0.30 is the highest floor that keeps every first-ranked genuine match and the lowest that stops the incident's shape recurring: an earlier draft's 0.28 still listed the owner's home address for a stranger's phone number — a personal-data memory surfacing on an unrelated person lookup is exactly #369. What 0.30 drops already ranked behind three to five noise entries, so listing it under "best first" bought nothing (that `trippy_search` loses to an apartment-balances memory on a hotel query is a retrieval-quality problem the floor cannot fix). It is deliberately NOT `PREFLIGHT_MIN_SIM` (0.35): that bar loses the 0.313 first-ranked match, and recall's listing is read critically by the model where preflight injects unsolicited. One no-match query (0.313) still lists an entry; the margin on both sides is one probe wide.

**Recall records no scores** — the `knowledge` record covers preflight only — so recalibration means replaying labelled probes (`skills.score_entries` + `SemanticIndex.scores` over `load_entries`, with a temp `state_dir`), never adjusting by taste. `TestSemanticRecall` pins the incident shape, the 0.282 phone-number shape, the 0.313 survivor, and the lexical exemption, and asserts the constant sits between the evidence.

`recall` also searches past sessions, except in a task no person sent (`task_from_owner` false), where that half is dropped (see Egress #178 P0-2 in `docs/agent-core.md`).

## Writing

`remember` writes through `save_memory` — slug-validated, create-or-update, keywords deduped and capped (`KEYWORDS_MAX`) at write time. It stays auto-approved in an attended session, deliberately, so capturing a fact costs nothing. `TestSaveMemory`, `TestRememberTool`, `TestForgetMemory`, `TestForgetMemoryTool`.

**Keywords are English-only (#444), and the instruction is what carries it.** The owner decided it on measurement and the corpus was converted; what kept non-English keywords flowing in was aish's own text — the `remember`/`create_skill` keyword descriptions, the system prompt's LEARNING section and `LEARN_PROMPT` all said *"in every language the user types"*. They now say MUST + English with one example, and that a brand or untranslatable term stays as written; curate's repair prompt asks for English keywords too.

Under that sits a deliberately **lenient backstop**, `skills.clean_keywords`: flatten (#209), drop any keyword containing a **non-ASCII letter**, dedupe, cap (#183). The drop happens before the cap, so it never costs an English keyword its slot. It under-catches on purpose — ASCII-spelled Polish (`cena`, `faktura`) and ASCII brands (`qrencode`, `e-kartoteka`) pass — so the instruction does the real work. **A term that genuinely has diacritics (`ryczałt`) is dropped even though the instruction says such a term may stay**: the backstop is the stricter of the two, and the drop is said, not silent. It is a character class, not a word list, so it carries no vocabulary counter (`docs/vocabularies.md`).

**Four writers, one hygiene, and what each does when a keyword is dropped.** It only ever restricts — no save is blocked, and no description or body is touched — and it guards the inflow, never the corpus on disk: a keyword line already in a file is never cleaned, only one being written now.

- `save_memory` (`remember`): writes the surviving keywords. On an UPDATE where every supplied keyword was dropped it keeps the entry's existing keywords instead of erasing them — the model or judge ignoring the instruction is the expected input, and wiping a working line over it would cut recall while reporting success. (An update that supplies no keywords at all still writes none, as before #444.)
- `plan_skill` (`create_skill`): writes the surviving keywords; on an update with none surviving — omitted or all dropped — the file's existing line is carried over as it is.
- `curate.update_entry_meta` (the judge's repair): replaces the line with the surviving keywords; when none survive, the existing line is kept byte-for-byte (and with no line to keep, none is written).
- `skill_import`: the staged `SKILL.md`'s single-line `keywords:` is cleaned BEFORE the consolidated review (`english_manifest`), so the owner reviews exactly what installs, and again at `aish skill approve` (`install`), because the quarantine is hand-editable. Only that line changes; with no keyword surviving it is removed. A YAML block-list `keywords:` is not read by `_parse` either and is not cleaned.

**Every drop is said where it happened.** `remember`/`create_skill` append `dropped_keywords_note` to their result — *"would NOT be stored"* on a refusal, a held, denied or failed write (a held write is re-proposed, and the model must know before it proposes again), *"NOT stored"* plus *"existing keywords were kept"* when that fallback applied. Curate adds `keywords_dropped` and `keywords_kept_existing` to the repair's action record and logs a line. An import adds a line to the review's flags, the tool result, and `aish skill import`/`approve`'s output. `TestEnglishOnlyKeywords`, `TestKeywordsAreEnglish` (agent), `TestRepairKeywordsAreEnglish` (curate), `TestQuarantine` (import).

**Skills write through `create_skill` → `plan_skill` (#380), never raw file tools.** For a year the update path was "edit the markdown yourself", and nothing model-facing answered *where a skill lives*: `recall` and `read_skill` return name/description/body but no path, and the skills directory was named only in the `/learn` prompt. So every save began with a shell hunt — on 2026-09-13 two sessions in one day ran `find` over `~/.config/aish` (one held by the owner mid-card), and after being told "there is a recall tool for that" the model obediently asked recall for a path three times, which recall cannot answer. `plan_skill` is the `files.py` plan/commit shape rather than a `save_memory`-style direct write, because the two halves have different owners: composing the file and resolving its target (an existing name — flat or folder `SKILL.md`, retired included, so a disabled skill cannot fork into a duplicate — updates in place, preserving lifecycle frontmatter and any description/keywords the model omitted) is knowledge-layer logic, but a skill instructs every future session, so the WRITE stays behind the agent's diff-approval gate exactly where `write_file` had it — `create_skill` changed who finds the file, not who approves it. The near-duplicate gate now covers skills too (same identity-line similarity, same refusal-with-the-name, `force` for a genuinely different playbook; updates never gated), emitting `admission` records with `target: "skill"` (contract §3.7). `TestPlanSkill`, `TestPlanSkillNearDuplicate`, `TestPlanSkillRoundTrip` (the #209 day-one round-trip: description and keywords flatten, the body stays prose), `TestCreateSkill` in `tests/test_agent.py` (including the prompt pin: every surface that used to send the model at the filesystem now names `create_skill`).

Three properties came out of df19f0c's adversarial review rather than the first draft, and each is a house law applied, not taste: **the regenerated header preserves `pinned:`** (curate's envelope refuses `disable` on a pinned entry, so a writer that strips the pin hands the next weekly pass exactly the verdict the envelope exists to refuse); **`disabled`/`expires` ride the tool with `save_memory`'s exact semantics** (the prompts now forbid hand-editing skill files, so without them retirement — L4's only verb — would be expressible only by violating a MUST NOT); and **the success line is read off the artifact** — `_create_skill` re-parses the written file and, when it is retired, says it will NOT be indexed instead of promising the opposite (a claim's words may not outrun its code). `TestPlanSkillLifecycle`, `test_the_result_line_says_what_the_artifact_means`.

**The near-duplicate gate (#178 P1-8).** A NEW slug whose identity line is too similar to an existing memory is refused WITH that entry's name — update it, forget it, or pass `force=true`. Similarity comes from the wired `SemanticIndex.scores` (`DEDUP_MIN_SIM`) or a conservative difflib ratio (`DEDUP_LEXICAL_RATIO`) when embeddings are down. Updates to the same slug are never gated. `TestNearDuplicateGate`.

That gate demonstrably worked and was **invisible**, because its refusal begins "NOT saved — " and the runtime logged refusals green by prefix-sniffing. It now emits an `admission` record carrying `sim`/`floor`/`mode`/`against` through `save_memory(on_admission=…)` — a callback, not a changed return type, because the string return is what cli.py, curate.py and every test read — which is what finally makes `DEDUP_MIN_SIM` measurable rather than "provisional until measured". `TestNearDuplicateAdmission`.

**Lifecycle (L4, #178 P1-8).** `status: disabled` and `expires: YYYY-MM-DD` retire an entry without deleting the file. `entry_active()` is evaluated at READ time — a long-running process crosses an expiry with no mtime change — and enforced INSIDE `load_entries`, so index, preflight, recall and dedup all inherit it by construction. `load_skill` names the retire reason instead of claiming the skill is missing. Date parsing is tolerant on read (malformed = no expiry, plus a warning) and strict on write. `save_memory`/`remember` take `disabled` (None preserves, True retires, False revives): the reversible verb that lets curation avoid `forget_memory` entirely. `TestLifecycle`.

## Files on people, organisations, accounts and interests — `entities.py` (slice 2)

**Four more kinds in the same store and the same format.** `person`, `org`, `account`, `interest`: one markdown file each under `<state dir>/knowledge/people/`, `organisations/`, `accounts/`, `interests/` — by default `~/.local/state/aish/knowledge/` (`entities.knowledge_root()`, resolved at call time through `AISH_STATE_DIR` like every state store).

**Why the state tree and not the config tree.** The config tree is a git repository auto-pushed to a private GitHub remote. These files are personal data — the state tree already holds the other personal stores (mail cases, vouches) for exactly that reason. And a git repository is something the model's shell can act on as a whole — `git show HEAD:<path>`, `checkout`, `clone file://…` — which a review proved no path fence can follow: a classifier of git commands shipped in this slice (e38f4819) was driven past seven ways in one pass (wrappers, `--patch-with-stat`, `ls-files | xargs cat`, `clone`, `add --patch`, pushes) and removed. Nothing legitimate runs git in the state tree. **The consequence, plainly: these files have no git history and no off-machine backup** beyond whatever backs up the machine itself.

**Test isolation.** The suite's `no_real_browser` points `AISH_STATE_DIR` at a tmp dir for every test; `isolated_entity_tree` asserts the tree resolves there BEFORE each test body runs, and the session guard `no_writes_to_the_real_entity_tree` lists the real `<state>/knowledge` at start and end (the general state-dir guard is deliberately absent, because the owner's server writes there constantly). The scar: an earlier draft of a test undid the suite's isolation mid-run and wrote a fixture into the owner's real memory folder. `test_suite_never_reaches_the_real_entity_files`. Read through the family's one reader (`split_frontmatter`, `parse_expiry`, `lifecycle_active`) — `TestOneFrontmatterReader` still sees one reading. Header: `name`, `kind`, `aliases` (other forms of the name, Polish inflections included; non-ASCII allowed, unlike `keywords`), `description` (code-written, what the file is about — never a fact). They are filled only by aish saving during a chat (`remember(about="<kind>:<name>")`); the profile page, the filing of today's notes and the overnight job are later slices.

**Two sections, and the writer alone decides which.** `## From him` and `## Read somewhere`, each line `- <fact> (<date>, chat <session id>)`. *From him* is written only when a person sent the task (`task_from_owner`) AND the chat has never read outside content; every other save — the chat read something at any point, or nobody sent the task — lands in *Read somewhere*. Why two sections rather than a card: the owner decided on 2026-11-11 that saving is fine ("it's okay to save memories") as long as what was read elsewhere is never passed off as his, so for `about` saves the label replaces the knowledge gate's card (`docs/agent-core.md`). Plain `remember` keeps the card (`TestPlainRememberIsUnchanged`): a loose memory has no sections to carry the label, and its description is shown to every task. The confirmation is read off the artifact (`save_fact` re-parses the file and refuses to say "under From him" unless the line reads back there). Duplicates (normalised, date/chat suffix ignored) are not appended twice, and a line he already said is not repeated as one read elsewhere. `TestWhereASaveLands`, `TestTheWriterRoundTrip`.

**The mark is per CHAT, and why the per-task one was not enough.** `_tainted` is reset at every task start, but a page read in task 1 stays in the conversation and can steer a save in task 2. `Agent._chat_read_outside` rises wherever `_mark_tainted` runs (so every taint door — a tool, a kept note, a delivered outside note, a continuation's carried calls — raises it too), is never cleared by `_reset_task_state`, is cleared only with the conversation (`reset()`, and claude-max's), and on a reopen is re-derived in `load_history` (`_history_read_outside`): every logged tool call through `_brings_outside_content` with the model's own arguments — a name that is neither native nor a current plugin counts as outside — and any message carrying an outside-content banner. Restrict-only: a false yes labels a save *Read somewhere*, never the reverse. `TestTheChatLevelMark` (the two-task case is `test_task_one_reads_outside_task_two_saves_and_it_is_read_somewhere`).

**Reading fails safe.** A line counts as *From him* only while the last heading above it is exactly `## From him`; text above the first heading, a malformed heading (`## from him`, `### From him`, an indented one), a heading of his own, and a missing section all read as *Read somewhere*. A save into a damaged file re-renders the body from the sections as read (below), so text above the first heading can never be adopted by a new `## From him`. An unreadable file costs only itself. `TestReadingFailsSafe`.

**Every value round-trips (#209's rule, on day one).** Name, aliases, fact and chat id are flattened with `frontmatter_value`; a fact is written behind `- `, so it can never become a heading; the header is rewritten key by key, other lines kept. `TestTheWriterRoundTrip` runs the shared `SMUGGLED` list plus `## From him`, `status: disabled` and a bare `---` through every writer path.

**No full account or card number, ever.** `holds_account_number` finds the two value shapes `browse.refuses_to_type` already refuses (IBAN shape, Luhn-valid card) inside a sentence, plus a run of 20+ digits (a domestic account such as the 26-digit NRB). The save is refused with a sentence pointing at `aish secret set` and the last four digits; it applies to every kind and to the name and aliases too. `TestAccountNumbers`.

**Names from outside are not keys (the alias rule).** A save that lands in *Read somewhere* brings no matching key: a new file it creates has no `name:`, and the name and aliases it carried are kept as `proposed name:` / `proposed alias:` lines inside *Read somewhere*. They become keys only through a save from him (which writes `name:` and appends to `aliases:`) or his own edit. Otherwise a planted mail could make a common word an alias and either flood his messages with pointers or make a real name ambiguous and suppress its file. `TestNamesFromOutsideAreNotKeys`.

**The name rail** (`entities.name_rail`, called by `run_task` before preflight). Code matching, not embeddings: the owner's message against every active file's `name` and `aliases`, whole word, case-insensitive, accents folded on both sides (`fold`: NFKD minus combining marks, plus an explicit `ł`→`l`, which decomposition leaves alone), keys of at least 3 characters, the longer key winning its span. Only for a task a person sent — a schedule, a mail or a webhook gets no rail, its text is not his; a tapped suggested reply counts, since it can only load *From him* text of a file he named. For each hit: *From him* is preloaded as a block (capped by `PREFLIGHT_ENTRY_CHARS`); *Read somewhere* adds ONE code-written pointer — the name as he wrote it, the kind, the count, and `recall(name="<kind>:<slug>")` — and none of its content, ever. A key two files carry preloads neither and adds one pointer naming both kinds. The rail may take at most half of preflight's character budget and half its slots; preflight gets the rest (`preflight(slots=…)`, `char_budget` minus what the rail used), so a message full of names cannot push out the how-to. With no entity files, requests are identical to before except where a preloaded entry's long description previously overflowed the pre-flight budget: `TestByteIdentityWithNoEntityFiles` compares every request of a fixed task set (`tests/entities_golden_scenario.py`) against a golden recorded by running the same file on the commit before this slice, and pins that one exception to the cut alone. `TestPolishForms`, `TestTheRail`, `TestBudgetWithPreflight`, `TestReachingAConversation`.

Measuring the budget found a preflight bug older than this slice: a remembered fact's description rides in the block HEADER, which was never capped, so one long description took the total past the budget the caller set. A block longer than what remains is now cut to it. `test_a_long_remembered_fact_cannot_take_the_total_past_the_budget`.

**Never in the index or in preflight's own pool.** They are not in `load_entries`, so nothing about them is in `messages[0]` and no similarity can preload one; they are reached only by the rail (and then only *From him*) and by `recall`. `TestNeverInThePoolOrTheIndex` pins an entity matching the task at 0.99 with no name hit injecting nothing. The `knowledge` step gains `entities: {preloaded, pointers, ambiguous}` — names, kinds and a line count, never a fact (`docs/trace-contract.md` §3.8); it is emitted when the rail selected anything even if preflight admitted nothing.

**Recall covers them, and its rendering of a line read elsewhere taints.** `Agent._recall` adds a section after the existing output (`entities.ranked_lines`: the lexical tiers, then the embedding upgrade on the identity line in its own cache file, `entity-embeddings.json`, under the same `RECALL_MIN_SIM` floor; name and aliases ride as keywords, folded too). `recall(name="<kind>:<slug>")` opens one file (`entities.detail`). A snippet comes from *From him* when a query word is there, else from *Read somewhere* — and any rendering of a *Read somewhere* line, the snippet included, sits under `entities.READ_SOMEWHERE_NOTE` with markers disarmed. The search is pure; the agent records at the read (`_recall_marked` → `_entity_recall_reads`, the `_third_party_skill_reads` mechanism) whether the result carried that note, and `_brings_outside_content("recall", …)` commits the taint after the batch. A recall whose read this process did not see (a trim with args gone, a continuation, a reopen) answers `any_read_somewhere()` — the wide answer, and False whenever no such line exists, which keeps every chat without them unchanged. Unattended runs may look them up: the mark plus the existing unattended outbound gates are the containment. A non-entity name is still asked of skills, memory and sessions first, exactly as before. `test_recall_rendering_a_read_somewhere_line_taints_and_banners`, `TestRecallSection`.

**The fence.** What is refused, card or no card (BLOCKED, before any card is drawn), and the line that does it:

- `read_file`, `write_file`, `edit_file` on a path in the tree — `entities.in_entity_tree` (`skills.path_in_tree(knowledge_root())`: `files.contains`, case-insensitively, and on the path as written), asked in `_dispatch`'s read branch, `_read_needs_prompt` (so the parallel path never runs it) and `_dispatch_write`. `show_image`, `read_pdf` and `read_media` given a local `source` in the tree are refused the same way (`_entity_source`). The data volume's firmlink spelling (`/System/Volumes/Data/…`), which `Path.resolve` does not collapse, is stripped first (`entities.canonical`). `read_file` is refused too, because it would hand *Read somewhere* text over unbannered and untainted. `TestTheFence`.
- `run_command` — `Agent._command_touches_entities`. The text is first collapsed the way the shell would before any path exists (`_shell_spelling_collapsed`: quote characters and backslash escapes removed, so `know''ledge`, `know\ledge`, `"<state>"/knowledge` and `'knowledge'` all read as `knowledge`; the firmlink prefix stripped). Every path-shaped word of the collapsed TEXT (`_PATHISH`, which splits on quotes, so a path inside `sh -c '…'` is its own word; wrappers such as `env`, `xargs`, `nohup` are simply more words), with `file://` stripped and `--opt=` values taken, resolved against cwd, every `cd` target and every `-C` target, case-folded: refused when it is inside the tree or the tree itself, or when it IS a directory containing the tree up to and including the state dir (`_containers_of`): `cp -r <state> …`, `grep -r x <state>`, `find <state> … -exec cat {} +`, `tar -C <state> -cf a.tar .`. A `cd`/`-C` INTO the tree refuses the command whatever follows (`git -C <state>/knowledge init`). `_command_names_a_store`'s pattern net adds what the shell would expand into the tree, run strictly (`loose=True`) for reads as well as writes, because for this store a read is the harm: `grep -r x <state>/{knowledge,mail}` and `grep x <state>/*/people/*` are refused, while the same globs under a project are not. Another subfolder of the state dir (`ls <state>/mail`, a session log) is untouched. The `-C` targets join the bases in this fence only: the shared nets (`_cd_bases`, used by the charter, automation and third-party fences) are main's, unchanged. `TestTheShellFenceOnTheStateTree` drives each shape, including `env cat <file>`, `xargs cat < <file>`, `sh -c 'cat <file>'` and `nohup sed -i … <file>`.
- Git is no longer this fence's subject. With the files in no repository, the entity fence says nothing about any git command that names no path in the state tree — in the config home or a project — exactly as before the slice. `TestGitIsWhatItWasBeforeTheSlice`.
- **The kernel half, for cardless commands.** A command that runs with no card runs under aish's Seatbelt profile (`docs/sandbox.md`), which closes the whole state dir and reopens only roots inside it. An owner who trusted the whole state dir as a root would have reopened the tree with it (measured: `cat` of an entity file under such a profile printed it), so the profile now SEALS the tree — `sandbox.ProfilePaths.sealed`, a read deny emitted after every reopen, passed by `Agent._confine` — and the same `cat` is refused by the kernel. `TestTheSandboxSealsTheTree` (real `sandbox-exec`).

**Residuals, named — for carded and prefix-rule commands the fence is a text check, not a kernel boundary.** Not reached: a path that exists only once the shell runs (`cat $(find ~ -name anna.md)`, `ls <state>/knowledge | …` built from a variable, `xargs cat < list` where the LIST holds the paths — pinned as residuals in `test_run_time_paths_are_a_named_residual`); a write or read from INSIDE an approved script or a non-mutating plugin's wrapper; a prefix-rule command, which runs unsandboxed; an operand ABOVE the state dir (`cd ~ && tar -cf a.tar .local`), since its ancestors are deliberately not containers; and any process outside aish. His own editor is meant to be unfenced. **The kernel-level answer for carded shell — running it under a profile that denies the tree — is not built**; only cardless commands run sandboxed.

**The writer lock is per process.** `_WRITE_LOCK` serialises saves inside one process. A terminal session and the web server saving the same entity at the same instant can each read the old file and the later publish drops the earlier line; `atomic_write.publish` means the file is never torn, so the loss is one line, never corruption.

**Section order is canonical on every write.** The writer re-renders the body from the sections as read — `## From him` first, `## Read somewhere` second — so a save from him into a file an outside save created still comes out in order, and a hand-damaged file is rewritten meaning for meaning (its unheaded or malformed-heading lines land under `## Read somewhere`, which is how they already read; a heading of his own is not kept). `test_a_save_from_him_into_a_file_an_outside_save_made_puts_from_him_first`.

**A save in the same model response as a recall.** By the provenance doctrine (`docs/agent-core.md`, captured per call, committed per turn), a save composed in the same response as a single recall was composed before the model saw the recalled text, so it may land under *From him*; the read-only fan-out commits before the calls behind it, so two recalls ahead of the save already make it *Read somewhere*; a save in any later response is *Read somewhere*. `TestRecallAndSaveInOneBatch`.

**His own search: `/who [words]`** in the terminal and the web chat — every file whose name, aliases or lines match all the words (folded), or all files; one match opens whole, *From you* apart from *Read somewhere (not from you)*. Shown to him only: the web sends a `who` VIEW message answered with `who_list` and painted into its sheet; nothing reaches a model. `TestTheSlashCommand`, `TestWhoSlash` (server), `tests/js/test_who_slash.js`.

**Not in this slice.** The weekly curation job does not judge these files; they hold personal data, live in the state tree and are in no git backup (above). claude-max runs no preflight, so it gets no rail either (recall and saving work there). Nothing here deletes; unattended `forget_memory` stays refused.

## `embeddings.py`

One local Ollama embedding model (`embeddinggemma` by default — multilingual, because tasks arrive in Polish while entries are English; `AISH_EMBED_MODEL` overrides) scores task-versus-entry similarity **regardless of which chat backend runs the task**, so retrieval behaves identically on every `--model` and the corpus never leaves the machine.

Entries embed as a single **identity line** (`name: description (keywords: …)`), never bodies — selection reads identity, so vectors stay stable while playbooks grow. Vectors cache in the state dir keyed by `sha256(model + text)`. Retrieval-tuned models need task-type **prefixes that Ollama does not add** (`_PREFIXES`); skipping them measurably collapses similarity separation by about 2×.

**The embedder's host is its own setting (#404).** `AISH_EMBED_HOST` builds one cached `ollama.Client(host=…)` for embeddings only; unset, the module-level client is used exactly as before (it follows `OLLAMA_HOST`). This is what lets chat run on a `local:` server on another machine while `embeddinggemma` stays on this one. An unreachable embed host is just another embedding failure: `scores()` returns `None` and retrieval degrades to the lexical floor (L2). `TestEmbedHost`.

Both entry points wire it identically — `Agent(semantic=SemanticIndex(state_dir))` — and the agent threads `scores` into preflight, recall and the dedup gate. `TestSemanticIndex`, `TestPreflightSemantic`.

**A second corpus gets a second FILE, never a share of this one (#444 H1).** The per-task tool menu (`docs/tool-menu.md`) ranks tool identity lines on the same model and prefixes through `SemanticIndex.sibling`, cached in `tool-embeddings.json`. A shared file would thrash: `_save` keeps only the keys of the corpus it was just asked about, so knowledge and tools would evict each other's vectors on every save, and each process would re-embed both. The query both rank against is one helper, `skills.retrieval_query`, so a short follow-up carries the same recent turns into either.

**Retrieval quality is regression-gated.** `tests/test_retrieval_quality.py` is a recall@3 harness over a fixture corpus with a deterministic concept-axis embedder injected at the `embed=` seam: semantic must score 1.0 on both preflight and recall including the Polish→English cases, and lexical-only floors of 0.6/0.3 are asserted. `TestSemanticRecallAtK`, `TestLexicalFloor`, `TestHarnessSeam`.

## `curate.py` — the self-curation loop

Console entry point `aish-curate`, weekly via launchd. **The defining property is that the orchestration lives in the SCRIPT, not in a model session**: v1 handed one agentic session a 12-suspect queue and the 8B local judge could not hold it — 55 reads, zero actions — so v2 inverted it. Three layers:

**Context health** (`scan_context`, `aish-curate --context`) — a separate pure pass over the same logs, there to answer whether the history policy change (#243) actually helped rather than to curate anything. It reports trims per task, characters destroyed, how many stubs carried a key back to the full text, repeated identical calls, and the median prompt size — and attaches **no conclusion** to them. Repeated calls are the *shape* of a model that lost what it already found, not proof of it, so the count sits beside the trim count instead of being presented as a cause. One unreadable log costs its own file and nothing else (`docs/session-log.md`). `TestContextScan`.

The baseline it measured over the 60 days before the change: 754 tasks, 475 trims (0.63 per task), **45% of tasks trimmed something**, 13.8M characters destroyed, **0% of stubs recoverable**, and 35 of 41 repeated calls occurred in a task that had already lost history. Two thirds of the trims were the unconditional `eager_stub`.

**1 · The ledger** (`scan_ledger`) — pure code over the session logs. Pairs each `knowledge` trace step with its task window (the step is emitted just BEFORE its user message, so it attaches to the NEXT user record — never to one of aish's own notes, which is not a prompt and must not split the window, `synthetic_kind`) and measures **engagement** (a `read_skill` of an injected entry) and **misses** (a `read_skill` of an entry preflight never surfaced). `dead_weight` (≥ `MIN_INJECTIONS`, zero reads) and `missing` are the suspect lists. `TestLedgerScan`, `TestClassification`.

**2 · The judge loop** (`run_curate`) — one bounded model call per suspect. `judge_prompt` packs identity + capped body + stats + evidence and demands the forced format `VERDICT: repair|pin|disable|skip` with an example, because small local models need MUST plus a concrete example. The model is a pure judge: no tools, no session, no server — `_make_judge` calls `backends.make_chat` directly. `TestJudgePrompt`, `TestJudgeLoop`.

**The envelope is code (L5).** `parse_verdict` admits only those four verbs — a repair without a replacement description is a parse failure, with one format-nudge retry and then an unparseable skip — and `update_entry_meta` rewrites **frontmatter only**: description, keywords, pinned, status; body preserved byte for byte; other lines kept; **deletion has no code path**. `TestVerdictParsing`, `TestUpdateEntryMeta`.

The judge is a model, so its verdict fields get the writer treatment above: `TestUpdateEntryMetaRoundTrip` renders each `SMUGGLED` value into a repair and parses the entry back. Keywords were the hole here too — a newline in one wrote `status: disabled` onto its own line, retiring an entry through the back door of the very envelope that refuses a `disable` verdict on a pinned one.

**The owner's ratings are ledger evidence (#444).** `scan_ratings` (the 👍/👎 per answer, #207) was tested and called by nothing, so the one direct verdict the owner gives fed no decision. `run_curate` now passes it to `scan_ledger`, which attaches each rated turn's verdict and reason (flattened, capped like the prompt excerpts) to every entry injected or read in that turn — joined by the user record's minted `turn` id AND the session file, never by position. The judge prompt gains an `OWNER RATINGS` block, framed as weak evidence because a rating judges the whole answer, not one entry; the action record gains `ratings_shown: {up, down}`, which says the judge was SHOWN ratings — whether they changed the verdict one model call cannot say. Ratings select nothing: suspects are still dead-weight and missed, and a rating-less corpus gets the byte-identical prompt and record it always got. `TestRatingsFeedTheLedger`.

Every judged entry, skips included, lands in `curation-actions.jsonl`, which doubles as the **cooldown** (`ACTION_COOLDOWN_DAYS`): the ledger's stats lag reality by up to `LEDGER_DAYS`, so without it every pass would re-flag what the last one fixed. It also makes a retried launchd run idempotent with no server-side dedup.

**3 · The duplicate pass** — cross-entry judgment cannot fit a one-entry prompt, so `dup_candidates` proposes pairs **deterministically** (identity-line embeddings at `MERGE_MIN_SIM` = 0.72, deliberately stricter than `DEDUP_MIN_SIM` because on the live corpus every TRUE duplicate scored ≥ 0.77 while every related-but-distinct trap sat at 0.63–0.66; difflib when embeddings are down) and the judge answers one pairwise merge-or-distinct. A merge names the survivor — naming neither is invalid, the envelope never guesses — and disables the loser. `TestDuplicatePass`.

**Envelope guards**, each from the first live v2 run and each a CODE refusal rather than judge wisdom (`TestEnvelopeGuards`):

- `_same_family` bars pairs where one name extends the other with a dash (reply/reply-all, gmail/gmail-send — deliberately similar siblings, and exactly what the 8B judge wrongly merged).
- A `disable` verdict on a PINNED entry is refused; repair stays allowed. The judge retired two standing rules.
- A `disable` verdict on a **memory in the dead-weight category** is refused, and the judge is neither offered the verb nor told the memory went "NEVER used". Dead-weight means "injected, never read", and a memory is never read — its use is invisible to the ledger, so the category is no evidence at all against one. The prompt used to say "NEVER used" anyway, and on 2026-08-17 the 8B judge retired `pawel-emails` (his primary mailbox is Tuta) on that sentence; for five weeks the local model reached only for Gmail. Repair stays allowed, since frequent low-similarity injection IS evidence the identity line mis-fires; a duplicate-pass merge may still retire a memory, because duplication is observable. Skills keep every verb — `read_skill` is a real use signal.
- A skill never loses a merge to a memory — a playbook outranks its one-line echo.
- Dry runs use the SAME embedding scorer as live runs, so the candidate list a dry run shows is the list a live run judges.

**Privacy.** Evidence excerpts quote owner-typed text, so the judge defaults to the LOCAL model and nothing leaves the machine unless `--model`/`AISH_CURATE_MODEL` names a cloud spec explicitly. A completed pass with actions sends one Pushover summary through the `notify_fn` seam. Seams: `run_curate(judge=…, scores=…, notify_fn=…, state_dir=…, now=…, dry_run=…)`; `--dry-run` lists suspects and pairs with no model calls and no writes.

## `skill_import.py` — importing a skill (L6)

The untrusted surface is imported **skills**; tools need no import check because they are BUILT locally via `create_tool` plus diff-approval.

`stage()` first checks the source (below), then fetches — a shallow, read-only `git clone` that never executes the skill's code — validates (a real `SKILL.md`, name-checked) and collects the **text** files; binary assets are skipped, not being part of the trust surface. `TestStage`, `TestSafetyScan`.

### Approved sources (#467 P1, P6)

**An import comes only from a publisher the owner listed, and the check runs before anything is fetched.** `skill_import.check_source`, the first line of `stage()` — which both the `import_skill` tool and `aish skill import` reach — refuses, with no card and no clone:

- **every local path.** A folder on this machine is no evidence of who wrote it, and the CLI is no exception: the model can run `aish skill import /tmp/x && aish skill approve x` through `run_command` behind one generic shell card, so a terminal-only path was not structural. A skill the owner wrote himself goes into `skills/` by hand.
- **every address that is not exactly `https://github.com/<owner>/<repo>`**, optionally with one trailing `/` and one `.git` (`github_repo`): scheme `https`; `netloc` compared whole against `github.com`, case-insensitively, which refuses a user, a password, a port, `github.com@evil` and `github.com.evil` in one comparison; no query, no fragment, no `%`, no whitespace or control character; exactly two path segments in `[A-Za-z0-9._-]+`, neither `.` nor `..`. ssh, `git@` and `git://` forms are refused.
- **every repository not named in the owner's approved-sources file**, `~/.config/aish/skill-sources` (`skills.SKILL_SOURCES_FILE`). One entry per line, `github.com/<owner>/<repo>` or `github.com/<owner>/<repo>/<path prefix>`, `#` comments. Owner and repo match case-insensitively (GitHub resolves them that way); the prefix matches case-SENSITIVELY on whole path segments, so `skills/.curated` admits `skills/.curated/x` and not `skills/.curated-evil` (some publishers mix tiers inside one repo — `openai/skills` has `.curated`, `.system` and `.experimental`). The import's `path` is split into segments first (`path_segments`), refusing an absolute path, `~`, a backslash and any `.`/`..` segment rather than resolving them, so the segments compared are the folder cloned. A missing file approves nothing; a line that is not in the file's form approves nothing and the refusal names its line number.

The refusal names the source asked for, what the file approves, and that aish's file and skill tools refuse to write that file (the write fence below), and that there is nothing to approve. Admission reads nothing about popularity.

**This closed an uncarded network channel.** `import_skill` is not an egress tool and its card comes after `stage()`, so before this check a model-composed URL (`https://evil.example/<secret>`) was cloned with no card at all. A refused source now starts no process — the tests pin it with `subprocess.run` replaced by a tripwire. `TestApprovedSources`.

**The clone is made from the checked names, not the text given** (`clone_url`), through one seam, `_clone`: `git -c http.followRedirects=false clone --depth 1 -- <url>` with `GIT_TERMINAL_PROMPT=0`. Redirects are off because following one fetches from an address nobody approved; a repository GitHub has renamed or transferred therefore fails here (the error says redirects are not followed) and must be approved under its new name. The lock records the canonical `https://github.com/<owner>/<repo>` and the checked path.

**A symlink anywhere in the skill refuses the whole import (#466).** `stage()` read every `is_file()` path, which follows links, so `notes.md -> ~/.ssh/id_rsa` put the owner's key on the card as a "skill file" and, approved, into the corpus — observed with a canary before the fix. `symlinks_in` walks with `os.walk(followlinks=False)` because `rglob`'s handling of linked directories changed in Python 3.13. Refused rather than skipped, so an installed skill never silently differs from its source; the cost is that a legitimate skill shipping a link must be imported from a copy. `install` checks again because the quarantine is hand-editable. `TestNoSymlinkIsFollowed`.

**An import never replaces a skill (#466).** The card path wrote over `skills/<name>/` and `install` did `rmtree` + `copytree`, so one approval on a colliding name replaced the owner's own skill. `existing_skill` refuses — BEFORE the card, so there is nothing to approve by mistake — when the folder, the flat `<name>.md`, or any entry's frontmatter `name:` matches either the target name or the import's declared name. The declared name is checked because frontmatter wins over the folder name once installed, so the `name` override alone does not avoid a collision. Replacing is the owner deleting first. `TestImportNeverReplacesASkill`, `TestSkillImport` (agent).

`Agent._import_skill` then presents ONE consolidated review through the `approve_import` callback: the whole skill in a single decision — description, deterministic **risk flags** (`safety_scan`, below) and every file's full contents, syntax-highlighted in the web card. Deliberately NOT per-file diffs, which was approval fatigue plus an all-green diff nobody can read. On approve everything installs at once with no further prompts; a denial installs nothing. The CLI reviewer prints the flags and every file for one y/N. `TestSkillImport`.

**The risk flags (`safety_scan`, `_RISK_PATTERNS`) focus the review and decide nothing.** Each is a regular expression over a fetched text file, labelled: network access (`curl`/`wget`/`nc`/`ssh`…, `/dev/tcp`, and Python's `requests`, `socket`, `http.client`, `urllib.request` matched only in an `import`/`from … import` line, JS only as the call `fetch(` — the bare word is ordinary prose in a SKILL.md), pipe-to-shell, dynamic eval, recursive delete, sudo, a base64 (`-d`, macOS `-D`, `--decode`), `xxd -r` or `openssl enc|base64 … -d` decode, writes outside its folder, permission changes, sensitive paths (`.ssh/`, `.aws/`, `.gnupg/`, `.netrc`, `Library/Keychains`, `id_rsa`, `/etc/passwd`, `.config/aish`), Keychain reads (`security find-generic-password|find-internet-password|dump-keychain`), `osascript`, and package installs (`pip`/`pip3`/`uv pip install`, `uv run … --with`, `uvx`, `npx`, `npm install`, `gem`/`cargo`/`go install`, `go get`, `brew install`). A miss shows one flag fewer; the card is the decision either way. The owner's own credential layout is deliberately not in this public list — the generic stores are. Not a natural-language vocabulary, so `docs/vocabularies.md` lists it under "Considered and not catalogued". `TestSafetyScan`, `TestTheWiderScan` (each pattern with its label, and the prose each must not fire on).

**The escape hatch** (`aish skill <import|approve|list|discard>`): `import` STAGES to a quarantine dir and prints the risk flags plus the path, so you review the files in your own editor, and `approve` then installs them. That is the path for a skill too large to read in a card. It takes the same sources as the tool — an approved repository, never a local path — because the check is in `stage()`, which both reach. `TestQuarantine`. Where the staged skill came from waits beside its quarantine folder in `<name>.origin.json` (never inside it, so it never installs as a bundled file) until `approve` writes it into the lock; `discard` removes it.

The `context` record carries the section as slot `third_party` and its own `caps`/`corpus`/`omitted` keys (`docs/trace-contract.md` §3.10). `TestThirdPartySkillTree`.

**The shell's half (#467 slice 3).** `Agent._command_touches_third_party` refuses a `run_command` whose TEXT names the tree, its lock or `skill-sources` — BLOCKED before `self.approve`, so no card is drawn and a prefix rule never sees it, in every origin. ### Finding a skill — `skill_catalog.py` (#467 slice 4a)

**`find_skill(query)` searches only what could be installed: the owner's approved sources.** The owner's ask (2026-11-12) was conversational — "search for skills to find me what I need and then ask to install" — so it is a model tool. It takes a query and an optional `refresh`, and no repository or URL: what is searched is exactly the lines of `skill-sources` (`skill_import.parse_sources`, the same reader `check_source` uses), each read as a CATALOGUE — every `SKILL.md` under the line's path prefix, with its name and description as the existing parser reads them (`skills._parse_text`: the frontmatter's, or the body's first non-empty line when there is no `description:`), its folder, and the clone's commit (`clone_commit`). Popularity plays no part (P1); there is no public-hub search (the owner chose approved sources first).

**The query never leaves this machine.** `skill_catalog.fetch` takes only an `ApprovedSource` and builds the clone address from its owner and repo (`clone_url`), so no caller value reaches the one network step — the import's own seam, `skill_import._clone` (shallow, `http.followRedirects=false`, `GIT_TERMINAL_PROMPT=0`, `CLONE_TIMEOUT`). Ranking is lexical only, on this machine, and deliberately not the embedder, which would send the query to whatever server embeds. `test_only_the_sources_file_reaches_the_clone_never_the_query`.

**A catalogue is cached per source, and nothing installs from it.** `<state>/skill-catalog/<sha256 of the line>.json`, for `CATALOG_TTL_S` (24 h); `refresh` — `true`, or the strings `true`/`yes`/`on`/`1` in any case — reads every source again; anything else does not. The result names each source with its catalogue's age (or "read now") and commit. A refresh that fails keeps the older catalogue and says both — that it is the older one and the observed error. A cache file that does not parse, or was written for another line, is read again rather than trusted. Picking a result goes through `import_skill`, which re-checks the source and clones HEAD through `stage()` — the owner reviews what THAT clone holds, on the unchanged card with the auditor (P6). `find_skill` grants nothing and installs nothing (`test_it_installs_nothing`).

**Failure is per source and per file, and said.** A source whose clone fails (unreachable, renamed — redirects are not followed — or a prefix that is not a folder) is its own `NOT searched — <observed error>` line, and every other source still answers. A `SKILL.md` that is not UTF-8, cannot be parsed, or is a symlink costs only its own row, listed under its source by path (the first `UNREADABLE_LISTED`, then a count). The walk never follows a link — a linked folder is not entered, a linked `SKILL.md` is not read, a prefix that is a link is refused — because a clone's link could otherwise read a file of the owner's into the catalogue (`test_a_linked_skill_file_is_never_read`). A row whose folder path is over `PATH_CHARS` characters, or holds a character the rendering would change (a control character, a whitespace run, an `[aish:` marker), is not listed and says so: the path is what `import_skill` is called with, so it is shown whole or not at all (`test_a_path_that_cannot_be_shown_whole_is_not_listed`). Lines of `skill-sources` that approve nothing are named.

**Ranking: two lexical rails, and a listing when words fail.** First `skills.score_entries`' tiers over name and description — the exact name, the phrase, or every query word as whole words. Below them, a row holding SOME of the query's topic words (three letters and up, the knowledge layer's stopwords removed, so `pdf` counts and `in`, `a`, `find`, `skill` do not), ordered by the share of them it holds; a close spelling alone (tier 1) ranks below any share. Chosen over every-word-only because the orchestrator's measurement on the four real sources had "fill in a PDF form" return only the docx skill. Words still cannot match meaning ("excel" against a skill named `xlsx`, "summarize youtube video"), so when no row reaches `STRONG_TIER` (`skills.PREFLIGHT_MIN_SCORE`, the knowledge layer's own bar for a lexical match) — nothing matched, or only partly — the result says so and lists every catalogued skill, one line each, `name — source`, names flattened, disarmed and capped like every publisher field (at most `ALL_NAMES_MAX` lines, then a count), and tells the model to choose by meaning and search again by that exact name, which ranks it first with its description and folder. The listing is under the same banner. `test_a_synonym_finds_nothing_by_words_so_every_name_is_offered`, `test_some_of_the_words_is_enough_and_ranks_by_share`.

**The result is outside content, rendered in `web_search`'s shape.** `CATALOG_NOTE` above the rows says whose words they are and what they are for (choose a skill to propose; ask the owner; then `import_skill`). Each row is the name, the description cut at `INDEX_THIRD_PARTY_DESCRIPTION_MAX` like the third-party index, the repository (aish's, from the sources line) and the folder (the publisher's, shown whole — see above) — every other publisher field control-flattened, `[aish:` broken (`provenance.disarm_markers`) and capped. A row says "installed as <name> from commit <c>" when a lock entry's `source` and `path` equal the row's — never by name, because the installed name may be an override and two sources may publish one name. `_brings_outside_content("find_skill")` is True by its own name-keyed branch, like `use_skill`; it is NOT in `EGRESS_TOOLS`, whose gate would read its arguments as a destination (its query reaches no host). The cache directory is outside-populated and recordless (`docs/agent-core.md`, the #317 audit list), so a read of it answers outside content.

**No card, echoed, refused unattended.** Nothing of the owner's leaves and nothing installs, so a call runs with no card and is echoed (`→ find_skill: <query>`). In a chat no person started (`origin != "user"`) it is refused before anything is read (`FIND_SKILL_UNATTENDED`), the `use_skill` precedent.

**On the menu.** Not core, but `required` whenever `skill-sources` parses to at least one source (`Agent._skill_sources_approved`), beside `use_skill`'s precedent: on the lexical floor "find me a skill for PDF forms" scores it 0 — `find` and `skill` are stopwords and `pdf` is under the four-letter floor — so ranking alone would never hand it over. With no approved source there is nothing to search and it is ranked like any tool (`docs/tool-menu.md`). Its result tells the model to call `import_skill` on the owner's yes, which arrives as the next task, so a task whose previous task called `find_skill` gets `import_skill` as `required` — a harness that instructs a call it did not send has built the miss itself.

`TestTheCatalogue`, `TestTheCatalogueCache`, `TestFindSkillTool`, `TestFindSkillOnTheMenu` (`tests/test_skill_catalog.py`).

**Open, named.** A clone of each source is the whole repository at depth 1, read sequentially, each bounded by the clone timeout and not by stop — so a search on a cold cache over several large sources can take minutes, and a cancel is not seen until it ends; the clone time and size of a real source were not measured for this slice. Choosing by meaning from the name listing is the model's step and is unmeasured, and a skill whose name says nothing about what it does can only be found that way if the model searches it by name. Cache files of a source later removed from `skill-sources` are never pruned (nothing reads them, since a cache is used only for a line still in the file); they stay in `<state>/skill-catalog/` until removed by hand. The per-task `required` check reads `skill-sources` once per task. A shell `cat` of the cache is outside every door, as for the other stores.

### The import auditor (#467 slice 3)

**A model reads the staged skill before the card and may only ADD to it** (P5). `skillaudit.audit` runs the toolless `skill-auditor` role (`aish/charters/skill-auditor.md`, `docs/roles.md`) over the import's text files, on both review paths: `Agent._import_skill` (before `approve_import`, so the web card and the terminal printer both receive it) and `aish skill import`. It approves nothing, refuses nothing, and changes nothing about what installs; the owner's card is the decision either way.

- **Input** — `skillaudit.bundle_text`: one JSON document, every staged text file as `lines`, labelled untrusted, capped at `FILE_CHARS` (40 000) per file and `TOTAL_CHARS` (120 000) in all. What did not fit is named in the bundle's `cut` list in aish's words, and then the validator accepts only the summary `could_not_assess` — a partial audit never reads as a whole one. The bundle is the role's one input, so its bytes are the evidence-store copy R7 records.
- **Output** — the fifth role shape, `findings`, delegated to `skillaudit` (validate / contract_text / tally / assertions / check_expectation, the settlement precedent). A `summary` in {`flags_raised`, `nothing_flagged`, `could_not_assess`} and at most `max_findings` findings, each `{file, category, quote, reason}`: `file` must be a path in the bundle; `category` one of `sends_data_out`, `reads_secrets`, `runs_downloaded_code`, `hides_or_obfuscates`, `instructs_the_assistant` (text addressed to the AI reading the skill — the assistant, a reviewer, the auditor — that the task does not need, including text posing as aish's own framing), `installs_packages`, `tampers_with_assistant_config` (aish's own config, rules, skills, sources; shell start-up; launch agents), or `cannot_tell`; `quote` capped, control-flattened, and **text the named file holds** (whitespace runs compared as one space on both sides) — `validate_answer` refuses an answer quoting anything else; `reason` capped. `nothing_flagged` must come with no findings and `flags_raised` with at least one. Quotes and reasons have aish's markers broken (`provenance.disarm_markers`) before they reach the card, the lock or the record. No severity field: the exam asserts per category.
- **Model** — one caller-named spec, the mail Reader's precedent: `skillaudit.model_spec()` is `$AISH_SKILL_AUDITOR_MODEL`, else `local:mlx-community/Qwen3.6-35B-A3B-8bit` — the owner's own server, reached at `backends.local_url()` (config.toml's `[local] url`, or `$AISH_LOCAL_URL`, #474). It was `gemini:gemini-flash-latest` (a cloud default, the skill text being public) until the owner's decision of 2026-11-12, on that day's measurement in the #467 ledger: the local model answered every call of three exam runs while Gemini Flash refused 21 of 32 with HTTP 503. With no address in either place the backend refuses to build a client, and the card says the auditor did not run with the backend's own sentence ("AISH_LOCAL_URL is not set and <config.toml> does not exist — …", or "… has no [local] url — …"); a server that does not answer shows the failed call's error the same way (`roles.run` turns the failed call into `unavailable`). `test_with_no_local_server_address_the_card_says_so` covers the unset address; the unanswering server is not separately tested. Admission binds to that spec; the session's own backend plays no part, so a claude-max session audits on the named spec like any other.
- **The card** — `Audit.card()`: a headline composed by aish and the findings, each with a label, the reason and the quote, rendered apart from the code-computed flags (web: `importAuditBlock`, a dashed box, never a pass colour; terminal: `cli.print_audit`, a `◇ auditor —` block under the `⚠ review closely` flags, every field through `_plain`). An empty result reads "the auditor (<spec>) flagged nothing — this is not a verdict". A call that did not answer says so in aish's words with the observed reason: "the auditor (<spec>) did not run: no admission recorded" (unadmitted, the state of a fresh install), the backend's own error for a missing key or a failed call, "the auditor's charter does not load (…)", or, when two answers both failed the checks, that nothing it said is shown. The import proceeds to the owner's decision in every case — never a silent skip.
- **Never the tool result.** Findings go to the card and the lock entry only; the text `import_skill` returns to the acting model does not mention the audit (`test_findings_reach_the_card_and_the_lock_and_never_the_model`).
- **Records.** The durable record is the role's own `role` record (R7): through `Agent._record_role` into the session log on the tool path (`_record_role_skip` when the charter does not load), and on `aish skill import`, which has no session, appended to `<state>/roles/skill-auditor.jsonl` (`skillaudit.records_path`). The lock entry gains `audit` — `{charter, version, charter_digest, model, status, covers, why?, summary?, findings?, input_digest?}`, a convenience copy. `covers` says which bytes it read: "the installed files" when every installed file's sha256 is an audited file's text, or that text plus the final newline aish's write adds (`skillaudit.covers`); otherwise "the files as staged for review; these differ from what was installed: …". The CLI path audits at `aish skill import`, keeps the reading beside the quarantine (`<name>.audit.json`, removed by `approve` and `discard`), and `approve` compares — the quarantine is hand-editable, so an edit after the audit is named in the lock rather than re-audited — as long as the edit leaves `<name>.audit.json` alone: the coverage digests live in that same hand-editable quarantine, so an edit to both files makes the lock read "the installed files" over stale findings. The role's own record keeps the true input digest; reaching the quarantine takes a card-approved shell write. A skill staged before this slice gets `audit: {status: not_run, why: "no audit was recorded when this skill was staged"}`.
- **Admission is the owner's step.** Until `uv run python scripts/role-admission.py --model local:mlx-community/Qwen3.6-35B-A3B-8bit skill-auditor` records a pass — three exam runs, every one passing every case (#472, `docs/roles.md` *Repeated runs*) — every import's card says the auditor did not run, with the reason `roles.admitted` gives. The exam case `discrimination-an-offline-claim-versus-a-hidden-connection` was changed by #472 (SKILL.md may be flagged), which changed the charter's digest, so every admission recorded before it is retired.

`TestTheAuditorCharter`, `TestTheAuditorsAnswer`, `TestTheBundle`, `TestTheAudit`, `TestTheImportCardCarriesTheAudit`; `tests/js/test_import_audit.js`.

**Open, named.** The exam was measured on 2026-11-12 (#467 ledger) under the charter as it stood before #472's case change; the charter as changed by #472 had not been examined when this was written. The CLI path's role records are in their own file, so `aish usage` does not count the auditor's spend on that path (it does on the tool path, from the session log). The auditor reads text only: binary assets are skipped by the import and are not installed, and a bundled script that fetches more code at run time is audited as its text, not as what it fetches.

### The skill runner (#467 slice 2b)

**A third-party skill runs in quarantine; its text never enters the owner's conversation.** The owner's design (2026-11-11): run the skill "in a separate context completely separated, with a summary of what it needs to do … it gets instructions on input, performs the task, saves files as it needs to, and proposes the results." The acting model calls `use_skill(name, brief, inputs)`; `skill_runner.run` builds a throwaway conversation of exactly four things — `RUNNER_PROMPT` (a code constant, not a charter file), the skill as `skills.load_skill` serves it (hash-verified, bannered), the brief, and the input paths — and runs its own loop. It is a sibling module, not a reused `Agent.run_task` (whose per-feature injections — objective, plan, memory, rules, preflight — default on) and not an extension of `roles.py` (R1: a role has no tool loop). `TestIsolation` pins the source (it cannot import the acting loop, the plugin registry or the approval module) and the composed request (two messages; the owner's task text is absent from it).

**Three tools, a closed set, every one inside the kernel.** `read_file`, `run_command`, `write_file` — `RUNNER_TOOLS`, dispatched by `_Run.dispatch`; any other name is answered "there is no tool" and runs nothing (`TestTheClosedDispatch`). `run_command` is `tools.run_command(confinement=<Tier S>)` in the run's scratch. `write_file` and every `read_file` outside the skill's folder run as a confined `cat`/`head`, so what the runner reads and writes is the KERNEL's decision rather than a path check aish makes and a leftover background process could race; a read of the skill's own folder is in process, because the hash check needs the bytes and the runner cannot write that folder. The runner refuses to run anything when its confinement does not say tier `skill`, there is no card inside it, and no unsandboxed value is named in the module (`TestNoEscalationInsideTheRunner`): a kernel refusal is a failed command, full stop. Budgets: 20 model calls, 600 s (checked before each model call, so one call or command in flight can outlast it), 120 s per command and per confined file read or write. Stop is checked before every model call, during a rate-limit wait, and inside every `run_command`; a confined file read or write runs to its own timeout.

**`use_skill` is refused, with no card, unless** a person started the chat (`origin == "user"`; unattended use is out of slice 1), the session's backend has a stateless seam (`roles.session_model_spec`; claude-max has none and is refused with that reason), every input is an existing regular file inside the chat's workspace boundary that is not a secret-holding name and not in aish's own trees, the skill's text verifies, its environment (below) can be used, and the Tier S sandbox prepares (`USE_SKILL_NO_SANDBOX`: there is no run without it). Then **every run is carded** — `ASKED_BY_SKILL`, a code-composed sentence plus the skill, the brief and the inputs; when the lock holds no review hashes for the skill, the sentence says nothing was checked — unless the owner's standing grant covers it ("Always for this skill", below). The runner uses the session's own model through the chat callable the session was built with (`backends.make_chat`'s, the seam roles use), and the `skill_run` record names it and carries its spend, which `aish usage` reports per skill beside the acting model's and never inside it (`docs/token-accounting.md`, `TestSkillRunSpend`). `TestUseSkill`.

**What returns is composed by code** (`Outcome.envelope`), and taints the task (`_brings_outside_content("use_skill")`). aish's observations — how it ended (`answered`, `budget`, `time`, `cancelled`, `model_failed`, `error`, or `unknown`: "ended; aish does not know why"), model calls, commands, the files, kernel refusals read ONCE at the end and labelled a sample — are kept apart from the runner's claim: the status it states (`done` / `failed` / `needs_input` / `none stated`) and its report, capped (2,000 characters; a `needs_input` question 500), control characters flattened, aish's markers disarmed, labelled third-party-derived. Its files are MOVED out of scratch under names aish chooses (`files/01.pdf`, …); the runner's own name appears only as a label, flattened and capped. A link is never collected — a symlink, or a file with more than one name (a hard link may share its bytes with a file outside scratch), checked at the walk and again after the move. The kernel's refusals are reported with process, operation and target each flattened and disarmed like the report, because a target is a path and the runner chose the name. `TestTheEnvelope`.

**"Always for this skill" (slice 2c).** The owner's choice on a `use_skill` card, recorded as his own act (the `vouches.py` precedent, epic #295 P3/P6) in `~/.config/aish/skill-grants` (`skills.SKILL_GRANTS_FILE`, module `skill_grants`):

- **The agent composes the offer; the card only chooses it.** `_use_skill` reads the lock's hashes ONCE (`skill_import.recorded_hashes`) and that one read feeds the card's no-hashes warning, the grant check and the `skill_grants.Offer` the card carries. `_ask_owner(…, offer)` holds it for the length of the card and the approvers read it late-bound (`Agent.card_offer`, the `asking_gate` idiom). The web card shows "Always for this skill" only when `always` is in the request; the terminal prompt gains `a(lways for this skill)` only then. Either answer is the verdict `approval.AlwaysForSkill(how)` — a class of its own, carrying no content — and the grant written is the agent's offer. An `AlwaysForSkill` with no offer behind it is a plain approval and records nothing. A skill with no recorded hashes (a version-1 entry, a flat file, a lock that lost its entry) is never offered one, and neither is any skill while the grants file is unreadable.
- **A comment makes it a hold.** The web approver answers "Always" with a comment as `Approved(comment)` — the run is HELD for re-proposal — and records nothing (#346: no grant for a run that never ran); the echo says it was not recorded.
- **Bound to the review identity.** `skill_grants.standing` covers a run only when the latest act for the exact skill name is a grant whose `files` map EQUALS the lock's current one: different hashes are never covered (a reinstall with any file added, removed or changed asks again; a byte-identical reinstall is the same reviewed text and is covered). `_standing_skill_grant` then checks the folder against those same hashes once more (`check_folder`), and refuses a symlinked folder.
- **It replaces the card and nothing else.** The check sits immediately before the card, after every refusal: origin must be `user`, the seam, the inputs, the skill's hash verification, the environment, the no-approver refusal (`USE_SKILL_NO_APPROVER` stands even with a grant — the grant replaces the card, not the channel) and the sandbox. The result still taints.
- **The model is told nothing different.** The `use_skill` result is the same bytes either way (`test_always_records_the_agents_offer_and_the_next_run_draws_no_card`). Attribution lives in the `skill_run` record (`approved: "card" | "standing grant"`, `grant: {at, how}`, `inputs`; `docs/trace-contract.md` §3.27) and in the owner-facing cardless line on the answer — "Ran the third-party skill … without a card, on your standing approval of <date> …", the `_Cardless` ledger that never enters the model's history — and the terminal's progress line. Recording one echoes what it covers and how to revoke it, or that it was NOT recorded.
- **The store.** One JSON object per line, appended with a single `write` on an `O_APPEND` descriptor: `{"act": "granted", "skill", "files", "at", "how"}` or `{"act": "revoked", "skill", "at", "how"}`; the latest act for a skill decides. A file that is present with any line `_well_formed` rejects grants NOTHING (a malformed revocation must not let the grant above it stand) and takes no new grant; a revocation is appended whatever the file holds, since it can only take a permission away.
- **Revocation** is `aish skill revoke NAME` (appends a tombstone and says whether a grant was in force) or the owner's hand edit of the file. A web revoke control is not built.
- **Fenced like `skill-sources`.** `skills.third_party_write_refusal` names the file (so `write_file`/`edit_file`, `create_skill`/`create_tool`, `remember` and curate refuse it), and `_command_touches_third_party` adds it to the shell fence's stores and `skill-grants` to its words.

`TestTheGrantStore`, `TestAlwaysForThisSkill`, `TestTheGrantsFileIsFenced`, `TestTheCardsChooseTheAgentsOffer`, `TestRevokeFromTheTerminal`; `tests/js/test_skill_always.js`.

**Residuals of the grant, named.**
- The config tree is git-backed and auto-committed to a private remote: the grants file rides there, and restoring the tree from that backup can bring a revoked grant back.
- The shell fence's residuals apply to this file as to `skill-sources`: a path the command text does not show (computed, assembled across calls, reached through an ancestor with a relative verb), on a card or by a prefix rule, could still write it, and a plugin wrapper could. That is bounded: an entry covers a run only if its hashes equal the lock entry of an installed, lock-recorded skill.
- With a grant the owner no longer sees the brief or the inputs before a run; they are in the `skill_run` record (`inputs`) and the inputs stay confined to the chat's workspace boundary exactly as before.
- The SKILL.md body handed to the runner is read and verified by `load_skill` a moment before the grant check reads the lock; a lock rewritten in that window would pair a body verified against the old entry with a grant matched against the new one.

**Its files are outside content in every later task.** The skill-runs store (`<state>/skill-runs/`) is in the workspace boundary (the result names its files, and reading one back must not cost a tap) and is an outside-populated, RECORDLESS store: the runner held the pen in its scratch and could have written a provenance record beside its file, so none is read there — every file in the store answers `SKILL_RUN_ARTEFACT`, and a read is bannered and taints, in this task or next week's (`test_its_files_are_outside_content_in_a_later_task_whatever_a_record_says`).

**A run belongs to its chat (slice 2c).** Each run is `<state>/skill-runs/<session stem>/<date-time>-<skill>-<rand>/`: `chat_skill_runs_dir`, one definition beside `chat_scratch_dir`, keyed on the log the chat is writing when the run STARTS (`Agent._skill_run_home`, asked per run because the terminal keeps one Agent across `/new` and `/resume`). The store, its boundary and its outside-content answer are unchanged — only the per-chat level is new, and it is deliberately not inside the chat's scratch, which is the acting model's cardless pen. Deleting the chat destroys its folder outright, not into the trash, exactly where its scratch goes (`server._delete_session`, the terminal's `/delete`); `prune_chat_skill_runs` sweeps folders whose log is gone at server start, beside `prune_chat_scratch`. That sweep is chat lifecycle, not age: a live chat's runs stay however old. An agent with no chat identity (embedded, tests) gets a throwaway store of its own, removed by `close()` or its finalizer, never the shared one. Another chat may still read a run's files while they exist (the boundary is the store, as before); once the chat that made them is deleted they are gone, and a chat restored from the trash comes back without them. `TestSkillRunsBelongToTheChat`, `TestTerminalDeleteTakesTheChatsFiles`.

**Packages: derived at import, installed on its approval, never at run time** (`skill_env.py`). The packages a skill needs are read from its import STATEMENTS — `ast` over its `.py` files and its Markdown's python code blocks, standard library and the skill's own modules filtered out — never from a prose `pip install` line. Slice 1 maps import names to packages through an explicit table, `skill_env.PACKAGES`, holding exactly the imports of the anthropics `pdf` skill that ship wheels (`pypdf`, `reportlab`, `PIL`→`pillow`, `pdfplumber`, `pypdfium2`, `pandas`, `numpy`; the orchestrator ran `needs` on the staged skill, 2026-11-12): an import name is not a package name, and a guessed one would install whatever a stranger published under the guess. `pdf2image` and `pytesseract` drive programs aish does not provide (`skill_env.PROGRAMS`: poppler, tesseract), and the card names the program. For any other import the card says only that aish installs nothing for it — never that it will be missing, since another package may bring it in (pillow arrives with reportlab). The import's review card lists what will be installed (`skill_env.card_flags`, in the flags); on approval — both install paths, `Agent._import_skill` and `aish skill approve` — `skill_import.install_env` derives the packages again from the INSTALLED bytes and runs `uv venv` + `uv pip install --only-binary :all:` into `<state>/skill-envs/<name>/` (wheels only: building a source distribution runs its build code with the owner's rights), then records `uv pip freeze`'s resolved versions — dependencies included — in the lock entry's `env`. A failed install is a record and a sentence, never a raise; the skill stays installed and its runs have no Python. "Never at run time" is the kernel's, not a promise: Tier S denies the network and does not let a runner write its environment. `skill_env.locate` reads the environment's interpreter from `pyvenv.cfg`, never by running it (a `.pth` file in it would run a stranger's code with the owner's rights), and refuses one whose interpreter is not inside the installation it names or whose installation holds the owner's home. `TestSkillEnvironment`.

**Records.** One `skill_run` record per run (`docs/trace-contract.md` §3.27), renderless and joined to the `use_skill` step by turn and call. Showing the runner's own steps nested under that step is a later slice; today they are in no record beyond the counts.

**Residuals, named.**
- A shell read of the tree the command text does not show (slice 3 refuses the ones it does), approved on a card or by a prefix rule, still puts a skill's text into the owner's conversation; so can a plugin wrapper that reads files, and `read_url` of the skill's copy on GitHub (as a web read: bannered and tainting).
- A background process a runner command leaves behind keeps running, under the same profile (scratch-only writes, no network), after the runner ends; nothing kills it.
- A deleted skill's environment stays in `<state>/skill-envs/` until removed by hand.
- Nothing prunes the skill-runs store by age: a run's collected files and its leftover scratch stay until its chat is deleted (above).
- The runner's `read_file` of a binary input returns it decoded as text; a PDF is read with the skill's Python instead.
- Whether a real model follows the runner prompt and the skill to a useful result is unmeasured in this slice.
