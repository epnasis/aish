How the aish web UI works, for answering the user's questions about it. Answer from this page; where it is silent, say so rather than guessing.

## Approval cards
- Every command aish proposes appears as a card with **Approve / This chat / Always / Deny** buttons and a pencil beside the command to edit it before it runs. File writes show a unified diff first.
- A card has an optional comment field; its text arrives with whichever button the user presses.
- Read-only commands auto-approve inside the chat's trusted folders. **This chat** auto-approves that command's prefixes until the chat closes (memory only). **Always** saves the same prefixes to the persistent allowlist (`~/.config/aish/allow.txt`).
- A command or file read that reaches outside the trusted folders gets a warning on its card and a **Trust dir** button: one tap adds that directory to this chat's trusted folders (memory only).
- A read-only command that auto-approves runs in aish's sandbox (macOS): it can read the chat's folders, write only to the chat's scratch folder, start only the programs on its list (read-only commands, plus mkdir/touch/rm for scratch), and has no network. When the sandbox refuses something to a command that then fails, aish tells the model what and adds a note to the turn (for a command that succeeded, the refusal is only recorded in the chat's log); if the model proposes the same command again, it comes as a card with an orange note saying what the sandbox refused — approving it runs the command outside the sandbox with the user's full rights. If the sandbox is not available, read-only commands come as cards too, with a note saying so; an automation nobody is watching does not run them.
- `ps` now asks first (it cannot run in the sandbox). "Is X running?" is answered by aish's own `processes` tool: pid, program name and running time, never another program's arguments.

## Typing in the composer
- A message starting with `!` runs directly as a shell command — the user's own action, no aish and no card. `!cd <dir>` is the `/cd` alias that moves the project directory.
- Slash commands: `/model /resume /delete /new /fork /cd /add-dir /jobs /watch /help`, plus `/learn` (distils the conversation into saved skills/memory; an optional hint follows, e.g. `/learn the gh flow`; `/learn lessons` migrates the legacy lessons file), `/objective` and `/plan`, and `/who [words]` — aish's files on people, organisations, accounts and interests, listed or one opened, in a sheet for the user only (nothing is sent to the model).
- aish keeps a file on each person, organisation, account and interest it has saved a fact about (`~/.local/state/aish/knowledge/people/`, `organisations/`, `accounts/`, `interests/`): a "From him" section for what the user said in a chat that never read outside content, and a "Read somewhere" section for everything else. Only From him lines are preloaded, when the user's message names the file (name or alias, Polish forms and missing diacritics included); Read somewhere lines are counted with a pointer, and reading them marks the task as having read outside content. A full account or card number is never saved. aish's tools never edit these files; the user can, in his own editor.
- Finding a skill (`find_skill`, "find me a skill for PDF forms"): searches only the repositories in `~/.config/aish/skill-sources`. Each is cloned (shallow, redirects not followed) and each skill's name and description (the frontmatter's, or the first line of the body when there is no description) are cached in `~/.local/state/aish/skill-catalog/` for 24 h; `refresh` (true/yes/on/1) re-reads them. The search words are not sent with the fetch and matching is by words, on this machine: skills holding every query word (or the exact name) rank first, then skills holding some of its topic words; when nothing matches that strongly the result also lists every catalogued skill's name, grouped under its source, so the assistant can choose by meaning (a skill named `xlsx` for "excel") and search again by that name. Each result gives the name, the description (the publisher's own text, marked as such, capped at 400 characters), the repository and folder to pass to `import_skill`, and "installed as …" when the lock records that repository and folder. Each source is named with its listing's age and commit, or the error that kept it from being read; one unreadable `SKILL.md` (or one whose folder path is over 200 characters or holds characters aish does not show as they are) is listed by its folder and costs only its row. It installs nothing — importing is the separate `import_skill` with its usual card. No card; refused in scheduled/mail-started chats; its result counts as outside content.
- Importing a skill ("import the skill at <repo>"): only from a GitHub repo the user listed in `~/.config/aish/skill-sources` (one `github.com/<owner>/<repo>` or `github.com/<owner>/<repo>/<folder>` per line); any other source and any local path is refused before anything is fetched, and the user edits that file himself — aish's file and skill tools refuse it. aish shows every file on one review card, then installs it in `~/.config/aish/vendor-skills/` — never the user's own `skills/` — recording a hash of every installed file. Imported skills are third-party: a separate index section, never preloaded, and never read by the model — `read_skill`, `read_file`, `read_pdf`, `show_image` and `read_media` refuse them. The model calls `use_skill(name, brief, inputs)`, which the user approves on a card naming the skill, the brief and the files — or with the "Always for this skill" button on the card, after which runs of that skill draw no card while the lock's recorded hashes are the ones he approved and its files still match them (a skill with no recorded hashes never offers it; a reinstall with different files asks again; a comment on the card holds the run and records nothing). Each cardless run is announced on the answer. `aish skill revoke NAME` withdraws it, or the user edits `~/.config/aish/skill-grants` himself — aish's file and skill tools refuse that file, and a `run_command` whose text names `skill-grants` is refused with no card; the skill then runs in an isolated runner that sees only the skill, the brief and the input paths, whose every command runs in aish's skill sandbox (of the user's files it reads only those, the skill and its packages — the home tree, other volumes and shared temp dirs are closed, system and world-readable folders such as `/etc` stay readable; writes only its scratch folder under `~/.local/state/aish/skill-runs/<chat>/`; no network). A chat's skill runs, and the files they made, are deleted with the chat — not kept in the trash. aish composes the result — how it ended, the files it made (moved to names aish chooses), kernel refusals — and keeps the runner's own report apart, marked third-party; the result and later reads of its files count as outside content. Refused in scheduled/mail-started chats and on claude-max. Python packages a skill's code imports are listed on the import card and installed on approval (wheels only, versions in the lock) into `~/.local/state/aish/skill-envs/<name>/`, never at run time; this version's table holds the pdf skill's imports (`pypdf`, `reportlab`, `pillow`, `pdfplumber`, `pypdfium2`, `pandas`, `numpy`); for any other import the card says aish installs nothing for it, and `pdf2image`/`pytesseract` are named with the program they drive (poppler, tesseract), which aish does not provide. A skill with no recorded review hashes says so on its run card. Before a run the skill's files are checked against the recorded hashes: a changed skill is refused, naming the files (the user deletes its folder and imports it again). aish's file and skill tools never write into `vendor-skills/`, and a `run_command` whose text names `vendor-skills/`, `skill-sources` or `skill-grants` (any letter case, reads included) is refused with no card (a path the text does not show, e.g. one a script computes, is not caught) — the user's own `!` commands are not. The import card's risk flags cover network access, a download piped to a shell, Keychain reads, `osascript`, package installs, decoded payloads and credential paths; they focus the review and decide nothing. Below them, in its own box, the import auditor: an isolated, toolless model (`local:mlx-community/Qwen3.6-35B-A3B-8bit` on the user's own server — config.toml's `[local] url`, or `$AISH_LOCAL_URL` — unless `AISH_SKILL_AUDITOR_MODEL` names another) that lists findings with a quote aish checks is in the file; it only adds warnings, an empty list reads "flagged nothing — this is not a verdict", and when it did not run the box says why. Its findings are recorded in the lock, never given to the model. It runs only after the user admits it with `scripts/role-admission.py`. A skill the user wrote and wants trusted goes into `skills/` by hand. In the terminal, `aish skill outdated` reports per imported skill whether its approved source has newer commits and whether this skill's files changed (added/removed/modified/executable bit; text files only, binary files not compared); a source removed from `skill-sources` is not contacted, and it installs nothing — a newer version is taken by deleting the skill and importing it again.
- Updating a skill (`update_skill`, "update the pdf skill"): replaces one installed third-party skill with its source's current version. The source and folder are the ones recorded at import; the installed files are checked against their recorded hashes first (changed files, or no recorded review: refused — delete it and import again). The review card shows what it replaces (commit a → b), the package changes and a diff of every changed file, then the new files whole; binary files are skipped, as at import. Nothing changes unless the user approves; then the folder is replaced, the Python environment installed again, and the record written — runs are refused until then. An "Always for this skill" approval does not carry over to changed files. Refused in a chat the user did not start.
- `/fork` (or `/branch`) copies the whole conversation so far into a NEW chat and switches there, leaving this one untouched — for a tangent or an alternative approach.
- `/watch` opens a live, read-only window on the page aish is driving with browse in this chat. It shows the page and changes nothing — no clicking, typing or scrolling, and it never interrupts aish.
- The ＋ button opens: attach file / reference a path (@) / slash command (/) / photo / send feedback / terminal mode (multi-command shell, prefix `!`) / interactive shell.
- The **interactive shell** is a real terminal for programs that prompt for input (gcloud auth, ssh host-key prompts, sudo). aish has NO access to it: its input and output stay private unless the user selects text and taps **Share**. Programs that take the mouse (Claude Code, tmux, vim) get the trackpad wheel and a plain drag — Claude highlights its own selection and copies it to the clipboard; to select with the terminal itself hold Option while dragging (Shift on a non-Mac), then ⌘C (Ctrl+Shift+C on a non-Mac, never Ctrl+C) or **Copy**. URLs printed there are tappable, even when wrapped across lines; a tap opens the link in the device's chosen browser, and HOLDING it offers their own browser, aish's remote browser (where they can see the page and sign in, as `/browser` does) or copy, plus a row that changes what a plain tap does. A sign-in URL should be held and opened in aish's browser, since that is the browser aish later reads that site as.

## Keyboard (desktop)
- Cmd/Ctrl+K opens the chat list (again moves down a row, with Shift up, Enter opens).
- Cmd/Ctrl+Shift+M opens the model list (again moves down, Enter picks).
- Cmd/Ctrl+M switches between local and cloud — to whichever model on the other side a chat used most recently.

## The header and the chat menu
- **Chats** (top left, badge when a background chat needs attention) opens the chat list: it slides over the conversation on a narrow screen and is a sidebar on a wide one. Swiping the transcript sideways pages through recent chats.
- A chat is named automatically — after the first answer, when a fork first differs from its parent, and occasionally when the subject really changes. A name the user sets by hand is final and never rewritten.
- Tapping the chat title opens the chat menu: **New chat, Rename chat…, Switch model…, Change directory…, Pin chat, Line wrap, Text size, Export to PDF, Workspace & jobs…, Copy log path, Reconnect, Delete chat**. The compose pencil (top right) also starts a new chat.
- The context bar under the title shows the working directory (tap for a folder picker) and the model (tap to switch — a switch applies to this chat and to new chats started from this device until it reconnects; ticking **make startup default** makes it what new chats start on, at once and after restarts (a device that switched model without saving keeps its own choice until it reconnects), unless the server was launched with `--model` or `$AISH_MODEL`, which the confirmation then names); the model chip also shows how full the context was on the last model call, as a percentage.

## Deleting, and getting it back
- **Delete chat is not final.** The chat moves to **Recently deleted** at the bottom of the chat list and can be restored for **30 days** before aish purges it.
- Deleted at once, and not brought back by a restore: the chat's throwaway working files and the stored copies of the requests its steps sent. The copy mirrored to the user's devices also goes at once and returns by syncing after a restore.
- Permanently deleting from Recently deleted is the one step that cannot be undone.
- Each of the user's own prompts has a row: the time it was sent, a trash chip, a pencil that puts the prompt back in the composer, and copy. The trash chip DELETES that whole exchange (their prompt, aish's work and answer) after a dialog naming what is lost: the text leaves the chat log and aish's context and every device's offline copy at the next sync; a "Message deleted" marker stays. It is the ONLY way to take something back — a message sent to the wrong chat, half-typed, or a pasted secret — and it cannot be undone.

## Answers and exports
- Every finished answer has a row of chips: copy, export that answer to PDF, and read-aloud where available.
- When a task the user sent went the long way round — very many tool calls, the same call repeated, steps refused, two or more comments on its cards, or stopped for looping — its answer also offers **Save this as a lesson?**. One tap sends `/learn`; nothing is saved without it, and every file `/learn` writes is approved first. It is never offered twice in a row in one chat, nor on a chat aish started itself.
- Both PDF exports render markdown locally and download the file. The whole-chat export holds only final answers, not thinking or steps, and is named after the chat; a single-answer PDF is titled after the ANSWER (aish writes that title when asked).
- PDFs embed pictures: local images inside the chat's trusted folders, web images, Google Maps snapshots (needs GOOGLE_MAPS_API_KEY) and YouTube thumbnails; anything unavailable becomes a captioned link card.
- Asked about an order, parcel, booking or other mail case — or told "I picked those up" — aish uses its `cases` tool: it reads the case store (titles, keys, the case's mails and their one-line readings) and proposes a change — close, reopen, merge, move a mail, rename, dismiss ("not a case": hidden, restore brings it back), a note, a reminder, a new case, or trusting one more exact address on a case (aish otherwise trusts only the address the user wrote to; the daily report's trust button sends "trust sender X on case C"; a trusted address also counts as someone the user deals with, so its mail anywhere is graded known) and untrusting it again — on a card with one sentence saying what changes. Only in a task the user sent; closing touches no mail, it only stops aish holding the case's keeper documents visible. A case reminder is listed in the daily inbox report from its due date while the case is open; nothing else notifies the user.
- Told in a report chat to ignore, hide, show first, stop listing, remind, or that a mail "needed action"/"was junk", aish uses `inbox_preferences`: one plain sentence aish composes, saved only on the user's card, in a task the user sent. The daily report obeys it from the next report and always ends with "Using N of your preferences — hid M items". A hide never hides a mail recorded as suspicious, as not matching its case's sender, as changing a payment account, or as failing a sign-in check its sender passed before; it is shown, marked why. Reminders appear only in the report; corrections are recorded, not applied. aish must never say it will remember something unless the tool answered SAVED. An `important` preference names a sender or domain AND a meaning (money, documents, anything); matching mail is listed under Needs your action, marked as there because of it, and every card that matches mail previews which past mails it would and would not have matched.
- Told in a report chat that an item is done or needs no reply ("Catherine already paid", "I answered that offer"), or that one is still open, aish uses `inbox_items` (`resolve` / `restore`, by the report's ref) — applied at once with NO card in a task the user sent (his word decides, 2026-11-12), and the chat shows a row, written by aish's code, saying what was marked and how to undo it; resolving an item marked CAUTION is always a card; the report's `[done]` and `[restore]` buttons send those words. A resolved item leaves the report until new mail arrives in its conversation. The report's *Probably settled* section lists items aish connected to later mail (the user's own reply, or a later mail its settlement judge read as settling it) with the evidence — including a bank payment of the bill's recorded amount (only its date and amount are shown); only the user's word removes them. The brief has no weekday rule: overdue bills stay on top, old undated bills and replies fold into one line per kind, and a decision whose date passed is listed the next day and then counted. aish must never say a matter is done unless `inbox_items` answered SAVED. A *later mail aish did not weigh* line may carry a "let <domain> settle <delivery|payment> items" button: it sends `vouch settler <domain> <meaning>`, which is `inbox_items` action=vouch — a card granting exactly that domain (no subdomain, no lookalike) for that kind of item until revoked.
- Asked for a PDF, report or printable summary, aish makes one with `make_report` and puts it in the answer as a file: tap it to preview the pages, then save or share (the share sheet also prints). The PDF lives in the chat's scratch workspace and is deleted with the chat — share or save anything worth keeping. Pictures in it come only from files the chat may show; a web picture must go through show_image first or it becomes a link.
- Tool activity (thinking, recalled knowledge, commands and output) is grouped into one collapsible activity trace per turn.

## Offline reading and pinning
- The web UI works OFFLINE for reading: past chats are mirrored to the device automatically (newest first, including chats started on the user's other devices), so with no connection the app opens, past chats open, and search works over their contents.
- **Pin chat** in the chat menu is a one-tap toggle: the chat floats under "Pinned" in the chat list and is never dropped from the local copy however old it gets. The pin is the USER's, not the device's — pinning on one browser or phone pins it on all of them. To keep a conversation for reference while travelling, pin it.
- There is nothing else to manage and no cache to clear: the mirror caps its own size and drops the least useful copies first.
- SENDING is paused while offline, by design: a prompt queued for later would run commands with nobody there to approve them.

## Attachments
- Upload with the ＋ button, a PASTE into the composer (Cmd/Ctrl+V on a desktop, the paste button on a phone), or a DRAG onto the window. From an iPhone, the share sheet can hand aish a file or a link through a Shortcut (README: "Share to aish from iOS"); a shared file is attached to the user's next message and reaches aish only when they send it.
- The user can TAP an attached picture or PDF to look at it (a PDF opens page by page) and save any attachment to their device from there, so aish never needs to copy a file out for them.
- A SCANNED PDF (pages that are pictures, with no text in them) is read with the Mac's own text recognition (OCR) — nothing to install. aish marks those words as machine-recognised (they may contain errors, a value in a table can be listed apart from its label, a ticked box can come out as a stray letter, and signatures are not captured) and says which pages it could not read and why: off a Mac, `AISH_OCR=0`, or more than 12 scanned pages in one go (asking again reads the next ones).
- A PICTURE file — a photo of a letter, a screenshot, a JPEG or HEIC saved from a mail — is read the same way: aish reads its words with the same OCR (`read_file` on it), marked the same way, and says if it found none or could not read it.
- In the user's own copy of a message an attachment appears as `![[cat.png]]` (wiki-link style, as in Obsidian) — a message quoted back with `![[…]]` in it refers to an attached file.

## Chats and history
- Every chat (conversation + command audit trail) is logged under `~/.local/state/aish/` in the same format as terminal aish, so a chat started here can be resumed in the terminal and vice versa.

## Doing something later
- "Check after 10pm" and the like become a one-shot automation: aish proposes it with schedule_task, and the user approves a card that states when it runs, the whole instruction, the commands that may run without asking and the sites it may act on as them.
- At that time it runs once in a NEW automated chat (the automation glyph on the row); anything else that changes something waits there on a card, and the usual hold/finish pushes apply. A run that cannot start within 24 hours is given up and reported once.
- Recurring works too ("every weekday at 9"): the automation gets a cron schedule like `0 9 * * 1-5` (local time) and the card shows its next five runs as dates; after downtime only the latest missed run fires.
- A recurring automation can end: `"until": "<ISO local time>"` beside the cron (cron only). No occurrence after it runs; the card says the last run and the end; a last run that could not start on time may still start up to 24 h late. Its ending pushes once, whatever `notify` says. Past its until, `/run-now` and enabling it are refused.
- A recurring automation can start later: `"from": "<ISO local time>"` beside the cron (cron only), with or without `until`. No occurrence before it runs (one exactly at it is the first); the card says the first run. A start already past is allowed and changes nothing. Before it, `/run-now` is refused — ask aish in a chat instead, or ask it to re-save the automation with an earlier start.
- "Tell me when X changes" becomes a monitor (`"kind": "monitor"`, cron only): each run compares against the previous run's snapshot and ends with a verdict; a change pushes its one-line summary, no change is silent (`"notify"`: `on_change` by default, or `always` / `never`), and a run aish cannot read keeps the old baseline and pushes once, then at most daily.
- Saved as a plain JSON file in `~/.config/aish/automations/`; editing its `at` or its cron expression re-arms it, deleting the file cancels it. Automated chats cannot create automations, and aish refuses its own file and shell writes into that folder.
- A monitor run that saved its baseline or found nothing changed does not count in "Needs you" and sits in the date list like a read chat; a changed, unreadable or failed run does, and so does any run holding a card.
- Asked to change an automation, aish reads it with its `automations` tool (the user's own chat only) and proposes the change on a card headed "Changes:" — only the named fields change, the rest (paused or not included) is kept. It can pause, resume or delete one the same way, each on its own card ("Delete file" for a delete). If the file changed while the card was open, approving writes nothing and aish says so.
- `/run-now` in an automation's chat (or `/run-now <id>` anywhere) runs it now, in a new chat. Its schedule is unchanged and the next scheduled run still happens. Refused for a disabled automation (Resume it in `/tasks` first), for a one-shot that expired, and for a recurring one past its until or before its from.
- `/tasks` (or "Show automations…" in the workspace sheet) opens the Automations sheet: each automation's id and note, when it runs, enabled / DISABLED / ENDED, where it stands (next run, or a one-shot's outcome), when it last ran, its notify policy, and the commands and sites it may use without asking. A file aish cannot load is listed as a PROBLEM with its error.
- Each row has Pause / Resume (no question — reversible; the only field it changes), Run now (the same as `/run-now <id>`), and Delete, which asks first: there is no way back short of a new automation on its own approval card. An ENDED automation offers only Delete. What an automation does changes only on a new approval card.
- The sheet fetches the list when it opens and after each action; a change made elsewhere while it is open shows when it is next opened.
- The list of recent runs is the terminal's `/runs`; typed here it answers "terminal-only".
- The inbox assistant's shadow results are the terminal's `/mail`; typed here it answers "terminal-only". The daily inbox report is a chat of its own each morning (*Inbox report — <day>*, automated, unread until opened): what needs action — one short line per thing to do, earned only by a recorded fact (a dated deadline, a recorded amount, an ask to pay or reply, a sender the owner writes to, his preference, a caution); a line stays every morning until it is settled or 60 days old, and mails on one case or from one sender share a line — follow-ups, and a count of everything else (mail that asks nothing is counted, not listed; there is no "may interest you" section). The owner reads a short brief (New, Still open, New from senders he has not dealt with — shown once —, Waiting on others, one counts line); the chat's model holds the full working copy as its note — refs, evidence, settlement detail, what looks handled — so asked "show what looks handled" or "why is this listed", answer from that note. It can be answered in place ("pay the first one"); every action there gets its card, except the ones that cannot reach past the owner (a mail only he receives, a note write he opted in). Its CSV review file is the terminal's `/mail export`.
- Renaming and deleting happen in the chat menu above.
